## 1. 数学的美是人脑只能装下简单抽象的补偿，真实世界的结构很乱

<small>▶ [00:00](https://www.bilibili.com/video/BV1Guxu6EERa?t=0)–08:55　·　开场　·　话题：数学之美是人脑的局限</small>

- **数学的美来自极小的内核，这种美可能是幻觉。** 讲者看到 OpenAI 压低 ETH 界限的新闻，开始怀疑数学之美的来源。
    - **OpenAI 声称压低了 ETH 的界限，但没有给出多项式算法。**
        - ETH 是 3-SAT 这类问题大约需要 2 的 N 次方时间的界限，此前被认为无法突破。
        - 若有多项式算法，就是 P 等于 NP，这世界就崩塌了。OpenAI 没有做到。
        - OpenAI 只把界限往下压了一点，但颠覆了很多人的认知。同一天还有别的重大结果。
        - **玩笑** 「如果他找到一个多项式算法，这世界就崩塌了，P 就等于 NP 了」
    - 数学的美在于内核极小，却能推出有趣的结论。讲者认为这种美可能是幻觉。
- **多项式时间对复合封闭，是为了数学上的简洁，不是因为贴近现实。** 封闭让算法可以随意嵌套调用，数学推导因此变简单。
    - 用 P 刻画有效计算，是因为 N 的 100 次方没有意义。N 等于 10 时就实现不出来，现实计算机在合理规模下跑不出结果。
    - P 被认为是有效的计算，NP 完全问题被认为是难的计算。
    - 讲者顺口问了一句：两者之间还有没有别的类别。
    - N 的平方和 N 的 100 次方在 P 里等价，这是为了追求数学的美。
    - **封闭性的含义：多项式算法可以调用另一个多项式算法。**
        - 外层算法只能生成多项式长度的输入。
        - 内层算法再花 2 次方、3 次方、4 次方的时间，返回的结果依然是多项式的。
        - 所以可以任意使用算法库里的算法，调用多少次都行。
    - 讲者的判断：这是人类大脑只能装下这么多抽象时做的 work around。
    - **吐槽** 「人类为了弥补自己的大脑只能想这么多、只能装下这么多抽象的时候，做的一个 work around」
    - 保研面试的建议：老师可能问 P 和 NP 是什么。NP 的 N 是 non-deterministic（非确定性），不是 not。
- **人类真正想问的是 RAM 模型下 K 步能解什么，但太细，只好用粗近似。** 多项式时间抹平了数据排布这类细节。
    - 近线性时间网络流的算法出现后，人们才意外发现，任意两个节点都相关的网络也能近线性求解。这说明我们对问题结构的理解有缺陷，也不知道算法里有哪些 trick 能压低复杂度。
    - **真正想问的问题：给定计算模型，运行 K 步能解决哪些问题。**
        - RAM 模型有 CPU 和指令集，指令包括 load、store、加法，每次读写内存花一个周期。
        - 它和今天有 memory hierarchy 的计算机不同，但可以形式化。讲者希望学生学完离散数学后能写出它的数学定义。
        - 人类想知道的是一台计算机能做什么、不能做什么。
    - **多项式时间是粗近似，抹平了很多细节。**
        - RAM 模型里每条指令都要精打细算。数据放在内存哪里、要不要压缩，会大幅改变 K 步的结果。
        - 多项式时间可以随便调用别的函数，好像不付出代价。
        - 人类很长时间以来一直在解决比较干净的问题。
- **真实世界的结构很乱，人类可能只是恰好处在能压缩的平坦区域。** 压缩经验产生智能，scaling law 的效果可能因此而来。
    - **生物分类树可能是图。**
        - 门纲目科属种的树状模型，人类花了很长时间构建，对应的 family tree 网站做得很漂亮。
        - 现代生物学对这个模型提出很多挑战。猫和狗容易分开，微观生物的界限却模糊。
        - 是否来自同一个祖先难以定义，结构可能不是树，而是图。
        - **吐槽** 「这个网站还是建得非常非常漂亮的，代表人类的文明」
        - **自嘲** 「但我不是这方面的专家」
        - **吐槽** 「实际的世界的结构其实是很差的」
    - 讲者的推测：物理世界在某个宏观尺度上比较平坦，我们刚好处在这个区域，所以经验可以压缩。
    - **讲者与 GPT 聊到的例子：对称性推出守恒量。**
        - 物理规律在不同时空应保持一致，只凭这一条 first principle，就总有一个守恒量，现在叫它能量。
        - 若世界结构很乱，我们可能只是刚好处在有守恒量的区域。
    - 经验可以压缩，压缩可以产生智能。因为我们正好处在这个区域，scaling law 才带来各种成果。这是因果关系。
- **讲者开场回顾上一讲，并说这类 AI 大新闻最近更频繁。** 上一讲讲了 DeepSeek harness 的插件设计、event bus。还讲了用许愿方式从外部加插件。
    - 讲者说最近让人震惊的频率又变高了（字幕原文：眩晕瘫坐的频率又变高了，待确认）。
    - 讲者说，AI 带着我们想到很多比较夸张的东西。
    - **吐槽** 「瘫坐的频率又变高了」
    - **吐槽** 「AI 带着我们想到很多比较夸张的东西」

> 原话：「有一种因果的关系，是因为我们正好处在这个区域里，所以我们的 scaling law 给我们带来了各种各样的东西」

## 2. AI交互轨迹是难以伪造的人物画像，能换来优势也等于交出灵魂

<small>▶ [08:55](https://www.bilibili.com/video/BV1Guxu6EERa?t=535)–19:50　·　转向　·　话题：用AI轨迹证明自己</small>

- **应届生可能被 agent 替代，毕业时的职场压力会变大** senior 带上 agent 就超过 junior，企业可能不再招应届生。
    - 以前的循环是家庭投资教育，学校培养人才，企业买走劳动力。
    - 中学阶段也是某种投资，你疯狂学习才考上大学。
    - 这个循环越来越难。资本家为应对竞争，会先稳住自己的优势，再谈把智慧交给后人。
    - 企业会发现招一个 agent 就够，没有理由花很长时间培养新人。
    - **玩笑** 讲者模仿资本家的内心独白：「诶我招一个agent也可以，我为什么要招一个新人来培养呢」
    - **玩笑** 讲者先给这段内容打预防针，说他最近在小红书发了很多「暴论」：「因为最近你们如果刷我的小红书的话会看到我发了很多的暴论」
- **AI 轨迹难以伪造，用人单位能抽查审计，也能看出成长潜力。** 讲者给学生的答案是，用压缩后的 AI 轨迹证明自己。
    - **轨迹是压缩后的时间轴，记录你做过的所有事。**
        - 压缩时去掉不必要的信息，例如「脱靠」的输出（字幕原文：脱靠/凸靠，待确认）。
        - 生成的图片等有用的 assets 保留。
        - 讲者做任何事都问 AI，包括今天吃什么、南大有没有开新店。
        - 上周去 CNCC，他把位置和偏好告诉 ChatGPT，让它做尽可能 comprehensive 的搜索。
    - **轨迹里的事实都能审计。** 包括 3 类：
        - 你今天聊物理、明天聊天文，你的想法、AI 的回答和你的反馈都有记录。
        - 生成的代码能否运行可以查。
        - 哪些想法来自你、哪些来自 AI 可以查。
    - **不可变日志更方便抽查，伪造的人在面试时会被打回原形。**
        - 讲者承认任何防线都有对策，但日志仍更方便用人单位审查。
        - 用人单位可以随机挑一天，例如 2026 年 3 月 10 日。请你回忆当时和 AI 的讨论，并用今天的眼光重新评价。
        - 你记得并能说对，几乎肯定是你自己做的。
        - **吐槽** 讲者说伪造轨迹的人，面试时会现出原形：「你就算是伪造了这个trajectory，你最后进入了面试，你一下子也会被打回原形」
        - 讲者总结，不可变的记录是很好的人物画像：「这个不可变的记录成为了一个非常好的你的人物的画像」
    - **轨迹能区分起点相同、成长不同的两种人。**
        - 高考同分的人进南大后，潜力无法从分数看出。
        - 同分的人，各科分布和题目分布也不一样。
        - 一种人进大学就是人生巅峰，此后没学过新东西。
        - 另一种人能力不断增长，例如发现和 AI 交流的更好方式，把 skill 写进 harness。方法学和人生观的变化都在日志里。
        - **吐槽** 讲者形容第一种人：「进大学那一刻就是你的人生巅峰，你从此以后再也没有学进过任何东西」
    - 学生没有商业机密，学的是人类已有的东西。学习历程可以交给用人单位，对方能全面评估能力和潜力。
- **交出轨迹能换来优势，也等于把灵魂交给 AI 公司。** 轨迹能窥探内心、预知未来，短期有回报，讲者自己无法抵御这种诱惑。
    - **轨迹让人恐惧，又让人难以拒绝。**
        - 轨迹能窥探内心，知道你的潜力，准确预知你的未来。
        - 把轨迹投影成简历，短期内会得到回报。
        - **玩笑** 讲者说交出轨迹像脱衣服：「你现在觉得啊你把这个衣服脱了就没有隐私对吧」
        - **玩笑** 讲者用「思想钢印」打比方：「有点那种思想钢印的那种感觉，就是他在窥探你的内心」
        - **玩笑** 讲者说这是和魔鬼的契约：「如果我把我的所有的跟ChatGPT的trajectory全部拿出来，那我就有一种我把灵魂都出卖给魔鬼了」
        - 讲者把生活都交给了 ChatGPT，OpenAI 对他在世界上的位置了如指掌。
        - AI 一边窥探他，一边给正向反馈、不断强化他，使他在竞争里占优势。
    - **agent 可以代替人先聊观点，人再接着辩论。**
        - 以前同学找讲者聊 AI 和 agent 工具，聊着聊着收敛到「英雄所见略同」。
        - 以后双方派出 agent 先聊，立即知道观点一致和不一致的部分，人再辩论，辩完由 agent 增强。
        - **玩笑** 讲者说轨迹编码了人格，交友也能交给 AI：「只需要由OpenAI来给你分配对象就可以了。开个玩笑」
    - **讲者建议学生保护隐私，并抢在别人之前做。**
        - 只和 OpenAI 或 DeepSeek 其中一家分享秘密。
        - **玩笑** 讲者把这条建议说成课堂奖励：「作为来给大家上课的时候，给一个小小的reward」
        - 用好的 skill 把轨迹蒸馏成简历或网站，用人单位可能给好 offer。
        - 大家都想到后会烂大街，进入恶性内卷，又会 reward hack。第一批意识到的人可以少 reward hack，更多追寻自己的内心。
        - **吐槽** 讲者预言这个做法很快会过时：「当然一旦大家知道想到要做这件事了，这件事就会烂大街」
- **上学可能变成期货，上班要先交保证金承诺超过 AI。** 讲者设想，毕业找不到好工作的落差，会变成入职押金。
    - 上学本身是期货投资：青春交给大学，毕业找不到好工作，落差很大。
    - **玩笑** 讲者把上学比作期货：「我觉得上学本身就是一种期货投资」
    - 设想入职时先承诺能超过 AI，并交保证金。
    - **玩笑** 讲者说以后上班像贷款：「你要贷款上班对吧」
    - **玩笑** 讲者设想入职的条件：「你要上班你就先承诺你可以超过AI，然后你就先交保证金哈」
    - 在 mentor 带领下一段时间内超过 AI、给公司带来价值，就得到回报。
    - 一直不再成长，保证金可能不退。讲者说这「是真的有可能会发生」。
- **讲者顺带讲了 3 件和主线无关的事** 临时加的内容、知识扩充的速度、AI 能力的限制条约。
    - 本节是讲者看到当天新闻后临时加的，之后回到 DeepSeek harness 像操作系统这个话题（见第 3 节）。
    - AI agent 代表领域里的全部知识。粗糙的想法能补全细节，也能告诉你哪些论文有人想过、哪里不周到、哪里还没人想过。人类扩充知识的速度会变快。
        - **玩笑** 讲者说到速度变快后顺口一句：「也不知道什么时候，突然有一天就全人类都被斩杀了，那就再另说」
    - 也许会出现类似核不扩散条约的约束，让 AI 能力不再增长。Anthropic（字幕原文：and sophie，待确认）和 OpenAI 在讨论，但没有趋缓。

## 3. everything is a plugin 让 harness 像操作系统，生态才是未来

<small>▶ [19:50](https://www.bilibili.com/video/BV1Guxu6EERa?t=1190)–23:30　·　回到　·　话题：harness是还没放飞机的航母</small>

- **harness 内核像操作系统，只有 event bus**　everything is a plugin 意味着内核不带实际功能。
    - 操作系统只提供进程 API、文件描述符和持久化数据管理。
        - 创建进程可以用 spawn 或 fork。
        - 进程可以持有指向系统对象的句柄或文件描述符。
        - 通过文件描述符可以 read、write。
    - DeepSeek harness 同理，只有 event bus 和原生插件。
    - 原生插件规定如何与 agent 和模型上下文交互。
        - 例如用 agent.inject 与 agent 交互。
- **航母已造好，飞机仍在试验，生态才是未来**　目前没有类似航母战斗群的形态，讲者期待生态长大。
    - 现在只有一些试验飞机，还不知道这艘航母上能放什么武器。
    - 最终成功的未必是 DeepSeek harness，但围绕 agent 的生态会让每个人用得更方便。
    - **手机端连接自己的 PC，让 agent 在后台工作**
        - DeepSeek harness 好像要发移动端应用。
        - PC 长期开机，手机端建立通道，PC 就一直在后台工作。
        - 形态像 GrabBot（字幕原文：GRAPBOT，待确认），但用自己的 PC。
        - 讲者认为这在中国是好模式，一定是未来。
- **一切皆插件，所以能把轨迹投影成实时简历**　开发者能监听所有插件。也能把轨迹做成个人画像（见第 2 节）。
    - 讲者建议大家回去，在 DeepSeek harness 上许愿做一个。
    - 可以监听各插件的行为。
    - 可以监听用户和插件的交互，以及插件和上下文的交互。
    - 还能把模型相关的内容留存下来，再做投影（字幕原文不清，待确认）。
    - 实时简历每天自动更新，不用自己维护。
    - 实时简历属于个人画像，界面可以做得非常 fancy。
    - **界面可以仿 GitHub 贡献墙**
        - 贡献墙是时间轴，颜色越深提交越多。
        - 提交 5 次深绿，2 次浅绿，没提交空白。
        - **玩笑** 今天没干活，格子就是空白：「如果我今天摸鱼了什么也没干，它就是空白的。」
        - 贡献墙可以作假，agent 能代为提交。
        - **自嘲** 讲者说自己的墙很绿（字幕原文为 AAAI，可能是 AI，待确认）：「我现在这个墙上面就非常非常绿，是因为这个提交都是 AI 帮我做的。」
- **插件生态会长出设计者没想到的用法，像 UNIX 管道。**　UNIX 诞生时没人想到今天会 cat 文件管道给 cloud gp。字幕原文可能是 claude -p，待确认。
    - **玩笑** 讲者说 UNIX 的设计者想不到这种用法：「UNIX 在他们诞生的那一刻起，做梦都不会想到今天我们有可能会写出这种 cat 什么什么，然后管道给 cloud gp。」
    - 这类用法一直存在，以前是 too long don't read 管道给 pager 看手册。

> 原话：「插件的生态就像操作系统一样。」

## 4. 航母这类复杂系统，都是从最简单的原点一点点演化出来的

<small>▶ [23:30](https://www.bilibili.com/video/BV1Guxu6EERa?t=1410)–38:45　·　举例　·　话题：航母不是一天造成的</small>

- **航母靠事先推演和操作手册运转，没人能整体读懂。** 讲者在 USS Midway 上看到蒸汽、电力、通信和损管叠在一起，感到震撼。
    - 讲者 2019 年参观圣迭戈的 USS Midway。该舰 1945 年下水，此时日本已投降，没有上太平洋战场。1970 年代做过现代化改造，1992 年是海湾战争的旗舰。
    - **舰内是多套系统并存。** 讲者是做软件的，看不出这样的复杂系统如何构建。
        - 当时有蒸汽管线，不像现在多数靠电。
        - 通信线路也要通电。
        - 航母是战争机器，随时可能遭鱼雷和轰炸机袭击，所以要做损管。
    - **老兵志愿者说，船员不需要懂整艘船，只照手册操作。**
        - 讲者问老兵，系统出故障怎么维护。
        - 老兵说设计者是天才，船员不需要知道系统怎么造的。
        - 每人一本操作手册，写明遇到什么情况做什么。例如某处起火，就把几号阀门从什么状态改成什么状态。
        - 讲者类比飞机的长操作手册，玩过模拟飞行的人见过。
        - 讲者判断设计者推演过各种可能，航母才能在战争里起作用。
    - 讲者由此理解造航母为什么难。中国第一艘航母不能说百分之百由中国制造。它买了苏联的航母，再做改装。
        - 讲者的困惑是，中国看起来有那么多船，造航母却显得那么困难。
        - 他的解释是，航母是一台战争机器。
- **所有航母都不是一天造成的，原点可能非常简单。** 展柜把美国海军第一艘航母到最新航母排成一代代演化，这是讲者最大的启发。
    - 展柜在 Midway 甲板的最底层。讲者把航母的历史追溯到最原初的点，再顺着演化看过来。讲者也用同样方式讲软件演化，包括 DeepSeek harness 的演化。
    - **船从桨帆到汽船，每一步都是平滑的小改动。**
        - 古代有桨船和帆船。几千年后材料和经验够了，才造出能远航的船。
        - 桑塔玛丽亚原是商船，1492 年成为哥伦布首次发现新大陆的旗舰。船上都是人类驾驭得了的机械装置。
        - **玩笑** 讲到泰坦尼克号时，学生没人看过那部电影：「你们有没有看过那个泰坦尼克号那个电影，没有对吧，我们有代沟哈，这这是这是代沟。」
        - 1811 年的新奥尔良号用高压蒸汽，沿俄亥俄河到密西西比河，1812 年抵达新奥尔良。轮子在外面，所以叫轮船，今天的螺旋桨在水下。
    - **演化只能是小改动，这是人类的局限。** 大脑和物理实验都有限制，任何时候只能从初始状态做一个小 delta。
        - 有用的结构加上，没用的结构减掉。
        - 古代桨和帆并存，远航船出现后桨被收掉。
        - 轮和螺旋桨可能并存过，后来只剩螺旋桨。
        - 汽船能挣钱，所以后人会研究更好的汽船。
- **运煤船改航母只是一个小 delta，之后才有升降机等架构改动。** 1913 年的 USS Langley 是试验型航母，由运煤船直接改成。
    - 讲者称这张 Langley 的图是他那天收获最大的一张。运煤船和泰坦尼克号很像，再往前也是平滑演化。
    - 想法只有一句：运煤船能载重，把上层运煤部分换成木质甲板当跑道，就是把机场搬到运煤船上。
    - **升降机是为解决船上空间有限而加的。** 这一步是工程师推理加实验的结果。
        - 工程师要计算跑道多大才够，飞机放在哪里。
        - 陆上机场可以在旁边修厂房，船上不行，飞机要放在船中间。
        - 甲板在上、机库在下，所以需要电梯把飞机运上去才能起飞。
        - 早期电梯在甲板尾后端有一部。现代航母在侧面，或有多部。
        - 直到二战，起飞速度仍是瓶颈。飞机要从机库运到甲板，无法并行。
    - Langley 是实验性想法。二战中日本和美国在太平洋战场证明了航母的用处，随后出现钢甲板航母。
    - **架构改变和小改动同时发生。** 把船改成机场，是之前所有船都没有的 feature，讲者称之为重构。
        - 两根管路谁在左边谁在右边，都可能影响可靠性。
        - 例如高热蒸汽管路保温做不好，会影响旁边的设备。第一版没考虑到，第二版修正。
        - 这些小改动包括 bug fix 和子系统重构。
    - 讲者总结，任何系统在设计时都经历这样一个通用过程。
- **AI 时代可以先做 MVP 再回头重构，不必从独木舟走起。** 能力无限的 chain of thought 模型让人从起点直接大跨步。
    - 过去造航母要从独木舟开始，再发明桨、帆、舵。现在不需要先做完整的东西。
    - 做 MVP，原型成功后，可以随时回到那个点重新构造。
    - 这是 AI 时代的许愿式编程。先许一个愿，看模型造出什么，再用严格的过程一点点把每个部分做好。
    - 讲者团队也在造航母，已经造出能起降飞机的航母，但还有很多问题。他们承诺做一个和 DeepSeek harness 一样好的操作系统，同样能支撑生态，并邀请听众读他公众号的征友帖。
        - **自嘲** 讲到自己团队的项目链接时，讲者刹车：「不能不能打太多的广告，因为这是只是上课时间。」
        - **玩笑** 讲完征友帖后：「属于夹带私货了哈，啊，开玩笑的。」
- **顺带：讲航母故事的由头是生态。** 讲者开头说，产品可能是商业公司的产品活到最后，但生态肯定是未来。所以要讲航母的故事。

> 原话：「其实所有的航母都不是第一天马上造出来的。」

## 5. 想理解复杂系统，就回到它的最简版本，把功能一路rebase过去

<small>▶ [38:45](https://www.bilibili.com/video/BV1Guxu6EERa?t=2325)–50:51　·　进一步　·　话题：回到最简版本再rebase</small>

- **复杂系统都从一个解决真问题的简单想法起步，再一点点演化**
    人、软件和航母都在积累中进步。早期通常只是一句话能说清的想法。
    - 想法可以很小：挖空一段木头就能过河，于是有了船。
        - **玩笑** 讲者用一句话讲发明船：「我看到一个木头，我能不能把它挖掉一块，诶，我就能从河的这边到那边了呢」，然后「你就发明了船」。
    - Linux 的起点是克隆一个免费 UNIX，最初的功能就是 UNIX 的功能。想法走在正确的路上，才能逐步改造成功。
    - **AI 能一步跳很远，但它设计的架构可能一开始就是错的。**
        - AI 会设计架构，也会一次跳很多步。
        - 软件维护时每次修改都更难，复杂度随之增加。
        - 讲者认为听众用 AI 编程时常有这种体验。
    - 很多架构经受住了时间考验，同时也有很多部分被重构。轮船今天还叫轮船，但已经没有轮子了。
        - **玩笑** 讲者说轮船的变化：「轮船真的有轮子的轮船，到今天我们还是说轮船，但是它没有轮子了」。
    - **Python 2 的 print 说明，早期设计只服务当时的最小系统。**
        - 听众入学时没见过 Python 2，讲者是从 Python 2.7 的时代过来的。
        - Python 2 与 Python 3 不兼容。Python 2 的 print 是内建语法，写成 print 加空格。
        - 设计第一天，系统里几乎只有 print，所以要让它好用。开发者没想到今天整个 AI 生态会装在 Python 上。
        - **玩笑** 讲者模仿当年设计者的心态：「我就这么随便一做吧」。
        - 这个写法给语法解析带来小麻烦。Python 3 把 print 改成函数，不再像关键字。
    - 上基础课的一个主要原因，是学软件系统早期的设计和它随时间的演化。
    - **吐槽** 讲者点评演化的例子，顺带说到 AI：「我觉得调度器的例子并不是一个很好的例子，Python的例子也不是一个很好的例子。所以我觉得AI还是没有办法共情。航母的那个例子显然是一个更好的例子。」
        - 讲者还说 CNIS 可能也不是一个很好的例子（字幕原文如此，待确认）。
- **想理解复杂系统，就回到没有这个功能的最简版本，再看功能怎么加进来。**
    今天的航母一定有平滑的演进过程。看不懂就回到独木舟，再看历史上怎么一步步加进来。
    - 跟着一个软件的发展学习，就能体会到世界一直在做同样的事情。大家一直在用简化的版本去理解软件。
    - 数学课直接给定义、定理、证明，不说人类走过多少弯路。
        - **吐槽** 讲者批评这种教法反人类：「这个东西你自己去悟吧」。
        - **吐槽** 讲者说现在这种定义、定理、证明的数学教法：「有点反人类」。
    - Linux 0.11 没有任何先进技术。讲者提到现在操作系统课从 xv6 学起。
        - 网上现在还能看到 Linux 0.11 的教程。
        - 很多课程爱讲某个东西多厉害，但厉害的东西都有一个平滑演进的过程。
        - **吐槽** 讲者学舌那些课程：「今天这什么东西怎么牛逼，怎么牛逼，怎么牛逼」。
        - 系统调用 read 像函数调用一样进来，执行 3 个操作再返回，一眼能看懂。
    - 讲者 Linux 2.6 时代入行。今天的 Linux 已复杂到人类理解不了。
        - 他理解新东西时，仍回到 Linux 2.6 问：这件事当时怎么做，好坏在哪，今天该怎么做。
    - **在 Linux 0.11 上想清楚一个 feature：系统调用不一定要穿过操作系统边界。**
        - 做法是内核和用户进程映射共享同一页数据，建议应用程序只读。
        - 页面里可以放当前 CPU 的 id 和当前时间。内核每秒写一次时间，进程创建或切换 CPU 时更新 CPU id。
        - 讲者在课上用这个例子。先在 0.11 上想清楚，再按 git 的思路把 feature 往后挪。
- **用 git rebase 把 feature 往后挪，只需看和它冲突的几个提交**
    软件架构把复杂性分解了。历史上大部分新引入的东西与某个 feature 无关。
    - 做法是在能理解的旧版本上加上这个 feature，再用 git rebase 一路把提交往后挪。
    - 每挪过一个改动，就问它是否影响这个 feature。比如新加了调度算法。没影响就跳过。
    - 理由：所有东西搅在一起，软件无法维护。好的架构耦合松，essential complexity 被分解下去。
    - 只需关注几个关键提交，看 feature 和谁冲突，冲突怎么解决。不能只用最简的理想模型理解软件。
        - **玩笑** 讲者把冲突说成打架：「你要理解他们怎么打架的」。
    - 类比数学：人类走了几百年弯路，才发现两样东西应该连在一起用，于是发明了 group theory。
    - 这是人类的局限（见第 1 节）。新手面对当前的 DeepSeek harness，只会感到无尽的复杂性。通过历史 rebase 想了解的 feature，可以理解任何东西。
- **程序员三大浪漫有了新答案，软件演化成为研究对象**
    git history 完整记录了创造的过程，是宝藏。讲者希望把这个思路用到数学史和造船史。
    - 以前的三大浪漫是自己做操作系统、编译器、数据库，也可能是 CPU。
    - 今天投 AI infra 的简历，同学都写在 nano-vLLM 上改了什么。
        - 例如迁移到多卡，或用 4 块 RK3588 这类带 NPU 的小卡做并行推理加速，接入魔改的 nano-vLLM。
        - 讲者认为这些都有意义，鼓励去做。同学们没意识到，自己做的就是这件事。
    - 有了计算机，才能把创造一个东西的过程从初始状态起完整记录下来。
    - 讲者认为在 AI 时代，还能守住人类最后一点创造力的人，应该去干更大的事情。
        - **自嘲** 讲者这样称呼在场的人：「我们作为还能守住人类最后一点创新创造力的人类」。
    - 讲者希望有人为数学发展史构建 git 历史。
        - 他不知道 OpenAI 或 ESHOP（字幕原文：ESHOP，待确认）有没有在做类似的事。
        - 他也希望把造船、造航母的脉络构建出来，把人类知识史整理成带分支 rebase 关系的样子。他承认这个 git 比喻不恰当。
    - 讲者说自己用 git 的模型解释了造航母和同学们的学习。这门课讲软件工程，所以只讲软件。

> 原话：「如果你觉得这个很厉害的东西你不知道他是怎么做出来的，你就回到一个不存在这个东西的版本，回到独木舟，然后再看一点它的发展的历史是怎么把这东西加进来的，你就马上就知道了。」

## 6. SWE-bench衡量的是小事，稀疏的大架构决策需要taste bench

<small>▶ [50:51](https://www.bilibili.com/video/BV1Guxu6EERa?t=3051)–65:00　·　进一步　·　话题：小事已被解决，缺品味基准</small>

- **提交史大多是小任务，SWE-bench 测的正是这类小事。**　绝大多数提交是 bug fix 或小 feature request。所以先要问 AI 能不能做好小事。
    - **SWE-bench 的做法是给 issue，让模型改代码，再用测试用例判对错。**
        - 论文约在 2023 年，是 GPT-4 时代，当时没有能真正跑起来的 agent。
        - 每个任务包括模型输入、issue、golden patch 和一组测试用例。
        - 同系列还有 SWE-bench Pro，以及更长任务的 Terminal Bench。
        - SWE-bench 是这个系列里知名度最高的工作之一。
        - 它在历史上的地位，是问大模型能不能把一件小事做好。
        - 当时的答案肯定是不能。
        - GPT-4 能力很强，但幻觉也很严重。
        - **玩笑** 讲者谈论文作者有没有看到这层意义：「虽然我觉得可能这些论文的作者可能都没有看到，我不知道他有没有看到，也可能看到了」
    - SWE-bench 不完美，但任务明确，有明确的反馈信号判断做对没有。测试用例有缺陷。有些 bug 源于代码设计的小问题，讲者作为人类会选择 refactor 而不是 fix。
    - 早期成绩很差。论文表 5 里 Claude 2 和 Claude 3 Opus 的解决率约 3.79%（字幕原文：3.779，待确认）。当时 OpenAI 领先，Claude 只能说在某些垂直领域做得更好。
        - 论文的结论是完全不行。
        - **吐槽** 讲者看到这组成绩时的评价：「惨不忍睹的这个比例」
        - **吐槽** 讲者形容当时 OpenAI 的地位：「没有人能打得过 OpenAI」
    - **小事做好，演化路线上的大部分就跑通了。** GitHub 上的任务可看作随机抽样，多数是日常小改动。
        - 例子：程序 crash 请人修；日期计算没算闰秒，请人改进；给功能再加一个星期。
        - 讲者说，大家日常开发多数时候都在做这类事。
        - **吐槽** 讲者对着听课的人说：「你们日常的时候做做开发，绝大部分时候都是在干这件事」
        - SWE-bench 被解决，就意味着工程里大部分琐碎（字幕原文：TDS，待确认）的事被解决。
        - 每年都有浩如烟海的 benchmark 论文。
        - 这个方向最有 vision 的地方，不在于多出一篇 benchmark。
        - benchmark 背后的意义，是站在人类的高度，看这件小事的价值有多大。
    - **吐槽** SWE-bench 隐含的预言，让大家今天都很焦虑：「如果我的 SWE-bench 刷完，低级工程师就被斩杀了，低级工种就全部被斩杀了」
- **重构与架构改变很稀疏，SWE-bench 没覆盖这部分。**　琐碎 bug 修多了才会触发重构。而架构变化在人类世界里本来就少，反馈也稀疏。
    - 新项目的第一个提交没有被覆盖。讲者开项目时，先在脑中有想法，再建 repo，放入初始状态和计划。这件事很难做成 benchmark。
    - **重构可以让 bug 直接消失。** 这是讲者团队自己项目里发生的事。
        - 有段代码像 AI slop，逻辑很复杂，原因是设计时两个模块没有解开。
        - 写这段代码时必须同时带着两个模块的状态。
        - **吐槽** 讲者形容那段代码：「那个代码写得就像是 slop，非常非常复杂的逻辑」「那个代码就写得非常恶心」
        - 团队把整个模块一起重构，重构完 bug 不再存在，根本不需要被 fix。
    - 重构意味着架构变化，可能只是局部变化。架构很难改。
        - **吐槽** 讲者形容修琐碎 bug 修到崩溃：「终于有一天你小事做得太多，这种琐碎的 bugfix 太多，你受不了了，你开始重构」
    - **大迁移也会发生，而且可能没出事故。** Claude 一段时间前把 Bun（字幕原文：棒，待确认）从 Zig 全部迁到 Rust。讲者认为，这和项目结构有关。换成 MySQL 这类项目，他估计就不行了。
        - **吐槽** 讲者看到迁移时的第一反应：「是一个非常疯狂的事情，竟然没有出笑话」
        - **吐槽** 讲者当时心里的独白：「这可以吗？这不会留下这种非常糟糕的 bug 吧」
        - **吐槽** 讲者说换成别的项目就不行了：「你如果去搞一个 MySQL 这种，我估计就不行了」
    - 架构分多个层级。有顶层架构，有代码里的架构，一个函数写成 functional 还是 imperative 也是微架构。
    - 子系统级的架构改变何时发生、怎样算好，样本都很稀疏。
- **大决策样本太少，只能指望模型从少数案例泛化。**　人类是 few-shot 学习者。讲者认为模型能否用很少样本泛化，是下一个研究热点。
    - 稀疏意味着模型没法靠大量反馈和样本学到。大家都希望模型有人类这种能力，但能否做到，讲者说「不知道」。

## 8. 没法阻止AI生成slop，只能用验证器在提交前拦下来

<small>▶ [78:03](https://www.bilibili.com/video/BV1Guxu6EERa?t=4683)–90:09　·　进一步　·　话题：用检查器挡住AI slop</small>

- **AI 没被说清楚就会猜，结果是多余测试和难维护的代码**：agent 缺开发者的上下文，只想完成任务。
    - 需求没说清有两种结果。用 grill me 这类 skill，AI 会反复追问。不用，AI 就自己猜。
    - **玩笑** 讲 grill me 的追问：「就疯狂的问你一遍一遍一遍一遍的问你然后问到你烦为止你就算了」
    - agent 会做不必要的测试验证。任务本身是实验性的，agent 又缺上下文。
    - 多余内容让维护和修改变复杂，所以 DeepSeek harness 仍由人驾驭。
    - 人不可能短时间做这么大的项目，像是「极速造航母」。所以要防止 AI 毁掉整个项目。
- **配对文档的 yaml 能挡住不一致，代价是仓库膨胀**。README 的中英文两份必须一致。靠 yaml 配对检查（上次课的国际化例子）。
    - 效果：至少阻止了文档不一致。
    - 代价：仓库膨胀，多出一堆意义不明的 yaml 文件。
    - IDE 可以配置成不显示这些文件，眼不见为净，但文件仍然存在。
    - **吐槽** 讲者说隐藏文件只是自我安慰：「就眼不见为净但它实际上存在的」
    - **吐槽** 讲者评价这个 yaml 方案：「我觉得很脏的非常脏的一个 yaml 来处理」
    - 这印证讲者前面的主张：软件项目不该用目录存储，该存下内容之间的关联。用文件存关联可能只是 workaround。
- **没法阻止 AI 生成 slop，只能写验证器在提交前拦下**：先想 AI 会生成什么样的 slop，再逐个写成检查。
    - 讲者承认没有好办法。DeepSeek harness 找出所有不好的特征，一个个强行排除。
    - DeepSeek harness 做了非常大的工作，去产出与人类对齐的好代码。
    - 讲者的原意是没有好办法找出所有坏特征再逐个排除。所以转去写验证器。
    - 验证器在 commit 时、push 到 remote 时、每日运行时检查。AI 犯错就阻止这次提交。
    - **dsh-prose-standard 把 AI 写文档的坏习惯写成规则。** 讲者让 agent 总结 gatekeeping，agent 自己激活了它。
        - 这个 skill 是文字编写规范，要求删除推理过程、重复和修饰，有去 slop 的味道。
        - **玩笑** 讲者对着屏幕点评这个 skill：「有一点on slop的感觉」
        - AI 写文档会把思维链写进去：这样设计、怎么验收、做了 A 做了 B 而不是 C。
        - **吐槽** 讲者评价这种写法：「这是一个非常糟糕的是一个非常非常糟糕的行为」
        - A、B、C 都和实现文件关联。实现改动时文档必须同步修改，这是同步代价。
        - 迭代几轮后，A、B 的代码可能没了，「不要 C」却被错误留下。不该留的东西就这样留在仓库里。
- **检查从低级错误管到架构约定，规则靠开发者的经验和直觉逐条写**。所有项目都该用 lint 和类型检查。
    - harness 的 checker 分 7 类。有代码与类型质量、架构与依赖约束、行为正确性、持久化和兼容性。还有文档、构建交付与评审（分法待确认）。
    - **lint 和类型检查拦低级错误。**
        - 模型再强也会犯低级错误，大代码库里更明显。
        - 改接口时所有调用方必须一起改，编译器能找出来。还要检查全部代码能编译。
        - 讲者估计听众自己的项目不会这么严：编译过了、改一处就 push。真实项目为防 agent 才加检查，例如不同用途的 id 不能因为都是字符串就混用。
        - **自嘲** 讲者模仿听众平时的做法：「我相信啊就你们你们自己开发自己的项目的时候肯定不会做这么严格的检查对吧」「你可能自己编译过了诶发现有一个地方要改一下嘛你就这样改一下你就你就把它放到push上去了」
        - 讲者要求静态检查让同一份代码遵守同一套 lint 规则。
        - 规则例子：丢失的 promise、危险断言、no deprecated、no unused variables、每个导出必须有 JSDoc、禁止硬编码 UI 文案。
        - 其他规则还有 prefer const、no unused expressions 和作用域检查。
        - 另有一些与项目相关的规则，例如 verify runtime closure（字幕不清，待确认）。
        - 对自己的 hobby project，任何不安全的特性都可以用。严格的包可以禁止 Rust 的 unsafe。
        - **吐槽** 讲者对比 hobby project 与严格项目：「这对于你们自己的hobby project来说任何不安全的特性都是可以使用的」
        - 实验性实现可以先用 unsafe，但过不了 lint 就推不到远端，必须改到做好。
        - no unused variables 能抓笔误，例如 for 循环里把 i 写成 j。
        - **吐槽** 讲者说第一门程序设计课不教 lint 有问题：「这就会让你们写出这种什么A等于空格一这样的代码」
    - **agent 不遵循架构约定，要用规则拦。**
        - agent 可能把功能完整另实现一份，再在代码里直接加一行函数调用，破坏架构。
        - **吐槽** 讲者描述 agent 的做法：「他就莫名其妙就是完整的把这个功能实现了一份」
        - 提示词里没写「遵循架构」。干净架构默认所有人遵守，对人类写这句没有意义。
        - 写进去可能让指令遵循更好，但文档更难读，需要取舍。
        - 做法是控制流检查：所有控制流由插件发起，硬编码函数调用就拒绝。
        - 其他规则：浏览器代码不能无意依赖 host，网络调用不能悄悄绕过 user agent。
        - 浏览器应用的请求要相对于当前文档解析。
- **检查分 pre-commit、pre-push、CI 三层**：越早的层越先拒绝坏提交，CI 做更复杂的检查。
    - pre-commit 跑一系列检查，包括中英文配对。两份文档的 commit hash 对不上，提交被直接拒绝。
    - pre-push 做 tab check（字幕原文：tab check，待确认）。
    - 测试讲者后面专讲。
- **顺带：讲者认为这套门禁做得好，但课上讲不完**
    - 讲者觉得 DeepSeek harness 里这些做法做得很好，想给大家一点启发。
    - 讲者说自己没办法在课上一个个讲过来。

## 9. 否定式提示词无效，需要反例驱动的循环去提炼品味

<small>▶ [90:09](https://www.bilibili.com/video/BV1Guxu6EERa?t=5409)–99:56　·　但是　·　话题：品味靠自我改进循环</small>

- **AI分不清轻重，否定式提示词会让上下文膨胀** 每个写进上下文的词，模型都当成重要的。纠正反而放大问题。
    - 模型有时过分自信，认为事情搞定了，实际没达到讲者预期。
    - 模型有时过度小心，不必谨慎的地方也写了很多测试。
    - **讲者一说「不要这样」，模型就把这句话复制多份。**
        - 模型先在文档里写一份，再在代码里写一份，再在注释里写一份。
        - 膨胀的上下文不断抢夺模型的注意力。
        - **吐槽** 「你但凡说不要这样，他就会把『不要这样』写到文档里，首先在文档里写一份，然后在代码里再写一份，注释里再写一份。」
    - 每个出现在上下文里的词，模型都认为重要。世界上还有无穷多个词没写进去，它们的权重和「不要放蒜」一样。
    - **玩笑** 讲者用点菜比喻模型分不清重要性：「我不要放蒜，不要放韭菜，不要放蘑菇，番茄炒蛋你就给我炒一个番茄炒蛋。但是模型不理解它们之间的重要性。」
    - **玩笑** 讲者说模型有自己的想法，顺势感叹：「我们每一个人都有自己的偏见，然后人类社会就是靠我们的偏见向前进的。」
- **给反例比给禁令更接近正确做法，但选哪个反例很难** 讲者以前做程序合成。这个领域早就用反例引导（counterexample guided）修正生成结果。
    - 程序合成指：给机器一份 spec，让它生成满足 spec 的程序。
    - 讲者说这和许愿编程有点像：给模型一个 spec，期望拿到正确实现。
    - spec 可以是样例：F1=2、F2=3、F3=4，机器生成 λx. x+1。
    - **Excel 智能填充是这类技术的产品化，2011 年前后引起小热潮。** 讲者上研究生课常拿它当案例。
        - 场景：收集到的电话号码写法不一，有 02512345678，也有 025-12345678。
        - 不会写程序的人给几个例子，系统生成基于正则表达式的程序，把区号和号码分开归档。
        - 这叫 Programming by Examples。另一种是 programming by demonstration，用户操作一遍，系统学出程序。
        - 这两个问题今天已被大模型解决。
    - 反例引导技术当年非常热门，到今天还有人在研究。
    - **这个过程和今天与大模型交互的方式很像。**
        - 模型只拿到 F1 到 F3，可能生成 x+1。
        - 讲者补一句「F4 等于 6」，模型可能只给这个输入打补丁，其余仍返回 x+1。
        - 选什么反例才能让模型生成正确程序，很难。
    - 「不放蒜」是糟糕的提示词，因为它暗示还有同样重要的不放香菜、韭菜、辣椒。
- **口癖词表是逐条反例的积累，缺少高层准则** dsh-prose-standard 靠列出禁用词去除 AI slop。但讲者不知道背后的总原则。
    - dsh-prose-standard 是 harness 里的写作 skill。讲者认为写英文论文的同学用它很有帮助。
    - 词表包括：ensuring、highlighting、framing、showcase、additionally、interplay、intricate，以及句型 not just X but Y。
    - 讲者说这些词是 GPT 的口癖，可能到现在还在。以前写文章几乎不用。
    - **吐槽** 「我不知道这是 GPT 的口癖，到现在可能都还有一个 ensuring、highlighting。」
    - 有些词严格来说也不算错，但语气太重。讲者说写论文要谦虚一点。
    - **吐槽** 「也要谦虚一点。」
    - 流程是：观察到 AI 做了 A、B、C、D、E，就要求 not A、not B、not C、not D。这是典型的 counterexample guided。
- **邮件风格实验：用可计算指标驱动循环，逼模型提炼通用准则。** 把全部旧邮件放进上下文，模型也学不会讲者的风格。
    - 讲者有自己回复过的全部邮件，但 AI 自动回邮件仍然失败。短邮件可能还行，长邮件不行。
    - 模型没有从样本里提炼风格的能力。
    - **讲者设计了 recursive self improve 的 loop。**
        - 讲者想要一个去 slop 的 skill，但不知道它该写什么，所以让循环去找。
        - 用 write email 或去 slop 的 skill，让模型回复讲者过去回过的邮件，但不让它看原回复。
        - 计算统计指标：回复长度、词语统计（字幕原文：瓷瓶，待确认）、句子长度、标点使用。
        - 指标离讲者更近，就保留这一版 skill。
        - 指标离讲者更远，就要求模型提取一条通用 guideline，加回 skill。
        - guideline 要看透本质。例如「不要 not X but Y」背后，要弄清不要的是无关内容，还是别的东西。
    - 讲者说这在今年还做不到，但自己乐观。
    - 这个 loop 和人类做软件、做工程的流程同构。讲者希望它最终把小事和大事都干好。
- **讲者顺带讲了 2 件事和主线无关的建议** 一是怎么学自己感兴趣的项目。二是小事已解决、大事缺评测。
    - 讲者承认具体语言和项目功能都是绑定的。细讲会显得枯燥，所以他展示的是遇到感兴趣项目时的做法。
    - **自嘲** 「具体的语言肯定是绑定的，以及这个项目本身的功能是绑定的，我要讲的话就显得很枯燥。」
    - 讲者建议听众用本课的方式打开自己感兴趣的项目。例如做生物信息学、要靠它拿博士学位的同学。做法是总结文档质量保障，再把提交整理成时间轴（见第 7、8 节）。
    - **玩笑** 「你真的就想要，你就要靠它拿到你的 PhD。」
    - AI 能力强，小事已解决，大事还需要 taste bench（见第 6 节）。

> 原话：「不放蒜是一个很糟糕的提示词，因为你说了不放蒜，意味着你有同样重要的不放香菜、不放韭菜、不放辣椒。」
