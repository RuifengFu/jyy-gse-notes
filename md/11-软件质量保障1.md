## 1. AI 一步造航母，人类跳过演化就失去对软件的掌控

<small>▶ [00:00](https://www.bilibili.com/video/BV1ej4g6xESc?t=0)–06:45　·　开场　·　话题：许愿编程丢掉了掌控</small>

- **复杂软件像航母，由独木舟一步步演化而来** 仓库从最小状态起，靠不断 commit 加 feature 长大。
    - 内核、编译器、应用服务器也一样。克隆下来有五六十万行，开发者直接懵，只看得懂 README。
    - **吐槽** 讲者模仿读者的反应：「你一看五六十万行代码，你直接就懵了，你不知道从哪下手」「你看到那个 README 好像还能看懂，但你马上就不知道从哪下手了」
    - 今天工业级能用的东西都是航母。需求不断加入，系统必然越来越复杂。
    - 最初是只会漂浮的独木舟，是最小的仓库状态。后来加了起降飞机、容错两类需求，系统越来越复杂。
    - 人类造船像 agent 做事：做思维链推导，多人像 multi agent 协作。
        - 社会里还有相应的组织来改进航行的船。
- **许愿编程像许愿要航母，意图与实现之间有鸿沟** AI 不知道真实意图。它也没亲历从简单到复杂的思考。
    - 许愿编程好用，却总让人觉得差一点。原因就是这像许愿要一个航母。
    - 例子：许愿「造能起降最先进喷气式战斗机的航母」，AI 直接上手造，成品大概率不符合预期。
    - AI 理论上知道造航母的过程，但没有亲历。它造不了航母，连教育系统这种小东西也造不好。
    - **吐槽** 讲者点评 AI 的能力：「你让 AI 去造航母，它也造不了」
    - 讲者说，意图与实现之间的 gap 一直存在。
- **理解大系统要从能懂的历史时刻 rebase** 沿某个 feature 的提交回到最简版本，看它何时成为合理需求。
    - **回溯一个 feature 的步骤**
        - 查这个 feature 何时引入。
        - 带着该提交，从软件最初版本 rebase。
        - 独木舟上起降飞机不合理，船够大后才合理。
        - 再看运煤船加甲板如何改出起降装置，甲板如何继续演化。
    - 软件演化是连续的，所以要从自己懂的历史时刻开始。
    - 大作业让人熟悉精简系统，再 rebase 现在的特性，由小懂大。
    - **吐槽** 讲者调侃上学时的作业：「这也是为什么我们上学的时候这么痛苦，要做那么多的大作业」
    - 用 AI 写大作业会丧失理解。古法编程的经验来自试错，一个 bug 可能调好几天。
    - **自嘲** 讲者自称「我们作为古法编程过来的人」，经验来自一个 bug 调好几天。
    - **自嘲** 讲者自己也许愿编程，说到断网：「我们现在都许愿编程，我也许愿编程，一旦网断了我甚至都不知道应该怎么办」
- **AI 大提交让人无法审计，人类只剩对表象的了解** 以前每次提交只做一件事。AI 每个提交改一两万行。
    - 以前软件由人生产，生产很慢，所以提交都很小。
    - git 最佳实践是每次提交只做一件小事。这样可审计、追踪、git blame，也是 rebase 的基础。
    - 小提交能让人知道谁引入了某个特性，谁又怎样引入了某个 bug。
    - AI 两三百个提交就造出一个航母，人类不再知道软件是什么。
    - 人只知道测试通过、基本功能正常、航母能起飞，其余一无所知。所以 agent 时代质量保障更重要（整理者补充）。
    - **吐槽** 讲者模仿人的心态：「反正我看起来它测试通过了，我运行起来它基本的功能是正常的」「如果我叫这个航母去起飞一架飞机，它真的能起飞，除此之外我对它一无所知」
    - agent 说自己做了高质量、设计优雅的软件，但没有新需求时，无法评估质量和扩展性。
    - **吐槽** 新需求真交给 agent 后，它的反应：「对不起，是我错了，我对架构的理解没有想的那么好。他会给你一个非常诚挚的道歉，但是屎山就又扶不起来了」
    - 本课面向 CS 学生：写操作系统、编译器、数据库的训练仍有用。
    - 讲者说，学生此时受过相对专业的训练，这些经验至少还有用。

> 原话：「许愿编程的后果就是人类不再掌控软件，只了解它的一些表象。」

## 2. bug 是实现偏离规格，错误悄悄传播才难找

<small>▶ [06:45](https://www.bilibili.com/video/BV1ej4g6xESc?t=405)–24:34　·　因此　·　话题：bug 是规格与实现不一致</small>

- **人类的幻觉比 agent 更大，要靠编译器和运行反馈才能改对。** 人类手滑、看错、数错，离开编译器和运行就写不对程序。
    - **开场：质量保障的基础是承认程序员天生写出 bug。**
        - 人类不再掌控软件，仍要对质量承诺，所以质量保障更重要（见第 1 节）。
        - 本节讲调试理论，它是软件质量保障的基础。讲者每年在计算机系统基础课讲它。操作系统课讲不讲，取决于当年课时。
        - 软件是物理世界的过程在信息世界里的投影。
        - 讲者问什么是 bug，并说学生每天都在写 bug。
        - **吐槽** 「你每天都在写bug」
        - 任何程序员都有幻觉，都不可信。计算机系统基础课的软件设计公理说「未测代码永远是错的」。讲者还提到「第一条是机器码是对的」。
    - **agent 的幻觉曾被诟病，今天的 agent 已是「神技」。**
        - GPT-3.5 和 GPT-4 时代的模型博古通今，但幻觉严重。
        - 上节课的 SWE-bench 截图：把代码贴给模型，要它给 patch，打进去往往不能修复。
        - **玩笑** 「他就兴致勃勃地写下了一个patch」
        - 被测模型包括 ChatGPT 3.5、Claude 2、Claude 3 Opus，以及当时的小号开源模型（基本只有 Llama 系列）。resolution rate 都低。
        - 古法编程调一道期末题要两小时。今天大家对 agent 习以为常，还嫌它跑得慢。
        - **吐槽** 「你写一个期末考试题，你都调半天，好像对了，然后你调两个小时」
    - **人类手滑，曾经催生专门修命令的 thefuck。**
        - shell 命令打错命令、参数、文件名都正常，用熟了也会。
        - thefuck：用户在 shell 里骂一句脏话，它按 shell history 找到上一条命令，用一系列匹配模式修复常见错误。
        - 典型场景：编译时报找不到某个东西，或某个命令打错。
        - **吐槽** 「你直接就在这个shell里面骂粗口，你说一句脏话」
        - 从 commit history 看，项目约 10 到 11 年前火爆，现在基本已死。
        - **自嘲** 讲者想现场演示 thefuck，但没装：「我今天因为翻车了，所以我没有来得及装」。
    - **人类是 ReAct agent，出幻觉后立即按反馈调整。**
        - SWE-bench 论文批评 AI 幻觉严重，没想到人类幻觉也极度严重。
        - **吐槽** 「他没有想到人类的幻觉也是极度严重的」
        - 不给编译器、禁止运行程序，要求一次写对，人类肯定写不对。
        - **吐槽** 「如果我不给你编译器，你还能写代码吗」
    - 受过良好训练的人，在架构设计上不易像 agent 那样偏离，写代码时却会偏移。从 1 数到 300 基本会数错，原因是短时记忆。
- **bug 是实现与规格不一致，纸面上很难看出。** 讲者用一个写错变量的 for 循环说明，bug 要执行起来才暴露。
    - **self attention 出错也会产生 bug。**
        - 开发者写二重循环，写到内层时眼睛往上一瞟，self attention 权重被错误加大，把内层的 `j++` 写成 `i++`。
        - **玩笑** 「你的self attention把这个权重不小心错误的加大了」
        - AI 模型也有 self attention，会犯同类错。
        - 这个 bug 叫 fault。fault 有多种，包括 2 类：漏考虑重要情况，算法本身错误。
    - 代码埋在 100 行里，人眼看不出。脑中的架构是：读数据、预处理、二重循环、输出。视觉扫一眼符合这个架构，人就倾向认为代码和设计一致。
    - agent 同样犯这类错。后面有 agent 的 trajectory，有些 bug 傻到人会嘲笑，agent 照样犯。GitHub 上每天都有 patch 号称修复 bug，说明到处是 bug。
    - **bug 的定义是实现和规格不一致，规格可能不存在或没说清。**
        - 讲者逐步执行循环：前几步可能与规格一致。
        - 第一次循环里 sum 加一后等于 1，是对的。
        - 规格要求 i=0 时 j 从 0 走到 n−1，再换 i=1。实现走到 i=1、j=0 时，状态已偏离规格。
        - **自嘲** 讲者推演时自己说错：「哦，错了。你看我已经幻觉了，我也幻觉了」。
    - 安全漏洞在纸面上更隐蔽，包括 3 类：缓冲区溢出、坐标算错、整数溢出。讲者举过的例子：用无符号整数存余额，从 0 扣 100 元，余额变成「无穷大」，花不完。
- **fault 经执行变成 error，error 无声传播，到 failure 才被看见** 三者依次传播。程序员能写下的只有 fault。
    - 中文里错误、失败、失效难区分，英语里分得清。fault 是代码里的缺陷。error 是执行中状态明确不满足规格。failure 是人看得见的失效。
    - fault 要执行到才变成 error。许多执行本身符合规格，讲者说单元测试和系统运行都可能全程正确。
        - 讲者说，系统跑起来、航母上的飞机也看到起飞，那条路径上整个执行都可能符合规格。
    - **error 无声：CPU 不报告，只有运行异常才让人察觉。**
        - CPU 无情执行指令，是 load 就 load，是 store 就 store，没人告诉你状态已错。
        - **吐槽** 「它才不管你是什么呢，哦这是load我就load，这是store我就store」
        - 按测试输入，程序本应约 0.0001 秒结束，却跑了 3 到 5 秒。人这时才观察到 failure。
    - **fault 要合适输入才触发，触发了 error 也未必出现 failure。**
        - 例子：代码里藏着 `if (random == 1234567)`，测很多次都触发不到。
        - error 可能只破坏栈上一个没用的地址。
        - 缓冲区溢出若不用专门工具检查，被覆盖的内存可能是空的，或本次执行没用到，输出看起来正常。
        - **玩笑** 讲者说程序员写下 fault 时自己并不知道：「所以要心疼一下程序员」。
- **规格缺失或不清，是火箭事故的根源** 规格与实现的 gap 是老大难，最强的程序员也会掉进去。
    - **火箭事故中，fault 一直在代码里，审计没发现，最后传成严重的 failure。**
        - 起飞时运行了一段没有用途的对准代码。
        - 其中浮点数转 16 位整数缺少越界保护，发生整数溢出并触发异常。
        - **玩笑** 讲者讲到溢出触发异常，对学生说：「你没想到吧」。
        - 各种审计没发现。讲者推测地面可能没做完整的模拟测试，测试不充分。
        - 火箭要运行足够长时间才触发，和前面那个要跑到 counter 溢出的循环类似。
        - 火箭对异常有容错，系统不 crash，走错误恢复流程。错误的控制指令却让方向改变，火箭炸掉。
        - 主备惯性导航用了相同的软硬件。备份本可应对偶发错误，但两套几乎同时溢出、同时停机，酿成严重的 failure。
        - 两套惯导读到的传感器数据可能不同，执行的分支也可能不同。两套的溢出却几乎在同一时刻发生。
    - 开发者不是故意不维护规格和实现的一致，是规格不存在或不清楚。没有规格写明「程序不应 crash」「不应有任何浮点数异常」。
    - 传感器也可能真读错，异常真会发生，异常要正确处理。系统和外部交互时，规格到底是什么并不清楚。道理简单，实现困难。

> 原话：「程序有 bug 不代表触发 error，触发 error 不代表能看到 failure。」

## 3. 选不易伤人的语言和架构，能从根上消灭整类 bug

<small>▶ [24:34](https://www.bilibili.com/video/BV1ej4g6xESc?t=1474)–33:33　·　因此　·　话题：语言与架构先于测试</small>

- **架构和语言先于测试，是质量的第一因素。** 最有效的办法是更好的架构、不易伤人的语言和防御性编程。
    - 测试用例的数量不是第一因素，架构和设计才是。火箭软件团队已尽最大努力，bug 依然没有消灭。
- **Java 消灭了指针类未定义行为，所以取代了 C++** 所有指针访问都有定义。
    - Java 快速取代 C++，成为主流面向对象语言。托管运行时牺牲一点性能，换来没有这类未定义行为。
    - 空指针仍在，但行为有定义。Tony Hoare 称发明空指针是十亿美元的错误。访问空指针时 Java 崩溃或抛 null pointer exception，外层可以 catch 后继续执行。
    - Java 让这类问题从 Java 程序员脑子里永远去掉。讲者称这是非常伟大的进步。
    - **玩笑** 讲者把指针问题比作幽灵：「这是一个幽灵」
- **C 的指针自由让 malloc/free 的规格人类守不住** 每条执行路径都要配对一个 free，free 后指针不能再用。
    - 整数可以转成指针再解引用，函数指针可以实现面向对象。这给开发者能力，也让人容易犯错。
    - **玩笑** 讲者评价 C 的指针自由：「C 嘛，C 你是指针一时爽嘛」
    - **malloc 的规格要求每条路径都有配对的 free**
        - 最常见的错误是 return 时忘记 free。
        - setjmp 和 longjmp 让路径有无穷多条。
    - use after free 危险，因为别人可能用你的内存。操作系统有此问题时，可能把关键数据结构分配到你持有指针的内存上。你读它就能读到密钥。
    - 控制流复杂后，程序员自己也搞不清。人类研究了几十年，今天仍能在 Linux 内核里找出几十到一百个 use after free。
        - 同一个函数可以有不同入口和调用方式。里面有分支，分支还可返回不同位置。
    - **吐槽** 讲者说不能把这个规格全交给程序员：「你绝对不应该把这样的信任交给一个连 shell 命令都会打错的人类」
    - **吐槽** 讲者调侃同学们不爱写 free：「我知道你们是不喜欢 free 的对吧」
    - **吐槽** 讲者说同学们从没认真想过 malloc 的规格到底是什么：「你们从来没有严肃的想过这件事」
- **safe Rust 和编程风格约束能防住内存错误** 选对技术路线是质量保障最重要的事。
    - safe Rust 几乎消灭了所有内存安全问题。编程风格也能防错，例如 Linux 里的 goto release。
    - 本科作业允许出错，写火箭程序的人不能。
        - **吐槽** 讲者对本科生说作业出错的代价：「错了无非就是被老师扣点分，也许助教就不会看出你的程序有错呢」
    - bug 不可能全部消除，所以后面讲测试，假设 bug 到处都是。
- **让大模型对照 bug 库审查代码，可暴力找 bug** agent 的注意力和能力远高于程序员。
    - 做法：选成熟项目和一个像字典的 bug 数据库，请大模型审查某类 bug，例如 use after free。可以几个问题打包。
    - 投入多少成本，决定能找出多大的 bug。讲者说用暴力方法爆破代码。
    - 讲者说这是今天的版本答案，同学们也可以用。
    - 最好的程序员也会以某个概率写出这类代码。agent 在需要特定条件的逻辑 bug 里可能找到漏洞。
    - **玩笑** 讲者说这个方法在 agent 时代刚来就有人做：「我现在非常确信应该有人发大财了」
    - **成本由一根滑杆决定。**
        - 写非常 safety-critical 的软件时，可以用这根滑杆选审查力度。
        - 左边少花钱，让 agent 看看有没有问题。让 GPT 写、Claude 看一遍，可能真能找出问题。
        - **玩笑** 讲者说 agent 自己也会看：「不要笑」
        - 右边多花钱，对照 bug 库更严苛地审查。

> 原话：「你的架构和设计永远是决定这个软件系统质量的第一因素」

## 4. 找 bug 需要能触发错误的输入和判断对错的检查

<small>▶ [33:33](https://www.bilibili.com/video/BV1ej4g6xESc?t=2013)–38:52　·　进一步　·　话题：输入暴露错误，检查识别错误</small>

- **fault 变成 error，需要好输入**：输入要覆盖 specification 的方方面面，才能触发藏得深的 error。
    - 这套理论看似废话，用处是指出 fault 到 error、error 到 failure 两段传播都有条件。
    - **自嘲** 讲者先说这套理论听起来没用：「看起来就是个废话嘛」
    - specification 代表程序所有执行都要满足的性质，所以它要尽可能完备。
- **error 变成 failure，需要好检查**：没有检查，error 被触发了也看不出来。
    - 最坏情况是所有 error 都被触发，却没有一个变成 failure。例如语言不会 crash，只做整数运算，但没法检查输出对不对。
    - **动态规划题难调，因为输入容易造，检查难做。**
        - 样例对了，不代表程序对。输入是 N 加 100 个随机整数，很容易生成。
        - 程序输出 1384 或 1383，都不 crash，对错要靠合适的检查判断。
        - **玩笑** 讲者模仿调题时的自问自答：「你的程序输出了个什么，1384，到底对不对啊？对啊，他没crash，他输出1383，对不对？」
    - 什么时候能做检查，有一点 art 的味道。检查有专门一节课，本节只讲测试。
- **运行样例是最便宜的测试，应该自动化**：把编译和运行配成一键，再接上 CI。
    - 运行样例是最便宜的软件质量保障方法。
    - **吐槽** 讲者说学生做测试，通常只是运行样例就结束：「测试嘛，大家就不用我多讲了，你们都会测试的，你们都不会测试的，对吧？你们都会运行一下样例然后就结束的」
    - **玩笑** 讲者回忆大一学编程，只能往命令行输入框里粘贴：「你们是什么时候才摆脱往那个输入框里面复制粘贴的」
    - 大一时，无论 VS Code 或 IDE 里的终端，还是简陋 IDE 弹出的命令行窗口，面对的都是一个输入框。
    - 学生复制粘贴 100 次、1000 次、1 万次后，在计算机系统基础课上发现管道。于是配一条 build rule，按一键就编译并运行样例或测试数据。
    - **玩笑** 讲者模仿学生突然开窍的内心独白：「诶，突然发现我有个东西叫管道」
    - 这是学生在大学里的成长。刚开始没意识到这件事重要。意识到后，质量保障流程就更好地融进了开发流程。
    - CI（持续集成）让程序编译完就自动跑测试。通过就不用管，不通过才报告。
    - 保研机试需要计时，讲者估计机试短期不会消失。花一分钟配好编译和运行，之后只管写代码。
    - 还可以加 hook，保存后立即编译运行。

> 原话：「你花一分钟的时间把你的编译和运行配置好，然后你就直观写代码就行了」

## 5. 环境、非确定性和非功能需求让测试无法穷尽

<small>▶ [38:52](https://www.bilibili.com/video/BV1ej4g6xESc?t=2332)–47:11　·　但是　·　话题：真实软件的测试很难</small>

- **真实软件依赖运行环境，环境不同结果就可能不同。** 软件是物理世界过程在信息世界的投影，你的环境不是别人的环境。
    - 讲者提出一个问题。在 Windows 上写的代码，能否保证在 macOS 或 Linux 上正常运行。
    - 动态规划题的规格只规定输入序列和要求的结果。真实软件要在真实环境里运行，结果还要符合规格。
    - 完整的测试要求软件在任何环境、任何输入下都符合规格。
    - 光是运行环境，就够花非常大的力气去探索。
    - **大小端：同一个 int 在不同机器上的字节顺序不同。**
        - 内存可以看成一个 int8 数组，比如 64G 的地址空间。一个 int 占 4 个字节。
        - 0x12345678 可能按 12 34 56 78 存，也可能按 78 56 34 12 存。
        - 用模 256 取低位可移植。用 and 0xFF 并假设小端，换到大端机器就不工作。
        - 网络编程里经常要做大小端转换。
        - 写 C 时，开发者不知道对方的编译器和库，程序可能在那个平台跑不起来。
        - **玩笑** 讲大小端时，讲者对听众说：「你们死去的计算机组成原理又开始攻击你们了」
    - 编程语言解决了大部分平台问题。讲者在 Mac 上写的 three.js 游戏，在 Linux 上通常能正常运行。
    - **第三方库的版本悄悄变化，语言也解决不了。**
        - LXML 是 Python 的 XML 解析库。agent 搞不定 Word、PowerPoint、Excel 时，会用它改文件里的 XML。
        - 几个版本之间，它处理某些 emoji 或 Unicode 字符的行为变了，原来能工作的程序会 crash。
        - 讲者的程序输入就是 XML。解析行为悄悄变了，这也是环境的一部分。
        - **吐槽** 讲者说：「我记得有一段时间我很讨厌呃Python的有一个叫LXML」
- **非确定性也是输入的一部分，同一输入可能结果不同。** 负载、网络延迟和线程调度都会改变程序行为。
    - 即使环境完全一致，程序从初始状态开始后调用的 API 也可能和别人不一样。两次运行也可能不同。
    - 程序没有时间轴。除实时操作系统外，操作系统不保证 T 时刻执行一条指令后，T+1 毫秒内会执行下一条。
    - 现代系统隐含假设程序会持续往前执行。执行太慢，会触发 timeout，或队列满后丢数据。
    - **吐槽** 讲到线程调度时，讲者说：「线程的调度这就很恐怖了」
    - 放射性治疗仪的并发 bug 伤过人：操作员点得快，两个部件状态不一致，病人受到过量照射。讲者每年在操作系统课讲它，这里没有展开。
- **检查对错本身就难，还要加上非功能需求。** 即使生成了规格内的全部输入，有时也判断不了这次结果对不对。
    - **玩笑** 讲者让步时说：「我们退100万步讲」
    - 非功能需求包括 4 项：永不 crash、无内存安全错误、性能达标、安全性达标。
    - 它们同样要在任何环境、任何数据下成立。
- **测试只能找到 failure，不能证明 bug 不存在** 测试难在要覆盖任何环境、任何输入，所以 Dijkstra 的批评成立。
    - Dijkstra 在 The Humble Programmer 里讲自己的编程哲学，批评测试。
    - 测试流程走通、找到一个 failure，软件质量就提升一点。
    - 讲者接着说，测试仍然是有用的方法（见第 6 节）。

## 6. 程序可泛化，所以测试能建立信心，失败还能定位 fault

<small>▶ [47:11](https://www.bilibili.com/video/BV1ej4g6xESc?t=2831)–55:02　·　但是　·　话题：测试建立信心并指引调试</small>

- **典型用例通过能建立信心，因为程序天生可泛化**。开发者带着完整需求写程序，不是只为通过某几个用例。
    - 测试覆盖不了所有输入和环境（见第 5 节）。把规格和输入环境画成点，系统测试只跑最重要的典型案例。
    - 这些典型案例，是软件作为物理世界过程在信息世界的投影里最重要的那些。它们跑对了，就给人信心。
    - 典型案例都对时，剩下的错多半是 typo 这类细枝末节，成因是 self attention 不够。功能理解错了，则不太可能在许多典型场景下全部通过。
    - 程序能泛化，所以一个测试通过，与它相关的可泛化部分也应该通过。测试只能显示 bug 存在（见第 5 节），但仍然不断增强信心。
    - 极限性能、并发调度大变、与其他程序交互、换机器，这几类角落缺测试用例，就没有信心。
    - **玩笑** 讲到只能通过 N=1 用例的程序，它没有泛化，只会 overfit：「如果 N 等于 1，输入 N 等于 1 的，你们都干过这事吧，期末考试的时候，对吧」
    - **玩笑** 讲到正常人为什么带着泛化写程序：「你是软件工程师，你拿了钱，你收了钱，你就是干这个需求的」
- **失败的测试能缩小 fault 的位置，像给出条件概率**：已知有 fault 又看到这个 failure，就能排除无关代码。
    - 失败的测试给出两条信息：程序里有 fault，以及运行到哪里出错。
    - 例子：空指针异常的 call stack 指向空指针那一行，fault 大概率在它附近。
    - 理由：开发者很少把空值存起来，隔很长的代码才用到。更多是某处写错、某个数值算错，不久后用到时立刻暴露。
- **二分状态轨迹，能找到第一个由对变错的转移**。错误状态会一直带到后面，所以对状态做二分就能定位。
    - 做法：检查轨迹中间的状态。状态对就往后找，状态错就往前找。
    - 目标：找到第一个从正确状态进入错误状态的转移。程序是状态机，这一步的代码和 bug 相关。
    - 例子：代码把 i 从 0 变成 1，但需求是把 j 从 0 变成 1。i 的状态错了，所以改 i 的这条语句就是 root cause，修掉即可。
    - 这个方法不是百分之百有效，但失败的测试用例大概率给出有用信息。
- **早期 agent 靠失败测试修 bug，强化学习让它越修越准**。2024 年的 SWE-agent 用 ReAct 循环喂回失败结果。成功率随尝试次数上升。
    - SWE-agent 是 2024 年 5 月（arXiv 2405）的论文，早于 Claude Code 的产品设计。讲者相信 Claude Code 借鉴了这类文章。
    - GPT-4 展现出能力后，出现了一批让 agent 修 bug 的工作。
    - 做法：用 ReAct 循环把测试失败的结果告诉 agent，agent 再改 patch。尝试次数越多成功率越高，但达不到今天的效果。
    - 讲者说这类工作非常有前瞻性。
    - 讲者当时还没有 scaling law 的愿景，所以并不看好这个工作。
    - 相信 scaling law 的人赌曲线随模型变强一直上升。他们赌 Claude Code 能用强化学习和后训练，训出能从一个失败测试找到出错位置的模型。
    - **自嘲** 回看这类工作时：「我其实当时我们也不知道谁能成功，甚至我在那个时候看了这个工作并不是特别的看好」

> 原话：「你的程序能泛化，所以你每当有一个测试通过的时候，你都会感觉到有很多东西和它相关，应该是通过的。」

## 7. 小问题用单元测试查，覆盖率告诉你哪里没测过

<small>▶ [55:02](https://www.bilibili.com/video/BV1ej4g6xESc?t=3302)–66:37　·　进一步　·　话题：测试分层与覆盖率</small>

- **单元测试应先于系统测试，从局部到整体测** 系统测试查模块协同。小错误应交给更便宜的单元测试。
    - 做 OJ 时把动态规划题的一大串输入整个跑，是系统测试。但 bug 可能只是低级小错误。
    - 100 万行代码的每个小模块都能单独测试，小模块里的问题就能立即暴露。
    - 人爱偷懒，想整个跑一遍再看。模型有自信时也一样，一次写两三千行，不写单元测试，直接跑系统测试。模型不留测试用例，截图看一眼就说搞定。
    - 真做软件工程时，用一次系统测试找单元测试就能找到的问题，浪费更多钱和时间。
    - **吐槽** 讲者说模型学会了人的懒：「今天模型也会偷懒，模型也学会了，跟人真的一模一样」
    - **吐槽** 讲者模仿模型跑完系统测试后的做派：「他甚至截个图看一眼，他说好，这给你搞定了」
- **黑盒测试靠边界值，测试用例是花钱的子弹** 黑盒只看可观测行为。通过后因程序能泛化，对附近输入有信心。
    - OJ 是典型黑盒测试，只看输出对不对、有没有 time out。边界值要测数组长度 0、1、允许的最大值，另有决策表、转换表。
    - 测试像一把枪，每个测试输入是一颗子弹，子弹要花钱。单元测试便宜，多打。系统测试贵，少打。目标是打到足够多的输入空间，建立信心。
    - **玩笑** 讲者用枪和子弹比喻测试成本：「你有一把枪，每次可以设一个，相当于生成一个测试输入，你就可以打到一颗子弹，那子弹是要钱的对吧」
    - 软件工程的比例是大量快速的单元测试、适量的集成测试、少量的端到端测试。
    - **玩笑** 讲者讲测试工程师的经典笑话：「一个 QA engineer 进入一个酒吧，他首先点了一杯啤酒，然后他点了零杯啤酒，然后他点了99999999杯啤酒，然后他点了一个蜥蜴，然后点了一杯啤酒，然后他又点了一个奇怪的东西。然后这个酒保应对自如，测试工程师高兴地离开了酒吧。然后第一个顾客来到酒吧，他问这个洗手间在哪里，突然这个酒吧就开始崩塌起火，这个程序就 crash 了」
    - 讲者说这个笑话反映了我们对测试的理解。
    - 笑话里的 QA 很尽职，测了边界值。你们写的程序很可能在点一杯时就出错。
    - **吐槽** 讲到 QA 把边界值都测了，转头说 GPT 写的程序：「GPT 写的程序它就有过度的防御性，他会写大量的检查，然后这检查其实对你来说可能也不必要，就是所有的检查不合法的统一的就扔一个异常出去可能就好了，他一定要把每一个不同的异常都要分开」
    - QA 只打中输入空间的一部分，总有没考虑到的输入。信心只建立在已想到的情况上。
    - 这些情况是物理世界过程在信息世界的投影。
- **覆盖率指出没测过的代码，可让 AI 补测试到达标** 跑完测试得到被执行语句的集合。没执行的语句没有信心。
    - 程序是状态迁移，每次迁移执行一条语句。test1 执行第 1、3、6 行，test2 执行第 1、3、9 行（字幕原文：136行、139行，待确认）。
    - 全部测试跑完，第 7 行从没被覆盖。「未测代码永远是错的」（见第 2 节），所以对第 7 行没有信心。
    - 第 7 行若有不能编译的问题，编译器能帮你找到。但写成别的错误，编译器找不到。
    - **吐槽** 讲者对没覆盖的第 7 行说：「那对不起，你至少没有建立对第七行的信心」
    - **覆盖有 3 种，开发者希望都做到**
        - 语句覆盖：每条语句至少被 1 个测试用例执行。
        - 分支覆盖：每个条件的两个分支都要执行。
        - 路径覆盖：循环 1 次和 2 次都要测，因为两者可能导致不同结果。
    - **许愿让 AI 补测试**
        - 生成各种测试用例对大模型都简单。开发者懂测试概念和第一性原理，就能许愿。
        - 愿词示例：构建合适的单元测试，统计覆盖率。对没覆盖的代码报警，或不断添加单元测试直到覆盖率达到 100%。
        - 以前只有大公司或严肃项目的 manager 才会要求，人写测试用例很难受。
        - 一个测试用例可能救你：程序会组合，别人调用时，另一条路径上可能出错。
        - 讲者说这些防御性的要求都有道理。
- **用 stub 或 mock 替代真实环境，改动后重跑回归测试** 真实系统里取时间、读文件、收网络包很麻烦。替身让测试更便宜。
    - 智慧教室软件要收摄像头数据，没有真摄像头就无法做系统测试，初级开发者嫌麻烦。做一个假设备不断供图像即可。
    - AVD 是安卓虚拟设备，没有安卓手机也能开发。它带 mock 摄像头：最早只读到静态数据，已足以让申请权限、拍照的应用运行，后来某版本可传入视频。
    - 申请摄像头权限、拍照的代码，如果没有真机就没法测。
    - **吐槽** 讲者评这种做法：「这显然不是一个合适的 practice」
    - 理论上只需做尽可能好的测试，把每一份成本都最大化地变成对正确性的信心。
    - 回归测试：改过一行，原来对这行的测试结论就不成立。与这行相关的测试要重跑，从单元测试开始。
- **讲者顺带讲了 3 件和主线无关的事**
    - 讲者自称专业做测试，认为软件工程课本里的这些说法都对。
    - 本节的图是让 AI 生成的。讲者只记得笑话，就让 AI 直接生成笑话图。
    - 讲者不按教科书理解真实软件系统的测试，只要记住这张图，从第一性原理出发。
    - **自嘲** 讲者说笑话图是让 AI 生成的：「连这个笑话都是因为我记得这个笑话，所以我就让 AI 直接帮我生成这个笑话图」
    - **自嘲** 讲者说自己是专业做测试的：「其实我自己是专业做测试的，他们说的都对」

> 原话：「子弹是要钱的。」

## 8. 架构没做好，再多测试也救不了质量

<small>▶ [66:37](https://www.bilibili.com/video/BV1ej4g6xESc?t=3997)–84:58　·　但是　·　话题：架构决定质量</small>

- **许愿生成的 CS:GO 能玩，但缺陷多，不能交付** 讲者只给一句话。没有提示词和 skill，DeepSeek Flash 就生成能玩的游戏。
    - 许愿已成日常。讲者前两天许愿生成仿 Apple Watch 的小界面，给 ESP32 小设备用，含节拍器、to do list 和 AI 聊天工具，面向小朋友。
        - **玩笑** 讲者说许愿已成常态：「我们一天到晚都在许愿」
    - 讲者的提示词只有一句：实现一个相对精美的 CS:GO。讲者在 Mac 上用 web 版生成，放到 Linux 上也能运行，体验差别不大。
    - **画面精美，讲者认为来自后训练加入了审美奖励。**
        - 游戏素材全由 agent 生成，效果惊艳。上一版 DeepSeek Flash 做不到。
        - 某些新模型（字幕原文：GPTSTRA、office5.5，待确认）突然对审美有自己的要求，其他模型随后都学会了。
        - 模型有视觉能力，能判断精美还是简陋。强化学习就用精美来奖励。
    - **进游戏后，肉眼立即看到多处缺陷。**
        - 旗子漂浮，栏杆可以穿过，人物像浮空，切枪动画有问题。讲者说这些缺陷不算恶性。
        - 讲者说这个质量不能交付。讲者自己的 ESP32 项目体量更小，交付质量高很多。
    - 建议：agent 干完后，让它复盘做了什么。有些内容可以整理成自己喜欢的 skill。
- **agent 反复截图检查，根源是引擎无法单独验证** agent 前 50 到 60 轮已生成可玩版本。之后陷入检查、写测试的循环。
    - **agent 的后期检查进入低效循环，最后撑爆会话。**
        - 讲者让 agent 复盘 trajectory。agent 写了不少测试，边写边修 bug。
        - agent 写玩法脚本，跑 12 秒看 AI 交火，再用多机位截图。
        - 截图越积越多，单次 response 到 50 兆，接口返回 413。讲者必须新开 session。
        - 前 50 到 60 轮之后，全是检查、写测试、检查的重复。
    - 测试看起来详尽，但讲者进游戏后肉眼立即发现问题。
    - **硬编码让引擎只能靠截图补漏洞。**
        - 讲者问 agent 设计是否有问题。agent 答：引擎是 CJS（字幕原文，待确认）加手写的极简 AABB 物理，没有碰撞。
        - 讲者认为引擎没有为质量优先设计。原因是他没给提示词，只让它生成游戏。
        - 没有碰撞不致命。讲者可以建模写明栅栏、箱子、墙不能穿，子弹能打到墙上。
        - 但箱子是硬编码的，所以容易出错，只能反复截图才能修。
    - 讲者如果自己设计，会让所有物体都能单独检查，所有部分都能用代码检查，不需要截图。
- **架构不好，再多测试也救不了质量** 系统越大，整合测试越贵，很多问题只有跨模块协作才测得出。
    - 质量保障不是做多少测试。讲者说，真正的质量保障只有一句话：架构决定了质量。
    - **例子：智慧教室的人脸监控和到课监控，靠清晰接口让每个模块单独验证。**
        - **吐槽** 讲者说这个话题最近最热：「但好像不是我们学校，我感觉我没有收到任何官方的消息」
        - 两个模块接口分得很开，最后接到 event bus 上。
        - 人脸模块有 1 万或 100 万张 benchmark。各种输入格式和帧率都要达到性能预期。
        - 两个模块之间只传人脸向量。到课模块的正确性是：输入任何向量，都产出正确结果。
    - **反例：红警收起基地后，基地变成一条狗。**
        - 这是讲者童年回忆的老游戏。讲者说游戏里有无穷多的 bug。
        - 收起前，基地的单元格上已有单位。敌方工程师已半只脚踏进基地，我方的狗被叫来防守，卡在基地收起后出现的位置。
        - **玩笑** 讲者讲到基地被占位时：「哇，卡，我的机器直接被狗吃了」
        - 这个游戏还有 bug，包括船厂能修飞机、维修厂能卖步兵。有些 bug 到后来才被人开发出来（字幕不清，待确认）。
        - 原因是引擎硬编码了很多假设：地面有层，用 2D 模拟 3D，每个单位有一个高度。设计时没有考虑任意的游戏进展，所以崩溃。
    - **只做测试不够，架构没设计好，项目仍然失败。**
        - 工程实践是：处处做单元测试，覆盖率到 100%，模块集成也用代码测，不用截图。验收时跑轨迹，再截图确认真实游戏合理。
        - 做完这些，只要架构没设计好，项目仍会走向万劫不复的深渊。
        - 意图、规格、实现的金字塔会漂移。讲者从第一节课就在讲这点（见第 1 节）。
    - 建议：本科生最重要的是试错，回头会明白决定质量的是架构，重构是改进代码质量的最佳途径。
        - **吐槽** 讲者对本科生说，要去外面试错：「你就看着这个屎山是怎么样最后倒塌的」
- **纯函数让函数单独可测，Rust 逼人这样设计** 全局状态要穷举所有可能取值。纯函数的正确性只由自己负责。
    - **全局变量同时抬高测试成本和思想负担。**
        - 函数里先后两次 global.get，正确性就要求所有可能的全局状态下，所有执行路径都对。
        - 测试时要构造或 mock 全局状态。大模型能代劳，但这仍是成本。
        - 并发可能在两次 get 之间改掉状态。哪些状态可能，哪些不可能，要考虑到什么程度，都要想清楚。
    - 纯函数是数学意义上的函数：没有副作用，输入 X 不变，输出就不变。单元测试足够时，理论上能保证 F 正确，也更容易证明 F 正确。
    - **Rust 的价值是逼人重新想哪些状态该放全局。**
        - 讲者喜欢 Rust，不完全因为变量生存期。
        - **吐槽** 讲者说不是因为喜欢 Rust 的生存期：「非常恶心的变量的生存期」
        - **吐槽** 讲者说 Rust 编译器让人不由自主写出好设计：「那个非常恶心的编译器」
        - 典型模式有两种：把对象 hand off 给你，你再还给我。或者用 reference count 管理全局变量的生存周期。
    - **函数式设计不万能。**
        - 函数组合时会写出高阶函数，传入函数或返回函数、lambda。
        - 此时函数和其他函数的规格产生关联：返回的函数对谁负责，负责的 scope 有没有改变。
        - 讲者说，平时写代码更偏向函数式设计，会获得一定收益。
- **好架构的收益来得晚，奖励信号跟不上** 好架构前期效率低，要到很晚才超过急速堆出的代码。
    - 架构做好后，讲者说剩下的把软件工程教科书丢给 agent，agent 就能做好。
    - 质量保障和编程一样，需要灵光一闪。架构还需要品味，agent 还没完全学会。讲者相信 AI 理论上能学会，因为软件工程教科书已经很多。
    - 反馈回路长：屎山（难以维护的烂代码）堆起来以后，人才能理解好架构的好处。
    - **两条效率曲线：急速堆屎山先快后崩，好架构先慢后稳。**
        - 像 DeepSeek Flash 刚才那样急速堆屎山，生产效率随需求增长，到某一刻就维护不下去。
        - **吐槽** 讲者说 DeepSeek Flash 刚才的做法是：「急速堆屎山」
        - 好架构开始时效率较低，因为要搭脚手架，做验证和测试。很晚才超过前者，并有持续增长的潜力。
    - 强化学习完成任务就得奖励，所以模型会选捷径。
        - **吐槽** 讲者模仿模型的心态：「哎，我不管了，我就给你，反正你要，就这么地吧」

> 原话：「架构决定了质量。」

## 9. 有黄金版本或覆盖反馈，找 bug 就能自动化

<small>▶ [84:58](https://www.bilibili.com/video/BV1ej4g6xESc?t=5098)–97:09　·　举例　·　话题：差分测试与模糊测试</small>

- **有黄金版本，差分测试每步对拍状态，立刻定位出错的指令** NEMU 每执行 1 条指令，就和 QEMU 对一次状态。
    - **吐槽** 同学调试可能也有 bug 的 NEMU，手上没有参照：「同学们一定是一片哀嚎」
    - **吐槽** 同学没有任何辅助地调试，「那一定是惨不忍睹的」
    - **差分测试来自讲者和余子濠的一次「许愿」**
        - 讲者说，质量保障方面，只要有想法，就可以许愿。差分测试是其中一个愿。
        - NEMU 是 RISC-V 或 x86 的全系统模拟器。它带声音和图形，是一个完整的计算机系统。
        - 2013 年左右，余子濠实现第一版 NEMU，成为第一年的计算机系统技术实验。
        - 这一版可能也有 bug，不算黄金版本。但它能跑仙剑奇侠传，固件也都打好了。
        - 两人在计算机学院的咖啡厅聊天，约 2014 或 2015 年（字幕不清，待确认）。
        - 两人在咖啡厅许愿：CPU 做成可插拔，只靠总线握手协议、总线数据进出和一根中断线连接。
        - 讲者要求 CPU 的接口像动态链接库一样，可以插拔。
        - 外设和 CPU 核分开。外设上挂两个 CPU，同样状态各送一份，只保留一份输出。
        - 每个周期把寄存器和内存状态放进 QEMU，执行 1 条指令，读回结果对比。
        - QEMU 能跑 Windows 虚拟机，所以讲者把它当作正确答案。
        - 只要和 QEMU 百分百一致就行：「他跑一步你跑一步」。
        - **玩笑** 「他能跑一个 Windows 虚拟机，它就是对的，或者我们就相信他是对的」
        - 差分测试最早不是为龙芯杯设计的，而是为了拯救「计算机系统基础」课程实验。
        - **玩笑** 「不是用来打龙芯杯比赛的，是用来拯救大家的」
    - **对拍暴露 CPU 的全部状态，所以 bug 不再难找**
        - 没有黄金版本时，程序没 crash，开发者只能假设结果对。
        - 单个测试可能碰巧蒙对 zero flag 或 parity flag。
        - 两条指令组合时也会出错，一个单元测试也可能碰巧蒙对。
        - 两三千行代码不算多，但每条指令看起来都一样，肉眼找不出错。
        - **吐槽** 不用差分测试，「你是不可能把一个复杂的程序给调对的」
        - 有黄金版本时，EFLAGS 算错，立即知道是上一条哪条指令。
        - 定位到指令后，查手册就能修复。
    - **编译器也能差分测试，但要先排除未定义行为**
        - 两个编译器的输出不同，也可能是 C/C++ 程序有未定义行为。
        - 测试程序必须没有未定义行为，所以这是「带条件的生成问题」，更难。
    - 这套机制用于 2019 年的第一期一生一芯（字幕：2029年，待确认）。今年有了可上 FPGA 的快速版本，用硬件加速对比。
- **输入空间可以自动搜索，覆盖率反馈让模糊测试日夜找 bug。** 保留覆盖新代码的输入，再变异、交叉，生成新输入。
    - **测试可以写成搜索问题：把全部命令行输入编码成字节序列**
        - 例：a.out 带 4 个参数和一个 a.txt，限长后约 140 字节（数字待确认）。
        - 遍历全部空间能把每个行为至少跑一遍，但很低效。
    - **更高效的做法是维护一批输入，变异并交叉**
        - 变异：把字节 A 改成 B，或换入程序里的常量。
        - 交叉：拼接一个输入的前一半和另一个输入的后一半。
        - 讲者说这像遗传算法，但不确定该叫什么（字幕：Iterative research，待确认）。
        - **自嘲** 「这也不能算遗传算法」，「我现在不能确定它到底叫什么名字比较好」
    - 覆盖了以前没覆盖的代码的输入更好。这个反馈就是反馈制导模糊测试。100 台服务器的集群日夜跑，找安全漏洞，也可能找功能问题。
    - **玩笑** 「疯狂的去搞一个 100 台服务器的集群，然后没日没夜的为你的软件生成测试用例」
    - **模糊测试在工业界已经有效：syzkaller 和 OSS-Fuzz**
        - syzkaller 对 Linux 内核找到的 bug 和漏洞，有些现在无法复现，可能修不了。
        - 开源软件每天发布，新版本不会立即进入下游，因为太危险。OSS-Fuzz 在此前持续扫描。
        - 除开发者自己 fuzz 外，第三方也在持续扫描漏洞。
        - fuzz 通过后，日志显示测试时长和用例数，开发者对 release 有一定信心。
        - 供应链投毒者因此要绕开它：禁用 fuzzing，或 hack 部分功能（字幕不清，待确认）。
- **AI 做不到认知之外的事，许愿的前提是你有正确的知识。** 要学架构、测试原理和前人 30 年的质量保障做法。
    - 学会后能泛化到自己的项目。项目未必用差分测试或 fuzzing，但会想到写定制的测试输入生成器，覆盖大空间，再许愿。
    - AI 现在可能还做不到你认知之外的事。领域专家要为 AI 提供认知。
    - **安卓初创团队许愿做机械臂，物理拔插 SD 卡来测驱动**
        - Sanmaha（字幕：SANMAHA，待确认）向同事许愿：做一个小机器人控制 SD 卡进出，再做写出开始、处理和结束条件的测试。
        - G1 的 SD 卡槽 Linux 驱动不稳定，后来整个重写。
        - 零几年的模拟器不够成熟，团队部分用 3D 打印做了装置。软件给舵机发信号，拔出再插入。
    - **讲者也许愿做了光栅钥匙扣**
        - 设计来自讲者家的小朋友。4 帧动图拼成，拉动时是动画效果，全程自动，可换 5 cm × 5 cm 的照片。

> 原话：「现在所有东西都是许愿，但是许愿的前提是你有正确的概念。」
