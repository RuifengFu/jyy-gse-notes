## 1. 软件工程靠经验、流程、工具积累，工具改进工具是自我改进史

<small>▶ [00:00](https://www.bilibili.com/video/BV1wysu6hEkz?t=0)–10:26　·　开场　·　话题：软件工程的自我改进</small>

- **intent 难以对齐，实现会偏移，软件工程由此而来**
    软件工程从不停失败中积累。积累出的有三类：经验、流程和工具。
    - 软件是物理世界过程在信息世界的投影。大家看到的一切都是软件。
    - 软件分三层：最上层是 intent，中间是 spec，最后是 implementation。
    - intent 可能很模糊，例如领导说「我要做一个好的教务系统」。spec 写明软件的架构。
    - 人和人也无法完全对齐。开发者经验不足、架构做得差，实现就会偏移。
    - 笑话里的商学院同学有 intent，但不知道自己要做什么。
    - **玩笑** 讲以前的笑话，商学院同学拉人入伙，说有个好商业模式：「就差一个程序员了」
    - **玩笑** 讲毛头小伙子做了不好的架构：「如果你也是一个毛头小伙子然后做了一个不太好的架构」
- **经验和流程来自失败，规模越大软件越难构造**
    人月神话说软件易失败。编码规范和流程把失败经验固定下来。
    - 人月神话：规模和团队增大，构造更难。10 万行比 1 万行难，肯定不止 10 倍，可能 100 倍甚至更难。
    - **玩笑** 说软件不能靠拍脑袋：「我们拍个脑袋说我们就差一个程序员了」
    - 经验还包括：怎样设计软件架构，怎样划分模块边界，源代码该怎么写。
    - 需求文档该怎么写，也是软件工程积累的经验。
    - **编码规范把人类程序员常犯的错写成规则。**
        - SEI CERT C 是 CMU Software Engineering Institute 早就发布的 C 编码规范。
        - 讲者点开 floating point 一节，规范说明怎样写才可移植，并附正例。
        - 规范提醒：不要假设数值，使用运算符要小心。
        - **吐槽** 点开规范页面时即兴说：「随便点一个我也不知道会有什么」
    - **agent 改了代码不改文档，下个 session 会出错。**
        - 两边不一致后，agent 只读文档不读代码，项目就不停失败，要改多轮才改对。
    - 流程：从最早被批判的瀑布模型到现在的敏捷开发。commit 前必须检查，push 后建议做更多检查。
- **工具以软件为输入，工具改进工具是开发者的自我改进史**
    开发者离软件工程最近，每天在流程里摸索。他们会把经验变成工具。
    - 软件工程的工具包括：版本管理、IDE 或 agent harness、编译器、编程语言、运行框架、调试器。
    - 版本管理出现在课程开头：做软件工程项目先要管理 repository，它随时间演化。
    - 讲者举的需求例子：教务系统、直播管理系统、录播教室系统。
    - 同学常有做 side project 的冲动，这也构成一个需求。
    - **软件分析工具以软件为输入。**
        - 输入可以是 .git 仓库、.c 文件或 TypeScript 文件。
        - 输出对程序员有用的结果，理想情况是判断程序有没有 bug。
        - 编译器和 Linter 在 IDE 里画的红色波浪线就是例子。
        - 软件分析和普通需求不同：它的输入也是软件。
        - 软件分析工具有 recursive self improvement 的味道。
    - 开发者给自己装 VS Code 插件查更多问题，或可视化 unit test 结果。build 时自动跑 unit test，再点进失败的 test case。
    - 这些事在软件工程实践里天经地义。大家甚至没有感觉到。
    - **吐槽** 说这些工具对开发者太习以为常：「你们甚至都没有感觉到」
    - **吐槽** 讲完这些插件流程，说现在的同学：「当然好像现在agent的时代这些事情你们都不care了」
    - 经典软件工程时代，大家总想再造软件，改进开发、测试、调试和维护体验。
    - **吐槽** 说开发者每天都在和流程较劲：「我们作为开发者我们每天就是在这个流程上面不断的battle」
    - **编译器自举是工具改进工具的例子。**
        - 有些 C++ 编译器用 C++ 写，C 编译器用 C 写。
        - 讲者说编译器自举勉强也算 self improvement。
        - **玩笑** 说编译器自举：「这不就自己编译自己吗」
        - 起初只能用汇编写机器码，编译一个 C 子集，再用子集写更复杂的程序。今天 GCC 用 GCC 自己编译。
    - 总有不安分的开发者，把经验变成工具放进自己的流程。讲者说这很自然。
    - **玩笑** 说开发者里的不安分者：「总有一些不安分的码农会跳出来想诶我能不能improve一下」
    - IDE 的插件生态在增长，编程语言在进步，各种工具被集成进 IDE。
    - 开发者想变成超级开发者：每造一个工具，效率就提高一次。
    - 开发者的循环：造工具，学会工具，效率提高，更快造软件，再造工具，直到不能再提高。讲者说这图画得不准，但和 AI 想要的 self improvement 异曲同工。
    - **自嘲** 说自己画的循环图：「我觉得这图画的不是很准」
- **agent 能提取经验、自己造工具，重走开发者的路**
    agent 已到临界点，能理解自己哪里出问题。
    - 这是 RSI（递归自我改进），主角从开发者换成 AI agent 和模型自己。
    - AI 足够强，不仅能从需求产出实现，还能理解自己哪里出了问题。
    - 以前 agent 只完成任务：生成 three.js 3D 世界，做 3A 大作游戏，画「提壶骑自行车」（字幕原文，待确认）。
    - **agent 会像开发者一样，从问题里提取经验并造工具。**
        - 开发者的经验：不能随便用指针，malloc 和 free 容易搞坏，要按 SEI CERT C 的规则写。
        - agent 的例子：优化器在精度较低时每次指数级爆炸，agent 可能造工具避免。
    - 建议：做 self improvement 的同学，去软件工程的历史里找有趣的 insight。

> 原话：「我能不能improve一下，我把我的经验变成一个工具放到我的流程里」

## 2. 传统分析工具只能把程序当数学对象，按明确规则执行

<small>▶ [10:26](https://www.bilibili.com/video/BV1wysu6hEkz?t=626)–29:52　·　转向　·　话题：传统软件分析</small>

- **传统工具读不了 intent 和 spec，只跑人写的规则** 两者是非结构化的。计算机课教的数据结构和算法处理不了。
    - 大语言模型是自回归模型，能靠 next token 吐出任何东西，包括代码和图形。
    - 生成式 AI 之前，分析软件很难，需要人类的智慧。
    - 生成式 AI 之前，软件分析工具是程序，是一个算法。它处理树和图这类结构。
    - 树的节点上可以带权重，图的边上可以带标签。
    - 软件只是 implementation，背后有 intent 和 spec。intent 在人脑里，老板可能只给一句话。spec 用自然语言记录。
    - 这些课最多对它们做索引、分词、词频统计。信号太弱，几乎不能指导工具输出有用信息。
    - 人要先把想检查的事转成明确的规则（rule based），工具才能执行。通用的 Linter 框架也要人配置参数或写额外程序。
- **CodeQL 把代码当数据库，人用查询语言写规则** 它把源码编译成关系数据库。然后它用另一种查询语言查程序的性质。
    - 查询可以引用函数、表达式、声明、调用关系和控制流。
    - 类比 SQL 的 select，CodeQL 可以 select 语法树节点。例：select 一个 malloc，要求同一函数里能看到它的 free。
    - **玩笑** 讲者为说明规则能写什么，举了个极端的例子：「打个比方就极端一点，比如说我的每一个表达式里面都不能有括号」
    - **玩笑** 讲完这条规则，他又补了一句：「那可能对于你们的项目来说，可能是有意义的」
    - 这是前人聪明的发明。但这类工具只能处理语法或形式语义上的问题。
- **程序是数学对象，每条语句是状态到状态的函数** 形式语义用 Σ 表示状态。赋值 x = e 把 x 换成 e 的求值结果。
    - 「程序是数学对象」是计算机科学的根基，计算机世界完全由状态驱动（Everything is a state machine）。讲者展示「编程语言的形式语义」一图，说听众不必看懂。任何语句都是 f(state)，得到下一个 state。
    - **玩笑** 展示形式语义的图时，他说：「看起来很怪对吧，你们不需要真正去理解它」
    - 定义可以追溯到皮亚诺算术公理系统。每条语句的行为因此有数学上严格、计算机可处理的定义。
    - **玩笑** 讲到皮亚诺公理时，他对听众说：「离散数学又袭击你们了」
    - 两条语句复合，如先 x = 1 再 x = 2，也是数学对象，可以推导性质。程序本身只是字符串。
    - 软件自动化的终极梦想：给一段程序，工具就知道它对不对，是否符合 intent 和 spec。大语言模型之前，这几乎是唯一的工具，但它无法与人类世界对齐。上节课讲过，因为有语义，也许可以证明整个程序正确。
    - 虽然无法对齐人类世界，但在它上面长出了有趣的应用，比如软件测试。
- **覆盖率只增加正确性信心，靠插桩开销小** 编译器在每个基本块加计数器。使用者只加一个编译器选项。
    - 人肯定可以写 test。软件要自我改进，就希望自动从软件生成测试用例。
    - 人已经写了多个测试用例时，也希望能评估这些测试做得好不好。
    - 测试和覆盖率与软件好不好相关，但不直接回答它是否满足 spec 或 intent，只增加信心。讲者问能否自动生成足够的测试用例，直接达到 100% 覆盖率。代码里断言足够时，信心更高。
    - 要求单元测试 100% 覆盖率是有意义的经验：「未测代码永远是错的」。项目早期不会要求这么严。
    - **玩笑** 讲者回忆第一次质量保障课讲的测试笑话：「测试工程师走进一个酒吧，点了各种奇怪的东西，然后这个酒吧都还好的，但是当顾客来了以后他问有没有洗手间，然后酒吧就烧掉了」
    - **对 AI 许愿做覆盖率 CI，AI 会补假测试用例** 讲者建议听众这样试。
        - 许愿内容：做一个 CI，单元测试覆盖率到不了 100% 就拒绝。
        - AI 调用多个工程工具，在 .github 里写配置。
        - 运行后发现到不了 100%，AI 会自动加假测试用例。
    - **覆盖率的原理是记录每个基本块有没有执行**
        - 理论上，开发者可在 GDB 或其他调试器里单步执行，记下每步停在第几行。最后比对是否所有行都覆盖。这样效率低。
        - 编译器把程序编译成图，一段顺序指令是一个基本块。分支和循环让图出现跳转。
        - 编译器给 id 为 n 的块加 counter n++。现代 CPU 能并行执行指令，隐藏延迟，所以连续指令上只增加少量开销。
        - 代价只是给编译器加一个选项，让它插桩。
    - **吐槽** 覆盖率统计本身有人长期研究，今天甚至能用硬件统计。讲者拿 AI 新闻对比：「你们可能会看到我今天 AI 又又写算子了，今天又又什么 GPT6 又又去操纵一个小模型的权重了，但其实你看到在人类的世界里面这个智慧还是很多的」
- **抽象执行能推出所有执行共有的性质，但难用于复杂程序** 它把多条路径合并成抽象状态。它假装执行，顺序程序没有问题。
    - 命令行程序的初始状态由操作系统传入，包括 argc、argv 和环境。参数可以是零个、一个或多个，初始就有无穷多种可能。
    - 一次执行只选一条路径，可能 crash，也可能不 crash。想知道所有执行的性质，需要把状态合并。
    - **玩笑** 讲抽象状态时，他说它比较聪明：「你可以不停地假装执行它」
    - **抽象执行的做法和例子**
        - 在 x = input 处，状态从 S0 分叉成 x = 0、1、2。合并后的抽象状态说 x 在 0~9 之间。
        - 接着 y = x + 1。按加法的语义，推出 y 在 1~10 之间。
        - 另一例：读入数组后任何字节都可能，用 memset 清零后又确定值是零。
    - **循环和真实语言特性让分析变难**
        - 函数指针会跳到哪，分析器不确定。
        - C 和 C++ 可以写 inline assembly。汇编调用奇怪的机器指令，把数据交给操作系统，行为不确定。
        - 所以难以得到好的分析结果。实际用它分析类型是否匹配、变量是否初始化。
    - **未初始化变量检查是抽象执行的实际用途**
        - 例：int x; 某条路径上直接 return x。x 是没赋值的局部变量，值是 undefined，会返回一个奇怪的数字。
        - **吐槽** 讲者问现场听众写没写过这种初学者代码：「你们都会写这种程序吗，int x，在初学的时候」
        - 如果原来的内存碰巧是 0，调试时一直是 0，程序看起来是对的，这很危险。
        - 编译器知道存在一条从声明到 return 的数据流，可以拒绝编译或给 warning。
- **顺带：这节先回望传统分析工具的历史，再看 AI 时代**
    - 讲者说今天先讲一点历史，再讲生成式 AI 时代软件分析会变成什么样。
    - 从分析工具的构建过程，可以看到 AI 时代自动化软件工程会变成什么样。

> 原话：「软件分析工具就只能运行程序或者查看结果，它只能处理语法或者形式语义上面的一些问题。」

## 3. 通用分析器不存在，但只需对人类写的一小部分程序负责

<small>▶ [29:52](https://www.bilibili.com/video/BV1wysu6hEkz?t=1792)–38:15　·　但是　·　话题：Rice 定理与舍弃</small>

- **Rice 定理说通用分析器不存在，但讲者不喜欢它**。程序图灵完备，总能写出让验证器验证不了的程序。
    - 定理的内容：没有分析器能分析任何程序的某个性质。性质包括程序是否终止、坏函数是否可达。性质再简单也做不到。
    - **吐槽** 讲者评价这个定理：「虽然这个定理我并不是很喜欢它，因为它其实什么也没说」，「给人类判了一个死刑」
    - **反例程序把分析器逼到绝路。** 讲者用 Python 的无限 generator 构造。
        - while True 循环里 i 每次加 1，生成所有整数，假设内存无限。
        - 讲者说，谈 bug 大多是指指针会不会为空。这是简单的性质。
        - 遍历 a、b、c、n，若 n>2 且 aⁿ+bⁿ=cⁿ，程序终止，并在此处故意解引用空指针。
        - 分析器答不出这个程序会不会有 bug。
    - **玩笑** 背景：讲者说分析器若能答出这题：「如果它能，他就可以在数学界大杀四方，他就比这个OpenAI的模型还要厉害」
- **人类写的程序带着先验，范围远小于所有程序**。需求经过客户拉扯，已落在人类已知范围内。
    - 人类有权写出刁难验证器的程序。但 Rice 定理忽略了从 intent 到 spec 到实现的过程里有人类知识（见第 1 节）。
    - **玩笑** 讲者让步说人类可以故意刁难验证器：「你作为一个人类，你完全有权利去写出这样的程序，然后故意去刁难一个程序的验证器」
    - 开发者有经验，知道有些需求做不了。领导许愿做万能数学证明器、证完全世界的定理，开发者会答做不了。
    - **吐槽** 讲者模仿领导许愿的口气：「哎呀，你能不能给我做一个万能的数学证明器」
    - 人类世界已有一系列软件工程工具、编程方法和框架。
    - 需求是人类过程在信息系统里的投影。开发者知道可用数据库表示中间状态，迁移是支付、选课这类业务过程。
- **缺陷预测只看表面特征，也可能省下成本**。它不看软件其他部分，只给单个 class 打分。
    - 缺陷预测是软件工程里有趣的研究方向。讲者说听课同学可能还在做。
    - **打分方法只数表面特征。**
        - 数 class 里的 int 关键字、循环、大括号个数，和括号最大嵌套深度。
        - 得到 1000 到 2000 维的向量，用启发式或机器学习得到函数 f。
        - f 可给出「99.9% 认为这个代码有 bug」这类判断。
    - **玩笑** 背景：讲者说完靠数括号猜 bug，台下笑了：「你不要笑你不要笑」
    - 在老软件工程项目里预测潜在 bug 成立，能找到风险最大的模块，可能省成本。
- **分析工具只为一小部分程序负责，舍弃其余就有可用结果**。sound 分析器要对所有程序负责，目标软件只占一小部分。
    - 这类工具都建立在 trade off 上。Rice 定理要求放弃对所有程序都成立的分析。
    - 讲者说，目标软件无非是用数据库表示状态、用 Java 语言实现这类软件。
    - sound 分析器指绝对正确的分析器。人可以写出每次支付宝下单都去验证哥德巴赫猜想的程序，没人能阻止。
    - **吐槽** 讲者说这类程序没人拦得住：「你没有任何办法阻止我写出这样 make no sense 的程序」
    - 只对一小部分程序负责，甚至只对用了某种语法特性的更小部分负责，软件分析就成为可能。
    - 几十年来，分析只要舍弃一些程序，生成的 test case 和分析结果就有用。

> 原话：「只要能够不断地去舍弃一些东西，我就可以得到有用的结果」

    - 关键算法用形式化定理证明。
    - 软件从代码里提取分布式系统的协议，用模型检查器或定理证明器证明协议正确。协议修改后自动同步，重新证明。

## 6. 程序既是形式化的机器，也是人类活动留下的概率样本

<small>▶ [57:12](https://www.bilibili.com/video/BV1wysu6hEkz?t=3432)–63:57　·　但是　·　话题：程序是人的样本</small>

## 7. 终极目标是验证所有执行轨迹都与人类意图对齐

<small>▶ [63:57](https://www.bilibili.com/video/BV1wysu6hEkz?t=3837)–70:41　·　进一步　·　话题：非形式验证的目标</small>

- **模型时代仍需要软件，因为 CPU 执行省九个数量级的能耗**。有人试图用模型直接渲染世界，讲者估算差约九个数量级，这是钱和电。
    - **吐槽。**「这就是钱，这就是电，资源在世界上还是有限的」
    - 保存数据交给数据库，能耗低。让人还是 NAS 保存数据，一定选 NAS。人可先预处理，其余交给 NAS。
        - 讲者承认，人在某些场景上会更可靠。
    - 讲者假设 implementation 仍有用：程序写对就不出错，又快又准，不受心情、环境和提示词注入影响。
- **终极目标是验证所有轨迹对齐人类意图** informal verification 合上 intent、spec 和实现之间的 gap。
    - 以前的形式方法证明每个执行都没有空指针引用或整数溢出。整数溢出可能让飞控崩溃。
        - 这对写在飞行器上的代码非常重要。
        - 溢出后，控制会从一个极端跳到另一个极端。
    - 现在要证明 for all trace：每条 trace 都与 intent 和 spec 对齐，即在人类世界的意义上合法。
    - 这无法用 formal verification 做，因为它超出形式语义的范畴。
    - 有了足够强的模型，理论上已可做到：把每条 trace 交给 agent，跑无穷长的时间，得到验证结果。
- **覆盖率只是启发式规则，今天可能改让模型近似验证**。覆盖率能程序化度量，但没有依据说多少才够。
    - **讲者模仿 Jim Gray，预言软件工程将有同样的变化**
        - Jim Gray 2006 年谈存储，说磁带已死，RAM locality 为王（字幕不清，待确认）。
        - 有些东西从此不再需要，闪存 SSD 到处都是。这句预言在 GPU 时代更准。
            - 每部手机里都是闪存 SSD。到今天，关键变成了 GPU 显存。
    - 以前的工具靠类型、test case 和覆盖率近似正确。覆盖率 80%、90%，加模糊测试后 95%、99%，都是可度量的目标。
        - 覆盖率是启发式规则，不代表绝对正确。但它能写成程序来判定。
    - 没人能说 95% 够了，也不能说 99% 比 95% 好。覆盖的可能不是特别重要的代码。
        - 99% 覆盖到的可能是不重要的代码。特别重要的那段代码，这次反而没覆盖。
        - **吐槽。**「你永远不能说 95 就够了，99 就够了，而甚至你都不能说 99 就比 95 更好」
    - 工具由人写，复杂规则只能用数字代替。讲者认为模型一定能做 informal verification，大部分软件系统今天已可以，要做的是近似这个过程。

> 原话：「为了最大化资源的使用，能让 CPU 算的东西就应该让 CPU 算。」

## 8. 日志挖掘和状态可视化已是非形式验证的雏形

<small>▶ [70:41](https://www.bilibili.com/video/BV1wysu6hEkz?t=4241)–83:21　·　举例　·　话题：日志挖掘与可视化</small>

- **规则抓不到的错误，要靠日志里的异常来找。** 空指针和 data race 是绝对错误，其余错误无法靠单条检查发现。
    - 绝对错误有 2 个例子：命中空指针，并发程序里的 data race。
    - 单条检查（字幕原文：surgeon，待确认）发现不了的错误，讲者认为仍可能找到。
- **给每条语句打日志，日志串就是模型可验证的轨迹。** 开发者写语句时知道意图，日志把这个解释留下来。
    - **意图在代码写下的瞬间丢失。**
        - 程序员写函数调用时知道它可能调向哪里，但不会写注释。
        - 软件分析领域研究如何把调用目标找回来。构建调用图至今可发编程语言顶会论文，因为形式语义难、语言特性多。
    - **日志串起来，就是给模型做 informal verification 的输入。**
        - 开发者或 agent 写每条语句时，用日志解释它要做什么。
        - 运行一次，得到每条语句的解释。
        - 然后问 agent：这次执行是否偏离原始意图？常理上不该做的事是否都没做？按 spec 和 intent 这个输入应得到什么？软件是否做到？
    - 模型与人类对齐后，只看日志就能检查程序至少看起来是否正确。讲者称这是疯狂的想法。
- **2009 年的论文已用日志检测异常。** 论文做日志解析、特征提取和异常检测，实验限定在分布式系统。
    - 论文是 Detecting Large-Scale System Problems by Mining Console Logs（SOSP 2009）。
    - 讲者说这篇论文是 informal verification 框架的一个投射。
    - **与多数日志顺序不同的那一条，会被高度怀疑。**
        - 收集 1000 万条日志，都含 ABC 顺序，唯独 1 条是 CBA。
        - 系统基本正确时，这 1 条很可能有问题。
    - **游戏穿模的例子说明：偏离常态的执行是 outlier。**
        - 玩家每次玩游戏都正常，某次穿模掉到地下，立刻觉得不对。
        - 玩家能看出不对，是因为人已和物理世界对齐。
        - 记录 CS:GO 中人物坐标，可提取位移量。正常执行的位移有界，不出地图。
        - 掉向无限远的那次执行，是明显的 outlier。
        - 方法还能指出执行从哪一点开始不正常，开发者再回去诊断 bug。
    - 2009 年有机器学习，没有能对齐人类意图的 LLM。方法学成立，是 informal verification 的雏形。
    - 后来有人用 AI 挖日志，还能把日志对应回程序中的具体位置。
- **DDD 把状态投射成人可读的图，思路也适用于模型。** DDD 帮人看懂数据结构，大模型时代把状态压缩到足够小。
    - **自嘲** 讲到这里接不上下一个工具，向听众承认没准备好：「我觉得逻辑断了」「我在准备的时候没有完全准备好啊」
    - **DDD 是调试工具，把数据结构画成图。**
        - DDD 是 GDB 的图形前端，讲者认为是 Andreas Zeller 的成名作（字幕原文：ANDERSELLER，待确认）。
        - 已知软件有问题，或想弄清软件行为时，用它把数据结构可视化。
        - 它提取软件状态，和前面讲的测试、验证不同，是另一种对齐工作。
        - 支持多种 layout，当时引起轰动。调试平衡树和课堂展示时可用。
        - **吐槽** 讲者点评幻灯片上的截图：「这个图没有任何实质性的意义，但是他还是画了一个，看起来很不错的图」
    - **AVL 树调试的例子说明：程序错但看起来对，是典型的对齐问题。**
        - 数据结构课要实现 AVL 树或红黑树。
        - **吐槽** 讲者形容这个作业：「那就是痛苦的，绝对的痛苦的折磨」
        - 理想要求：每条执行 trace 的每个中间状态都是合法 AVL 树，指针指向合法。
        - 这些性质难证明，程序没 crash 时连看出来都难。
        - 常见办法：构造完后遍历一次，应从小到大打印递增序列。结果要么 crash，要么序列不递增。
        - **自嘲** 讲者说不清该用哪种遍历：「我现在不记得那个 term 了，sorry」
        - 调试时不断加 printf，输出越来越乱。
        - **吐槽** 讲者说输出越乱人越烦：「你越不可读你就越心烦气躁」
        - **玩笑** 讲者问现在的学生是否让 AI 写：「你们现在是不是用 AI 魔法编程了？说『给我实现一个 AVL 树』，然后他就自动地正确了」
    - **投射的目标是人可读，模型可能也更可读。**
        - 把程序所有可能的状态，投射成另一种形式。
        - 人读图有限：几十个节点就不可读，每个节点里建议只有 3 到 5 项。
        - 东西特别大时，人会觉得它与自己无关。
        - 大模型时代做了同样的投射：把 Linux 内核的状态压缩到足够小，对人和机器都有用。
        - informal verification 框架下，可把每个状态投射成可检查、和机器相关的形式。

> 原话：「我不需要程序了，我只需要程序所有的输出日志，我就可以检查这个程序至少看起来是不是正确。」

## 9. 文档应从代码导出，模型学会重做需求后传统软工终结

<small>▶ [83:21](https://www.bilibili.com/video/BV1wysu6hEkz?t=5001)–91:37　·　转向　·　话题：No doc 与软工终结</small>

- **文档能从代码导出，就不该手写进仓库** 讲者主张 No doc 模式：用 skill 生成文档，像编译出 a.out 一样。
    - 传统软件工程认为文档很重要，因为文档记录设计和想法。
    - 讲者说 agent 时代很多这类假设变了。
    - **玩笑** 讲者对着现场的软件学院同学说：「我知道这边有软件学院的同学，大家都说文档很重要」。
    - No doc 不是完全不写文档。能从代码直接导出的文档，就不手写。
    - **玩笑** 讲者形容生成文档的方式：「把它像编译出来那种 a.out 一样」。
    - skill 随 CI/CD 流程生成文档，文档永远不提交进仓库。
    - skill 控制文档粒度，粒度能像 checker 一样与代码对齐。读者包括 3 类：人、新手、大模型。
    - 一行代码对应一段文档解释。程序执行时，这段解释被拼进日志。日志送给大模型，检查是否与 intent 一致。
    - 同一份文档在不同场景下功能不同。
    - 只有设计决策值得手写：为什么选这个架构，为什么排除其他设计。这些道理要用文章表达。
- **语义正确这个开放问题，今天看起来已基本解决。** 大模型在语料上训练，agent 又吸收了软件工程工具几十年的研究。
    - 讲者 2024 年的一张截图列出软件制品的 3 层要求：语法正确，阅读自然，语义正确。
    - 符号主义时代只能做到语法正确。
    - 阅读自然指软件不只给机器看，也要给人看。
    - 当时已有 GPT-4，用 beam search 生成，如 SWE-bench 论文所示，模型能力惨不忍睹。语义正确是开放问题。
    - **吐槽** 讲者评价当时的模型：「大家模型的能力惨不忍睹」。
    - 大模型训练越多，越接近人类在乎的软件所需的合理语法。不能保证 100% 正确。
- **coding agent 先猜一个点，再靠工具反馈修正** 许愿编程今天能用，但没有从根本上解决 intent 到 spec 到实现的 gap。
    - agent 不能保证猜对。但它能越来越好地采样一个起点。
    - 采样之后，agent 利用现有的软件工程工具。
    - agent 不确定时先猜，再跑单元测试、编译、link，甚至截图查看。
    - 全部通过，agent 认为猜对。工具拒绝时，agent 读懂反馈，再猜，从 initial guess 走向与 intent 对齐。
    - **玩笑** 讲者形容 agent 反复试错的过程：「不断的这个猜猜猜猜猜」。
    - 初始采样点很大程度决定软件质量，讲者称第一节课讲过。
    - 架构一开始做错，需求增加后无以为继，软件后期失败。
- **模型学会重做需求后，传统软件工程走向终结，可能不超过 10 年。** 今天的模型不把重新理解软件当作 first principle。
    - 讲者相信模型的采样方式会越来越好。
    - 模型也可能自己进入对软件的理解。
    - 今天的模型只会不停调用工具修代码。
    - **吐槽** 讲者形容今天的模型：「他现在就不停的调用工具修修修修修往后修然后改代码」。
    - 理论上模型应能换一种 intent 理解：重构，重做需求，重写 spec。
    - 这些操作的反馈信号很弱，代价很大。模型一旦学会，就是从 first principle 构造软件。
    - 讲者从软件分析和质量保障看这个未来，因为质量保障最终回到需求。
- **顺带：工具世界和软件分析领域都会变**
    - 讲者认为整个软件工程的工具世界都会发生重大变化。
    - 他认为软件分析领域也会发生很大变化。

> 原话：「他在不知道的情况下先猜一个点。」
