## 1. 需求工程直面本质复杂性，架构负责分解它并收缩可能性

<small>▶ [00:00](https://www.bilibili.com/video/BV1JGap6LE74?t=0)–14:36　·　开场　·　话题：需求面对本质复杂性</small>

- **需求工程直面本质复杂性，不假装软件简单** 选课要同时考虑容量、先修、时间冲突和教室。这些来自物理世界，无法消除。
    - 软件复杂到一定程度，就会面对 intent、specification、implementation 之间的 gap。上节课从瀑布模型讲起，用数据依赖理解 gap，用 MVP 控制复杂性。
    - 讲者引 Brooks：软件工程的本质是驾驭复杂性。
    - 讲者说，看到需求规格说明书，就知道现实中的软件非常复杂。
    - Essential Complexity 来自问题本身。教务系统要排课、排教室，老师和同学都能借教室，物理世界在信息世界里的投影同样复杂。
    - 无法消除的复杂性，要靠软件架构来更好地管理。
    - 看需求的层面不同，结论不同。上节课用浏览器操作逆向出教师相关的需求规格说明书，符合软件工程实践。架构师则要站在需求之外思考。
    - 需求工程承认系统复杂，并不断与客户沟通，想清楚到底要什么。方法可以是让 GPT 写需求规格说明书，也可以是用 Grill Me skill。
- **技术选型带来 Accidental Complexity，做决定那一刻起就背上技术债** 文件系统与数据库各有优点和代价。
    - 技术债从第一个设计决定开始，之后一直要背。架构从 10 行代码到 1000 万行系统无处不在。开发者可以交付满足 100% 需求的产品，但维护可能陷入长期泥潭。
    - 上节课的图说明：从什么都没有开始，就要做决定。一旦决定，就会影响未来走向。所以软件架构设计通常有很大改进空间。
    - **文件系统管理方便，但性能和并发控制较弱。**
        - 管理方便，想 hack 也容易。
        - 性能可能远不如数据库，并发控制有问题。
        - 不支持原子性事务（要么全做，要么全不做）。读写多个数据时没有「上一把锁、stop the world」的保证。
        - 有人想在操作系统里实现文件系统级的 transaction，讲者称之为「比较疯狂的人」。
    - **数据库提供事务，但调试要多经过一个中间层。**
        - 看数据库时不能直接用 UNIX 工具组合。
        - 理论上可以把 query 与其他工具组合，但会多一个转换层。
    - Essential Complexity 与 Accidental Complexity 要分开。长期学习好架构，能看到什么时候用什么架构减少 Accidental Complexity，好系统又怎样应对 Essential Complexity。
- **登录一个功能就牵出一串需求细节，需求要深度与广度并用** 直接让 GPT 做登录，它会替你猜一个。每个猜测又连着下一个决定。
    - 讲者推荐试用 Grill Me skill。以购物车为例，它会把细节问一遍，比如认证接第三方微信公众号，还是自建 login page。
    - **GPT 猜的登录方案，一步步把开发者带进泥潭。**
        - GPT 先猜要注册用户，要用户名和密码，首次注册还要密码确认。
        - 接着要不要做忘记密码。没有这个功能，用户一定会忘密码，数据留在里面又无法访问，体验糟糕。
        - 做了就要发短信或邮件，邮件又要选发送方式。
    - 微信或支付宝登录更方便，很多网站支持，但要交钱，对个人开发者不友好。可能需要公司实体，因为个人与公司承担责任的能力不同。
    - **玩笑** 讲到开发者不用第三方登录、坚持自己管用户数据的动机。原话是：「你可能就是想要偷这个用户的密码，去构建自己的密码库。当然这个事情肯定是不合规的啊。」讲者补充，体量足够小时可能有人想这么做。
    - **吐槽** 讲者模仿开发者的想法：「因为所有人都有一个用户名密码登录，所以我的软件也理所应当做一个用户名密码登录」。讲者说这样做设计，就已经「进入了一个泥潭」。
    - **吐槽** 讲者感叹登录只是一件事：「这仅仅是登录这一件事儿，你就有无穷的细节」。进去以后还有各种其他细节。
    - **吐槽** 讲到忘记密码功能：「如果你没有忘记密码的功能，用户一定会忘掉密码的」。
    - **深度优先和广度优先不矛盾。**
        - 深度优先做 MVP，能快速知道最重要的功能点满足了多少，需求要不要做第一轮、第二轮重做。
        - 广度优先要面对多个决策，包括登录框选哪种实现、界面怎么布局、首页怎么展现。这些都在需求 space 里。
        - 讲者认为两者要平衡，只能动手做。
    - 设计哲学会影响需求。如果设计宗旨是简化复杂性，实现麻烦的东西就交给第三方管理。
- **架构有两个作用：分解本质复杂性，收缩实现的可能性** 数据库把存储隔离在接口后面。需求收缩 intent，架构收缩 spec 与 implementation。
    - 分解的做法是把无法避免的复杂性隔离在不同模块里，再把模块之间的接口切分好。
    - **数据库是好的架构设计，它给出可靠的 contract。**
        - 数据放进数据库后，开发者不再关心数据怎么存储。
        - 云厂商的数据库一般承诺备份，数据不会丢。出问题最多降低 availability，备份很快顶上。
        - 开发者不用担心数据可靠性和访问原子性，可以专注业务需求。
        - 数据库是通用 system，部分逻辑也可以下放给它。同样，自己的系统里也可以设计不同模块（MVC 见第 5 节）。
    - **学校的信息系统说明模块之间要打通，但财务系统还没有打通。**
        - 学校希望信息只填一次，统一身份认证花了很长时间才完成打通。
        - 学生不从学校领工资，也不管理项目，所以多半没有用过财务系统。
        - 财务系统有大量领域知识，要把账做平、接受审计。研究生给老师报销单据时会用到它。
        - 它与现有系统没有完全打通，数据共享和通知推送还不能用。讲者希望需求和架构能做到这点。
    - **需求收缩 intent 的不确定性，架构收缩 spec 与 implementation 的可能性。**
        - 从 intent 到 spec 再到 implementation 会漂移。
        - 每个 intent 有多种 specification，每个 specification 又有多种 implementation。
        - 一旦确定下来，就会背上一定程度的技术债。
    - **自嘲** 讲完这段回顾，讲者担心听众没听懂：「还是觉得哦，不知道我说了什么，对吧」。
- **讲者顺带讲了 3 件和主线无关的事** 包括第一个实验的做法、代码即需求、需求工程没有捷径。
    - 下一个实验这两天会放出。做第一个实验时，可以像上课一样把需求直接复制给 AI，再不停聊天修改。但第一反应是「这样设计数据库可以吗」时，应回头多想，可能有更好的方案。
    - 理论上代码本身就是需求。把实际项目的文档全部删除，让 AI 运行并读代码，可以还原出需求点。但还原结果会很长，也没有自顶向下的设计理由。
    - 需求工程没有特别的办法，只能多看多做。可以想象自己来做教务系统会怎么做，一个系统为什么这样设计，换一个设计会变好还是变坏。

> 原话：「代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的规律。」

## 2. 人脑容量有限，所以必须靠抽象和分层来分解复杂性

<small>▶ [14:36](https://www.bilibili.com/video/BV1JGap6LE74?t=876)–34:09　·　转向　·　话题：用 AI 读经典论文</small>

- **AI 让读经典原著变得容易，应当直接读第一手原文。** 以前引用的书挖出来读太费时间，现在可以直接读原文，并按自己的方式处理。
    - **讲者用 Dijkstra 的《结构化程序设计》演示怎么读原著。**
        - 他打开 PDF 原文。这是一本老书，书里都是小程序，还有流程图，不是现代意义的软件工程书。
        - 书讲顺序、选择、循环三种结构。论点是不需要 go to，这三种结构能表示任何程序逻辑。
        - 当时的人还在争论「Go to is harmful」，而且只是在小函数的层面争论。
        - 书里挑出一个看起来简单的示例程序。这个程序已经开始出现一些结构。讲者说这本书写得很好。
        - 讲者不想用传统方式读，先让 AI 总结全书。
        - **玩笑** 讲者面对这本好书，即兴说「那我们当然不应该用这种传统的方式来读它对吧」。
    - 教科书脚注常引用这本书。讲者读书时基本选择忽略，因为把原书挖出来读太浪费时间。现在可以直接读最原始的第一手信息，按自己想要的方式处理。
        - 经典的编程语言书和软件设计书，常常引用这本书，因为它太有名。
        - **自嘲** 讲者读书时脑子里的独白：「看一下哦，Dijkstra好像写过这本书，忽略它」，因为「如果我要把这本书挖出来然后再去读它，这件事情对我来说会浪费太多的时间」。
    - **AI 能批量找出经典文献，质量接近讲者自己的推荐。**
        - 讲者让每个博士生读经典文献。他做操作系统、PL（字幕原文：pr，待确认）和软件工程。他认为这三个领域 1980–2010 年是黄金时代，之后越做越窄。
        - 那段时间想法天马行空，讲的是系统还不存在时怎么把它构建出来。
        - 讲者让 Grok bot（字幕：grog bot，Cursor 送了额度，后台有云电脑）收集这段时间值得读的 systems 文献。它每个领域找了两三百篇，共约 1000 篇。
        - 讲者读过其中大部分，逐条核对，认为列表质量高，很多文章他也会推荐。
        - **吐槽** 讲者看完核对结果，感叹「然后这就是件非常恐怖的事情」。
    - 读 paper 的方法是从已知知识向外扩张。先弄清论文解决什么问题、用了什么不知道的手段、得到什么结论，再和已有知识连成网络。
    - 讲者开车时打开 GPT 或 Claude 聊 paper。他的 paper 被索引，AI 能看到全文，所以他可以边开车边问今天这篇怎么读。
- **人脑容量有限，所以必须用抽象和分层来分解复杂性。** Dijkstra 在原文承认人脑小，主张尊重这个限制，而不是忽略它。
    - 需求本身复杂（见第 1 节），需要架构的原因是人的能力有限。Dijkstra 原文：「I have a very small head and had better learn to live with it, and to respect my limitations and give them full credit, rather than try to ignore them」。
    - **玩笑** 讲者解释人的能力有限，把人比作模型：「我们是一个参数有限的大模型对吧，我们还是承认我们自己是大模型」。
    - 结构化程序设计看起来过时，因为今天流行面向对象和各种框架。但这些东西过去已经被想过一遍。办法是把人不能一次理解的东西，变成人可以逐层理解的东西。
    - **吐槽** 讲者说用前端的人可能选 React 或 Vue，两派社区至今圣战，背景是类比编辑器之争：「就像以前这个 Vim 和 Emacs 的开发者还在圣战，虽然他们两个都越来越像了」。
    - **人脑能做的只有枚举、归纳、抽象三件事。**
        - 这是讲者最喜欢的观点，出自 Part one 的 mental aids（字幕：amental aids）。
        - 书里的案例今天看都是小程序。
    - 书里把做软件系统比作做项链，把一颗颗珍珠串起来。这个比喻是在分解复杂性：把人不能整体理解的东西，变成可以逐个理解的东西。
    - 讲者认为，今天好的软件系统做的事，这本书里已经讲过。
- **抽象把复杂性隔离在概念内部，协程是为搭概念层次而生的** 讲者让 AI 带读 Part three，回到当时的动机。
    - 讲者没仔细读过 Part three，说它面向本科生。他让 AI 翻译并去掉他认为不必要的部分。
    - **自嘲** 讲者开始即兴试读时说「好，那我们就试一试，因为我也没有仔细读过」。
    - 书的做法是把数据加操作打包成一个概念，再用前缀机制把概念一层层搭起来。书里讲了 class 和 object，时间是 1972 年。
    - 做模块不管叫 class 还是 method，都要把内部复杂性与系统其他部分隔开。讲者举了选课、一门课、教室管理，它们之间要适当分类并关联。
    - 书里的观察：学生程序写得烂，是因为一次要同时放进脑子里的东西太多。
    - **协程是把一项工作拆成几条各自推进的线，讲者用人和共享空间来比方。**
        - 讲者说，书里考虑的是怎么构造各种概念层次，协程就是为此而发明的。
        - 协程和线程相似。线程是人，shared memory 是物理空间。
        - 每个人有自己的 memory，知道做到哪一步、今天和明天做什么。
        - 共享空间里有要合作完成的事，人与人的通信成为协议。
        - 一个工作可以拆成 3 条线，各自向前推进，通过数据结构共享，互相通信完成整个任务。
        - 书里还举了博弈下棋和编译器的例子。
        - 书里有一个概念层次的金字塔。
    - 学生可能在操作系统课第一次听说协程。今天它主要是为性能实现的轻量级线程，例如 Go 的协程模型，切换和 bookkeeping 开销小，用起来像线程。
        - **吐槽** 讲者先说假设大家前面的东西都已知道，又戳破说「但其实你们不知道对吧」。
    - 书写成时几乎没有现成的线程模型。回到那个时间点，可以看出协程是在应对软件世界的复杂性。
- **动态规划难调试，是因为写代码时扔掉了抽象层。** 把状态的概念放回代码，就能可视化，也能逐层调试。
    - **模拟题能分层，动态规划不能。**
        - OJ 题里最难调的可能不是模拟题，而是带数学性质的题，例如动态规划。
        - 第一次样例和数据都对还好。一两百行的动态规划出错，根本不知道从哪里调。
        - 模拟题可以拆成几个大部分，封装成 class，单独测试和调试，中间状态能对应有物理含义的状态。
        - 动态规划的中间状态是纯数学表示。
        - **吐槽** 讲者说调这种动态规划：「而如果你是调一个像动态规划这种两三百行的动态规划，好，那就是灾难」。
    - 书上和学生都写 dp[i][j][k] 加三层 for。一处弄错，整个都错。程序 crash 反而好找，因为知道越界。不 crash 就算出一个错值，比如转移弄错。
    - **抽象层存在，只是写代码时被扔掉了。**
        - 动态规划背后是一个优化问题，有图结构。
        - 它在状态空间上做，有无后效性，本质是有向无环图。
        - 讲者思考时工作在这一层，写代码时却把它丢掉。
    - **做法是把状态概念放回代码。**
        - 先弄清 dp[i][j][k] 代表什么，再可视化，打印关联的状态和迁移。
        - 实现 get(i,j,k)，返回该状态所有可能的迁移。
        - 这样还不够好，就用 state 替代，一层层做抽象，程序就可以调试。
        - 调通后，改写成等价的更高效形式。
    - 更大的例子是模拟并行。可以用状态机直接模拟，也可以做协程抽象。书里有 hold、wait、activate、simulate（字幕原文：hold weightactivate和simulate，待确认）这类抽象。有合适的抽象，模拟时间和直接上手写模拟很不一样。
- **没读懂就继续追问 AI，语音模式和联网调研能把经典连到现代例子。** 讲者自己有概念所以听得懂，没有概念的人可以一直追问。
    - GPT 的实时语音模型从今年开始，可以在后台调用更强的思考模型，同时保持对话。
    - 做法是把论文丢进去。简单问题它立即回答，复杂问题交给后台模型。
    - 讲者让它给一个符合现代软件前端的比方，它找到了 React Fiber 架构。效果取决于提示词和想象力，讲者事先不知道它会给什么。
    - **自嘲** 讲者说不知道 AI 会给什么例子：「我不知道GPT可能给什么，我完全完全不知道」。

## 4. Unix、关系数据库、Internet 靠简单统一的接口长出生态

<small>▶ [49:42](https://www.bilibili.com/video/BV1JGap6LE74?t=2982)–63:50　·　举例　·　话题：Unix、数据库与互联网</small>

- **Unix 用文本接口加管道，让小工具可以无限组合。** 文本统一了人和程序的接口，管道把各个只做好一件事的工具串起来。
    - Unix 三原则的前两条是 Do one thing and do well，以及程序之间能协同工作。第三条是程序处理文本流。文本统一了人与程序、程序与程序的接口。二进制字节流对人不友好。
    - **人需要立即的东西，不适应每件事都加一层间接。**
        - 数据库好用，但每次查询都要写一条 SQL query。讲者觉得用数据库像隔了一层纱。
        - **吐槽** 「你们在用数据库的时候你们都知道数据库好，但是用数据库的时候你总是觉得隔了一层纱」
        - **玩笑** 讲者用模型和人做对比：「当然模型可以，比如说你可以让模型每说一句话以后都说一个喵，他能遵循指令。但如果是人来遵循这个指令的时候，人就会觉得非常痛苦了」
    - **这个想法 1964 年就有了。** 讲者让 AI 收集资料并总结原文，得到 4 个要点。
        - 第一个要点是「像接花园水管一样连接程序」。管道在 1983 年（讲者说「应该是」）引入 Unix。
        - 原文还有一些操作系统设计想法，包括动态链接、库索引。讲者说它们对今天的系统设计影响深远。
    - **Unix 靠统一的约定让人和工具都好理解。** 讲者提到有人写过 Unix-Haters 吐槽 Unix 设计不好。但统一标准仍然成立。
        - 所有命令行工具遵循大致一样的命令行参数，人容易理解。
        - 输出格式尽量保持一致。sed、awk 这类工具奠定了基础，其他程序的输出开始向它们靠拢。
        - 退出状态（Exit status）让程序出问题时，能及时告诉另一个程序。
    - **工具的组合性体现在可以给任何编辑器配一个自己的打开文件菜单。**
        - 软件要打开文件，要么自己实现菜单，要么用操作系统的菜单。两者都不满意时没有办法。
        - 讲者说学校买的 Premiere（pr）自带菜单，带预览。符合习惯时好用，不符合时难用。操作系统的菜单也不那么好用。
        - **吐槽** 「你说它好用吧，它好用的时候挺好用，说难用吧，它不符合你使用习惯的时候很难用」
        - Unix 的答案不同。无论用 vim、Emacs 还是 nano，都可以配一个自己的菜单。
        - 讲者现场演示：配好菜单后，用 nano 打开第一课的 index。他说这是偶然，系统设计者可能没想到这么多。
    - **文本接口、编程语言、管道一脉相承，合起来给出无限组合和复用的空间。** 讲者上操作系统课时对学生说，每个命令都是小程序，负责组合各种做好一件事的工具。
        - 今天很难在一个 GUI 程序里得到这样的组合性。讲者认为可以创造这样突破性的东西，可以畅想。
- **关系数据库用二维表和 SQL 隔离复杂性，同时留出扩展空间。** 数据怎么存、是否可靠，全部交给底层数据库系统。
    - E.F. Codd 1970 年的论文提出关系模型。它要保护用户，使其不受数据库增长和流量变化引起的数据表示变化干扰。
    - **用文件系统管数据，得到的是原始接口，好坏并存。**
        - 好处是 Unix 世界里的工具可以复用。
        - 坏处是太自由，没有统一的管理。
    - 讲者做过一段时间程序合成。只要做和人类世界相关的程序合成，就绕不开 Codd 的论文。
    - 关系模型的做法：世界里的数据用二维表表示。然后用表与表之间的操作（如 join）处理任何需要的数据管理。
    - **SQL 是又一个可以生长的接口，带有语言的性质。** bash 是语言，SQL 也是语言。接口足够灵活，就会像编程语言。
    - **有了 SQL、查询优化器和事务，数据库在任何时刻都是当前世界的状态。**
        - 一次事务把状态带到下一个状态。
        - 视图是用一条查询创建的、对当前世界的理解。
        - 数据库的实现给出近乎无限的 scale 能力。今天仍可以处理海量数据。
    - **数据库带起了一波信息化浪潮。** 图书馆的书、学籍管理、财务信息、在线商城的订单，都可以用关系数据库表示。只要理清实体之间的逻辑关系，就能实现信息系统。
    - 数据库只规定世界里有表和 schema。schema 的内容由开发者按应用定制。讲者称它是隔离了复杂性的顶级抽象，扩展能力无穷。
- **Internet 只负责连通，让上层应用自己长出来。** 架构不预设上面跑什么，所以应用可以爆发，协议也可以逐层更换。
    - 它解决的问题：讲者一边上课一边推流，手机同时能看推流结果和弹幕。Internet 把整个世界连起来。
    - **TCP 解决可靠传输，对上层应用不做预设。** 数据流可以稳定可靠地从一个点送到另一个点。上面跑什么应用，能支持什么就支持什么。
    - **RFC 1958 讲 Internet 的架构原则，核心是变化。** 1996 年 6 月的这份文档说，唯一应该永存的原则就是变化本身。
    - **网络只做 connectivity 一件事。** 其余交给别人。
        - 网络只管高效传 datagram。
        - 拥塞控制和连接中断的管理，必须包含在架构里。
        - 讲者说数据中心现在仍有在用 TCP/IP。在 GPU 之间传数据，可能需要更好的协议。
    - **协议在共同规则之上逐层更换，HTTPS 成了 TCP/IP 的上一层。**
        - 讲者读书时没有全网 HTTPS，直接用 telnet 连南京大学小百合 BBS 灌水。今天 telnet 安全性不够，换成了 SSH。
        - **玩笑** 讲者回忆当年没有全网 HTTPS：「我们都是在 HTTP 上裸奔的」
        - FTP 本身支持断点续传，所以当年在校内网下电影很顺利。今天 FTP 缺安全性，即使有安全扩展也不够。
        - 当年网络不稳定，下到一半常要停下来，下次要能从断点继续。
        - **自嘲** 「我们 FTP 一下电影，在校内里面下电影，下得非常开心」
        - 今天做软件变容易了，这些功能都实现在 HTTPS 接口里。访问微服务，以及出本地后访问任何服务商，都走 HTTPS。
        - RESTful API 是建议的规范，可以不严格遵循。
    - 讲者的比喻：这像建设了一个城市的交通网络，建筑在上面一直演进。（整理者补充：交通网络对应 TCP/IP 与 HTTPS 的共同规则）
- **这三个系统是通用抽象层，学它们是为了理解好设计怎样应对变化。** 好设计能支撑生态，讲者回到软件架构的主题。
    - 具体技术要学。讲者说有一天真要写 SQL 时，得有概念，才能手写出来。
    - **自嘲** 「有一天你脱网的时候，你真的需要一个 SQL 的时候，你还得自己手写一下，你得有概念」
    - 更重要的是看这些保存下来的经典为什么成为经典。讲者说这里讲的偏软件架构，可以体会它们如何应对变化。
    - 讲者说这是生成式软件工程课，仍要讲软件架构，并从这些系统层的例子切入。

> 原话：「你们在用 UNIX 的那一刻起，你每个人都是程序员，因为你做的每一个命令它都是一个小程序」

## 5. 需求点映射成数据库事务，视图是状态的纯函数投射

<small>▶ [63:50](https://www.bilibili.com/video/BV1JGap6LE74?t=3830)–72:47　·　转向　·　话题：业务系统与 MVC</small>

- **每个需求点对应一个数据库事务，状态变化由事务驱动。** 数据库把物理世界的过程投影成表格，开发者据此把需求拆成事务。
    - 地基打好后业务系统才能上线。操作系统、数据库和 Internet 是通用抽象层（见第 4 节），教务系统、图书管理系统建在它上面。
    - 1998 或 2000 年的开发者，最直接的做法是把每个页面或功能做成一个 CRUD 事务。
    - 软件工程书把需求拆成需求点，每个需求点变成一个数据库事务。讲者说，这样就能理解那些书为什么这样写。
    - 讲者评价，需求点与事务一一对应时，这个架构非常好。
    - 数据库视图提供当前状态的各种切片。例如用一条 select 查出哪些学生选了讲者的生成式软件工程课，显示在某个位置。
- **嵌入服务端脚本的模板，让数据库应用前所未有地容易开发。** 一个页面只需一个事务取出数据，放进 list 或 map，再投射成 HTML。
    - **模板语言比拼字符串更好维护，自己写 AI 应用的 prompt 也适用。**
        - 拼法是 prompt = A + B + C + D，越拼越长，难维护。
        - 模板里写「you are …」，留一个 instructions 变量。渲染时传入变量，字符串直接贴进去。
        - 模板语言可扩展。例如把今天的日期传进模板。讲者以 Python 环境里的 Jinja（字幕原文：gr to、金家兔，待确认）为例。
    - 在页面里嵌服务端脚本，最早在 PHP、ASP 时代探索。Java 早期可把 Java 代码和 HTML 嵌在一起，甚至一起循环。Jinja 也有这个功能。
    - 1998 年 Java 如日中天，OOPSLA 的 keynote 讲了 Java 语言设计（见第 3 节）。讲者说，在 HTML 里写代码不是新想法。
    - HTML 把 DOM 树和样式分开。开发者给不同元素不同 CSS 样式，可排出几乎任何界面，也能放按钮和代码生成的动态内容。
    - 操作系统、CRUD 数据库、Internet 和这种模板一起带来一波应用浪潮，图书管理系统在那时集中爆发。
- **MVC 把应用三分，视图只读、操作才能改状态。** 每个页面对应一个 SQL 事务，这个做法导出了 MVC。讲者带着读了一篇 1979 年的两页纸文章。
    - Model 是当前世界知识的唯一来源，例如谁选了什么课、有哪些订单。
    - View 是 Model 的可视化表示，是 Model 的纯函数。所以 View 不应有任何改变状态的能力。
    - Controller 是用户与系统之间的连接。它接收用户输入，翻译成命令和数据。要改变世界，就需要 Controller。
    - 需求中能修改的点翻译成事务，看到的东西是状态的投射。讲者称这是非常干净的架构，自然成为信息系统的标准架构。
    - 教务系统的对应关系：Model 是课程和选课记录，View 是页面，Controller 是按钮和输入框，点击后进入数据库事务。

## 6. 界面自身的状态也要建模，界面是状态的纯函数

<small>▶ [72:47](https://www.bilibili.com/video/BV1JGap6LE74?t=4367)–79:07　·　进一步　·　话题：MVVM 与 React</small>

- **界面自身的状态不属于数据库，要单独建成模型。** 菜单展开、搜索框、hover 只改界面、不改数据，所以不该走数据库事务。
    - 单页面每次点击都整页刷新时，只有数据库状态的 MVC 成立。
    - 现在界面上有些元素的状态不在 model 里，例如展开的菜单、搜索框、鼠标移过时亮起的元素。
    - 列表已在视图里时，只需要一个过滤器。过滤不改 model 状态，也不再查 model，但视图状态仍要改。
    - 学生列表的搜索框，可以按名字或学号查找同学。
    - 教务系统的搜索流程是：先输入，点搜索，再返回结果。
        - **吐槽** 讲到教务系统的搜索设计：「教务系统讨厌的地方就是搜索被做成了一个某种 database transaction」
    - MVVM 的由来：这些状态需要模型，但不该存进数据库，所以把视图状态也当成一个 model。讲者称它是最近比较时髦的概念。
- **React 把界面定义成状态的纯函数，再用虚拟 DOM 解决性能。** 纯函数写法直观，但状态一变就要重算整棵 DOM。
    - 讲者偏向 React：view 对开发者直观，写过前端就能立即上手，而且 React 更纯粹。
        - **玩笑** 表态偏好 React 之前：「我不引起圣战哈」
    - 视图是整个数据库的投射，视图上还有自己的状态，例如是否 hover、query string。query string 与文本框绑定。
    - 每个元素都可能有自己的 hover 状态。
    - 设想是写一个纯函数：DOM tree 等于函数（界面上的所有状态）。纯函数没有副作用。
    - 问题是性能。页面可能有几万个元素，输入一个字符就要重算全部状态。
    - React 用 virtual DOM 把这份复杂性藏起来。开发者只声明状态是什么、怎么变，框架负责更新。
- **Vue 用依赖关系图保持同步，思路和 React 接近** 两者都由状态决定界面，只是更新模型稍有不同。
    - Vue 在开发者写 input 等于什么的时候建立依赖关系，并保持同步。
    - 讲者认为两者差不多，新版本好像更像了。讲者用得少，自称没有发言权。
    - **自嘲** 讲者说自己用 Vue 用得少：「我们用的比较少，所以我没有发言权」
- **两个框架的共同做法是把变与不变分开，让人一次只想一件事。** 这样逻辑和数据的源头可以分开管理。
    - 关注状态时，不必关注状态怎么变成 DOM。状态完全确定以后，再看怎么翻译成 DOM。
        - **玩笑** 解释为什么要把状态和 DOM 分开想（呼应第 2 节人脑有限）：「因为我们是 small head，我们头很小」

## 7. 只存当前状态会丢掉过程，长流程必然出现不一致数据

<small>▶ [79:07](https://www.bilibili.com/video/BV1JGap6LE74?t=4747)–82:50　·　但是　·　话题：长流程里的状态不一致</small>

- **只存当前状态，表示不了长流程的进度** 下单到售后要经过 9 步，其中支付需要用户确认。
    - 讲者用淘宝举例，并说不会真去实现这么复杂的系统。
    - 9 步依次是：下单、库存锁定、计算优惠、支付、风控、发货、退款、售后、对账。
    - 前面的例子假设「用当前状态表示事件」，讲者说这个假设不切实际。
    - 讲者承认，用二维表存当前状态本身没有问题。
    - 难点是在当前状态下，表示不出订单到哪一步。
    - **自嘲** 讲到前面的做法时：「刚才我们其实做了一个不切实际的假设，就是我们用当前状态来表示这个事件」。
    - 前面的做法没有解决长流程的 Essential Complexity，即问题本身固有、无法消除的复杂性。
- **进度只能塞进 state 字段，状态机越写越复杂** 开发者在 order 表加一列 state，用数字代表进度。
    - 编码方式：1 是下单，2 是库存，3 以后对应后续步骤。
    - 也可以把 state 展开成多列，例如是否下单、库存、是否支付。
    - 某个节点触发风控后，开发者要设计返回逻辑。这是业务本身的 Essential Complexity。
- **bug 或特批 override 会让数据落入矛盾状态** 系统越长越大，错综复杂的逻辑越容易产生无法解读的数据。
    - **风控被 override 的例子说明矛盾状态无法解读。**
        - 风控本应触发，但没有问题，另一个人 override 了它。
        - 订单最后处于风控失败状态，却进入了下一个环节。
        - 这条数据该怎么解读，没有答案。
    - 教务系统里有学生处于既可以毕业又不能毕业的状态，原因是程序 bug 或特批。
    - **吐槽** 讲到教务系统的矛盾数据时：「你会发现有的学生处于既可以毕业又不能毕业的状态」。
- **不一致数据可能悄悄损坏，最后只能不管** 数据可能 silently corrupt，系统不返回错误。
    - **吐槽** 讲到本校教务系统时：「我相信我们学校的教务系统里面有无穷多这样的，因为经常手操，工程师手操。教学里面有很多这种就根本不对、不一致的数据在里面。反正好像最后没有影响这个同学毕业，然后他也就只能……只能不管了。」
    - 讲者给的根源：业务流程是一整条长流程，既要编码过去，又要编码现在（后文见第 8 节）。

> 原话：「有的学生处于既可以毕业又不能毕业的状态」

## 8. 记录事件而非当前状态，现在才是过去的可重放结果

<small>▶ [82:50](https://www.bilibili.com/video/BV1JGap6LE74?t=4970)–99:43　·　因此　·　话题：Event Sourcing</small>

- **只存当前状态无法追查错在哪，会计因此发明复式记账法。** 每笔交易记入两个以上账户、金额相等方向相反，不一致时能被检出。
    - 当前状态只是一个快照，由过去推演而来。怎么过来的过程一旦丢失，就容易不一致。
    - 讲者用记账引入，先问同学有没有记过账。支付宝自带记账，但严肃记账要求用复式记账法。
    - 复式记账法为防错而设，防的是数据库式的不一致。它能做试算平衡，只记一条做不到。
    - 只记一条虽然简单，但反映不出业务的完整结构，也没有自平衡的校验能力。
    - 人类发明这种做法，是因为当前状态很可能已损坏，而且要能找出为什么不对。
    - 资产负债表是例子，条目有现金、存货、固定资产、应付账款、短期借款、所有者权益。符合会计法规的记账，必须得到这样一张表。
    - **自嘲** 讲者对会计没有知识，却要设计记账系统：「你们不需要知道这是什么，我也不知道它是什么」
    - **自嘲** 讲者坦白自己不懂会计：「但是我对会计没有任何的知识」
- **Event Sourcing 只记流水账，当前状态由重放得出** 讲者不懂会计，就不记当前状态，改记所有状态的迁移。
    - 数据结构既可以记当前状态，也可以记它是怎么来的。讲者选后者，写成流水账，例如今天收 1000 块，明天减 1000 块，并写明原因。
    - **讲者让 AI 搭了一个像编译器的结构，用 LLM 把流水账编译成操作。**
        - 流水账是 persistent history，不可篡改。允许某位不能毕业的同学毕业，也要在里面写一条。
        - 每条流水账由 LLM 编译成多个小操作。操作取自最终资产负债表里所有可能的条目，表格完全由 AI 生成。
        - 例如付营业成本，货币资金、所有者权益、应付账款和现金流量表各怎么变，都写在操作里。
        - 讲者选择相信 AI，也相信最终的校验能发现问题。
        - **自嘲** 讲者对 AI 生成的表格不加核对：「我就选择相信AI」
    - **当前状态是所有操作 reduce 的结果。**
        - 每个操作说明资产负债表、第二张表、现金流量表各怎么改。
        - 把操作按时间顺序重放一遍，就得到要提交的资产负债表。
        - 例如隔一段时间整理银行收支，它对报表的所有副作用都记在条目里，再按时间顺序推一遍。
    - GPT 写的代码一开始很长。讲者用函数式编程的小技巧合并：给 payroll 加一个参数，参数确定后得到一个新函数。记账从此不再是问题。
    - **吐槽** 讲者嫌 GPT 一开始写的代码又臭又长：「GPT写的代码很糟糕，就一开始写的非常非常长的代码」
- **成绩更正的连锁影响，只存当前状态的数据库很难评估。** 挂科会牵动学分、毕业和先修关系，当前状态库容易漏改。
    - 数据库管理的是现在：学校当前有哪些学生、哪些课程。状态可变，逻辑一改就容易从对的状态走到错的状态。
    - 好架构要能生长（见第 3 节）。规则改了，要为状态生成补丁，数据库迁移是危险操作。培养方案修正、成绩更正都会带来一串后果。
    - **成绩更正的例子：一次改动在当前状态库里会连锁失控。**
        - 学生想要分，老师说不要，学生坚持查卷。
        - 查卷发现最后一题空着，老师当时多给了 20 分。现在只能扣掉，学生挂科。
        - 挂科使学分数减 1。学分又影响能否毕业、能否准出、能否选下一门课。
        - 学生因通过计算机系统基础才选上操作系统。基础课挂科后，还能不能选操作系统，数据库内部天生不一致。
        - **玩笑** 讲者调侃坚持查卷的学生自食其果：「好的，这下好了，他查了卷子，只能把这20分扣掉，然后就挂了」
    - 这个修改不在业务逻辑里，对数据库是摧毁性的。成绩只是从 1 改成 0，其余部分被改了什么，很难评估，容易漏掉。
    - Essential Complexity 里存在大量互相依赖的关系。Event Sourcing 不维护当前状态，而是搞清所有原始数据之间的 dependency。
    - **出错时可以改正并重算，不付代价。**
        - LLM 把记账条目翻译成操作，也可能出错。当期的账有人工审核，发现错误就直接改正。
        - 学生通过 ICS（计算机系统基础）后，许多结论是事后算出来的。这个事实反转成不通过时，可以把计算全部重做。
        - 讲者举了超额选课这类情形。改了一个事实后，在这种架构里能看出它影响了哪些课程。
        - 用自动数据流分析，就知道通过变成不通过会影响哪些结论。data flow 被显式化，不再藏在当前状态里。
    - 所有计算逻辑可溯源。加学分时，要取该时刻 ICS 课的学分。课程学分可能变，有 Event Sourcing 就知道当时是几，也能判断减学分后够不够毕业。
- **事件流能推演未来，并把事实与预期分开。** 当前状态完全由过去决定，预期落空时追加新事实，不手改数据库。
    - 在下单流程中途（见第 7 节）推演出风控成功、风控失败后状态各是什么。
    - 有了账本，就能评估会不会破产、破产概率多少。条件是有一个模型，并知道应收账款有多少回不来。
    - Event Sourcing 消除不了 Essential Complexity：先修依赖、毕业依赖都是已存在的事实。
    - 世界没有按预期发展时，开发者追加一条事实。例如领导认为这位同学可以毕业，其余规则不管，他就能毕业。工程师不必手改数据库，让它越来越糟。
    - 当前状态库里的依赖可以画成 data dependency graph，但实际仍只留在计算逻辑里。Event Sourcing 把它们显式建模。
- **关系代数没有把可计算关系当一等公民，留下不一致的隐患。** 毕业与否只存成 0 或 1，成了不一致的潜在点。
    - **玩笑** 讲者借 Tony Hoare 自嘲发明空指针是十亿美元错误，类比关系代数：「因为有 null pointer，程序 crash 嘛，而 crash 的火箭可能也爆炸了」
    - **吐槽** 讲者直言关系代数犯了大错：「SQL，或者说关系代数，他犯了一个 billion dollar mistake」
    - 关系代数在当时是可扩展的好架构。但它管理数据时，没有把任何图灵可计算的计算关系作为 first class citizen。
    - 学生表里有一个「能否毕业」字段，取值 0 或 1。数据库几乎都这样设计，因为要快速查询。它无法用关系代数建模复杂的计算，这个 0 或 1 就可能与其他数据不一致。
    - 现在的框架各用方式找补：MVVM、React、data flow、Event Sourcing，都在把 derived state 和 dependency 显式化（MVVM、React 见第 6 节）。
    - 讲者建议回头看老旧的东西，再理解新设计为什么要做 Event Sourcing，会觉得有意思。

> 原话：「现在是过去的结果」
