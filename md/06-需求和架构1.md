## 1. 软件是容不下细微差错的逻辑制品，工程方法为管理这种脆弱而生

<small>▶ [00:00](https://www.bilibili.com/video/BV1Rch76WEfQ?t=0)–07:11　·　开场　·　话题：软件为何不软</small>

- **瀑布把 intent、spec、implementation 连成依赖网。Royce 批评前面出错会让后面作废**：他的分析来自各阶段产物之间的数据依赖。
    - 瀑布的路线是 intent 走向 spec，再走向 implementation，最后产出软件。软件还要维护，生命周期不止于实现。
    - 需求阶段的认识进入 specification。实现时又产生 4 类 artifacts，包括模块、函数、代码、测试。它们之间有直接和间接的依赖，交织成错综复杂的网络。
    - **Royce 批评的是错误会沿依赖回溯到前面。**
        - 后面发现错误，会追到前面的某个环节出错，例如设计不合理或需求做错。
        - 前面的环节被证明有错，依赖它的部分全部失效，可能要重做，成本高。
- **软件工程为管理这张依赖网而生。可追踪性与 UML 是其中的手段**：人与人很难对齐。只剩一份代码时，出错也不知道追溯到哪里。
    - 上一节讲过软件危机：当时软件开发不下去，需要工程化方法来解决问题。
    - 软件工程研究需求分析、系统设计、系统实现各环节的方法。这些方法包括：checklist、产品经理管人、写测试、自动化测试、自动化分析。
    - 可追踪性：最理想时，每个测试用例或代码片段都能追到过去的某个设计。改设计会影响哪些测试用例，因此可以维护。
    - UML 用有语义的结构化语言表示这些关联，试图对齐全世界的软件工程实践。
- **软件不软，因为它是容不下细微差错的逻辑制品**：椅背按下去会弹回。程序一个 bit 出错就可能整体崩溃。
    - 椅背有弹性，压下去能弹回，下次仍可用。软件是纯粹的逻辑制品，有形式语义。
    - **玩笑** 讲者指着教室里的椅背说：「你们现在坐在教室里面的这个椅背，它就是软的。」
    - **一个 bit 的翻转能让程序彻底崩溃。**
        - 程序从 stdin 读入 N，N 等于 1，循环读数组元素。
        - 程序跑在卫星上，宇宙射线击中内存，unsigned integer 的最高位变成 1。
        - N 变成巨大的数，程序无限读输入。可能一直等待，也可能读了一百或一千个数后出现 memory error。
        - 这是个极端例子，运行环境本身可能无法预见。
    - 开发者写代码时从不考虑内存位翻转，而位翻转之后程序就不再正确。
    - 静默错误：data center 里，制程越先进，密度大的指令在热噪声下越可能出现 Silent Data Corruption。同一条指令在不同机器上结果不同。
    - 有些缺陷来自制造，服务器运行一段时间后才出现。
    - **玩笑** 讲者收束这一段：「所以软件其实一点都不软。」
    - 软件同时承载客户需求，需求堆积会变成屎山（见第 3 节）。
    - 软件被认为集成了人类智慧，却要同时承载客户的需求。
- **软工课只能从代码学起。没写过代码就做不好产品经理**：判断事情能否办到、成本多少，需要一手经验。
    - 软件工程关乎整个软件生命周期，但学生被迫从最底层开始学。
    - 没写过代码、没体会过码农开发的痛苦，就无法判断某件事能否办到、要花多少成本。
    - **吐槽** 讲者直言：「如果你写不出代码，没有体会过码农开发软件的痛苦，那你是不可能做好一个产品经理的。」
    - 所以学生先学 C 语言。
        - **吐槽** 讲者说起入门要学的 C 语言：「先学一个最基础的，老的，已经过时了，没有人用的，也还算有一些人用的编程语言」。
    - 学生在此基础上积累新知识，知道旧世界怎么失败、新语言为何被创造，一层层往上走。
    - 往上走到需求、产品、架构，这是本课的主题。

> 原话：「它是一个纯粹的逻辑制品，这个逻辑制品是容不下任何细微的差错的。」

## 2. AI 时代写代码很便宜，真正决定软件走多远的是需求、产品和架构

<small>▶ [07:11](https://www.bilibili.com/video/BV1Rch76WEfQ?t=431)–15:01　·　转向　·　话题：需求与架构决定走向</small>

- **软件走向在 intent 到 spec 阶段定下，却少有人研究** 起点方向影响最大，但研究多集中在编码。
    - 项目总从空项目出发，所以前面先讲版本管理。这一节讲空项目往哪个方向走。
    - 软件走向像船往东南西北哪边开，起点的选择影响很大。
    - 需求、产品和架构难做成研究。研究者要么说没办法，要么列出“要做 A、B、C”。
    - 讲者查 CSRankings 上 ICSE 的文章，大部分和实现（implementation）相关。
    - **吐槽** 说到学校里做软工的人很多：「我们号称南京大学软件工程世界第一对吧」
    - 做 NLP 的研究者会训练神经网络，从数据推导可追踪性。讲者认为 GPT-6 也许能做到，但今天仍要讲需求和架构。
- **AI 让目标明确的代码变便宜，压力转到需求和架构** 边界划清、能做好 validation，就可以放手让 agent 实现。
    - 讲者让 AI 生成代码时，只划清边界，已经不再看实现。
    - **吐槽** 讲者说自己已经不看 AI 的实现：「我其实真的已经不看他的实现了」
    - 讲者称 GPT-6 昨天写的代码超出人类能理解的范畴，但结果是对的，稍后展示。
    - 前提是边界划清、知道怎么做 validation。这时可以铺开多个 agent 并行实现，质量有一定保证。
- **MVP 先做最重要的功能，避免研究会被扔掉的东西** MVP 是切片，能走完整流程，但不完备。
    - MVP（最小可行产品）是从 intent 到 spec 再到 implementation 的一个切片。
    - **按钮样式不该在 MVP 阶段调** 样式依赖界面设计，界面设计依赖功能实现。上层设计一变，样式可能作废。
    - 每个人都有不做无用功的本能。据此选出最重要的功能，就得到可运行的版本，AI 能给出这个版本。
- **几个字的 prompt 就让 AI 生成不同架构，并留下技术债。** 技术债是早期决策累积、使后续维护代价越来越高的负担。
    - 今天的 AI 不会主动从需求、产品设计和架构角度做事，除非 prompt 明确说，几个字也行。
    - **同一个 MVP 需求，加不同的几个字，得到完全不同的 MVP。** 功能看起来差不多，例如都实现了 coding agent 或学生 agent。
        - 要求 client-server：AI 先设计数据存储，选一个数据库，生成 db.ts。
        - 要求 CLI（字幕原文：CRI，待确认）：可能生成 cli.py，或 JavaScript 的命令行库。
    - **db.ts 一写下就进入 agent 上下文并累积** 之后每个新需求，都带上之前全部历史。
        - 做任何决定都背上债务。MVP 阶段的决定应来自需求。
- **需求、产品和架构是撬动 AI 软件生产力的杠杆** 三者决定生成软件的走向，也决定技术债累积多少。
    - 需求因人而异。想帮助学习、或有很强的读研究论文需求，软件走向就不同。
    - 只给自己用的产品很顺手，给别人用就不舒服，因为里面有讲者自己的知识和偏好。讲者举例：命令行的工作方式，普通人受不了。
    - 讲者用两节课讲需求和架构。
- **讲者顺带讲了 2 件和主线无关的事** 一件是直播翻车，一件是 AI 默认不写日志。
    - 讲者的设备翻车：鼠标键盘都失灵，插新鼠标也没用，OBS 仍在推流。出问题要看日志，这是软件工程实践。
    - 讲者的系统 UI 还在正常工作，却不知道出了什么事。
    - 讲者想让 AI 帮忙诊断，但不确定能不能找到问题。
    - **自嘲** 讲者承认直播出了事故：「我刚才翻车了嘛」
    - **吐槽** 讲者说设备全部失灵：「我鼠标键盘都没用了，我插上一个新的鼠标也没有用」
    - 写软件要输出足够的日志。不告诉 AI，它不会主动做，会生成没有日志的软件，同样是技术债。

> 原话：「在 AI 时代你生产一个目标明确的代码已经变得非常便宜了」

## 3. 真实业务系统的需求层层叠加，学生很难面对真实客户做需求

<small>▶ [15:01](https://www.bilibili.com/video/BV1Rch76WEfQ?t=901)–23:27　·　举例　·　话题：教务系统的需求爆炸</small>

- **AI 之后独立开发者数量爆炸，学生的能力仍不够面对真实客户。** 从学编程语言到毕业，学生的能力增长不足以面对真实软件的客户。所以需求工程很难讲。
    - 学生见不到真实客户，也做不了需求规模真实的软件系统。
    - AI 之前只有少量精英独立开发者。他们经过几年开源社区历练，才觉得自己能独立，并有了付费用户。
    - 现在独立开发者数量爆炸。
    - **玩笑** 讲到独立开发者变多时，讲者说付费用户：「付费用户瑟瑟啊瑟瑟发抖」
- **教务系统是需求爆炸的典型，教师端功能多且有 bug。** 讲者当场登录教务系统一路点下去，找到新功能、大量功能点和 bug。
    - 讲者称它是非常典型的业务系统。
    - 讲者说教务系统这几年一直在进步。
    - **玩笑** 讲者给这个系统起了个称号：「我可以称它是史诗级的需求爆炸」
    - **新增的 AI 搜索，讲者之前不知道它存在** 讲者平时只用快捷搜索栏，不知道这个功能何时加上。
        - 讲者问仙林教学楼（字幕原文：仙灵，待确认）的灯一直没修该打给谁，系统答基建处。讲者说他在平台上提过，被基建处打回。
        - 讲者问现在在上什么课，系统返回教师课表。讲者猜它读到了登录上下文。
    - **吐槽** 看完 AI 搜索后：「我觉得他们更应该把这个教室的灯给修好」
    - **教学任务页面的功能点多，讲者认为有需求分析的痕迹** 每个按钮背后都是一条需求。
        - 学生名单里能看到电话号码，讲者认为这是糟糕的 feature。
        - **吐槽** 讲者点评学生名单显示电话号码：「这显然是一个比较糟糕的feature」
        - 页面有编辑联系方式、当前教学学期、最新排课学期、历史授课信息。选学年学期的体验一般。
        - 期末考试签到表：考试发布前点击，会弹窗提示无法打印。
        - 上次演示过用 AI 的 slop 填满教学周历（字幕原文：教学周底，待确认）。没有人审计填的内容。
        - **吐槽** 讲者说填了什么没人管：「没有任何人来审计我填的任何内容，至少还没有」
    - **讲者当场发现 2 个问题** 说明功能越多，出错的地方越多。
        - 点编辑教材，弹窗没有正常出现。讲者说曾经可以，再试一次后确认是 bug。
        - **玩笑** 讲者确认出错后说：「好我们已经成功发现了一个bug」
        - 查看大纲等了一段时间才刷新，页面只展示最新一个教学班。讲者说这可能不满足功能性需求。
        - **玩笑** 讲者继续找别的可点之处时说：「我还是用古法方式来点」
    - **吐槽** 讲者认为系统开发和购买算力的钱，不如变成 token 补贴。他估计用 agent 查一次约一毛两毛钱：「把token送给大家，然后不要实现任何的功能，可能是更便宜的」
- **需求随时间层层叠加，慕课助教是例子。** 每一层需求都建在上一层上，旧系统里留着历史上的各次决定。
    - **慕课助教的需求在疫情前后分 3 步加上** 讲者推断疫情前没有慕课功能。
        - 疫情中，领导要求为老师添加慕课。
        - 加完慕课后，需要慕课助教。
        - 慕课助教不能当作普通教学班助教，要单独处理。
    - **讲者在助教页面又碰到异常** 讲者这门课没有助教，课表内教学班显示没有助教。
        - 页面出现一个讲者称「史诗级 bug」的界面，他不知道原因。
        - 点新增时提示请在可维护时段内操作，现在不能申请助教。
    - **玩笑** 看到助教页面里的教学班名称时：「教学班名称堪比agent」
- **学生不敢签合同，agent 敢** 学生担不起合同责任，所以讲者让 GPT 去探索系统，替学生做需求。
    - 学生不敢说「给我 20 万，我们找几个同学把南大教务系统包了」，因为担不了责任。
    - 合同里有逾期交付，以及功能和非功能要求不达标的责任，学生会傻眼。成年后可以成立公司与学校签协议，但讲者认为学生也不敢。
    - **玩笑** 讲者说学生遇到逾期交付、要求不达标时：「你就傻眼了」
    - **玩笑** 讲者说学生不敢这件事：「你们不敢不要紧，agent他敢就行」
    - 讲者让 GPT 帮他探索教务系统，目标是得到需求说明书。字幕在此截断，后续见第 4 节。

> 原话：「看到这个需求是不断叠加的」

## 4. 需求写清楚后，编码、追踪和测试 AI 都能搞定，但需求本身永远说不清

<small>▶ [23:27](https://www.bilibili.com/video/BV1Rch76WEfQ?t=1407)–35:32　·　进一步　·　话题：需求说明书到假系统</small>

- **GPT 能把真实系统整理成带编号的需求说明书。** 讲者让 GPT 只探索教务系统里和教师相关的功能。得到的是一份结构完整的说明书。
    - 《南京大学本科教学服务平台需求说明书》是真实的需求报告案例。软件工程课通常只给学生看企业说明书的一部分。想教需求工程时，可以直接把身边的系统变成说明书。
    - **目录覆盖了完整的需求工程流程。**
        - 目录项包括：调研方法、证据边界、业务目标、成功标准。目录项还包括：详细用例规约、功能需求目录、术语文档、配套文件。讲者没有逐项念完。
        - 术语文档有用。面对客户时，agent 看不懂的词可以查术语表来对齐。讲者说这不是 UML，也不在早期意图沟通阶段，但仍有用处。
    - **吐槽** 讲者说在学生看来，教务系统已经做好，这么长的目录像灌水：「这就完全的slop对吧，就突然间写了好多好多的东西」
    - **玩笑** 讲者说 GPT 懂软件工程，所以才写这么多：「所以你看GPT是懂软件工程的，他为什么要写这么多」
    - **编号给可追踪性一个形式语义。** 每条需求有带语义的 ID，对应角色、参与者或业务目标。自然语言只能说「教学班和学生管理有关」，ID 让这种关联可以追查。
    - **说明书写到了真实系统的细节。**
        - 一条需求是：一个服务支持多种身份时，提供身份选择并显示当前身份。讲者回忆自己看教师课表时，确实选过本科生和教师身份。
        - 另一条允许在授权范围内切换学年学期或业务批次。它对应一线教师打开页面后想要什么界面的意图。
        - 讲者说教务系统的交互有设计感。它设想用户做这件事时想要什么，并留一个下拉框选学期。
        - 条目还包括教学周历、课程与大纲、教材选用。讲者说这类条目琐碎到让人不想写。
        - 讲者说这些可以不写，但系统里到底有没有，说明书必须回答。
- **写长需求文档很枯燥，但做多了会量变引起质变。** 学生的课程作业已经在训练这件事，NEMU 是第一份长需求文档。
    - **吐槽** 讲者说一条条写需求，对学分和保研机试没有帮助，学生自己不会想写。背景是 TDS（字幕原文，可能是 tedious，待确认）：「这就是一个非常TDS的事情，然后这个事情TDS到你根本就不想干」

        - 系统大到一定程度后，训练是相通的。讲者说学计算机系统基础，某种程度上就学了软件工程。

## 5. 小需求变更会沿依赖传遍全系统，AI 迭代会造成驾驭的错觉

<small>▶ [35:32](https://www.bilibili.com/video/BV1Rch76WEfQ?t=2132)–44:21　·　但是　·　话题：改需求会撕裂整个系统</small>

- **小需求变更会沿依赖传遍全系统，每次补丁都累积屎山**。需求出现裂缝后，裂缝会传到系统的各个部分。
    - **离散数学拆成两门，让原有毕业规则失效**：这是 AI 虚构的案例，讲者认为学校里可能真的发生。
        - 拆课的原因：讲者认为第一门离散数学没有教会学生数学的语言
        - 学院把离散数学从 1 门拆成上下学期 2 门，准出结果和保研要求随之改变
        - 旧系统规定计算机学院学生必须选修离散数学，新旧规则衔接不上
        - 第一版需求没人想过这件事：教务员界面只有「毕业要求」、一个课程下拉框和「增加一条」按钮
        - 拆课后要调出需求文档重构，在下拉框里加「或」
    - **吐槽** 讲者模仿开发者发现旧设计失效：「好完蛋了，这个东西不能适应我们新加的需求，好，那就对不起重构吧。」
    - 每叠加一个「或」，屎山就累积一层。改需求会破坏原本一致的整体设计。
    - **吐槽** 「每当你叠加一个这个东西的时候，这个史山就开始累积了」
    - **吐槽** 「你让我做个东西，好吧，改需求真的受不了」
    - **吐槽** 「当你一个看似很小的需求要改的时候，牵动了整个系统的各个部分，你就一团一团乱麻」
- **真实世界的情形是开放的，规则穷举不完，最后靠人工改库兜底**。系统里没有的情形，由人决定，由工程师改数据。
    - 包括重修、交换、抵扣在内的规则，也会牵动系统的各个部分
    - 转学生的抵扣问题没有穷尽。别的院系也有一门离散数学。它抵扣离散数学一和二，还是只抵扣一、仍要上二，没有标准答案。
    - **第 6 年的学生只能靠人工 override 毕业**：
        - 该生因离散数学拿不到学位，已是春季学期、即将毕业，来不及修新课
        - 教学主任认为两门课可以互相替代，教学院长认为旧课可抵扣新课
        - 工程师接到电话，在数据库里把该生毕业条件改成满足，审批流程档案可查
    - **吐槽** 「最终怎么办？好，打电话给工程师，这个同学的毕业条件你把它改成满足，然后这个就过去了」
    - 讲者结论：做了需求分析，就背上了技术债。
    - **吐槽** 「一旦你做了需求分析，你就背上了技术债」
- **看似无害的输入也可能让系统崩溃，只能靠工程师改库修复**。这是讲者在真实教务系统里的亲身经历。
    - 2018 年讲者第一次用老师端，发现可以给同学设缺课次数，并认为这个功能不该放进系统
    - 讲者说学生手册里写了，无故缺课达到一定次数就可以开除
    - **吐槽** 讲者说自己做，不会留这个功能：「同学缺课就缺课吧……你不需要在系统里留证据，只要老师有一个签到表点名表留证据，扫描一下我就可以把你开除了。」
    - 讲者绕过前端校验，输入很大的次数被拒绝。把一位同学的缺课次数从 0 改成 1，所有能选出该同学选课记录的页面都 500 崩溃
    - 讲者打电话给教务，次日工程师登录数据库修复了该条目
- **AI 让 MVP 前所未有地容易，但会造成驾驭的错觉，因为没有银弹**。AI 能往后修几个版本，修不了长期运行带来的变化。
    - 需求和产品设计应另开产品课，本课只带过
    - MVP 先做最重要的功能，看到产品就知道哪里设计错，推倒成本低
    - AI 迭代 3 个版本都能往后修。系统运行足够长后，如计算机系改成计算机学院，原设计就失效
    - 没有银弹：吸血鬼和狼人杀不死普通子弹，要用银子弹。软件工程没有对应的万能方法
    - 软件要生存、要挣钱，第一时刻定下的决策会不断累积后果
    - 课程里的软件可以清零重做。软件上线后与物理世界「交火」，必须持续背着技术债维护，早期决策越不前瞻，成本越高
    - **玩笑** 「这个软件一旦上线，它就开始和物理世界产生交火」

> 原话：「你一旦面对这个开放的物理世界的时候，你就没办法了。」

## 6. 架构的本质是分解复杂性，每个好的小设计背后都映射着需求

<small>▶ [44:21](https://www.bilibili.com/video/BV1Rch76WEfQ?t=2661)–50:43　·　因此　·　话题：架构就是拆开耦合</small>

- **架构从最小的软件就开始，核心是解开耦合**：一开始不区分哪些概念可以分开。原型虽快，却容易陷入维护泥潭。
    - 需求变多时，应对方式是架构。MVP 阶段不必放进所有功能，先想第一步迈向哪里，最利于软件长期生存。
    - 第一步要做的是软件架构，不只是 MVP。
    - AI 生成的那个 slop 项目已不算 MVP，只算小型产品原型，维护会变得困难。
    - 目标是做一个最小的软件，让它随需求膨胀和改变，仍有一定韧性。
    - 例子：一开始就用一个数据库存放所有需求，能快速得到可运行的原型，AI 也能快速实现。
- **架构不玄学，本质是分解复杂性**：代码稍有规模，就可以考虑复杂性怎么拆。getopt 是一个小而完整的例子。
    - 讲者用 OJ 题的 main、读输入、处理输入、写输出作例子，问学生是否这样拆分。
    - **吐槽** 讲者说架构常被当成玄学：「大家都觉得有玄学，好像很高大上，但其实不是的」
    - **getopt 把命令行参数的复杂性隔开**
        - argc 和 argv 是操作系统与进程的约定，参数以字符串数组传入。
        - 参数本身复杂：npm 的 help 有很多选项，还支持 UNIX 风格的长参数和短参数。
        - C 时代自己写 parser 很复杂。保研机试若要求处理 argv，学生会想起 getopt，而不是逐个 string compare。
        - **玩笑** 讲者反问学生：「如果你今天在保研的那个机试的现场，那个题目要求你处理这个 argv，你会 string compare 吗」
        - getopt 按 POSIX 标准的约定解析。开发者只写一个 while 循环加 switch case。
        - 学会 getopt，就学会了一种 parser 的架构模式。
        - 这只是一个很小的例子。
        - 学生在课上、实验里，以及包括 ls 在内的实际项目里，都见过这种代码。
        - 讲者还举了 Redis，作为学生感兴趣、可以去看其实现的实际项目。
- **好代码背后都映射着需求，架构是抵抗需求变化的方式**。getopt 把复杂字符串变成简单的 parsing state。argv 怎么变都能应对。
    - 任何符合 best practice 的代码背后都有架构设计，也都映射到需求。
    - 讲教务系统有点过度（见第 3 节）。任何软件工程行为都有 intent、specification 和 implementation。在一个模块里都可以谈需求、架构和优雅。
    - 建议：看到好项目的 README 或 getopt 时，往后想一步，会发现它是一种模式。
    - **吐槽** 讲者与学院老教师曾有分歧。讲者主张讲 C++11、14、17 的新特性和用法。老教师说他讲过了：「我很讨厌那种老登的那种语言律师的授课方式」「我讲了我怎么没讲呢」「lambda 这个 a b 等于返回 return a 加 b，没有了」「这个讲了和没讲有什么区别呢」

> 原话：「它就是一种抵抗需求变化的方式」

## 7. 架构水平取决于对需求的掌握，要跳出问题，用中间语言隔离变化

<small>▶ [50:43](https://www.bilibili.com/video/BV1Rch76WEfQ?t=3043)–72:45　·　进一步　·　话题：汉诺塔与二维码的抽象</small>

- **架构水平取决于对需求的掌握，10 行代码也分得出高低。** 同一道非递归汉诺塔题，4 种写法对应 4 种理解深度。
    - 架构和需求连在一起。没有需求就谈不上架构，开放需求下的架构好坏，取决于对需求掌握到什么程度。
    - 讲者开场说，现在大模型对架构的掌控还不好。
    - 讲者说架构是一种品位。
    - 讲者以前问保研的研究生能不能写非递归汉诺塔，研究生摇头。这道 10 行的题后来成了课上的例子。
    - **同一道题有四种表达，由不同的模型和网页给出。** 讲者给模型同一个 prompt，再搜网上的代码对比。
        - GPT-6 找出数学性质：盘号等于 1 加步号二进制末尾 0 的个数。讲者说这应该是对的，但看不明白，也不确定每个盘子的移动方向是否固定。
        - **吐槽** 讲者模仿 GPT-6 的内心独白：「你写不出来是因为你的数学不如我好」。看不明白的代码他评为：「highly optimized，极度最优，对吧」。
        - **吐槽** 讲者调侃 OpenAI 把力气都押在数学上：「也就 OpenAI 在数学道路上狂奔，然后希望他在数学上面的能力能够拯救人类世界的一切」。
        - DeepSeek V4 Flash 写出近乎标准答案：递归要把剩下的任务留在栈里，每次执行栈顶任务。
        - **玩笑** 讲者评价 DeepSeek 的写法：「同样的 prompt，这个 DeepSeek V4 Flash 就更有人感」。
        - 豆包选了同一方案，但代码有瑕疵，讲者没有展示。
        - **吐槽** 讲者没展示豆包的代码：「豆包写了一个错的，然后我就呵呵，我就不展示了」。
        - 讲者自己的写法是第三种：把 C 语言的小步语义翻译成状态机（见下一条分论点）。
        - 搜索引擎给出的第四种是 CSDN 博客里的代码，讲者认为它比 AI 生成的低质内容更糟。
        - **吐槽** 讲者评价这份 CSDN 代码：「它甚至比 AI slop 还要问题还要严重」。
        - 讲者指出这份代码自己定义了 move，而标准库本来就有 move（字幕不清，待确认）。
        - 讲者怀疑页面右侧的评论也是 AI 生成的，造出博客质量很高的假象。
    - **玩笑** 讲者搜非递归汉诺塔，百度第一条居然是递归版：「百度很搞笑，百度第一个条目还是递归汉诺塔」。
    - **吐槽** 讲者看完 CSDN 的代码，劝学生别被这类内容污染：「你还不如跟 AI 学，跟 DeepSeek 学都很好，不要 GPT-6，已经不当人了」。
    - 讲者说学生如果被这类低质内容污染，不如直接跟模型学。
- **非递归汉诺塔写不出来，是因为没把程序看成状态机。** 程序的一步一步执行就是状态转移，递归可以机械地翻译成状态机。
    - 讲者故意选这道题，检验学生对递归的理解够不够深。
    - 讲者称这道题是理解 C 语言形式语义的好机会。
    - **程序是状态机，每个单步是它的小步语义。** 讲者在操作系统课上花了一整节讲这件事。
        - C 语言程序的状态可以定义出来。
        - 一个 single step 对应一条操作语义，也叫小步语义。
        - 比如 hanoi(n-1) 这样的调用，在程序语言里是定义清楚的一步操作。
    - 学会模拟这一步，就能写 C 语言解释器。把互相调用的两个函数翻译成状态机没有难度，只是把形式语义换成状态机的写法。
    - 栈版本和状态机版本等价，从状态机化简优化就得到栈版本。对汉诺塔来说，状态机版本是 overkill。
    - 讲者认为 GPT 懂这些，但不会往这个方向想。他有较强的信心，认为强化学习能把模型引向这个方向。
    - **玩笑** 讲者说自己还守得住品位：「我现在还可以守住我的品位」。
    - **跳出问题看问题，四种写法站在不同的层面。** 每一层都投射出对世界的不同理解。
        - GPT-6 跳出程序，去找数学规律。
        - DeepSeek 在语料里学到「递归是栈」，做了正确的事。
        - 讲者再往外走一步，把对编程语言世界的理解，投射成递归和非递归的区别，再写成代码。
        - CSDN 那份代码，讲者判断是训练还没收敛。
        - **吐槽** 讲者评价 CSDN 那份代码：「这训练还没有收敛」。
    - **吐槽** 讲者模仿 GPT-6 的数学自信：「我只要把程序世界里面的数学规律理解清楚，那没有任何问题是我解决不了的。我服。」
- **看似明确的二维码需求藏着坑，需求一变硬编码设计就得推倒重来。** 把二维码塞进 Excel 公式，会被 Excel 版本和布局变化摧毁。
    - 讲者在课上做过 Excel 生成二维码的例子，演示时输入一个长字符串，得到可以扫描的二维码。
    - 需求本身明确：Excel 里有一个输入单元格，若干输出单元格，生成一个 0/1 矩阵。任务是确定性的。
    - **agent 对自己的能力有估计，任务太难时会不做。** 讲者用两个例子对比。
        - 两个工作表，按学号把实验成绩拉到期末成绩表里。这在能力范围内，agent 一把梭。
        - 二维码超出能力范围，agent 仍会尝试分解问题，也在做架构。讲者判断，至少今天的模型在架构上稍落后。
    - 直接写成一个公式会很长。Excel 的计算能力有限，讲者比作用 brainf*ck 那类语言写大型程序。
    - **吐槽** 讲者形容硬写公式的结果，像用极简语言去写大程序：「好比是让你们用那种什么 brain 去实现一个 nontrivial 的程序，什么毁灭战士的游戏，你就写出来程序就会是这样」。
    - **玩笑** 讲者讲了一个 Lisp 程序最后一页的笑话，类比公式太长（字幕不清，待确认）。
    - **需求里的坑：Excel 有版本，兼容范围决定写法。**
        - 讲者看到之前 AI 给的两个版本，都没考虑到这些坑。
        - 从 2019 到 2023，Excel 不断加新功能。
        - 按学号查成绩，旧函数是 VLOOKUP，微软后来推出了 XLOOKUP（具体年份讲者不确定）。
        - 要兼容旧版，让教务老师也能打开，还是自己用即抛，用最新语法写最简单的公式，需求并不清楚。
    - **玩笑** 讲者问课上有没有人知道 VLOOKUP，没人举手，他顺势夸学生：「说明你们都不是 Excel 的 power user，太好了，你们是 agent 时代的第一类人」。
    - **吐槽** 讲者说有了 agent，学生不必再学 Excel 公式：「你永远永远不需要再学一个像吃屎一样的语言了」。
    - **玩笑** 讲者调侃微软推出新函数的原因：「微软大概终于受不了了」。
    - **需求一变，代码维护极度痛苦。** 硬编码的设计从头来过。
        - 如果 AI 用 Excel 2023 公式生成了代码，用户突然说要改成 2019 甚至 2003，设计和实现会回到原点重做。
        - 2000 行的项目可以重做。
        - 如果它已经嵌进教务系统，和其他部分产生关联，就只能向项目经理要人要钱。
    - **玩笑** 讲者替项目经理说话：「我要加人，我要加钱」。
    - 另一个变更：结果放的位置不满意，要整体右移一格。所有单元格都硬编码时，系统立即崩溃。
    - 讲者因此说，这个设计对需求变更的抵抗很差，是架构没设计好。
- **在 Python 和 Excel 之间造一门中间语言。让一份逻辑两种方式执行。** 变化只落在翻译规则上，不再推翻整个设计。
    - **跳出问题看，这是一个编译问题。** 讲者让模型给出从字符串到二维码的伪代码。
        - 二维码有完整规范，模型的伪代码很短。
        - 问题已经非常明确，模型仍然是先去读文件（ReAct 式做法）。
        - 内容包括版本、纠错等级、掩码、大小，数据编码是 0100 加字节模式，再算纠错码并放进矩阵。
        - 纠错码部分的数字包括 26 次方和 134 个码字，字幕不清，待确认。
    - 讲者问：这么简单的东西，为什么在 Excel 里实现这么困难，差距到底在哪。
    - 用 Python 实现二维码很容易，最后打印 0/1 矩阵。讲者说明年保研机试可以出这道题。
    - **玩笑** 讲者半开玩笑地说要出题：「明年保研机试我就出一个这个题」。
    - **Python 到 Excel 没有现成的编译器。** Excel 为财务报表设计，不是为图灵完备计算设计，所以不存在 PYXLC。
    - 让 LLM 直接把伪代码编译成 Excel，遇到需求漂移时，同样出大问题，因为它直接上手就做。
    - **中间语言是一棵表达式树，两头各有翻译规则。** 讲者做了这个设计。
        - 它像表达式求值程序，节点有异或、加法，或取字符串某一位的 x[1]。
        - 译成 Python：递归遍历左右子树，按节点拼接。
        - 译成 Excel：每个节点各有一条翻译成 Excel 的规则，结果可以放进任意格子。
    - **一份中间语言两种执行方式，一个验证，一个交付。** 讲者的流程如下。
        - 让大模型用这门语言生成二维码的计算逻辑。
        - 译成 Python 验证公式是否正确。
        - 验证通过后，再译成 Excel 交付。
    - 这和最小例子里的 getopt 一样：先得到 parsing state，再从这个状态出发做下一步（见第 6 节）。
    - **有了中间语言，还能做优化。** 讲者用编译器的做法举例。
        - 写改写规则，把程序从一种形态改写成另一种。
        - 循环里每次算出相同值的变量，可以提到循环外。
        - 手工写 Excel 公式时也能做这个优化，但有了中间语言，可以让大模型来优化。
        - 可以用计算机系统课学的 profiling guided optimization：先找性能瓶颈，再据此指导改写。
    - Excel 版本改了也没问题，只需要用另一种方式实现部分算子。讲者说，AI 推理里也有类似的做法（字幕不清，待确认）。
- **架构能力来自你学过的好东西和与人打交道的经历。** 讲者给出的路径是：把学到的东西压缩成第一性原理，再去理解别人。
    - 讲者说：代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的规律。
    - 每个优雅的东西都促使你思考问题。压缩就是智能，从压缩后的第一性原理推导该怎么做。
    - 这些能力来自学校的学习和社会上的积累。你必须和教科书、做题之外的人打交道。
    - 讲者以一位快退休的教务老师为例：他对教务系统的想法，可能和你的不一样。
    - **吐槽** 讲者说工程师总想着最高性能，而老师要的很简单：「他只是想要那个字大一点，他能够点鼠标的时候，不要手滑到那个按边上那个按钮上」。
    - **吐槽** 讲者替工程师说出心里话：「你的想法总是最好的数据库最高的性能，Whatsoever」。
    - 学生像无监督学习的神经网络，看好东西看多了就能泛化。讲者要求看的时候有意识地想为什么这样做，有一天会突然想通。
    - **玩笑** 讲者把学生比作神经网络：「你们作为一个 unsupervised learner，你们作为神经网络」。
    - 想通以后会发现，各个领域的人做的事情都差不多。
    - 讲者说各领域的人因为有领域知识，有很多好的设计，值得大家学习。

> 原话：「你在任何一个小的地方都能看出架构水平的高低」

## 8. CRUD 丢失历史，保存事件的 event sourcing 才能抵抗需求摧毁

<small>▶ [72:45](https://www.bilibili.com/video/BV1Rch76WEfQ?t=4365)–96:53　·　转向　·　话题：CRUD 之死与事件溯源</small>

- **GPT-6 生成的教务系统工程上像样，但本质是 CRUD**　GPT-6 自评能维护，讲者跳出问题后认为它不是好的架构。
    - 讲者说，一提架构师，听众会想到框图、数据库、微服务、流式数据处理、应用框架。好像选几个框架搭起来就解决了教务系统。
    - **玩笑** 讲者在 GPT-6 生成中途看到结果，当场发了条小红书：「这个啊 GPT-6 说这个我不当人，我不做人了」
    - 生成的代码是单体：一个 83KB 的 TSX 文件，一个 38KB 的 services 文件。GPT-6 还自己用格式化工具整理了代码。
    - **GPT-6 自评：软件能维护，设计有生产级水准。** 讲者另开一个独立 session，问它这个软件能不能维护。
        - 它答能维护，只是业务逻辑挤在几个大文件里。
        - 它给的架构评价是经典三层单体、前后端分离。
        - 它列出的横切设计包括：乐观锁、idempotent、事务、审计、统一错误处理。
        - 讲者说这些设计，之后会在某一次课专门讲。
        - 它还说数据驱动、扩展性好，也有差的一面。
    - **自嘲** 「惊了以后我就启动了一个独立的 session」，然后「害怕的问」它软件能不能维护。
    - 讲者认可这些设计：至少要摸爬滚打几年才会懂。这说明模型有软件工程的直觉，AI 生成生产软件可能要超过人类。
    - **吐槽** 讲者说这些是「你们做不来的这个至少要摸爬滚打几年才理解的设计」。
    - 但讲者跳出问题看，认为这还不是非常好的架构，因为本质是增删改查的 CRUD 架构。
- **CRUD 只留当前状态，历史丢失后不一致会越积越多**　当前状态看着一片祥和。计算过程和物理世界的事实都没了。
    - **CRUD 把世界建模成状态机，数据库存当前状态。** 讲者说软件是物理世界过程在信息世界里的投影。
        - 物理世界有状态，Everything is a state machine，讲者自己也是。软件因此容易建模成状态迁移系统。
        - 持久状态放在数据库里，学生、学院、选课各用一张二维表。
        - 数据库范式要求消除冗余：别的表引用学生时存学号，不存姓名，学号像指向学生信息的链接。
        - 好处是学生改名只改一处，再记一个曾用名。同一个名字存两份，就要改两处。
    - **自嘲** 「Everything is a state machine，我自己也是一个 state machine」
    - **玩笑** 讲到学生改名时，讲者对现场笑声补了一句：「不要笑，这件事情在中国是合法的」
    - **玩笑** 讲者举退学例子：我退学是一次 update，数据库迁移到下一个状态，A 的记录不再存在。背景是「我没有买到 token，然后我选择退学」。
    - 网页看到的始终是当前状态的投影，所以视图总是一致的。这是非常经典的架构，没有错误。
    - **吐槽** 「当我看这个当前状态的时候我看到的是一片祥和的景象」
    - **姓名存两次这类冗余，会让数据库内部不一致。** 比如授予记录里把姓名拼成字符串写进库，没有用关联。
    - **「是否允许毕业」字段只剩结果，丢了原因。** 这是 GPT-6 举的例子。
        - 该字段由多个状态算出，包括学分和毕业设计状态，每次变动都由触发器重算。
        - 辅导员要导出还毕不了业的学生，一个个谈话，这是典型需求。
        - 当前状态里只有能或不能毕业，没有「为什么」，计算过程丢了。
        - 讲者说，过程丢掉后，软件就成了物理过程的有损投影。
        - 于是系统建模不了的部分，全要靠别的途径解决。
    - **物理世界已发生、系统没建模的事，只能靠人工补。** 讲者说学生经常遇到。
        - 培养计划已通过、学期已开始，新方案还没导入教务系统。
        - 第一周仙一一带的教室在修不能用，系统没建模，只能手改、重新安排教室。
        - 第一周大家就先去别的教室上课了。
    - 数据随时间积累成无法解释的黑洞。比如没交学费、本不该毕业的同学为什么毕业了，没人说得清。
    - **吐槽** 「明明这个同学没有交学费应该毕不了业的为什么他能毕业呢」
    - **吐槽** 「系统里面就无数这样你想都不能想的不一致」
- **院系更名让 CRUD 进退两难，每次变更都要迁移数据库**　改名会篡改历史事实。不改又要新建对象，迁移还要冒数据库损坏的风险。
    - **改名会让旧记录与事实不符。** 讲者以院系调整为例，计算机系现在是计算机学院，南大是最后一批系。
        - 把对象的名字从计算机系改成计算机学院，查到的就是「2011 年毕业于南京大学计算机学院」。
        - 2011 年时它还叫计算机系，打印证明时会生成不符合事实的内容。
    - **吐槽** 「你们在面对这种需求的时候 CRUD 就会死」
    - **玩笑** 「在南大院系发生调整的时候这个教务系统就瑟瑟发抖了」
    - **吐槽** 讲者说改名还是不改，都是「要也不对不要也不对」。
    - 不改名也麻烦：学生记录里的 department id 仍指向旧对象。必须做数据库迁移，新建对象，再理清新旧对象的关联。
    - **迁移要覆盖历史上所有情况，而库里已有不一致。** 讲者说很难写出规则，还要冒迁移完数据库损坏的风险。测试环境迁移一次，和全校真实数据迁移，难度不同。
        - 数据库更新是事务，一次更新后状态彻底挪到新状态。
        - 代码可以重写，但历史没了，迁移要考虑历史上所有情况。
    - 如果假设投影永远不变，CRUD 是完美的架构。只要需求会发生摧毁性变化，每次变更都涉及数据库迁移和业务逻辑重写。
    - 讲者因此说，到今天为止，教务系统、ERP 这类系统的设计、实现、维护都是手艺活。
    - **教务系统背上技术债，是早年选择的代价。** 讲者调侃教务系统做得不好，又替开发商说话。
        - 公司 2000 年成立，当时唯一的选择是参考已有的企业架构，抢教育市场的第一桶金。
        - 做成 CRUD 后，它要在中国大学教育改革的几十年里，不断扛下所有变化。
    - **研究生院系统变成屎山，是讲者读 PhD 时亲眼见到的。**
        - 当时隔壁的软件工程组接了学校研究生院教务系统的订单，可能二三十万。在定制软件里算小订单，要长期维护。
        - 讲者和做这个系统的室友抬杠，说他是典型的 CRUD 架构，最后会遇到各种问题。
        - **吐槽** 讲者当年对室友说：「你最后会面临各种各样的问题」，后来果然应验。
        - 那几年研究生大幅扩招，培养类型增多，政策常调整，开发者没有预料到。
        - 系统最后变成屎山，不再存在，现在统一由公司维护。
- **Event Sourcing 先记事实、再回放出状态，能抵抗需求摧毁**　事实不可篡改，所以出错可以退回快照重来。
    - 讲者重做教务系统架构时，会把 single point of truth 视为太危险，因为一旦不一致，没人知道怎么恢复。
    - **持久数据结构能保留全部历史，思路来自数据结构课。**
        - 树新增节点时，只复制它到根的路径，左子树仍指向旧节点。无论树多大，历史都存得下来。
        - 状态、操作日志、操作的 delta 这三种视图等价。
        - 日志是数据库、操作系统课学过的 write-ahead journal，delta 是 git、svn 版本管理的思想，当前状态就是 CRUD。
        - 三者都能回放历史，得到当前状态。
    - 所以更好的架构是先把做过的所有事记下来：今天张三退学了，今天张三又复学了。
    - **复学例子：回放可以找回被抹掉的状态。**
        - 如果世界里原本没有复学操作，退学就是把张三从库里抹掉。这时要付很大代价重建他与其他部分的关联。
        - 记录所有操作时，可以回放得到张三复学前的状态。
        - 逻辑不会减少，复学仍要写新逻辑。
        - **玩笑** 讲者说复学是因为他「又买到 token 了」。
    - 事实不可篡改，世界里的一切都是事实的投影，所以做数据库迁移时手不会抖。出错可以退回过去的快照，修好逻辑再来。
    - **玩笑** 讲者说，没有 Event Sourcing 时，人会像「我要做一个数据库迁移的时候我手在抖」。
    - **院系调整变成一个事件，既能查过去也能查现在。**
        - 查过去的人，得到他过去的版本。查他毕业时的状态，直接查毕业时刻。
        - 想要新信息时，裁出与这个人相关的历史，再回放。
        - 例如某同学 2007 年入学、2011 年毕业，都是计算机系。计算机系在 2014 年（字幕原文：202 14年，待确认）改为计算机学院。
    - 讲者说，这样设计，你就发明了 Event Sourcing。想法简单：从历史事件生成状态，不直接维护 CRUD 状态。
    - **玩笑** 「祝贺你，你就发明了一个叫 event sourcing 的非常经典的设计模式」
    - 讲者建议听众回去让 agent 带着了解它。
    - 听众可能反应过来有性能问题，因为要大量回放。讲者说这不是大问题，可以用快照缓存等优化。
    - 已经在屎山上，改成 Event Sourcing 很困难。从一开始就这样设计，很多问题不会发生。
    - **顺带提了 2 个相关概念，都不必先学。** CQRS 是命令与查询职责分离，与 Event Sourcing 相互独立。另一个是领域驱动设计。讲者说回到 first principle，设计 50 万行的教务系统时跳出问题，看根源，没听说过这些也能做对。

> 原话：「哪怕你没有听说过这些，你也能做一个正确的架构设计」
