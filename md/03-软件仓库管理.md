# 软件仓库管理 [03-Raw⧸26生成式软件工程⧸NJU]

> 原视频：<https://www.bilibili.com/video/BV1kybV6DE47>　·　课程合集：<https://space.bilibili.com/202224425/lists/8942017>　·　讲者：蒋炎岩（NJU《生成式软件工程》2026）

## 全课主线

这节课的核心主张是：AI 能作为强大 assistant 帮人挡掉不顺心、大幅解锁执行力，但前提是说清真实意图、训练细节注意力，并理解软件工程 best practice。讲者想让大家在生成式软件工程中把项目组织成由 atomic change 推进、可回溯的 Git 快照，同时让 agent 按 best practice 做事，而不是只做被指派的一小步。

1. AI 可以挡掉不顺心，但必须先交底真实意图，并可蒸馏成 skills；GPT-6 能力提升且省 token，却仍缺有经验工程师的 taste，开放 intent space 会让它漂移。因此能力提升不等于替代有品位的工程师。（第 1 部分）

2. 讲者把 GPT-6 最大惊喜归为空间感知与理解，并把 AGI 入口放在数学：数学有全球共识、可做 grounding，与软件工程的 intent specification gap 反向。因此数学和空间感知成为判断模型能力可被学出的两个支点。（第 1、2 部分）（整理者串联：把“数学 grounding”与“空间感知”并列为两个支点）

3. 由此推论，空间感知不是绝对学不会：从简单空间任务可做 RL，复杂空间想象也能做到；GPT-6 one-shot 已覆盖原先靠对话补足的应用。所以模型一旦学出能力，会迅速覆盖旧工作流。（第 2 部分）

4. 模型同时具备空间感知与数学能力后，在具身赛道明显能做好，甚至未调 prompt 已达 SOTA。因此讲者判断模型一定会继续进步。（第 3 部分）

5. 但模型越强，越要回答 AI 时代还要不要学数据库、操作系统等基础；汽车史类比显示过去必须懂原理、今天无需懂也能开。讲者现阶段答案是肯定要学，因为理解正确概念能更好解锁 AI 的创造力。（第 3、4 部分）

6. 进入生成式软件工程后，真实项目第一步是新建目录，项目被理解为“目录 + 文件”最终构成可交付产品；localhost 暴露了 intent 和 specification 的重要性，软件则是需求在信息世界中的投影。因此，管理这个目录及其历史成为核心问题。（第 4、5 部分）（整理者串联：从“项目是目录+文件”推出“需要管理目录历史”）

7. 于是需要版本管理：从 U 盘、压缩包、作业 V1/V2 到 Git；项目级时间回溯是刚需，因为人都会犯错；从 list/切换/回退可推出简化版 Git，分支、合并、冲突会在使用中自然出现，SVN 存 delta 不如 Git 追求快速回到任意版本。所以 Git 的根本出发点是项目级时间回溯。（第 5-12 部分）

8. Git 的 best practice 是改动一发生就 commit，message 要写清做了什么；不能把作业 V1/V2/V3 当成提交，空提交只在偶发触发流程时可接受，git add . 合法但不自动等于 best practice。因此 Git 难的不是命令，而是水面下的 best practices。（第 12-14 部分）

9. AI 可以审查提交、甚至重写历史，但 agent 时代更重要的是知道 Git 能干什么，并让 agent 按 best practice 做；git blame 追每一行来源，git bisect 把提交历史当数组定位 bug，每次提交应能通过构建和测试。因此 Git 的细节最终服务于可审计、可回溯。（第 15-17 部分）（整理者串联：把 blame/bisect/构建测试统一为可审计、可回溯）

10. 相应地，要训练学习意识和惊人注意力：中学“听话”策略会让人在 GitHub 上只做被指派的一步；多点点、多对比 README/路牌，virtually implement，先自己想再与外部材料比较，追问为什么别人更好。这样才能从 AI slop 和高密度外部材料中真正学到东西。（第 6-9 部分）

11. AI 让实现成本趋近于零，但仍会生成 slop；commit message 有 Conventional Commits 等规范，中英文空格等工程细节会形成一致性和可维护性，市场细节标准也会水涨船高。因此真正有价值的是愿意花时间学习并用 AI 消化概念。（第 24、25 部分）

12. 最后，项目管理本质是把人类处理不了的混沌拆成可理解、可审计的小任务：管理很多快照就可开分支尝试，失败丢弃、成功合并、并行推进；小 commit 让 bisect/blame/冲突局部化；架构阶段先用高智力模型定好接口、压小共享状态，再让多 agent 实现、人验收。因此 Git 是软件工程，核心是把项目组织成由 atomic change 推进的快照。（第 26-28 部分）

讲者的结论/号召是：在 AI 时代仍要学习基础、训练细节注意力，并让 Git/agent 按 best practice 把项目推进成一串可回溯的 atomic change。

## AI 是帮人挡掉“不顺心”的 assistant，前提是说出真实意图
- 前几次课讲怎么用 AI 的案例；刚才讲者现场教学，示范如何把 AI 整合进自己的生活流程。
- 生活中会遇到无穷多不顺心，用很多工具时都会感到不顺心。**AI 作为非常强大的 assistant**，可以帮你把不顺心的事情挡掉。
- 你只需要告诉它你的**真实意图**。
- 还可以把这个过程**蒸馏成 skills**，让流程更平顺。
- （整理者串联）这段的链条：遇到不顺心 → 交底真实意图 → AI 代理/挡掉 → 蒸馏成 skills → 生活流程更平顺。

## GPT-6 发布：惊喜在能力提升，缺口在“品位”
- **GPT-6**（转录作 GP6）真的发布了；讲者用过，认为还是有惊喜。
- 讲者认为编程上的提升有限：有经验的软件工程师有**好的品位/taste**，这种品位可以指导 AI 做出更好的东西；但 GPT-6 更多是在**完成任务**，还没有学会很好的品位。讲者常骂它，并开玩笑说自己可能还能再“苟活”几个月。
- 不过 GPT-6 各方面能力都提升了；做更复杂任务时更快，**省很多 token**。讲者特意 measure 过，确认如此。
- （整理者串联）所以：能力提升 ≠ 替代有品位的工程师。

## 觉得 GPT 做得不好，常因开放的 intent space 无法直接与人脑对齐
- 讲者指出，我们面对的是一个非常开放的**意图空间（intent space）**。
- 同一个任务，例如“给我做一个国民级的应用”，每个顶级产品经理脑袋里想的都不一样。
- AI 没有办法和人脑直接做这样的对齐，所以一定会按自己的方式**漂移**。
- 因此觉得 GPT 做得不好，往往是因为开放意图空间下的对齐问题。

## AI 代码越来越紧凑，人类越来越不 review
- 讲者发现 AI 写出来的代码，人类越来越难读。
- GPT-6 可能受**思维链变短**影响：思维链变得非常紧凑，写出的代码也非常紧凑。
- 从 GPT-5 到 GPT-5.6，再到 GPT-6，代码写得越来越紧凑，人越来越不想看，没办法 review。
- 曾经会用各种 prompt 让 AI 写出符合人类工程规范的代码；现在讲者认为我们再也不看 AI 写的代码了，随它去，反正它能**把代码弄对**。
- （整理者串联）因果链：思维链压缩 → 代码紧凑 → review 成本升高 → 人类放弃审阅、只看结果正确。

## GPT-6 最大惊喜：空间感知与理解；讲者把 AGI 的入口放在数学
- 讲者认为 GPT-6 带来的最大惊喜，是它的**空间感知和理解能力**。
- 讲者一直认为，OpenAI 对 AGI 的理解是：AI 首先得学会**数学**。
- 原因是数学是所有人类世界里面**最难的那种语言**；它有一个全世界所有人都认同的**推理系统**。
- 这与软件工程中的 **intent specification gap**（ASR：intent spec in cation）相反：数学有全球性的共识。

## 数学与软件工程的 intent specification gap 反向：定理有全球共识，可做 grounding

- 讲者认为，数学与软件工程里的 **intent specification gap** 是反着走的。
- 数学有全球性共识：一个定理只要能证明出来，全球的人都会判断这个证明对或不对。
- 因此，讲者认为数学是非常好的、能 **grounding** 的东西。
- 讲者进一步主张：数学的逻辑推理可以解释人类生活里的各种行为。

**逻辑链：**
1. 数学证明有全球共识 → 定理可被全球判定对/错。
2. 因此数学是很好的 grounding 对象。
3. 讲者认为数学逻辑还能解释人类行为 → 可把日常决策也接到数学/逻辑上。

## 午饭选择不是“灵魂”决定，而是多因素投票，可落到命题逻辑

- 例子：今天中午吃什么、去挤食堂，是马上会面临的问题。
- 你可能觉得这是人类世界的问题，必须由“灵魂”给出答案；讲者说不完全。
- 讲者说，大脑其实在不停“投票”：他自己会选择在义父楼（保留转录；疑为“逸夫楼”）订饭，因为对他来说这是最快的选项；他下午还要开会；如果时间来得及，中午还可以小睡一会儿。
- 所以，讲者认为自己是在各种因素之间投票。
- 这些因素之间的关系，比如 \(A \Rightarrow B\)——“如果我做了 A 就会做 B”——可以 grounding 到离散数学里的命题逻辑（转录为“立命题逻辑”）。
- 讲者据此推测 **OpenAI** 的路线：先把数学学好；现在数学已经学会了，然后再用强化学习去学别的能力。

## 空间感知不是绝对学不会：从鲁班锁、骰子展开图等简单任务开始 RL

- 讲者认为，空间感知不是那种绝对学不会的能力。
- 例子：给一个很复杂的 **鲁班锁**，问按什么方向可以把第一块抽出来，人脑就会开始推演。
- 小时候的智力题也类似：给一个立方体或奇怪形状的投影，问哪一块和它一样；或者给一个六面骰子，问哪一个展开图对应，人会在脑袋里做空间想象。
- 有些 benchmark 里就是这样的题。
- 讲者判断：只要从简单的空间任务开始给模型做强化学习，复杂空间想象肯定也能做到。

**逻辑链：**
简单空间任务可训练 → 逐步扩展空间想象 → 空间感知能力可被学出来（这是讲者的明确断言）。

## 3D 打印与光栅玩具：从对话辅助到 GPT-6 one-shot

- 讲者看到相关例子时， **GPT-6（转录为 GP6）** 还没有发布。
- 他心疼自己的 PhD student：他们已经做了小半年的 **3D 打印**工作。
- 在 **GP5.6（保留转录；按上下文指某代 GPT）** 空间感知能力很差的情况下，他们仍能通过直接对话生成一个还像样、各方面符合规范的 3D 打印模型。
- 他们也有一些比较 killer 的应用：做小的 **光栅玩具**（转录为“光山玩具”；他也说“光栅尺”），从左边看和从右边看是两个不同图案。
- 比如可以说“我要做这个”，再用一个很长的搜索树帮你做一个光栅纸/光栅卡（转录为“光产纸”）。
- 结果昨天 **GPT-6 one-shot** 直接出，直接搞定。
- 讲者说，他们现在还在想怎么解决这个问题；他把这一变化同样归因于模型已经具备了空间感知能力。

小结：讲者用数学 grounding 与空间感知两个例子支撑同一判断：模型能力可以被逐步学出，且一旦学出，会迅速覆盖原先靠人对话补足的应用。

## 模型有了空间感知与数学能力后，在具身赛道已能做得很好

- 讲者仍在想如何解决前面的问题；接着指出：当模型有了**空间感知能力**，又有**数学能力**之后，它在**具身赛道**明显可以做得很好。
- 证据：第二天小红书上很多人发，直接用 **GPT6** 控制机械臂，完成抓取、叠衣服等复杂动作。
- 讲者提醒：GPT6 本质是**语言模型**；虽然它有视觉能力，但只是“一帧一帧地”问下一步要做什么，而且还没有用上 **prompt engineering（提示词工程）**。
- 即便如此，讲者认为它已经做得相当好，达到 **state of the art / SOTA**。
- 逻辑链：空间感知 + 数学能力 → 具身任务可做好 → 语言模型可控制机械臂完成抓取/叠衣 → 未调 prompt 已达 SOTA → **模型一定会进步**。
- 讲者半开玩笑：也许某次上课时，他突然就可以说“这课不用上了”，大家就可以直接去做产品。

## AI 时代还要不要学数据库、操作系统？讲者用汽车史作类比

- 讲者认为今天仍需要学一些**软件工程**知识；并重申：**AI 解锁的是人的执行力**。
- 有人问讲者：AI 时代为什么还要学、还要不要学**数据库、操作系统**这些。讲者说自己答案也不是特别确定，于是打了汽车比方。
- **100 多年前汽车刚发明时：**
  1. 汽车开 **12 km** 就会出故障。
  2. 所以每个司机/driver 都必须非常清楚汽车工作原理。
  3. 因为车一旦出故障，就得知道它是怎么工作的。
  4. 那个时代，想开车就要掌握汽车基本原理，这是理所应当的。
  5. 类比到 **computer science / 软件工程**：就要学**操作系统、数据库**，把基础打好。
- **今天开车：**
  1. 在地下车库直接说“帮我开到什么地方”，**自动驾驶汽车**就出发。
  2. 人已经不理解整个系统是怎么工作的。
  3. 但讲者指出，最终动力还是传递到一个机械装置，和 100 多年前的汽车仍有一点相似。
  4. 中间经历的所有东西，你都不需要知道，就可以把汽车开起来。
- **类比结论**：人工智能可以想象成类似汽车的东西，而且比汽车更强；它替代的不只是人的腿部向前走的能力，还替代人的**智力**。于是问题变成：那我们是不是还要学？
- （整理者串联）这个类比的关键是：汽车从“必须懂原理”走到“无需懂原理也能开”，对应到软件基础是否还要学的问题。

## 讲者答案：现阶段要学，但未来怎么学不知道

- 讲者今天的答案：**肯定要学**。
- 理由：你们学了以后，可以更好地**解锁 AI 的创造力**。
- 但“以后应该怎么学”，讲者暂时不知道。
- 讲者欢迎学生如果有答案来探讨；并强调这是**个人观点**。
- 讲者认为，至少在现在的阶段，学习还是有好处的。

小结：讲者主张现阶段仍要学基础，因为学习能更好解锁 AI 的创造力；未来学习方式则尚未确定。

## 学习正确概念仍有益：它能帮你从别处借鉴知识，创造更好的东西
- 讲者先说明：如果你们有答案，也欢迎来和他探讨；以下是他个人观点。
- 讲者认为：至少在现在阶段，学习仍然有好处。理由不是死记，而是**理解正确概念**后，可以帮助你从别的地方借鉴知识，创造更好的东西。

## 进入生成式软件工程：第一步不是下载作业，而是新建目录
- 讲者今天进入“真正的软件工程”，即**生成式软件工程**。
- 如果开始做软件工程 / **vibe coding（原文转写为“web coding”，按语境疑似）**：做作业时，你通常从课程网站、老师要求或某个下载物开始；但真正想做项目时，讲者说第一件事一定是**建一个目录**，给它起名字。名字甚至可以是中文，比如“我的最酷的 game”。然后才开始 vibe coding。

做作业：课程网站/老师要求 → 下载一个东西 → 从那里开始工作。  
真做项目：新建目录 → 命名 → 在目录里开始 vibe coding。

（整理者串联）这两条路径的差别在于：作业从已有骨架开始，真实项目要先建立自己的项目容器。

## 软件工程项目是什么：一个目录 + 一堆文件 = 可交付产品
- 讲者问：创建后面对一个空目录，你们怎么知道该做什么？
- 他回顾学习方式：看老师上课打开一个工程项目，里面有文件，于是无意中记住一些东西；老师或同学推荐某个发布物，你拿到 **GitHub** 或 **git** 链接，打开网页，看到人类友好的界面上有一些文件，于是知道“我的目录里会要有文件”。
- 所以开始一个软件工程项目时，你会建一个这样的目录，里面有一堆文件。
- 这些文件共同构成一个**可以交付的东西**，最后会变成你的**产品**。
- 这个目录可能直接在本地运行：你对 **agent** 说“请你帮我运行”，窗口或网页就弹出来。

`看老师项目 / 打开 GitHub 链接 → 看到文件结构 → 记住“目录里要有文件” → 建目录并放文件 → 得到可交付产品`

  3. 所以学生会觉得上课耽误学习。
- 但讲者补充：传统教学方法没有教大家怎么把这些海量、高密度信息用好；大家也没有准备好去拥抱这样的知识。

**讲者认为自己当老师的原因与要训练的能力：惊人注意力**
- 讲者认为，他现在做老师，是因为他有这种 **惊人的注意力**。
- 他认为大家要训练的也正是这种惊人的注意力。
- 这种注意力表现为：
  - 看到任何东西之前，大脑先把眼前看到的所有东西忽略掉。
  - 先想：如果我要自己来解决这个问题，我会怎么做？
  - 然后立即比较：我看到的东西和我脑袋里所想的东西，谁更好？
  - 如果我做得更好，就认为这是一个 **slop**（原文作 “slob”，按上下文指低质作品）。
  - 如果发现他做得比我好，就很惊喜：诶，他为什么做得比我好？
- 讲者认为，养成这个习惯后非常“恐怖”：你在任何时候都在疯狂地从外面接收信息；你能留意生活里各种小细节时，就不停地在提升。

**读论文/学课程的方法：virtually implement**
- 讲者说，很早大家就有推荐：如果你们要读一个 **research paper**，研究论文应该怎么读？
- 他提到早先展示过：AI 会被 **注意力机制** 带到作者的 **逻辑陷阱** 里面去。
- 他给出的好学习方法叫 **virtually implement**（在脑中先实现一遍/虚拟实现），也适用于学任何课程，包括 **高等数学**、**计算机系统基础**。
- 做法：
  1. 你现在有一个具体的问题或具体的需求。
  2. 先在脑袋里把这个问题自己做一遍。
  3. 你会得到一个什么样的结果？
  4. 如果你的方法和作者的方法一致，那很好，说明你已经学会、完全掌握这个知识。
  5. 如果你不一致，讲者说还有两种情况；这一段只说到第一种：
     - 成熟、好的教科书上的方案，比你想象的方案更好、更精巧、更简洁。
     - 这时你就要想：为什么他能想到？

**逻辑链总览**
- 讲者给出的链：
  - 外部材料（README / GitHub / 论文 / 教材）信息密度高 → 传统课堂无法匹配 → 学生会觉得上课耽误学习。
  - 要利用这些材料 → 先自己想一遍 → 与材料比较 → 判断谁更好 → 若对方更好，追问“为什么他能想到”。
  - 学习上的具体化 → **virtually implement** → 一致=掌握；不一致=进入追问。
- （整理者串联）本段把 README、GitHub、论文阅读和课程学习串到同一件事上：不是被动接收，而是先形成自己的方案，再拿外部方案做对照，用差距驱动理解。

**小结**
讲者用 README 和成熟 GitHub 项目说明：外部材料的信息密度已超过课堂，真正要训练的是“先自己想、再比较、再追问为什么”的惊人注意力；在论文和课程学习中，这个方法叫 virtually implement。

- 但讲者认为，他们未必意识到：GitHub 竟然成为今天 **AI 时代**的**底层基础设施**。
- 证据：**npm**，以及你各种 npm 的配置，大都在 GitHub 上。
- （整理者串联：讲者用 npm 生态说明，Git/GitHub 已不只是“放代码的地方”，而是许多工具链和 AI 工作流的默认底座。）

## 推免面试观察：学生会说 Git 的用途，但 merge 冲突后的现象是盲点

- 讲者上周末参加 **推免面试**；他提醒听众大约一年或两年后也会到这种场合。
- 他问“什么是 Git”。大家多多少少能说两句：
  - 从 Git 上下载、分发代码；
  - 有同学能讲到 Git 管理项目目录的**快照**。
- 讲者态度：没必要因此把所有人都挂掉；能讲一些就可以，具体看能讲多少来评估。
- 问 **git rebase** 是什么，也在讲者意料之内（学生不熟或答不出符合预期）。
- 但讲者比较意外的是：他问“**git merge 发生冲突以后会观察到什么**”，大家似乎没有观察过，或答不上来。

## merge 冲突不是立刻被 resolve，而是把责任交到开发者手上

- 场景：作业中老师发布更新，你本地已经把东西改得面目全非；你让 **agent** 来，它自动啪啪修好，最后说“好了”，甚至测试通过；讲者自己也遇到 **merge 出错**，让 agent 帮修，看一眼结果看起来 OK。
- 但讲者认为，这时候**真正的注意力**才有用。若你愿意在冲突时停下来——尤其学生常想“我再学一点吧，反正一秒钟，学一下没坏处”——你会看到很神奇的东西：**很多等号、很多箭头**。
- 讲者给出的责任链：
  1. **merge 冲突发生**；
  2. 冲突不会立即被解决，不是自动 **resolve**；
  3. 解决责任落到**开发者手上**，曾经是每一个开发者；
  4. 开发者发现冲突后，就有义务解决冲突；
  5. 要解决冲突，他就必须**能看到冲突**。
- （整理者串联：因此，若让 agent 直接把冲突抹平，你就跳过了“看到冲突”和承担解决责任的过程，也跳过了讲者所说的细节学习机会。）

## 讲者的主张：AI 代修越顺手，越要在冲突处保留“看一眼”的习惯

- 讲者不是否认 agent 能修好；他描述的是自己也会让 agent 修，测试过了、看起来 OK。
- 但他强调：冲突时的等号、箭头不是噪音，而是 Git 把**解决责任**和**冲突现场**暴露给开发者的方式。
- 对学生而言，讲者认为在冲突处停一下的成本很低（“一秒钟”），却可能把一次自动修复变成一次对 Git 细节的感知训练。

小结：讲者把 Git merge 冲突从“让 agent 修掉的麻烦”改写成“把责任交回开发者、训练细节注意力的入口”。

## 开发者必须解决冲突，因此 Git 必须让冲突“可见”
- 讲者先给出义务：**开发者有义务把冲突解决掉**。
- 逻辑链：
  1. 有冲突 → 开发者要解决。
  2. 要解决 → 他必须能看到冲突双方。
  3. 因此 Git 不能只说“对不起，冲突了，我不能合并”然后停在那里；这会把决定负担全丢给使用者。
- 例子：一个文件原来是 `1111`；一个人把第二行改成 `2`，另一个人把第二行改成 `3`。那这一行到底是 `2` 还是 `3`？Git 不能替人决定，但也不能只报冲突后不管。
- 讲者认为，如果 Git 只是“冲突了不能合并”然后躺在那，对人的负担非常大：人还得自己判断这一行应该放 `2` 还是放 `3`。

## Git 的冲突呈现遵循“把信息放到现场”的第一性原理
- 讲者说所有 **first principle** 都是连起来的；自己之前无意中举的地铁标识例子，Git 也在用同一个原则。
- 原则是：如果现在发生了一件事，最好就在这个地方，把它所有需要的信息全部放进来。
- 所以以文本方式看 Git 冲突时，会看到：等于号、多个尖括号、`incoming` / `HEAD` 之类的标记；至少**冲突的两部分代码同时显示在这里**。
- 如果使用 IDE，上面还会多出按钮，比如 **accept incoming change**；可以在 IDE 里自己 **resolve**，决定谁进谁出；完成之后再创建一个 **commit**，把这个冲突 resolve 掉。
- 讲者认为这只需要一点注意力；只要有一两次经验，就会形成印象：至少能说出两边冲突的代码会显示在一起。

## 大家答得不好：原因一是没用过，二是没留意
- 讲者说大家答得不好让他吃惊。他判断原因：
  1. 第一，没有用过、没有开发过。
  2. 即便用 A 证（音；疑指 AI/agent）开发，如果你让它在不同分支开发，也很容易遇到 **conflict**。
  3. 第二，还是没有留意。
- 所以比较重要的两件事：第一，多去用；第二，试图拥有更好的注意力。

## Git 的起源：从“复制目录保存旧版本”的需求到目录级版本管理
- 讲者先否定：在 U 盘上放一个目录、每次打个包的方式不行。
- 但他的观察是：上学时同学们确实这样干——复制目录成 **作业 V1、作业 V2（原音近 VR）、作业最终版**。每次复制一个目录，非常直觉。
- 这种方式可以找回旧文件。因为万一哪天手滑，或者不小心改错，尤其在新手阶段，误操作非常正常；人会想回到上一个版本，看看当时到底怎么写的。**这不就是一个需求吗？**
- 从这样的需求出发，讲者认为你自己就能发明一个像 Git 这样的东西，因为本质上所谓的就是**版本管理**。
- 讲者对项目的定义：项目就是一堆东西——代码、文档、**Intent spec**、**implementation**、各种东西、测试用例——全部搅在一起，放在一个目录里。
- 接着的设想是：如果我们能够把**这个目录的版本**管理起来，那么就不再叫作业一、作业二、作业三，而是**只有一个作业**。
  - （整理者串联：也就是让版本历史由系统保存，而不是靠复制目录和文件名来区分。）

# 目录版本化 + list/切换/回退 = 简化版 Git

- 讲者从一个思想实验开始：只有一个**作业目录**，不再叫“作业一、作业二、作业三”。
- 如果提供一个命令行工具，可以：
  - `list` 作业有哪些版本；
  - 把当前版本变成另一个版本；
  - 回到过去的某个版本。
- 讲者明确推出：这样你就已经发明了一个**简化版 Git**，虽然还没用到分支、合并、冲突这些概念。
- 讲者认为，分支、合并、冲突会随着使用自然被发明出来。

# 同步、同文件修改会逼出分支/冲突

- 用着用着，你可能会要和室友同步。
- 同步中出现“两个人一起改同一个文件”的情况。
- 就会坐下来想：一起改了同一个文件该怎么办？
- 于是就可以发明 Git（转录中作“get it”）相关机制。
- 讲者由此感叹/认为：这体现了人类的局限；在 Git 之前，还用过 **SVN**，你们可能听都没听过。

# SVN 存变化 vs Git 追求快速回到任意版本

- SVN 有 **check in / check out**。
- SVN 的设计：存储的是**项目的变化**。
  - 有最初版本；
  - 文件改一行，就存一个 **patch**；
  - 再改一行，再存一个 patch（转录作 PCH）。
- 讲者评价：这看起来没问题，甚至是非常高效的实现。
- 但讲者说，这种高效会随着项目增长把大家拖入泥潭。
- Git 的模型要干净得多。讲者的 **first principle** 是：我想先回到过去某一个版本，就应该马上、一秒钟回去。
- 反例逻辑：如果每次存的都是 **delta（德尔塔）**，要回到早期版本，就得一个一个往回退。
- 可以用缓存等方法优化，但讲者认为这条路线确实像是走错了。
- 讲者链条：**SVN 存 delta → 回早期版本需逐个回退 → 不符合“快速回到任意版本”的目标 → Git 的 first principle 更干净**。

# Git 的历史：Linux 维护痛点催生 2005 年的 Git

- Git 的作者是 **Linux 的作者**。
- 1991~2002 年维护 Linux 时，用的是类似“作业 V1、作业 V2”的手工方式，在**邮件列表**上发补丁。
- 具体流程：
  1. 我改了 `a.c`，手里有一个 `a.c` 新版；
  2. 我把新版发到邮件列表；
  3. 维护者每天看邮件列表，把它放进核心仓库；
  4. 再去 **release** 这个版本。
- 之后还用其他工具 **BitKeeper**（原转录 [get it key / keeper]；此修正为整理者按上下文判断）。
- 直到 Linux 受不了，认为应该要一个**绝对简单、非常好用、概念正确**的版本控制工具。
- 结果：2005 年做了 **Git**。讲者强调它比我们想象中年轻。
- 有兴趣的同学可以看相关文档（原词 [PROPATE?]）；讲者说不用再读，他读书时都看过这些文档。

# 项目级时间回溯是刚需

- 讲者最后指出：我们需要**项目级的时间回溯**。
- 因为**我们都会犯错误**，所以只要能进入 Git 的历史里回溯/恢复。

**小结**：讲者强调 Git 的根本出发点是项目级时间回溯；分支、合并、冲突等概念是后续使用中自然长出来的。

## 项目级时间回溯：会犯错，所以要用 Git 历史把东西捞回来

- 讲者先立目标：需要 **项目级的时间回溯**。
- 理由：我们都会犯错误。
- 因此，只要能去 **Git 的历史**里把误删、误改的东西“捞回来”，就可以了。

逻辑链：
1. 项目会犯错。
2. 需要项目级时间回溯。
3. 只要能进 Git 历史把东西捞回来，就足够。
→ **（整理者串联）** 所以 Git 的历史不是装饰，而是恢复机制。

## 从已有经验推出下一个概念：讲者把这称为数学推理

- 讲者建议用这种方式推进：从已有经验出发，明确“你知道什么”“你想要什么”，然后推出“下一个概念应该是什么样的”。
- 讲者说：这就是 **数学的推理**。
- 他补充自己上课时，每一句话都和之前有逻辑关联；这些逻辑关联多多少少都有数学联系。
- 由此，**OpenAI**（原转录：open a）认为要先把数学训好；训好以后，它所有问题可能都能解决。讲者认为这件事可能真的要成真；讲者自己觉得“品味”（taste）可能也能解决。

## `git init`：把一个普通项目变成 Git 版本管理的仓库

- 讲者现场建一个空的 **terminal**，讲什么是 Git（原转录多处像 get it / kit）。
- 开启项目：`git init`（原转录：get in it / get it event）。
- `git init` 会输出一些奇怪信息；讲者说这些信息不重要。
- 面对不懂的信息有两种选择：
  1. 让 **agent** 帮你做、帮你解决、回答你不懂的问题；
  2. 把它忽略掉。
- 讲者认为前者显然是更高效的学习方法，也更好。
- 结果：得到一个空仓库，或者说得到一个 **`.git` 目录**。`.git` 默认不显示，所以看不到；讲者说这就是全部了。
- 做完 `git init` 后，项目就变成被 Git 版本管理的 **仓库**。
- 后续能力：可以从远端下载代码，也可以把代码推到远端。

## 基本命令链：`git add` → `git status`，Git 的核心是项目快照

- 例子：有一个 `hello.c`。讲者说随便，你们喜欢写 C 好。
- 运行 `git add hello.c`。
- 再用 `git status` 可以看到当前 **工作区** 里有 `hello.c`，并有一些提示。
- 讲者强调 Git 很重要的一点：创建 **项目快照**，使你能在任意时间之间穿梭。
- 可以创建一个 **有消息的快照**；消息很重要，体现 **软件工程的智慧**。
- **（整理者串联）** 所以 commit message 不是形式，而是让快照可理解、可回溯。

## 不要用“作业 V1/V2/V3”代替提交：每次改动都应立即 `git commit`

- 以前用复制粘贴的方式命名：目录一、项目版本 V1/V2/V3、作业 V1/V2/V3。
- Git 的世界不是这样。讲者看到很多同学在用 Git 时，把 Git 当成作业 V1/V2/V3 来用；这不是 Git 推荐的 **practice**。
- 推荐 practice 来自长期软件工程实践经验：
  - 对项目做任何改动后——改文件、修 bug、增加功能、调整脚本、调整文档——都应该立即做一次 `git commit`。
- 演示 `git commit` 时打开 **Nano**（讲者：哎呀这怎么是 Nano）；可以在文本编辑器里写“我这是做了什么”。

逻辑链：
改动（改文件 / 修 bug / 加功能 / 调脚本 / 调文档） → 立即 `git commit` → 得到带消息的快照 → 可以在任意时间之间穿梭。

## 改动一发生就 `git commit`，message 要写清你做了什么
- 讲者主张：只要你调整了某个文档，就应该立即做一次 `git commit`。
- 演示：他打开文本编辑器（惊讶“哎呀这怎么是 Nano 啊”），写一段文字说明“我做了什么”，保存后提交成功。

## 不能把一切交给 AI：要知道为什么做、何时 `git add`/`git commit`、message 怎么写
- 讲者认为，不能把所有事情都交给 AI；你多多少少还要知道我们为什么要做这件事，什么时候应该 `git add`，什么时候应该 `git commit`，commit message 应该怎么写。
- 学习方式：碰到新东西时马上追问：“你刚才做的是不是符合 **best practice**？”比如刚做完一个 `git commit`，就问“这个符合 best practice 吗？”
- 他举例：向豆包输入法提问只需一秒钟，但它会给很多解释。它说这个 commit 不太符合 best practice：主要问题在提交信息，其次代码本身也有问题；提交信息的可读性有问题。
- 讲者故意写了一个 `I added some cool stuff`，完全看不出做了什么。

## Git 存快照，但项目历史被理解为 V1 → V2 的修改，所以 message 必须描述改动
- 讲者说：Git 本质上存放的是快照，但我们的项目本质上还是从一个版本 V1，经过一次修改变到 V2。
- 因此 Git 鼓励你在 message 里描述你改了什么。
- 讲者的链：**message 写清改动 → 一直读提交记录 → 就能知道项目怎么发展到现在**：修了多少个 bug、加了什么需求、经历了什么样的重构；可以在 message 里看到项目历史的轨迹。
- 讲者认为这也是好的软件工程 practice，使别人更容易理解你的项目。

## 极端反例：10,000 条 “I did some cool stuff” 会让 commit message 变成 slop
- 如果每一个提交都是 `I add some cool stuff`，想想 10,000 个提交以后会怎样：commit message 就变成 **slop** 了。
- 如果 10,000 条都是 `I did some cool stuff`，那 commit message 这个特性就不应该存在；不要叫 commit message，直接从 V1 到 V2 就行了。
- 讲者说，你会在不同时候使用不同的 commit message。比如一个版本要收尾了，可能会写一个 commit message 说“我要 finalize 这个版本”。

## 空提交的边界：普通 Git 拒绝，agent 可以做，但理论可行 ≠ best practice
- 讲者提出一个边界情形：不改任何代码，V1 和 V2 完全相同，再做一个提交。
- 普通 Git 会拒绝这个空的、没有修改的提交；但 agent 可以。讲者说，他让 agent 做一个提交，并要求它在不修改的情况下提交，agent 能做到——讲者说“它知道，它有知识”。
- 讲者强调需要保持注意力，尝试追问：“从理论上说应该可以吧？”比如“我就要发布一个版本了”这种提交。
- 但讲者认为：这个不是 **best practice**。

**小结：** commit 不是随手保存；message 要让项目历史可读，AI 可以快速答疑，但 best practice 仍要自己追问和判断。

发布/收尾场景的推理链：
- A：上一次已经修完最后一个 bug，得到一个可以 release 的版本。
- B：Git 可以在这里打 **tag**，比如 **V0.1**，说“这是 V0.1”。
- C：讲者说也可以强行做一个无改动的提交，说“我要 **finalize**”，为了 **0.1 freeze** 所有东西。
- D：这样就把 **bug fix 的提交**和 **finalize 的提交**分开了。
- 讲者结论：这件事偶尔可以允许；但不能创建大量这样的空提交。

## Git 命令只是表面，真正难的是水面下的 best practices

讲者认为：学了 `git push`、`git pull` 等基础命令（原文 ASR 含糊）后，好像就会用 Git；但真正在水面下的冰山，是各种 **best practice**。每一个 best practice 都是“血和泪的教训”。

他举出一个要追问的问题：**为什么 commit message 要那样写？** 他建议反过来问 AI，或跟更智能的模型讨论（ASR: 更有质检模型），问这样做有什么好处。

讲者的个人观点：
- 很多时候模型表现比他好。
- 知识可能是内化在他脑子里的；给他两小时，他也可能写出很好的“为什么要做这件事”。
- 但他的智力、精力、注意力有限。上课时要专注和大家上课，大脑中做思考的容量不够，所以讲一个概念时讲的不是最好的版本。
- 因此，回头可以把“为什么 commit message 要这样写”这类问题拿去和 ChatGPT 聊。讲者把这比作求助一个自己无法掌控、但“好像知道世界上所有东西”的东西；它能把这些概念讲清楚。
- 这些约定俗成的 best practice 是核心。

## `git add .` 合法，但不自动等于 best practice

讲者举一个“不是 best practice”的常见做法：
- 场景：有一个 **untracked file**，tutorial 里会看到一个很好用的命令 `git add .`。
- 如果你改了三五个文件，比如 `a.c`、`b.c`、`c.c`，你不需要写 `git add a.c b.c c.c`，直接用 `git add .`。
- 然后就可以提交。
- **Git 不阻止你这么做**；这是完全合法的。
- 讲者接着问：那么 Git 提交里有什么不符合 best practice 的吗？——这个问题引向下一部分。

小结：空提交只在无改动却要触发/标记 release 的偶发场景可接受；Git 的难点不在命令，而在 best practice。

## 编译产物入库的后果链

1. 项目可能有 1 万个文件、100 个合作者。
2. 每个合作者的环境都不一样。
3. 每个环境 build 出来的东西也不一样。
4. 编译产生的文件每次都可能不同：可能带日期，甚至带 hash，带你本机的指纹。
5. 所以同一个二进制文件，你这里一个 `hello`，对方那里一个 `hello`，哪怕源代码相同，编译出来也可能不同；如果源代码不同，就更不用说了。
6. 把它放进版本库，下一次就会产生冲突。
7. **二进制冲突很难合并**。讲者还举例：如果生成的是图片，也会遇到“怎么合并”的特殊问题。

→ 因此才有这一堆 Git best practice：生成物不要入库，用 `.gitignore`，让构建系统重新产出。

## 有能检查 bug 的测试后，git 历史可被当成“0…0 1…1”数组做二分
- 前提：bug 可能是过去某一个地方引起的；你有一个测试用例，或任何能检查出这个 bug 的东西。
- 讲者给出的推理链：
  1. git 历史里有一些提交 OK，有一些提交不 OK。
  2. 某一刻引入 bug 后，从某一时刻开始这些提交都不能通过。
  3. 在这个时刻之前的每一个提交应该都是 OK 的。
  4. 所以状态序列是：前缀全是 0，后缀全是 1。
  5. 要找的是第一个 1。
  6. 二分查找能做的事，就可以对整个 git 历史做二分。
- 讲者结论：有可检查 bug 的东西，就能用二分查找定位引入 bug 的提交。

## Git 的底层入口：它是持久化数据结构，持久化的是目录树
- 有了 **AGENTS.md**、**CLAUDE.md** 后，下一步学 Git 如何工作、底层原理。

逻辑链（讲者给出的思路）：

## 改一个文件时，快照只需复制“到根的路径”

讲者先设问：项目已有 **V1**，现在要创建 **V2**；如果只改了 **b.txt**，是否要把所有文件都复制一份？答案是不需要。

逻辑链：
1. 改过的 **b.txt** 需要一个新版本。
2. **从该文件到根的路径都要复制一份**：如果根或父目录仍指向旧节点，就等于还在引用旧的 b.txt。
3. 路径之外未变的 **a.txt、d** 等，可以用**指针**指向旧对象。
4. 因此 V2 只是一个小增量，而不是整棵树的副本。

讲者用 a.txt、d 的指针作示意：结构“虽然不太好看，但这就是 V2”。

## 目录深度有限，使“小增量”在超大项目中也成立

- 即使项目里有 **100 万个文件**，目录本身也不可能很深；讲者说没人会建 **1000 层深**的目录。
- 从**渐进式披露**角度也没必要建巨深目录；每一级索引可以指数级增加，很快就能把所有类分完。
- 所以只需要创建一个非常小的增量，就能得到一个版本的快照。

## Git 底层：commit / tree / blob 三种对象

- `.git` 里有各种 **objects**，它们是普通文件，带 **hash 索引**。
- 对象可看作节点：目录节点、文件节点、commit 节点。
- 三大类型：**commit object**、**tree object**、**blob object**。
- **blob** 是 binary，即字节序列。
- 这个数据结构可以不断向后生长；讲者认为版本记录问题由此解决。
- 讲者认为，从 **first principle** 出发，一个大学生完全有可能设计出这样的东西。

## Merge conflict：两人重构同一处 → index 里保留 base/ours/theirs，工作区显示冲突标记

## 为什么必须及时 commit：复杂项目会把大提交的 bug 定位成本放大

讲者给出的起点是：在复杂项目里，你修改的东西越多，出错的可能性就越多。小项目刚开始其实不要紧，一次提交两三千行代码都 OK；但项目里一旦有错综复杂的关系，一个大的 commit 可能 break 多处东西，引入多个 bug，后面又要引入多个 fix 来修它。

逻辑链：
1. 复杂项目 + 大 commit → 一次改动同时影响多处。
2. 多处被 break → 引入多个 bug。
3. 多个 bug 需要多个 fix，但这些 fix 都被归因到那个大 commit。
4. 如果大 commit 是 V2，后面修了 100 个 bug，都说“这是 V2 产生的”，就很糟糕：修不过来，也不知道 V2 到底修好没有。

## 小 commit 的好处：冤有头债有主，bug 和 fix 可以配对

讲者认为，如果每次 commit 都很小，只做一个修改，那“冤有头债有主”：这个 bug 就是你写出来的，你修完就完了；bug 所在 commit 和 fix commit 可以配对。这带来：

- **审计能力**：每个改动和修复有清晰的对应关系。
- **远端备份**：如果你改了很多，电脑又物理损坏，还没推到远端，就会丢失；做一个小提交后立即 **push**，就能得到互联网上的备份，电脑马上坏也不怕。
- **AI 可用能力**：讲者说 AI 很清楚可以 **review**、可以 **revert**、可以做 **bisect（二分查找）**。后面可能还会讲 **hooks 和 CI**。

## agent 在 GitHub / GitLab 上的行为：调 gh / glab，失败后回退到“古法编程”

讲者提到，如果项目托管在 GitHub / GitLab 上，会看到 AI agent 试图调用一些 **gh** 或 **glab** 命令；然后会看到一个 **command not found**，于是它又回退到“古法编程”，开始写 git 命令。

讲者给出的理由：GitHub 太 popular、太好用，所以值得为它做一个命令行工具。

## GitHub 的 issue / 评论不随 Git 持久化，因此需要额外命令行工具

讲者说明：Git 管理了很多代码快照，但 GitHub 上还有 **issue**，也可以对代码做 **comments**；这些东西不随着 Git 持久化。若想管理它们，就可以做一个命令行工具：

- fetch 一个 issue；
- 找 assign 给自己的 issue（需要登录）；
- 找到后还可以把 issue **close** 掉。

对 AI/agent 来说，这个命令行工具很好用：装了 **gh** 以后，可以在 agent 里设置一个 **goal**，让它完成一个很长的任务，并要求它做小步提交、可审计的提交、遵守分支规则、保持线性历史等。

## 讲者项目里的例子：大量小提交，很多他都不管

讲者举例：他的项目里就有大量这样的提交；从开始提交代码起，就有大量这种提交。他说自己很多时候都不管它们了。

## 今天最该记住的总结：Git 是软件工程，用 atomic change 推进快照

讲者强调，讲了这么多 Git，这门课讲的还是软件工程。最后的总结更重要：Git 本质上是一个软件，它要求我们把项目组织成用 **atomic change** 推进的快照。这是今天要记住的事情，所有东西都从这句话推出来：你组织一个软件项目，要管理很多快照，这样就可以随时开启一个新的分支。

小结：核心是把项目组织成由 atomic change 推进的快照。

## 一切从“项目要管理很多快照”推出：分支、丢弃、合并、并行

讲者说，后面所有做法都从这句话推出：**组织一个软件项目，本质上要管理很多快照**。由此得到一条明确逻辑链：

2. 尝试失败 → 可以安全扔掉。
3. 尝试成功 → 可以合并进来。
4. 因此甚至可以同时推进多个主线，最后以合并完成，而不会互相干扰。

讲者用大作业经验说明：如果你要改好几个地方，改着改着很可能改乱，和这个部分、那个部分冲突。**（整理者串联）**分支/合并的价值就是把“多处同时改”隔离成可丢弃、可合并的尝试。

## 项目管理的本质：人类处理不了一团混沌，所以必须拆成小任务

讲者断言：**项目管理的本质是人类没有办法处理一团混沌**——很多需求、很多代码依次做一大波。于是很自然要：

- 把需求分解成**可理解、可审计的小任务**；
- 一小步一小步来。

小步之后，出了问题才能：

- 用 **bisect** 定位；
- 协作时用 **blame** 归因；
- 让冲突更容易解决。

讲者进一步举例：如果我在一个**公共祖先**上做了好多事，但每个提交都很小，那么发生冲突时，我可能知道是哪一个**小提交**冲突；剩下不冲突的部分合并起来会比较容易。**（整理者串联）**这里的关键不是“小步”本身，而是小步把定位、归因、合并都变成局部问题。

## 线性历史：AI 能轻松 rebase/resolve，所以更值得强制

讲者区分两种做法：

- 普通 **merge**：把一个提交合上来；一个 commit 可以有**两个 parent**；历史继续分叉、合并，最后形成很典型的 Git 结构。
- 现在更流行 **linear history**：讲者说反正都是 AI，**resolve、rebase** 都很容易，所以他会强行要求整个 commit history 都是线性的，“好像是线性的一样”。

讲者也说这不全是好处，但至少对现在维护项目来说：

- 历史更易于追溯；
- 对 **cherry-pick** 和 **blame** 更友好。

讲者的时间限定是：在**无限大能力的模型到来之前**，这件事都是好的。链条是：把 Git 记录拆分得好 → 很容易找到这次修改由谁引入 → AI 维护项目效率更高 → 省 token；有些文件就可以不用去读。

## 架构阶段先用单线程 + 高智力模型，把组件库接口定好

讲者分享自己的项目管理经验：虽然知道要小步前进，但具体怎么做？他会在**架构设计阶段**先用**单线程**，用一个**智力比较高的模型**跟它讨论。

讲者强调这很重要，因为：**如果软件设计不好，后面就是无穷迭代**。他提到第一次课展示过这个例子：他会把**组件库的接口定得非常好**。接着他准备展示一个例子，说明他为什么信任 AI 的代码：项目里有很多**互相关联的组件**，程序会运行、会产生结果。

**（整理者串联）**因此，讲者的思路是：先固定架构和接口，减少后续无穷迭代；接口稳定后，才更容易信任 AI 写出的实现与维护代码。

## 为什么讲者信任 AI 代码：架构把接口和共享状态压到极小

讲者解释自己为什么信任 AI 写的代码。这个项目里有很多互相关联的组件：程序运行会产生结果；拖动进度条不仅关联到程序编辑器，还关联到上方/其他可视化区域。讲者的处理方式是：

1. 把绝大部分接口设成 **functional de**（原词；随后讲者解释为 **pure function**）。连 **trace** 也是程序的一个 pure function。
2. 有一个标准的程序 **DERVISION graph**（原词如此；疑似 derivation graph，未确认），要求 agent 按这种方式展开。
3. 所有全局互相影响的状态都注册到一个全局地方。比如光标位置怎么影响可视化，包括菜单条，都收进这个非常干净、非常小的状态里。
4. 因此这个 **playground** 的核心共享状态只有十几行，组装也只有十几行，剩下所有东西都是黑盒子。
5. 讲者直接要求 agent 在设计 **visualization** 时禁止看任何库函数的实现，只看接口。

结果是花费很省：上下几万个 token 就能做出一个这样的 playground。

## 多 agent 协作：不调视觉模型/浏览器，人放另一块屏实时验收

架构设计完成后，讲者会开三个（或几个）terminal/agent。他的 **agent.md**（原词：agent点MD）里有明确协作规则，讲者说可能后来改过一些内容。

规则和做法包括：

- 不需要调用视觉模型去检查；讲者说 AI 很喜欢做这件事，会花很多很多 token。
- 也不调用浏览器任务。
- 讲者在旁边另一块屏放一个浏览器，浏览器实时刷新，他肉眼观察。
- 他开始开三个 agent，哪里不满意就骂他；肉眼看着右边那个东西不停地变好，最后问题解决。
- 讲者判断：这是一个 agent 能力范围之内的项目。

## agent 能力继续增长：更多项目会被“轻量讨论 + 剩下完成”，但版本控制会成为问题

- 讲者非常确信：agent 能力会不断增长。
- 因此越来越多项目能被 agent 以这种方式完成：先比较轻量地讨论，然后剩下部分由 agent 完成。
- 讲者认为这是一件非常可怕的事情。
- 他留下问题：如果 agent 快了 1000 倍，我们还怎么管理版本控制？下一节课再讨论。
