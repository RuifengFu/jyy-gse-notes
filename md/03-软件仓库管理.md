## 1. 模型会持续变强，但现阶段学基础仍能解锁 AI 的创造力

<small>▶ [00:00](https://www.bilibili.com/video/BV1kybV6DE47?t=0)–08:58　·　开场　·　话题：GPT-6与还要不要学</small>

- **GPT-6 更省 token，但品味未到位，代码更难读** 讲者实测更省 token，编程提升有限，写出的代码越来越紧凑。
    - 前几课讲过把 AI 接进生活流程：告诉它真实意图，它就挡掉不顺心的事，还能蒸馏成 skills。GPT-6 是这个过程里的新进展。
    - 讲者用过 GPT-6 后觉得还是有惊喜，各方面能力都提升了。
    - 有经验、有品味的工程师能指导 AI 把东西做得更好。GPT-6 还没学会这种品味。
        - **自嘲** 因为品味不够，讲者还得骂它：「我经常还要骂他所以我觉得我可能还能再苟活个几个月」
    - 做复杂任务时更快，讲者特意测量过，确实更省 token。
    - 从 GPT-5、5.6 到 6，代码依次更紧凑，人没法 review。讲者猜可能和思维链变短有关，不确定。
    - 以前会用 prompt 要求 AI 写符合人类工程规范的代码。现在讲者觉得不会再看 AI 写的代码，只要它把代码弄对。
    - **吐槽** 讲者对读不懂的 AI 代码干脆摆烂：「所以就随他去吧他反正能把代码弄对」
- **AI 会漂移，因为人的意图空间是开放的** 同一个任务在每个人脑中都不同，AI 无法与人脑直接对齐。
    - 意图空间，指人脑中对一个任务的各种想法（整理者补充）。讲者认为 AI 做不好，是因为面对这个开放的空间。
    - 例：「给我做一个国民级应用」，哪怕是顶级产品经理，脑中想的也各不相同。AI 因此按自己的方式漂移。
- **GPT-6 数学先行，带来空间感知，机械臂已达 SOTA** 讲者推测 OpenAI 先学数学，再用强化学习学其他能力。
    - 讲者认为 GPT-6 给的最大惊喜，是空间感知和理解能力。
    - **数学是最容易 grounding 的语言。**
        - 讲者说数学是人类世界里最难的一种语言。现在数学已经被学会了。
        - 数学有全球共识的推理系统。定理能否证明，全球的判断一致。这与软件工程里意图和规约的差距方向相反。
        - 数学逻辑能解释日常行为。中午吃什么，大脑在各因素间投票：义父楼订饭最快，下午要开会，时间够还能小睡。
        - 「做了 A 就会做 B」这类推理，对应离散数学里的命题逻辑。
        - **吐槽** 讲到午饭，转头对着学生：「你们马上就会面临这个问题了去挤食堂」
    - 空间感知不是学不会。从简单任务开始强化学习就能做到。例：鲁班锁里第一块往哪个方向抽，骰子对应哪个展开图。
        - 一些 benchmark 里也有这类题：给立方体或怪形状的投影，问哪一块与它相同。
    - **GPT-6 在 3D 打印上超出讲者预期。**
        - 讲者团队已做了小半年 3D 打印。GPT-5.6 空间感知差，也能通过对话生成像样且符合规范的模型。
        - 光栅玩具左看、右看是两个图案（字幕原文：光栅尺、光产纸，待确认）。此前要靠很长的搜索树，GPT-6 昨天 one shot 搞定。
        - 团队还在想怎么应对这个变化。
        - **自嘲** 看到鲁班锁的例子时 GPT-6 还没发布：「我就心疼我的这个PHD Student因为我们已经做了小半年的这个3D打印的工作了」
    - **GPT-6 能控制机械臂抓取、叠衣服。** 发布第二天，小红书上就有人展示。GPT-6 是语言模型，有视觉，逐帧被问下一步做什么，没做提示词工程，已达 SOTA。
        - 讲者认为有了空间感知加数学能力，GPT-6 在具身领域明显能做好。
    - **玩笑** 说完「模型一定会进步」：「也许在我上课上到某一次的时候我突然就可以说这个课不用上了呵呵」
        - 讲者接着说这样也好，大家就可以去做产品了。
- **现阶段仍要学基础，学了才能解锁 AI 的创造力** AI 解锁的是执行力。讲者答案是要学，但以后怎么学暂时不知道。
    - 起因：有人问讲者，AI 时代还要不要学数据库、操作系统。讲者对答案不确定，所以打了汽车的比方。
    - **汽车类比：门槛会随技术成熟而消失。**
        - 100 多年前汽车开 12 km 就出故障，每个司机都必须懂原理。对应今天要学 computer science、操作系统、数据库。
        - 今天在地下车库说「帮我开到某地」，自动驾驶就出发。人不理解整个系统如何工作，也能开车。
        - 自动驾驶最终的动力仍传到机械装置，这点和 100 多年前的汽车有些相似。
        - 但中间经历的一切，人都不需要知道，就能把车开起来。
        - AI 像汽车但更强，替代的不只是腿，还有人的智力。
    - 至少现阶段，理解正确的概念有好处。讲者欢迎学生讨论以后怎么学。

> 原话：「我今天答案肯定是要学，因为你们学了以后，可以更好地解锁这个AI的创造力」

## 2. 软件是需求在信息世界的投影，落地成一个带文件的目录

<small>▶ [08:58](https://www.bilibili.com/video/BV1kybV6DE47?t=538)–17:11　·　转向　·　话题：项目就是一个目录</small>

- **项目从新建一个目录开始，目录里的文件合起来就是可交付的东西。**
    开发者先建目录并起名，再开始 vibe coding。这堆文件最后变成产品。
    - 做作业时，起点是从课程网站下载的文件。做自己的项目时，第一步是新建目录，名字可以是中文，例如「我的最酷的 game」。
    - 面对空目录，开发者知道该放什么文件。这是因为看过老师上课打开的工程，或看过 GitHub 链接里的文件列表。开发者是不经意间记住的。
    - 老师或同学推荐的 GitHub 链接，打开是对人类友好的网页。网页上能看到文件，开发者就知道目录里要有文件。
- **只在 localhost 跑通不算交付，因为别人打不开**
    localhost 指本机，只有自己的电脑能访问。要让全世界看到，得在 intent 和 specification 里写明。
    - 目录可以在本机直接运行。开发者让 agent 运行，窗口或网页就会弹出来。
    - **玩笑** 讲者引用一个著名笑话，讽刺只能在本机打开的「产品」：「GPT-6太牛逼了，我又做了多少个killer级的产品，他们是 http localhost 下的 5137，然后发一个 twitter」
    - 如果不写明，GPT 可能把你当成开发者。开发者通常先起本地 development server 调试，ready 之后才推到远端。
    - 这些都是知识，计算机系学生会在各门课里反复学。
- **软件是需求在信息世界的投影，今天落地成带文件的目录。**
    标准定义是代码、文档和一切相关东西的集合。讲者的说法更短：目录里有各种东西，就这些。
    - 目录里有 hello.c，能编译出 hello，就已经在做软件。
    - 学编程的路径：先在 VS Code（字幕原文：WHCV，待确认）里一键编译运行，大二再用 GCC 把 hello.c 变成 hello binary。build 目录里的东西都由命令行工具创建。
    - 这种做法不符合现代最佳实践，但 10 年前大家就是这样做的。
    - 讲者说，以前老先生喜欢问学生什么是软件。
    - 软件是如此基础的东西，到处都有它。
    - **玩笑** 讲者讲完这个定义，补了一句收尾：「目录里面有各种各样的东西，ok that's all」
- **U 盘和邮件都管不好项目，git 能保存、比较和恢复历史。**
    git 除了保存目录，还保留历史版本，可以比较和恢复。细节后面展开。
    - **U 盘丢代码的故事说明，没有版本管理，代码随时会丢**
        - 讲者 2012 年入学南大的第一个博士生，大一常去机房，因为自己笔记本屏幕小。
        - 讲者说，现在大家应该会买块屏幕，二手的只要几百块，宿舍就能有很好的编程体验。
        - 那时的标准答案是去机房，屏幕没有那么便宜。
        - 来回拷贝代码麻烦，他把代码存在 U 盘上。
        - 讲者说，大家多半也干过这事，比如中学上电脑课时，把作品存在 U 盘上。
        - 大二 U 盘坏了，代码和启蒙时期的作业全部消失。他有点伤心，但没有太大关系。
        - **玩笑** 讲者转述学生丢作业后的心情：「他珍藏的那些，启蒙的时候的作业不见了，有一点伤心，但是好像也没有太大的关系」
        - 讲者说，自己很长时间也是这样管理代码的。
    - 讲者上学时交作业的方式是打压缩包发邮件。现在是在网页上传。
    - 讲者说，谈软件工程时，今天有标准答案：用 git。
    - 有了 git 以后，讲者再也不需要发邮件。他很难想象过去是靠邮件管理项目的。
    - **玩笑** 讲者说起 agent 时代，自己用 codex 时选择完全信任：「我有了十倍一百倍的生产力提升，我真的选择信任他，我真的就不管了，这事就过去了，我甚至看都不会看，我让他结束以后把这个浏览器给关掉」
    - **git 让作业分发变简单**
        - 学生用 git clone 从远端获取作业。
        - 作业更新时，讲者在上课时告诉学生用 git pull 下载，不用给每人发压缩包。
        - 讲者的 mix submit 脚本把包打好，自动上传课程网站。这类似 CI/CD，讲者计划专门讲一次。
- **讲者顺带讲了 2 件和主线无关的事**
    - 软件无处不在：没有软件，教室屏幕是黑的，升降桌也升不起来，桌上显示高度 106 厘米。
        - **玩笑** 讲者指着教室里的升降桌即兴说：「你看，如果没有软件，我这个升降桌都是升不起来、降不起来的」
    - 学习变容易以后，讲者说这门课上讲的知识都不重要。他几乎每节课都会讲这个话题，后文接着展开。
        - **玩笑** 讲者抛出这句反讽式的结论：「当我们今天学习变容易了以后，这门课上讲的知识都不重要」

> 原话：「软件是人类世界的需求在信息世界里的一个投影。」

## 3. 学习靠注意力：先自己想一遍，再对照好项目找差距

<small>▶ [17:11](https://www.bilibili.com/video/BV1kybV6DE47?t=1031)–24:31　·　转向　·　话题：从好项目里学细节</small>

- **学习要靠自己留意项目细节，不能只做老师交代的事**。不同项目的文件和文档写法各不相同，这些信号累积起来，就能判断该怎么用 git。
    - 讲者问学生有没有留意过，有的项目有某个文件，有的项目没有，有的项目文档这样写，有的那样写。
    - **带着中学听老师话的心态上 GitHub，只会拉作业**。这样的学生像被强化学习训练过的 AI，只做被交代的事，因为这样最省时间。
        - **吐槽** 对着只拉作业的学生：「你就有点像 AI，有点像今天干活的 AI，你被强化学习成了一个当老师说让你做这件事的时候你只做这件事，绝对不会多碰一点点的，因为这是最省时间的。」
        - 讲者解释：中学时老师交代的事太多，不听话就做不完。
        - **玩笑** 模仿这种心态：「老师说好你去把作业拉下来」。
    - 讲者建议多花一点点时间点进项目里看，可能会灵光一现。
- **对照好范例才会写文档，AI slop 是反面教材**：老项目的 README 很短，链接够用。路牌对比让讲者学到要站在用户角度设计。
    - 现在 GitHub 上的项目多是超长 README，带 Unicode 字符画的目录结构框图，有 AI slop 的感觉。
    - 一个维护了几十年的老项目，README 很短，看完后想看的东西只要点三个链接，文档该这样写。
    - **香港和南京地铁的路牌对比，让讲者学到 UI 该怎么设计**：
        - 讲者说多年前在香港，对路牌设计印象特别深。
        - 香港的地下系统很复杂，每当前方有三个口等不确定处，正前方一定有路牌说明。
        - 南京的地铁站里，找接下来要走哪个口，需要环顾四周，甚至走远去找地图。
        - 讲者由此谈到中国被称为发展中国家，意味着提升空间很大。
        - 有比自己做得好的范例，对比中就能学到一课。
        - 讲者由此得出：UI 要想用户站在页面上想什么，不同人要 A、B、C，用最少的方式全部呈现。
    - 看过几个好 README 后就会写。讲者说可以直接问 AI，这个 README 为什么没有 AI slop 的感觉。
    - **吐槽** 对着只会让 AI 写 README 的学生：「你们都会用 AI 生成 slop README，但当你看过几个好的以后，你就会写 README。」
- **课外的信息密度已超过课堂，要靠注意力吸收**。成熟项目是工程师十几年的心血，传统教学没教过怎么用好这些信息。
    - 同学怨气大、觉得上课耽误学习，原因是课外的信息量和信息密度已远超任何课堂。
    - 成熟项目背后可能有过一次崩溃和大版本重构：工程师发现旧 practice 不够好，才呈现出现在的样子。
    - 讲者说学生也没准备好去拥抱这样的知识。
    - 讲者说学生要训练的，是一眼看到东西就能快速判断的注意力。
    - **自嘲** 讲到训练注意力时：「可能为什么我现在在做老师，就是因为我有这种惊人的注意力。」
- **先自己想一遍再对照，是读论文和学课程的通用方法**。与作者一致说明已掌握，对方更好就吸收，自己更好是难得的正反馈。
    - 看到东西前先忽略它，想自己会怎么解，再比较谁更好。自己更好就算 slop，对方更好就问为什么。
    - 这个习惯让人随时从外面接收信息，讲者称为「非常恐怖的习惯」。
    - 讲者说早先有人推荐过读论文的方法，当时还展示了 AI 被注意力机制带进作者逻辑陷阱的例子。
    - **读论文时先在脑中把问题做一遍，结果有三种。**（也适用于高等数学、计算机系统基础）：
        - 讲者称这种方法为 virtually implement。
        - 与作者一致：已完全掌握。
        - 作者的方案更精巧简洁：想他为什么想得到，它就成为你知识的一部分。
        - 你的方法更好：可能 1 万次才有 1 次，但正反馈很大，会想去做点好玩的东西。
        - **玩笑** 讲自己的方法比作者更好：「还有一种情况那就真的是惊喜中的惊喜，你的方法比他还要好。」
    - AI 时代更要对细节保持注意力：读各种 git 仓库、别人的东西、AI 生成的东西，都要感知细节。

> 原话：「如果我发现他做的比我好，我就很惊喜，说诶这个他为什么做的比我好。」

## 4. git 的设计都能从真实需求推出，冲突时要把信息给全

<small>▶ [24:31](https://www.bilibili.com/video/BV1kybV6DE47?t=1471)–35:01　·　进一步　·　话题：从需求推出git</small>

- **学生答不好 merge 冲突，因为没亲手遇到，也没留意** 讲者上周末面试推免生。多数人能说出 git 分发代码和目录快照，冲突后看到什么却答不出。
    - 讲者说在座学生一两年后也会来这个场合面试。
    - 讲者问「什么是 git」，学生多少能答两句：可以下载分发代码，也能管理项目目录的快照。
    - **玩笑** 讲者说评估答题的方式时：「我觉得你没有必要把所有人都挂掉」
    - 讲者对 git rebase 的回答情况在意料之内（字幕原文：get it rebase是20，含义待确认）。意料之外的是 merge 冲突后会观察到什么，大家答得不好。

## 5. 会用命令只是冰山一角，水下是靠追问 AI 得来的最佳实践

<small>▶ [35:01](https://www.bilibili.com/video/BV1kybV6DE47?t=2101)–63:32　·　举例　·　话题：git实操与最佳实践</small>

- **git 的基本命令几步就能学会，推荐用法是每改一次就提交一次**。init、add、commit 三步就得到快照。但讲者强调不能把 git 当成「作业V1、V2、V3」来用。
    - git init 后，项目里多出一个默认隐藏的 .git 目录，项目就成为 git 管理的仓库。开始时终端会弹出一些奇怪信息，讲者说可以让 agent 解释，也可以忽略，前者学得更高效。

## 6. git 是持久化的目录树，新版本只复制改动到根的路径

<small>▶ [63:32](https://www.bilibili.com/video/BV1kybV6DE47?t=3812)–78:23　·　进一步　·　话题：git底层：持久化目录树</small>

- **git 的新版本只复制改动到根的路径**。没改的文件和目录用指针指回旧节点，所以每个版本的增量很小。
    - git 是持久化的数据结构，持久化的对象是目录树。因为项目就是版本一、版本二、版本三这样不停推进的快照。
    - **例子：V1 只改 B.txt，生成 V2。**
        - V1 的根下有 A.txt、B.txt 和目录 D，D 里有无穷多个文件。
        - 不需要把所有文件复制一份。
        - 新建一份 B.txt 的新版本，再复制它到根的路径。
        - 新根里的 A.txt 和 D 用指针指回旧节点。
        - 新根不能指向旧 B.txt，否则读到的还是旧内容。所以到根的路径都要复制。
        - **吐槽** 讲者在黑板上画 D 的指针连线，说：「虽然不太好看」
    - **项目有 100 万个文件，增量也很小，因为目录不会很深。**
        - 没有人会建 1000 层深的目录。
        - 从渐进式披露的角度，也没有必要建很深的目录。
        - 每一级索引的文件数呈指数增长，几层就能分完。
    - 从 first principle 出发，一个大学生完全有可能自己设计出这个结构。
- **git 由 commit、tree、blob 三类对象组成**：每个对象是带 hash 索引的普通文件，整体是只向后生长的数据结构。
    - .git 目录里有各种 objects，每个 object 是一个节点。
    - 三类对象：commit object 是提交节点，tree object 是目录节点，blob object 是文件节点。
    - blob 是 binary，也就是字节序列。
- **纸面讲解不够踏实，要用可视化工具看真实的 git**：讲者先用 Learn Git Branching，再用 vibe coding 自己做了真实仓库版。
    - 纸面讲完还有疑问：分叉之后合并会发生什么。分叉的做法是从 V1 另建一棵 tree，记作 V1'。
    - **玩笑** 讲完纸面讲解，模仿学生的怀疑：「我们的 git 真的是这样实现的吗？老师上课说这个 commit object、tree object、blob object，真的有这样吗？」
    - **玩笑** 接着说想看可视化，网上一定有人做过：「根据计算机科学定律，你想要的东西就一定有人做」
    - **Learn Git Branching 用动画模拟命令，讲者称它是「古法编程的巅峰之作之一」。**
        - 讲者以前上课也会用这个网站。
        - 输入 git status，显示有文件改了。
        - 输入 git commit，右边动画多出一个版本。
        - 输入 git checkout 并点某个版本，能看到版本的变化。
    - **讲者用 vibe coding 做了真实仓库的可视化工具，提示词有 4 条要求。**
        - 实现一个 git 可视化命令行工具，对象是真实的 git 仓库，可以调用 git 命令。
        - 任何对象都从文件系统里的真实文件读出，从原始字节出发，展示一步步如何解析。
        - 持续监听目录中 git 的变化。
        - 变化发生后用动画展示仓库的变化。
    - **这个工具和 Learn Git Branching 的区别：后者是模拟，建了一个 git 模型，这个工具直接看 live 的仓库。**
        - GPT-6 有视觉能力，但一遍直出仍然产生了一些 AI slop。
        - **吐槽** 讲者点评这版成品：「GPT-6 虽然他有视觉能力，但是一遍直出还是产生了一些 slop 的」
        - 对象之间的连线视觉效果不完美，因为是 one-shot 直出，没有调。
        - 讲者认为再发一个 prompt 能去掉一部分问题，对话几轮可以得到近乎完美的可视化。
    - 讲者认为 vibe coding 的质量还没有那么好，但今天已经可以直接做这类工具。
    - 讲者说学生有时间的年纪，最大的乐趣可能就是 vibe coding（字幕在此截断）。
- **演示里每个概念都对应磁盘上的普通文件**：blob、tree、分支和 HEAD 都能在 .git 里看到原始字节。
    - 演示删除工作区文件，右边的文件树同步消失。
    - main 分支最早的提交是「I did some cool stuffs」，里面有一个空的 hello.c，内容来自 .git/objects 下的对象。
    - **blob 就是文件内容的字节序列，工具能解压并显示。**
        - 小文件压缩反而浪费：31 字节解压出 23 字节。
        - 文本 blob 大小 15 字节，内容是 int main。
        - hello 可执行文件的 blob 大小 158 字节，开头是 7F ELF 文件头。
    - **tree 记录目录里每一项的权限、名字和指向的对象。**
        - tree 在磁盘上 52 字节，解压出 43 字节。
        - 每一项有 mode 644、name hello.c，指向对应的 blob。644 代表文件访问权限。
        - 该版本的目录有两个文件：hello 是 755，可执行；hello.c 是 644。
    - **分支是指针，HEAD 是指向指针的指针。**
        - 工具创建 A、B 两个分支，左右两边的动画实时同步。
        - refs/heads/A 是一个文件，分支就是指向提交的指针。
        - HEAD 在磁盘上也是几个字节，指向分支。
        - A 分支指向的 tree 里有新版 hello.c，内容是 int main void。B 分支同样指向自己改过的版本。
- **冲突时 index 里悄悄保存 base、ours、theirs 三个版本**：工作区只显示带尖括号标记的合并结果。
    - 冲突场景：团队里两个人都对同一段代码不满意，各自重构。A 在这，B 在那，把 A 拉到本地就进入冲突状态。
    - **玩笑** 讲者描述冲突怎么来的：「你和你的团队成员每个人都对这个代码不爽，你们两个都重构了」
    - 工具展示冲突现场：未提交区的 index 里，hello.c 有三个版本，叫 base、ours、theirs（字幕：贝斯、hours）。平时看不到。
    - **玩笑** 讲者说 git 在 index 里偷偷存了东西：「git 悄悄的在这里面留了三个版本」
    - 工作区的 hello.c 是带尖括号冲突标记的版本。
    - 点 resolve 后，临时文件消失。merge 创建了新的 commit object，有两个 parent，也有 author，指向关系被正确保留。新 commit 的 tree 选了其中一个版本（字幕不清，待确认）。

> 原话：「所谓的分支就是指向这些东西的指针，然后 head 是指向指针的指针」

## 8. 约定俗成的规范保证一致性，AI 能替你把细节守住

<small>▶ [86:18](https://www.bilibili.com/video/BV1kybV6DE47?t=5178)–93:47　·　回到　·　话题：规范让协作一致</small>

- **规范让协作一致，AI 能替人守住这些细节** 提交格式和文档排版的约定，让团队用同一种方式书写。项目变大后也是如此。
    - **AI 提交信息混用了中英文。** 前面的 commit message 是英文：一行标题加详细解释。后来 AI 自由发挥，混进中文，但仍保留 scope、总结和 message body 的结构。
        - **吐槽** 看到 AI 混用语言后：「其实 AI 还是挺 slop 的」。
    - Conventional Commits 是一份很短的公开规范。提交必须带类型前缀，例如 feature、fix。前缀后要有冒号和一个空格。
    - **中文和英文之间加一个空格，是 markdown 文档里通行的约定。** 讲者不知道何时流行，但已成肌肉记忆，例如「你好 hello.c」。
        - 同一文档里有的加、有的不加，最让讲者难受。只要前后一致，他就认为作者在遵循某种约定。
        - **吐槽** 讲到和同学合作时：「高血压时间还是比较多的」。
        - **吐槽** 看到文档里加空格不一致时：「我看到这个时候我就是浑身难受」。
        - **吐槽** 说到这类不一致：「我真的是有点头大」。
    - 代码要以同样方式排版，文档也一样。这样人维护起来更好。
    - 讲者认为 AI 时代这些细节可能没那么重要，因为 AI 会处理。他说用 AI 的学生都不会生成这样不一致的 slop。
    - 讲者说自己还是很喜欢 AI。
- **提交要小而及时，每个 bug 才能追到对应的提交** 提交越小，越容易审计，也越早有远端备份。
    - 在复杂项目里，改动越多，出错的可能越多。
    - 小项目刚开始，一次提交两三千行没关系。项目有了错综复杂的关系后，一个大提交可能同时破坏多处，引入多个 bug。
    - **大提交会让 bug 无法归因。** 例如 V2 有一个 1 万行的提交，之后修了 100 个 bug。这 100 个 bug 都算在 V2 头上，可能修不过来，也不知道 V2 是否修好。
        - 每次提交只做一个修改，bug 就能对应到引入它的提交。修复和引入两个提交可以配对，这就是审计能力。
    - 小提交也是备份。电脑物理损坏前，如果已做小提交并立即 push，互联网上就有一份备份。
        - **玩笑** 说起电脑随时可能损坏：「你的电脑马上坏了也好」。
    - 这些网上的 best practice 文档，都来自工程实践的经验。
    - 讲者让听众回去读网上的 best practice 文档，例如 commit often（字幕原文：commitOftenperfect leader published ones，待确认），并让 AI 帮忙读。AI 清楚 review、revert 和 git bisect 的用法。
- **gh 让 agent 管理 git 之外的 issue 和评论** GitHub 上的 issue 和代码评论不随 git 保存，所以需要命令行工具。
    - GitHub 太流行，所以值得做 gh。它能 fetch issue、找出 assign 给自己的 issue（需先登录），也能 close issue。
    - agent 会尝试调用 gh 或 GitLab 的命令。命令出错时，agent 退回手写 git 命令（字幕不清，待确认）。
        - **玩笑** 调侃听众的注意力：「你们如果还有惊人的注意力」。
        - **玩笑** 讲到 agent 失败后的表现：「他又回退到古法编程」。
    - **做法：装好 gh 后，在 agent 里设一个很长的任务。** 讲者要求 agent 小步提交、可审计，并规定分支规则和线性历史。
    - hook 和 CI 讲者说后面可能会讲。
- **项目应组织成用原子变更推进的快照** 这是讲者要求听众今天记住的结论。这门课讲的仍是软件工程。
- **讲者顺带讲了 3 件和主线无关的事** 讲者的时间有限，今天讲的 best practice 还有很多。
    - **自嘲** 开场说自己学习时间有限：「我马上就要淘汰了」。
    - 今天表面讲 git，讲的是 best practice，这样的 best practice 还有很多。
    - 讲者的项目从他开始写代码起就有大量小提交。他很多时候不去管这些提交。

> 原话：「如果你每一次的 commit 都是很小的，都只做一个修改，那冤有头债有主。」

## 9. 项目管理就是把需求拆成可审计的原子快照，并先定好架构

<small>▶ [93:47](https://www.bilibili.com/video/BV1kybV6DE47?t=5627)–100:16　·　因此　·　话题：原子快照与架构先行</small>

- **项目管理就是把需求拆成可审计的小快照** 人处理不了一团混沌，所以要一小步一小步推进。
    - 分支让开发者随时尝试：失败就扔掉，成功就合并，也可同时推进多条主线，互不干扰。
    - **玩笑** 说到同时改几处容易改乱时，讲者提到大作业：「如果你们做大作业自己是古法做大作业，肯定有这个感受」。
    - 任务拆小后，出问题可用 git bisect，协作时可用 git blame。
    - 小提交建在同一公共祖先上，冲突时能知道是哪个小提交，其余部分更容易合并。
- **现阶段强制线性历史更好** 因为 AI 做 rebase 和解决冲突都容易，讲者强行要求提交历史线性。
    - 更严肃的项目也会要求主线保持线性历史。
    - 合并提交可以有两个祖先，历史会分叉又合并，这是典型的 git 结构。
    - 线性历史更易追溯，对 cherry-pick 和 git blame 更友好。
    - 这不全是好处，但在无限大能力的模型到来之前是好的。
    - 提交拆得好，AI 找得到修改的引入者，维护效率更高、更省 token。
    - 有些文件 AI 因此可以不用去读。
- **先用强模型单线程定架构，后面才不会无穷迭代** 软件设计不好，后面就要无穷迭代。
    - 讲者在第一次课就展示过这一点。
    - **纯函数接口加十几行共享状态，让 AI 能放心写。** 以可视化 playground 为例：
        - 讲者信任 AI 写的代码，是因为组件库的接口定得非常好。
        - 项目里有很多互相关联的组件。
        - 拖动进度条时，要同时关联程序编辑器和可视化部分。
        - 绝大部分接口是纯函数，包括程序的 trace，另有标准的 derivation graph（字幕原文：DERVISION的graph，待确认）。
        - 全局互相影响的状态注册到一处，如光标位置对可视化的影响，菜单条状态也很小。
        - 核心共享状态十几行，组装十几行，其余是黑盒。
        - 禁止 agent 看库函数实现，只看接口，几万 token 就写出这样的 playground。
- **架构定好后并行开几个 agent，人盯效果** AGENTS.md 写明协作规则，agent 各自推进。
    - 讲者开三个 terminal，各跑一个 agent。
    - **玩笑** 讲者在屏幕上找 AGENTS.md 时即兴说：「我看看在不在」。
    - 规则：不调视觉模型检查（agent 爱做且费 token），不调浏览器任务，改在另一块屏放浏览器即时刷新。
    - **吐槽** 讲者说 agent 爱做视觉检查：「很喜欢做这件事然后花很多token」。
    - **吐槽** 开三个 agent 后，讲者对着右边屏幕：「哪里不满意就骂他」。
    - **玩笑** 讲者描述骂 agent 的效果：「你就可以肉眼看着右边那个东西不断的变好变好变好变好变好」。
    - 讲者肉眼看着右边的页面不断变好，问题最终解决。
    - 这是 agent 能力之内的项目。讲者确信 agent 能力会增长，越来越多项目能这样完成。
    - agent 快 1000 倍后怎么管理版本控制，讲者称「非常可怕」，留到下一节课。

> 原话：「项目管理的本质是人类没有办法处理一团混沌」
