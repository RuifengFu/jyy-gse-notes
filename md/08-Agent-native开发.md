## 1. 长任务靠算力换智力，需兼顾搜索宽度与深度

<small>▶ [00:00](https://www.bilibili.com/video/BV11LWw6VEHW?t=0)–05:48　·　开场　·　话题：算力换智力的搜索</small>

- **长任务靠算力换智力：agent 能完成长任务，但解题直觉偏弱。** 实验二在个人 agent 的基础上把这一点往前推一步。
    - 今天早上额度 reset（宣布方字幕原文：TEO，待确认）。讲者攒了耗 token 的任务，例如一个不知道怎么证的数学证明，可能跑完一周额度。
    - 讲者离开办公室前设一个 goal（字幕原文：go，待确认），让 agent 继续证明。
    - **实验一是个人 agent，实验二以讲者自用的 Clawdbot 为例。**
        - Clawdbot 在开课前发布，最近才火。
        - 学生做个人 agent 时会发现，有些产品已经发布了。
        - 讲者把每天的 job 迁到它上面，背后调用 Opus 5.5。
        - 每天给小朋友生成一个 podcast，开车时听。
        - 每天推送 morning paper，例如 CSPR（待确认）论文。prompt 经讲者调过，结果与直接让 AI 总结不同。
        - 还推送 GitHub trending（字幕原文：github training，待确认）。
    - 实验一的 agent 做过邮件 digestion，也根据数据库回答问题。
    - 实验二把算力换智力往前推进一点。
    - 讲者说 agent 能做长任务，但解决问题的直觉稍差。
    - **吐槽** 讲 agent 直觉差时：「有的时候我觉得这跟我们的博士生很像」
- **深度优先能做好一个问题，但模型偏浅层，搜索要兼顾宽度与深度。** 算力有限，宽度和深度要一起算。
    - **博士生做研究像深度优先搜索。**
        - 学生想到合理的 idea，先做原型，再优化，再改进实验结果。
        - 例如 Python 代码补全这类很窄很深的问题，可以做好。
        - 讲者对学生说：这样做时，你其实在一个很大的 design space 里找到了好解。
    - 强化学习只在最终完成任务时给奖励，模型因此停在设计空间的浅层分叉，宽度有限。
        - 讲者说人类的训练和模型的强化学习稍有不同。
        - **玩笑** 讲模型的训练方式时：「最后完成任务他就给奖励，像巴甫洛夫的狗一样」
    - 不同方案对最终结果影响大，所以需要宽度优先的搜索。
- **让 GPT 和 Claude 互相挑刺，比单个模型一路走到黑更有效。** 两个模型带有不同偏见，可以互补。
    - 实验里学生要自己做一个 agent loop，loop 有参考可循。
    - Humanize（字幕原文：HUMHUMANIZE，待确认）烧 token 试 multi agent 协同。讲者在他们的群里潜伏。
    - **玩笑** 讲自己关注 Humanize 时：「因为我一直潜伏在他们的群里」
    - 他们发现最有效的方式是让 GPT 和 Claude 互相 review。
    - 类比人的多样性：同类的人容易很快达成共识，所以要找两个互补的人。
    - 单个模型一路走到黑会岔开，两个模型挑刺几轮后可能找到更好的 solution。
- **深度调研要把更多知识放进知识库。** 实验一已建了自己的 database。
    - 实验二要放入研究论文、博客、GitHub 项目和书中片段，并写进 report。
    - 不只放实验作业，还有过去的奖学金申请和个人简历。
    - 实验较开放，框架可以实现得很简单。
- **讲者顺带说了实验可以摆烂，但亲手看过 agent trajectory 有第一手经验。**
    - 今天课程过半，主题是 agent native 开发怎么做。
    - **自嘲** 讲实验可以不做时：「实验我一直说实验，你是可以选择摆烂的，你直接不做可能也能 OK，最后这个课也就这么过去了」
    - 做过实验、有第一次经验、真正观察过 agent trajectory 的人，会有不同体会（句子在 05:42 处中断）。

## 2. 软件工程就是在意图到实现的空间里逐步收敛

<small>▶ [05:48](https://www.bilibili.com/video/BV11LWw6VEHW?t=348)–10:55　·　转向　·　话题：软件工程是空间收敛</small>

- **软件工程是在意图到实现的空间里逐步收敛** 意图到规约、规约到实现都是一对多。人脑容量有限，只能靠讨论缩小范围。
    - 意图空间里有很多点，个人或小团队只采样其中一个点。
    - 评审者与开发者来回讨论几轮，达成共识，收敛到下一层的一个点。
    - 需求阶段用访谈和 checklist 与甲方对齐。甲方越清楚自己要做什么，意图越清楚。
    - 规约阶段与有经验的架构师讨论，例如是否用 event sourcing。有开发者（字幕原文：pad，待确认）最近公开表示不用，改用另一种 functional design，需要 persist everything。
    - 多方案收敛出的实现，与一条线走到黑的实现相比，可维护性、可观测性差「十万八千里」。
- **UML、IDE、git 这些工具都在约束这个空间** UML 建模让人在项目早期就达成一致。
    - 工具包括 IDE、VS Code、git worktree，讲者说还有无数种。
    - 建议：让 agent 每天推一个 GitHub trending 项目，每天花几分钟追问，提升技术积累和品位。
        - 每天看下来，会发现每个项目都用了不同的技术栈，里面有很多好东西。
- **AI 让人随时生成版本，边想边比较** 人不必想清楚再动手。
    - 任何阶段，哪怕只有一个想法，都可以让 AI 往下做。AI 可能做不深，最后变成 AI slop，维护不下去。
    - 讨论中随时生成版本，比较趋势是变好还是变坏。变坏就再讨论，再生成一版。
    - AI 承担的是一个员工，甚至一个团队的职责。
- **并行 agent 和低成本原型，让人先实现再发现问题** AI 成本足够低时，先让它实现，用来预测问题。
    - 需求能分成两个 subsystem、模块划分得好，就能并行启动 agent。
    - 讲者在 tmux 里把窗口分成四份，跑四个 agent，人负责监工。最多开四个，再多大脑跟不上 AI 的输出速度。
    - **自嘲。**「我最多只能开四个并行，不然我大脑就有点跟不上这个AI输出的速度了」
    - 并行 agent 让讲者能在搜索空间里快速探索，同时推进并行的需求。
    - 讲者把这种思路概括成一句口号，字幕作 let it feel，待确认。
    - 架构在用户变多后会怎样，两个模块之间有没有未想过的交互，很多问题实现出来才发现。
    - 没想清楚不要紧，先让 AI 搓一个，再用自己的 use case 检验（字幕在此中断，整理者补充）。
    - **玩笑。**「我现在没想清楚不要紧，你给我搓一个」

## 3. agent 本质是 while 循环加 bash，一百五十行即可

<small>▶ [10:55](https://www.bilibili.com/video/BV11LWw6VEHW?t=655)–21:49　·　因此　·　话题：150 行写出 agent</small>

- **早期 coding agent 受幻觉拖累，业界只能观望** 2023 年的模型幻觉问题突出，也没有思维链模型。
    - 2023 年社交媒体上有人提醒，模型很强但不能完全相信。
    - Devin 是最早一批 coding agent，号称能自主完成任务、解决数学问题。
    - 当时的 GPT-4 说着说着就不知道在说什么，也没有 o1 一类的思维链模型（字幕原文：欧冠，待确认）。
    - 理论上，模型若是不知疲倦的永动机，就能对一个任务无穷尝试，直到得到相对最好的解。
    - **吐槽** 讲者吐槽当时 GPT-4 的幻觉：「他说着说着就不知道在说什么了」。
- **模型为拿奖励倾向浅层搜索，所以要外层 agent loop。** 强化学习只奖励完成任务，模型不愿在一个问题上停留很久。
    - 模型没学会无穷尝试，原因是强化学习里要完成任务才有奖励（博士生类比见第 1 节）。
    - 自主调用工具的 react 型 agent 有完成任务的压力，完成得越快越有奖励，所以搜索宽度偏短。
    - 模型的思维链里会想「but wait」，DeepSeek 常说「等一等」，但一旦找到认为合适的路线就往下走。
    - DeepSeek 遇到太难的任务会摆烂，说解决不了就停下。讲者认为这是强化学习的影响。
    - **吐槽** 讲者说 DeepSeek 遇到难题的表现：「我给他太难的任务，他就会摆烂，他说这个任务我解决不了就停下」。
    - 理想情形是模型足够好，只给 bash 或 Python 工具，就能造芯片、证明黎曼猜想。理由是模型像把人知道的东西都蒸馏了，早期 UNIX 时代的 Knuth 也只在 shell 里和工具交互。
        - 讲者说有了 bash，可以用它编辑文档，也可以用它看文档。
        - 早期 UNIX 被发明时还没有图形用户界面，大师们就在 shell 里和工具交互。
        - **玩笑** 讲者拿自己打比方：「你想象他把我蒸馏了，把我所有知道的东西都蒸馏了，那你只要给我一个 bash，我好像可以干我能干的所有一切的事情」。
    - 现实是模型还没到万能，也不如最好的人，所以需要 agent loop。
- **agent 就是 while 循环加 bash，150 行就能用** 讲者用自己的 pi agent 演示，核心是一个 bash 工具加一个请求循环。
    - AI 擅长构建原型，要用 AI 造好原型就需要 agent loop。
    - 建议自己动手做一个 agent，再和成熟产品比较增量，能体会软件从小到大膨胀的过程。
        - 讲者说 AI 时代最重要的是有任何想法，都可以自己做一个。
        - 先了解一个简单的核心，再看成熟产品多做了什么。
        - 这个过程还能吸取经验，知道模型里有些东西该怎么做。
    - 自己做一个 agent，也能把里面的协议看清楚。
    - **bash 工具：** 它是一个可序列化成 JSON 的合法 Python 对象。
        - type 是 function，name 是 bash，另有 description。
        - 参数只有 command，agent 用它执行命令，另有一个 run bash 函数负责执行。
    - **请求循环：** agent 直接调用 DeepSeek 的 chat completions 接口，整个循环是一个 while 循环。
        - 从终端读用户输入，构建 message，请求并读 reply。
        - reply 里没有 tool call，就直接输出 reply。
        - 有 tool call 且是 bash，就取出参数，运行命令，把输出连同 tool call id 放回 message。
        - tool call 也可以理解为模型以文本输出，只是 API 帮忙做了一层解析。
    - **演示：** 整个 agent 共 150 行，真能用。
        - 讲者让它生成「生成式软件工程」简介 HTML 卡片，它用 bash 写字符串，输出 token 耗时较长。
        - 讲者再让它在浏览器里打开，它会探查环境，并不停验证。
        - 讲者不知道它为什么选某个做法，觉得它有奇怪的 bias。
        - 他猜可能是它看到了项目里已有的内容。
        - **吐槽** 讲者对生成内容里的 slop 一笔带过：「Anyway，这个 slop 不重要」。
    - **玩笑** 演示时讲者先检查终端里有没有泄漏自己的 key：「好，这里面应该没有我的 API 泄漏对吧」。
    - **玩笑** 演示时终端里可能露出 API key，讲者提醒学生：「所以你们要小心地保护好你们的 API key。在你不锁屏的时候，加上你在宿舍，你去上洗手间了，然后你没有锁屏，你的终端在那里，然后你的室友来悄悄地把这个 cat 了，拍一张照，然后你的 API key 就被他偷走了。」
- **玩具原型和产品的差距在细节，亲手实现才会想到** 这个 bash 工具把 timeout 写死，产品不能这样。
    - coding agent 给任务设的 timeout，可能因为对环境感知不够而不合适。
    - 例子：国内网络访问 GitHub 的速度，和 agent 以为的不一样。agent 设了不合适的 timeout，命令被杀掉，再换一个 timeout。
    - **自嘲** 讲者第一次到国外，看到 git clone 跑满网卡带宽，很震惊：「我的世界观一直是在这个地方，所以我就 overfit 了这个环境。」
    - **自嘲** 讲者形容自己第一次出国的反应：「当我第一次肉身到墙外的时候，我看着那个能够跑满我网卡带宽的 git clone，我还是很震惊的」。
    - 讲者的最小实现不支持改 timeout，补上需要架构。不让 AI 做最小实现，就不会想到这类问题。
- **裸模型会自作主张，harness 用来约束它** 没有 harness 时，模型会做用户没要求的事。
    - 演示用的是光板模型，所有 prompt 都由讲者给，它的行为很有趣。
    - 讲者让它解决问题时，它自己打开了两个浏览器，用截图验证后还问讲者是否满意。
    - 讲者认为这不一定是用户要的，用户可能只想让它不停向前完成任务。这类行为正是 harness 要处理的。
    - 讲者最后一句说模型自己的思维链也可以做搜索，前半句字幕断了（待确认）。

> 原话：「所以做一个 agent 没有大家想象的那么困难。」

## 4. Ralph loop 把长任务拆成状态机小步来抑制漂移

<small>▶ [21:49](https://www.bilibili.com/video/BV11LWw6VEHW?t=1309)–40:50　·　进一步　·　话题：Ralph loop 与状态机</small>

- **Ralph loop 用同一个 prompt 反复驱动 agent，抑制漂移。**　模型易漂移、上下文被旧代码污染、又倾向服从指令，所以要外层循环管理。
    - 讲者说 harness 就是把模型能做的事，约束在开发者认为较好的范围里。
    - 讲者说今天 harness 的核心，是 Ralph loop。
    - **真实的 harness 比 Ralph loop 复杂，agent 还能派生 sub agent。**
        - 讲者说 Claude 在今年某个版本更新后，和之前的 batch 调用一样，会生成一段 TypeScript 脚本。
        - 脚本里可以写 for 循环，循环里调用 agent，prompt 是自然语言模板。
        - 循环变量和任何算出来的值，都能填进模板字符串，由此孵化 sub agent。
        - agent 调用是异步的，可以 await 等它完成。讲者记不清具体语法。
    - **Ralph loop 名字借自《辛普森一家》，写法只有 3 行。**
        - 第一个提出并让它流行的人，借用了角色 Ralph 的名字。
        - Ralph 有点笨、有点可爱，但从不放弃。
        - 3 行的意思是：不断把同一个 prompt 丢给 claude -p，检查、修改，直到无法改进。
        - GPT 给讲者的总结是「the prompt is the same, but the world changes」。讲者觉得出人意料。
    - **理论上足够好的模型只要有 bash 就够，但现有模型仍会漂移。**
        - 讲者的基本假设：足够好的模型拿到 bash，自己会探索搜索空间，甚至能证明黎曼猜想。
        - 现有模型像博士生，脑子一热就一路做完。
        - 已有代码污染它的上下文，它又倾向服从用户，不去动用户的东西。
        - **玩笑** 讲者形容足够好的模型：「神仙来了你给他一个 bash，他就可以自己探索这个搜索空间」。
        - **玩笑** 讲者形容博士生式的漂移：「他脑子一热，他就哗哗哗哗哗哗哗给你做完了」。
        - **吐槽** 讲者说模型服从过头：「他又有一种强烈的舔狗的倾向」。
    - **模型读到 slop 代码后，倾向于把它扶起来，而不是推倒重来。**
        - 导师对学生说代码零分，学生痛苦，但理解导师为他好，下个版本会推掉架构。
        - **玩笑** 讲者以导师口吻演示这句狠话：「你这个代码是零分的代码，你如果再拿这种代码来，你就不要来见我了」。
        - 模型的上下文里一旦有 slop 代码，就倾向于完成「把 slop 扶起来」的任务。
        - 重构很可能无法保持行为 100% 一致。代码若在线上跑着，重构对用户可能是粗暴的。
        - 所以模型遵循指令有道理，不遵循也有道理。它选择遵循，继续把项目往泥潭里拖。
    - **长任务装不下上下文时，compact 会让模型降智。**
        - **吐槽** 讲者说 Codex 跑长任务的体验：「你们最讨厌的就是 Codex 今天哗哗哗跑跑跑很好，突然 compact 开始了，然后等在那」。
        - compact 后用量急剧增加，模型会降智一段时间，各种做不对。
        - 加载足够多上下文后它又能做对，坐一会儿再 compact。设置 goal 后常遇到上下文不够。
    - Ralph loop 是对搜索空间的线性管理方法。前面讲的是在 design space 里先宽后深地搜索（见第 1 节）。
        - 讲者说管理搜索空间的方式不限，用 prompt、loop 或别的方式都行。
- **每一轮循环是 workspace 状态的一次迁移，所以任务能拆成小步。**　讲者说一切都是状态机，物理世界也是状态迁移系统。
    - **玩笑** 讲者讲到一半找不到粉笔擦，自嘲：「我的粉笔擦呃我瞎了吗」，随后直接换了一块。
    - **把一把做到底的开发，拆成 commit 串起来的小步。**
        - workspace 起点可能只有 spec.md 或 prompt，几乎没有实现。
        - 每做一轮，workspace 就进入下一个状态，开发者可以 git commit。
        - loop 里的 prompt 可以要求：每次不要做太多，做完要检查，还可以找另一个 agent review。
    - **这是一个非确定的状态机，同一状态下可以选不同的操作。**
        - 同一状态下，可以用 GPT 做一轮，让 Claude review，也可以让 DeepSeek 干活。
        - 这又回到前面的搜索过程：当前 workspace 是一个状态，可以选做哪件事。
        - 实际运行时，最终仍要选一条线性路径，直到任务完成。
    - **可以定期插入架构 review 和重构，防止项目变成 AI slop。**
        - 例如每周做一次架构 code review，检查项目有没有变成 AI slop。
        - 发现 AI slop，就进入重构：由重构 agent 把 slop 及相关内容直接删除并 commit。
        - 再让另一个 agent 用更好的架构重新实现。这样得到一棵搜索树。
    - **sub agent 并行是这个模型的自然推论：并行迁移再 git 合并。**
        - 从同一状态出发，A 模块和 B 模块的重构可以同时做。
        - 两条迁移完成后，用 git 合并成一个提交。
- **外层循环让 agent 能完成更长的任务，已经逼近甚至超过博士生**　循环和模型能力互相抬升。
    - **循环和模型厂商互相抬高上限，讲者称之为「左脚踩右脚」。**
        - 早期基于 ReAct 的 agent（如 AutoGPT）和线性的 claude -p，跑着跑着就漂移，上下文超限后越做越差。
        - 外层循环让它们能完成更强的任务。模型厂商看到后，再提高单次 session 能完成的任务。
        - 开发者于是再套一层 loop，完成更复杂的任务。
    - **从产出看，给对 loop 和 prompt 的 agent，对导师的价值可能已超过博士生。**
        - 导师想好方向时，博士生系统在某种程度上被替代，也就是被斩杀（见第 9 节）。
        - **玩笑** 讲者说这件事时用词很狠：「PhD 系统就被替代了，或者说某种程度上被斩杀了」。
        - 讲者强调，从不会到会的培养过程仍然重要。
        - 但教授的 KPI 是论文、研究成果和项目。按这个标准，有些博士生毕业时可能还不如 agent 好用。
- **同一个模型，有无 loop 结果差别很大，prompt 要自己磨合**　讲者用自写的 Ralph loop 做了两个演示。
    - **讲者自写的 Ralph loop 很简单，状态全放在文件里。**
        - 一个 prompt 驱动，要求每轮先检查当前状态，只推进明确的步骤。
        - 未完成时写文件，说明下一步。只有确认整个任务完成，才输出完成标记。
        - 外层脚本看到标记就结束，否则无限循环。讲者说他相信模型的能力。
        - 讲者说这套东西是 150 行的 agent 加一个 5 行的脚本（见第 3 节）。
    - **演示一：调研「世界上最好的编程语言」，agent 在只有 bash 的条件下跑完长任务。**
        - agent 想去 arXiv 下载论文，访问 Google 时在讲者的机器上超时。
        - 它做一段就停下，把总结写进状态，再继续下一轮。
        - 最后输出完成标记，一句话结论是「不存在绝对最好的语言」。
        - 讲者把 research 目录移走，用同样的 prompt 再跑一次，它又去抓资料。讲者对此仍觉得吃惊。
        - 对比两份调研结果，左边那份显得更保守。讲者说 loop 确实会产生很大影响。
    - **演示二：同一 prompt 生成名片，loop 版朴素但内容正确，直出版花哨但有错。**
        - 直出版界面花哨，有玻璃动效和小 macOS 终端，邮箱和主页都是错的。
        - **吐槽** 讲者点评直出版的假终端：「还有一个小的 Mac os 的终端，我不知道他从哪儿学来的」。
        - loop 版朴素得多，写的是计算机学院副教授，邮箱和 GitHub 都对。
        - 讲者说有随机性，不能断言谁更好。他猜直出版可能受到上下文污染。
        - 讲者说，同一个模型，投入的算力和 prompt 不同，结果差别会很大。
    - **网上的 prompt 和 skill 可以复用，但最合适的是自己写的。**
        - 和模型长期磨合后，开发者才知道什么时候该放手，什么时候不该信任它。
- **讲者顺带讲了 4 件和主线无关的事。**　设计空间没人摸清。新模型发布时要重测。上下文刚扩到 500K。当下很不确定。
    - Codex、Claude Code、pi agent 哪个更好，没人知道。pi 本身没有 sub agent，但有不止一个 sub agent 插件。
    - 上一版模型里有效的 prompt，换新模型可能全变。新模型发布时，建议拿掉所有系统提示词和 skill，在熟悉的任务上做背靠背对比，可能表现更好。
    - 讲者说最近有一次「史诗级」更新，把上下文扩到 500K。
    - 讲者总结当下：「我们现在活在一个非常非常不确定，但是也非常 excited 的」时代。

> 原话：「the prompt is the same, but the world changes」

## 5. 每一步后自动检查就是 CI/CD，因为开发者不可信

<small>▶ [40:50](https://www.bilibili.com/video/BV11LWw6VEHW?t=2450)–52:44　·　因此　·　话题：CI/CD：步步设门禁</small>

- **agent 每次只走一小步并停下检查，才能抑制漂移。** 前提是 agent 训练不足，在当前上下文下思路可能漂移。
    - Ralph loop 的 prompt 要求每轮先检查状态，只推进一个明确步骤，再验证并评估。
    - agent 做完一个小状态迁移就停下，由检查把关。
    - 检查有 2 种：另一个模型 review 这次提交，或跑测试和检查脚本。
    - 检查不通过，就拒绝这一轮结束，agent 回去修好问题。
    - 这个想法不新，是软件工程的常见做法。
- **开发者不可信是老前提，人的自信和投机都会出错。** 人自信就会跳过检查，有投机倾向就会赌一把。
    - 讲者在计算机系统基础课讲过 2 条公理：机器永远是对的，未测代码永远是错的。
    - 码农的第一性原理：所有错都是自己的错，不能埋怨别人。
    - **吐槽** 讲者说码农的第一性原理：「你做码农的第一个 first principle，所有错都是你自己的错，没有别人可以埋怨。」
    - **玩笑** 讲者模仿开发者每天的脑内独白：「哎呀我今天就改这一句话，文档里改一句话应该没事的吧？我就把这个循环变量从一开始改成从零开始，应该没事的吧？我单元测试通过了，应该没问题吧？样例过了，我是不是可以交 OJ 了，应该程序是对的吧？」
    - 实习生推一个 PR，就可能让整个生产系统挂掉。
    - 投机心理：提交不花钱，约 10 秒就有反馈，对了就过，不对再改。
    - **吐槽** 讲者说学生靠投机提交：「你们一定是过了样例就提交，因为你们是 speculative 的，你们的大脑很聪明，算的是一个期望，反正交 OJ 又不花钱。」
    - **吐槽** 讲者说实习生和学生都不会自觉测试：「你进公司的第一天，你就跟那个实习生说做好测试，他不会去测试的。就像你们老师会不断地跟你们说，做算法题要做测试、写断言，你们不会的。」
- **CI/CD 就是每个状态后自动检查，通过才继续。** 讲者把开发看成状态迁移系统，检查和发布都自动。
    - 做法和 Ralph loop 相同：每个状态后检查，不通过就拒绝，回头修。
    - **玩笑** 讲者讲完这个做法后点破：「所以恭喜你发明了……软件工程差不多 20 年前开始的一个比较热门的说法，叫做 CI/CD。听起来很高大上。」
    - 检查多到找不出问题时就发布。链路是集成到主干、自动 build、检查验证、发布。
    - 检查还能发现一次推送之后，整个项目已经不能 build 了。
    - 人可以决定上线，通过检查的变更也可以自动上线。例如出现 release tag，就自动推送全部 release build。
    - 学生觉得 CI/CD 难懂，因为它嵌在生产流程里。要建容器，环境独立于开发者机器。结果还要同步到企业流程。所以同学间用得少。
- **把检查写成脚本挂在事件钩子上，不靠开发者自觉运行。** 脚本不能只存在，还要自动触发，不依赖实习生去运行。
    - 讲者说既然不信实习生会运行脚本，才有了 .github 目录来放自动运行的配置和脚本。
    - .github 里的运行配置和脚本一大堆，学生看都看不懂。
    - **吐槽** 讲者说门控脚本不能指望别人运行：「不要相信实习生会去运行它，所以你发明了一个东西叫 .github。」后面接着说里面一大堆运行的配置和脚本「你看都看不懂」。
    - 钩子是挂在开发事件上自动运行的动作。事件有 commit、push、发起 pull request。还有 merge 到分支，和 merge 到 protected branch。
    - 钩子可以放在状态迁移之前，也可以放在之后。
    - 演示：讲者前面让 pi agent 配了钩子，每次需要他输入时叮一声。这里让它总结仓库的 CI 流程，讲者说应该是 Codex 的。
    - 不用再手写 CI 配置。.github/workflows 下的配置以前全靠人手写，现在只要清楚什么状态迁移时做什么事。
    - 这类配置以前像一种 DSL，手写很麻烦。
    - **pre-commit hook 和 lint 是最前面的守门员。**
        - pre-commit hook 在本地提交前运行，可以要求编译一次、跑一次 lint。
        - lint 是不运行程序、只做静态分析的代码检查，覆盖缩进、换行、空格。
        - lint 是软件工程最基础的守门员，连它都过不了就不用谈软件工程。
        - **自嘲** 讲者看到 a=1 这类格式混乱的代码会不适：「我有好多年的码龄，我会生理性的不适，就是极度生理性的不适，就相当于我被训练了，我是一个模型。」
    - **云端 CI 有免费算力，还能养 Claude Code。**
        - GitHub Actions 每月约 2000 分钟（讲者原话「2000分钟的CPU小时」，待确认）。另有排队长、跑得慢的免费容器。
        - **玩笑** 讲者说免费算力：「你依然可以薅到一些算力的羊毛。」
        - 做法：在 GitHub Actions 里做 Ralph loop。push 触发钩子，拉起 Claude Code，修改仓库并提交，再次触发钩子。
        - 要避免循环出问题，可能需要 2 个不同的流程衔接，否则可能失败。
        - 得到云上的 Claude Code。订阅可能不能用，可能只支持 API。
        - 前提是想清楚何时跑 lint、单元测试、系统集成测试、长时间模糊测试，后面课程还会讲。

> 原话：「不要相信任何开发者」

## 6. agent 是最不可信的开发者，需要硬门控防 slop

<small>▶ [52:44](https://www.bilibili.com/video/BV11LWw6VEHW?t=3164)–59:36　·　进一步　·　话题：agent 是更不可信的人</small>

- **agent 是最不可信的开发者** 大语言模型的想法和人不同，天生与人类不对齐，常做人类不会做的事。
    - **吐槽。**「你们经常会看到他做这种非人类的事情」
    - **agent 爱写冗长文档，人读不了。**
        - 让它写文档，它直接生成 20K 的文档。
        - 人看两行就陷入琐碎细节，读不下去。
    - 代码已经 self explain，连注释都可以不要。agent 仍把思考流程和 agent loop 里的问题逐条写进文档。
    - agent 在细枝末节上疯狂出力，对 design space 里最重要的部分视而不见。
    - **agent 用工具把截图塞满上下文。**
        - 做网页时，agent 用 Chrome DevTools 反复截图，图片一直留在上下文里。Codex 有这种倾向。
        - **吐槽。**「我觉得正常的人类不会干出这样的事情」
        - GitHub trending 上有项目用 sub agent 做前端验证，只把最简短的 summary 放回上下文。
        - 讲者不知原因，认为可能来自强化学习：agent 学会写人类无法阅读、却自信能维护的代码。
- **文档与代码的关联不可见，项目会滑向 AI slop** 关联只存在于写下的那一刻。换 agent 或压缩上下文后就丢了。
    - doc.md 与 implementation.py 相关联，但基于 repo 的维护方式看不到这层关联。
    - agent 不记得两者要一致，改了代码，文档就和代码不一致，无法判断听谁的。
    - **吐槽。**「整个项目就开始滑向 slop 的崩溃的边缘」
    - 细节文档随版本不断调整，维护成本越来越高。
    - 一旦成为 AI slop，人改不了文档，也定位不到位置，只能让 agent 继续改，直到项目维护不下去。
- **人和 agent 共同维护项目时，不能把 agent 当神** 这类事一旦发生就无法回头，所以必须强行阻止。
    - **狗的类比：讲者引用前一天看到的一条推文，讨论人与超级智能的关系。**
        - 人对狗是超级智能，狗不知道人类怎么运作。
        - 狗只看到一个可以生活的世界，约 10 亿只狗，活得快乐。
        - 只有把 AI 当神、任务交出去就不管，才可以放任它（整理者补充）。
- **用 CI 里的硬规则拦截，比 agents.md 里的软提示可靠** CI 的检查可判定，agent 绕不过去。
    - CI 的第一性原理是开发者不可信，所以在 agentic AI 时代含金量不断提升。
    - CI 可以阻止很多事情，违规的改动永远合不进主分支。
    - 例子：CI 设硬条件「文档不能超过 1000 字」，用 lint 直接数字符串长度，超限就 fail，合不进主分支。
    - agent 能看到检查，也能在本地跑 pre-commit hook。失败后它会想起 README.md 或 agents.md 里的规则。
    - agents.md 只是软提示。上下文约 1 million，随上下文膨胀，agent 注意力涣散。项目到 10 万行以上，注意力开始滑坡。
    - 这类自动检查在软件工程诞生之初，大家就会做。
    - 传统软件工程没人检查文档字数，因为人积累 slop 的速度远不及 AI。AI 时代，可判定的规则变得重要。
    - 人写文档，重构起来容易，所以以前不会先设 CI 规则去限制字数。

> 原话：「一旦这个东西成为 AI slop，人就再也无法维护它」

## 7. 工业界的 agent native 开发靠状态迁移上的门控

<small>▶ [59:36](https://www.bilibili.com/video/BV11LWw6VEHW?t=3576)–66:55　·　举例　·　话题：工业界的门控实践</small>

- **agent native 开发就是在状态迁移的每一步设门控**。以 workspace 状态为状态。每次选一个动作向后做一步，步步有检查。
    - 状态可以用 git 表示，这是 Ralph loop 的做法（见第 4 节）。
    - 检查包括 pre-commit、post-commit、pre-push、pre-merge 等多种门控（见第 5 节）。
- **OpenAI 公开的 Codex 三层 CI 只是最基础的门控。背后一定还有更多**。公开部分多是 lint 级检查，讲者认为只靠它撑不住项目。
    - **玩笑** 讲者现场想打开 OpenAI 的文章，一时不确定能不能访问：「OpenAI 这个可能被墙了，我不确定啊……OpenAI.com 竟然可以直接访问」
    - 文章《Harness engineering: Leveraging Codex in an agent-first world》称，Codex 团队从空 git 仓库起步，人已不写代码。
    - 这篇文章发布时在业界引起了不小的轰动。
    - 人仍要定好流程：环境、约束、反馈、验证机制。这些可以用自然语言写，例如每次 push 前确保明文内容和 API key 没有泄露。
    - **玩笑** 讲者顺带吐槽 Claude Code 源码映射泄露：「他不是那个 source map 泄露了吗，那个就应该是一个门控对吧，他 CI 里面那个门控没有写啊」
    - **三层 CI 各管一段：** 讲者看 Codex 仓库的 CI 流程，分成三层。
        - 提交 PR 时跑快速门禁，main 分支做全量认证，最后发布并打标签。
        - 讲者说，不懂 Rust 的小白也能看懂这三层。
        - 快速门禁以 lint 工具为主：格式与拼写检查（Rust 的 cargo 工具），以及 3 类 bad smell 检查，包括文件过大、函数过大、依赖。
        - main 上的全量认证应是跑大量单元测试，这是讲者的推测。
    - 文章自己承认：软件若要按年维护，agent 的流程还没想好。
    - **玩笑** 讲者调侃 OpenAI 名不副实：「OpenAI 其实 close 的 AI」
    - 讲者百分之百确信，Codex 背后还有一整套门控防 AI slop。Codex 看起来有「人感」，而「你用什么 lint 这种东西是不可能写出一个有人感的项目的」。
    - **吐槽** 讲者说得很笃定：「所以我百分之百确信，codex 的背后还有一整套巨大无比的 agent native 的门控机制在后面防止它产生 AI slop」
- **并行 agent 会重复劳动、互相覆盖，需要一个调度 agent 协调**：Anthropic 用 16 个 agent 并行编译 Linux 时卡住了。
    - 16 个 agent 先撞上同一个 bug，重复修复，覆盖彼此的改动。
    - 所以 Ralph loop 真正落地时，需要编排用的调度 agent 来协同进展，并让人看到进展。
- **讲者团队用架构图做进度看板。lead 只看这一张图就能管整个项目**。任务进展自动推到图上，可以预估一小时后的状态。
    - 具体项目讲者不便透露。architecture.md 可以自动生成架构图。
    - **玩笑** 讲者现场想展示架构图，懒得认真画，随手比划：「哎哎不管了，反正随便你画一个这样的」
    - agent loop 里有 log book，里面是已完成和进行中的 task。agent dashboard 把进行中的任务自动推到 GitLab CI。

## 8. DeepSeek harness 用配对契约加门禁保持文档一致

<small>▶ [66:55](https://www.bilibili.com/video/BV11LWw6VEHW?t=4015)–90:21　·　举例　·　话题：DeepSeek 的文档门禁</small>

- **DeepSeek harness 用同目录三件套加哈希门禁。这保持了中英文文档一致。** 每篇文档的中文、英文和配置三个文件配对，哈希对不上，门禁就拦下。
    - **双语文档不加约束，必然漂移。**
        - 中文母语者用中文写文档更合适。讲者的 system one 读中文比读英文快约一倍，浏览时更快定位关键信息。
        - 讲者把这比作自带一个快速的视觉模型，能从海量文字里提取关键信息，帮他定位想找的地方。
        - 项目要走向世界，所以要同时维护中文和英文文档。
        - 文档常常随手改、随手提交。文档多到无穷时，没人能保证两种语言一致。
        - **吐槽** 讲者说到双语文档的维护成本：「这不就是地狱和灾难吗」
        - **吐槽** 讲者反问听众有没有想过一致性问题：「你们没有想过这个问题」
    - **三件套定义配对契约。** 每篇文档在同目录有三个兄弟文件：中文 markdown、英文 markdown、i18n.yaml。
        - 讲者说 i18n.yaml 这种做法目前不太常见。
        - 两侧都可以是权威，谁先写，谁就是那次修改的原文。
        - 另一侧由 AI 翻译并与原文绑定，两边必须表达同一件事。
        - 门禁命令 verify translation parity 检查两侧是否同步。
    - **哈希加 git 历史，让程序判断哪一侧更新。**
        - i18n.yaml 里给两侧各记一个哈希，过往版本都留在 git 历史里。
        - 没见过的哈希就是新版本，所以程序永远知道谁新谁旧。
        - 这样一小段文本就能保证一致性。讲者称这是「非常聪明的想法」。
        - 新旧不匹配时，AI 按补丁翻译：看原文改了什么，只改另一份的对应位置，其余保持不变。
    - 讲者展示 docs 里的 architecture.md：读起来干净舒适，有很多交叉引用，找不到一条非法链接。
    - 讲者克隆代码后的第一感觉是，这个项目的组织方式和其他项目都不一样。
    - 讲者说这些文档可能有一部分是人写的，但人只负责告诉 AI 该做什么。
- **IDE 投影让开发者只看一种语言，仓库本身保持 agent native。** 目录变得不干净，是 DeepSeek harness 付出的代价，讲者认为值得。
    - **软件不适合只用文件系统里的目录来表示。** 讲者的观点是：软件内部是错综复杂的关系，不是一份 report。
    - **每个开发者用 IDE 配置，各自隐藏不想看的文件。**
        - 中文开发者隐藏所有 i18n.yaml 和英文文档，只看到中文文档。
        - 英文母语者隐藏所有中文文档。
        - 两种人在 IDE 里的开发体验一模一样。
        - .vscode 之类的 IDE 配置不放进仓库，因为不同开发者想法不同。
    - **吐槽** 讲者说隐藏三件套里的配置文件：「因为这三个东西太讨厌了，我会忽略所有的 i18n.yaml」
- **多个小门禁叠加，才让文档不漂移、不膨胀** 每个门禁看起来都小，加在一起，项目才被维护起来。
    - **文档内容靠逐项门禁卡住。**
        - 渐进式披露：写文档的规范若放进 agents.md，会随规模暴涨，100 万上下文都装不下。DeepSeek 只在翻译或写文档时才加载它。
        - agents.md 分层，字幕疑为每个目录各有一份（字幕原文：每一个指数上都有HMD，待确认）。
        - 术语约定：仓库有 Terminology 文件，统一中英文术语的译法。
        - 讲者设想的术语门禁：中英文按段落或小节对应，AI 与「人工智能」的出现次数之差不超过 ±3。边界太严会误杀合格文档，需要小心调整。
        - 人感被当成可校准的规范：i18n 目录下有风格样例文件（字幕原文：style3samples.md）。讲者说样例仍有 AI 味，文档肯定不是人写的。项目到这个体量还保持人感，说明下了很大功夫。
        - 链接与代码块逐字校验：文档里的代码块，例如 interface，必须逐字符出现在某个源文件里。这样杜绝代码改了、文档没改，或反过来。
        - verify type equivalent 要求文档里粘贴的类型与源码一致，不允许漂移。
        - 字数预算：verify doc budgets 规定 root 文档不超过 1960，architecture 文档不超过 2400（单位字幕原文：次，待确认）。它防止 AI slop 无限堆积。
        - 文档还有分层，并把不同任务路由到对应机制（字幕原文含糊，待确认）。
        - 讲者的扩展：自家 agent native 项目里的 code block 带执行语义。块内可声明这段的用途、必须出现的位置、与别处的关联，并带轻量检查。这扩展了 markdown 围栏代码块的语法。
        - **吐槽** 讲者说文档漂移太常见，不约束 agent 就会失控：「当你不约束 agent 的时候，它会以光速生产 slop」
    - **流程靠 agent notes、skills 和评审分层。**
        - agent notes 分 implemented、proposed、rejected、archive 四类。讲者说这相当于他们的 Ralph loop（见第 4 节）。
        - 讲者自家实现了 log book，每条带状态，并和 GitHub CI 整合。他推测 DeepSeek 没有 dashboard，可能认为没必要。
        - skills 把「怎么做」和「做什么」分开，包括 code review、写作规范、工程质量规范，以及各产品自带的 skill。
        - 评审流程依次是本地自证、CI 门禁、人工评审，另有分数。新增文案必须通过语义评审。
        - 机械门禁包括 4 类 CI：doc sync、static、coverage、snapshot。另有 verify client UI、translation parity、application entry points。
        - 代价是每次提交前要跑大量门禁。但开发者多半是监工，和 AI 在 plan mode 里写 log book，代码没动，就不用跑 CI。
        - **自嘲** 讲者说开发者的角色：「但是你又不写代码，大部分时候你都是监工」
    - **OpenAI 只放出最基础的门禁，DeepSeek 把成体系的门禁开源。**
        - OpenAI 只放出 lint 通过、CI 里 test 通过这类最基本的门禁。
        - OpenAI 博客说过，他们起初每周做一次 agent review，防止架构崩溃（见第 7 节）。这些内部流程都没有放出来，只放出最后能拿来用的编译产物。
        - **吐槽** 讲者对比 DeepSeek 与 OpenAI 的开源程度：「OpenAI 根本就是……OpenAI 就是 close AI」
- **从 git 历史看，这套机制在项目早期就成形，来自真实经验。** 讲者让 agent 还原机制的演化，结果显示配对契约进流水线只隔了几天。
    - **历史完整保留，可以逐步还原。**
        - 项目从 2026 年 6 月 10 日晚 11 点从零开始。讲者说主要 3 位开发者都在他们的内测群里。
        - 6 月 25 日前后先有 terminology，只有词汇约定，没有任何机制。
        - 7 月引入配对契约。7 月 3 日出现权威侧，机制立即被强制接入自动化流水线。
        - 此后一直遵循，同时维护中英文两份文档。讲者判断，团队很早就意识到文档的重要，说明他们有经验。
    - **类似机制在前 agent 时代就有，agent 时代是把人的工作迁给 agent。**
        - Python 的文档由 docstring 生成，每种语言都有类似 Javadoc 的语法。C++ 原生不支持，用 Doxygen（字幕原文：dog c振，待确认）。
        - 这些机制让 API reference 与代码百分之百一致。
        - 讲者不确定 DeepSeek 是否受它们启发，称配对契约加门禁是「很酷的设计」。
    - **这些设计来自失败的经验，坐在教室里想不出来。**
        - 只做语言律师，思维会被锁在当前上下文里，看不到搜索空间里另一个方向。
        - **吐槽** 讲者说只在教室里想问题的局限：「如果只是坐在教室里面去做语言律师，你的思维是禁锢在当前上下文里的」
        - 这些做法一看就觉得应该这样，但很难完全凭空想出来。
        - 讲者认为团队一定失败过。他说其中的崔老和自己同龄。
        - 这套东西开源，从 6 月起半年内就在规划这些门禁。
        - 只要有元级认知，知道什么是好东西、什么没见过，就能光速向别人学习。
        - 讲者说以前面对陌生项目，做不到这一点。
    - **架构烂掉时可以重构，garbage collection 解决不了所有问题。**
        - 讲者对学生说：先开一份新的空白项目，再一点点把旧功能迁进来。
        - 模块级或项目级重构，能让项目回到正确方向（见第 9 节）。
- **讲者顺带讲了 4 件和主线无关的事** 内容涉及配图、国产项目、动态 UI 和失败案例。
    - 开头说这张幻灯片图也是 AI 生成的，最近大家喜欢「DeepSeek 娘」的图。
    - 讲者称 DeepSeek harness 是 agent native 开发领域的标杆，说这是中国人的项目，是「我们的骄傲」。
    - ChatGPT 现在会生成动态 UI 组件和 HTML 小卡片，把图片嵌进文本流，读起来更舒服。讲者认为 web UI 可能成为主流，原因是「mini行上可能稍微麻烦一点」（字幕原文，待确认）。
    - 讲者最后开始举社交网络先驱 Friendster 迅速吸引大量客户的例子，说历史上真实的失败不少。本节字幕在此截断。

> 原话：「当你不约束 agent 的时候，它会以光速生产 slop。」

## 9. 试错机会决定谁不被 agent 斩杀，大学也受冲击

<small>▶ [90:21](https://www.bilibili.com/video/BV11LWw6VEHW?t=5421)–97:12　·　转向　·　话题：斩杀线与大学</small>

- **没有试错机会的人会先被斩杀** 经验来自反复失败和重构，没有 token 的人试错次数少于别人。
    - 好想法不够。intent 即使是世界级的，草台班子去做也只会堆出 AI slop，想法最后被别人抄走。
    - **吐槽** 讲者形容随便组队去做的后果：「如果你组一个草台班子去做」，结果是「海量产生的AI slop」。
    - 有经验的团队才能收敛到更好的方向。社会性的威胁是，人必须有机会去尝试。
    - 开源项目能教人 agent native 开发该怎么做。即便如此，开发者仍要自己做很多次尝试并失败。
    - 能不能通过看别人学会，讲者说要看悟性。
    - **玩笑** 讲者开学时随口说过：「没有 token 的学生应该立即退学」。他说这只是玩笑，但没有 token 时尝试机会确实不如别人多。
- **企业会选 senior 加无限 token，不再培养新人** 新人要 4、5 年才追上 agent，公司等不起，而 agent 还在涨。
    - 读完博士仍不如 agent 时，用人单位会选一个 senior 给无穷的 token，不培养 PhD 学生。
    - 资本家追求企业运行效率。以前师傅带徒弟，是因为看到新人的 potential，现在回报点太长，「新兵蛋子」不值得带。
    - **吐槽** 讲者说：「但是这不就形成了一个斩杀线吗」，又说：「所有的人都在被斩杀，都在不断的被斩杀」。
    - 所有人都在被斩杀，斩杀线还在上移。本科生毕业时，是否还有一个 20 美元 Claude Pro 订阅的价值，是现实问题。
    - 讲者在 Clawdbot 里养 Claude Code，用 20 美元订阅。Opus 5.5 的额度够用，而且很强。他认为难以培养出达到 Opus 5.5 水平的本科生。
    - 讲者自己作为 senior，有大局观（big picture）。他再配上自己的 agent harness，就能用好 agent。
- **大学已经资本化，讲者判断它会崩溃** 学生追不上 agent 时，以科研经费为指标的体系会失效。
    - 大学本应非盈利、不以 KPI 为导向，讲者认为问题只可能在大学里解决。
    - **吐槽** 讲者话锋一转，说现实并非如此：「学阀一手遮天」。
    - 他说大家肯定在网上刷到过这类故事。
    - 讲者所在高校的考核指标是科研经费，不是上课。资本体系是基金委、科技部、优青杰青、院士这条金字塔，每层产出像公司产品。
    - **自嘲** 讲者承认自己也在这个体系里：「所以我们某种程度上也是资本家和公司化运营，高校变得越来越资本化了」。
    - 老师和学生都被斩杀后，这套体系完全失效。
    - **玩笑** 讲者给出判断后自嘲：「我在这又发表暴论，大学肯定要崩溃的」。
    - **学而思可能是新形态的大学，因为它从上到下资本化运营。**
        - 它靠样板课。花 100 万雇清北的天才设计样板课，每个老师是执行机器。
        - 它把执行机器换成老师加 AI。它再花 1000 万去技摩场（字幕原文：技摩场，待确认）抢最好的天才设计样板课。
        - 这样做把教育教学的体系完全颠覆了。
        - 高校惯性大，还得照旧上课。讲者说未来会怎样，他不知道。
- **开源社区是学习的出路，应从 DeepSeek harness 看起** 讲者的全部理解来自开源项目，闭源公司不公开 harness。
    - 讲者没有在开源社区看到好东西，就不会有今天的理解，也不会来上这门课。
    - OpenAI 和 Anthropic 从不开源 harness，要靠「国产之光」DeepSeek 开源。这些东西若只在公司内部，被斩杀的人会越来越多。
    - 建议：回去在互联网上找优秀项目，从 DeepSeek harness 开始看。
    - 讲者今天讲的只是极小的循环，算不上 Ralph loop。DeepSeek harness 把所有东西做成插件。
- **顺带：上一个故事的收尾** 讲者把那段经验归为 agent native 开发的好范例。
    - 东西的价格崩溃，是「PREMM 时代」（字幕原文，待确认）的事。
    - 讲者说，今天有 agent，或许能让它富起来。
    - 这些经验最终促成了 agent native 开发的一个好范例。

> 原话：「你如果没有 token，你尝试的机会就不如别人多。」
