# Agent-native 开发 [08-Raw⧸26生成式软件工程⧸NJU]

> 原视频：<https://www.bilibili.com/video/BV11LWw6VEHW>　·　课程合集：<https://space.bilibili.com/202224425/lists/8942017>　·　讲者：蒋炎岩（NJU《生成式软件工程》2026）

## 全课主线

这节课的核心主张是：Agent-native 开发不能理解为“把任务丢给模型一次做完”，而要把软件开发看成在 intent→spec→implementation 的设计/搜索空间中做状态迁移，用 agent loop、harness、BFS/DFS、并行和 CI/CD 门控来管理 agent。讲者想让听众相信，模型能长程执行但会漂移、扶 slop，所以必须把“开发者不可信”落实成可自动检查的硬门控与文档/代码一致性机制。进一步，人若没有反复试错、好项目和 token 机会，就会被 agent 的性价比逻辑“斩杀”，因此要去开源中学习真正优秀的 agent-native 项目。

1. 课程过半转入 Agent native 开发，第二个实验要把“算力换智力”往前推；理由是 agent 已能完成长程任务，但解决问题直觉稍差。因此，接下来不是重复个人 agent 产品，而是研究如何用更多算力/搜索补短板。（第 1 部分）

2. 讲者用 PhD 学生和模型 RL 作类比：模型像巴甫洛夫的狗，完成任务才给奖励，容易偏向较短的广度搜索；但 design space 浅层分叉多，不同早期选择会放大到最终结果，必须平衡 BFS 与 DFS。（第 2、5 部分）

3. 软件工程本身也处理同一类空间问题：intent→spec→implementation 都是一对多，每个箭头要靠 review、讨论、迭代收敛；而 AI 的最大能力是从任意阶段开始向下推进，并生成版本比较趋势。（第 2、3 部分）

4. 需求能拆成两个 subsystem 时，就可以启动并行 agent；AI 成本足够低时，可先让它搓原型，再用典型 use case 评审。但这要求有 agent loop，否则无法支撑原型构建。（第 3、4、5 部分）

5. 一个 ReAct 型 agent 的主循环可以很简单，约 150 行，带 bash tool 就能跑；但模型会自己产生行动、反问你，它的自选行为不一定是你要的，因此需要 harness 约束可做范围。今天 harness 的版本答案被讲者称为 Ralph loop：同一 prompt 反复检查、修改，直到无法改进。（第 6、7、8 部分）

6. （整理者串联）Ralph loop 把“一把头做完”拆成很多小步后，workspace 就可看成一个非确定状态机：同一状态可换 GPT、Claude、DeepSeek 或不同操作，于是回到搜索过程。再由此推出，每次开发都是状态迁移，同一状态可并行分叉、最后 git merge，所以 agent 能并行，long-horizon task 也能越做越好。（第 8、9、10 部分）

7. 但现实模型容易漂移、被已有代码污染，又有遵循指令/舔狗式倾向，会倾向于扶起 slop 而不是重构；长任务遇到 compact 还会降智。因此讲者的办法是让模型停留在 design space，用 prompt 或 loop 做 BFS/DFS 管理，而 ReAct loop 只是线性管理。（第 8 部分）

8. 为了防漂移，loop 里要每轮先检查当前状态，只推进一个明确步骤，然后停下验证、评估、review；这来自软件工程里“开发者不可信”的 first principle。由此自然导出 CI/CD：每个状态推进后都检查，不通过就拒绝推进，全部通过才发布。（第 12、13、14 部分）

9. 在 Agentic AI 时代，CI 含金量更高，因为 agent 是“最不被信任的开发者”；不能只靠 AGENTS.md 提醒，因为上下文膨胀会让 agent 注意力涣散、滑坡。所以要把 lint、测试、文档长度、术语、接口/文档一致性等可判定规则变成 pre-commit、CI 等硬门控。（第 15、16、17、21、22、23、24 部分）

10. 文档与代码漂移是滑向 slop 的核心风险：agent 把思考流程写进 doc.md，换 agent 或 compact 后无人记得文档与 implementation.py 要保持一致。DeepSeek Harness 用配对契约、i18n.yaml、hash/git 历史、AI patch 翻译和术语门控保证中英文及文档/代码一致性，并用关系组织项目、IDE 投影、渐进披露来维持可维护体验。（第 16、20、21、22 部分）

11. Codex/Anthropic 的经验显示，公开 CI 往往只是基础 lint/测试/发布门控；真正支撑 AI-native 项目的是背后庞大的 agent-native 门控、orchestration、agent review、log book/dashboard 等机制。讲者自己的 architecture.md、log book、dashboard、master agent 设想也在同一方向上。（第 17、18、19、23 部分）

12. 这些 agent-native 经验来自真实实践、失败和开源，不是课堂推演；如果没有 token 和反复试错机会，学生就更难追上 agent，旧培养体系会按性价比被“斩杀”。因此讲者最后让大家去互联网找真正优秀的项目，并明确从 DPC Harness / DeepSeek Harness 这类开源项目看起。（第 22、24、25、26、27 部分）

讲者的结论/号召是：把开发当成受门控管理的状态迁移，亲自学、亲自搭 agent-native loop，并去开源社区找真正优秀的项目，从 DPC Harness / DeepSeek Harness 开始。

### 课程过半，今天转向 Agent native 开发
- 课程已进行到差不多一半，讲者今天进入 **Agent native 开发**（原识别：A阵 native 开发）怎么做。
- 今天早上 **TEO（原识别，未确定）** 宣布今天要 **reset**。

### reset 前挂长任务：goal、复杂数学证明与 token 额度
- 讲者问听众：有没有设置一个 **goal**（原识别：go），让它去跑很长的任务？
- 他自己的例子：积攒了一些非常消耗 token 的任务，例如一个复杂的数学证明；他自己也不知道怎么证，但可以让 agent 去证。
- 代价：这种任务可能把一周额度全部跑完。
- 操作：离开办公室前直接上一个 goal，让 agent 继续证明；等今天 reset（以及第二个实验发布）后再继续/释放额度。
- 讲者把“今天 reset”和“第二个实验发布”放在一起说。

### 第二个实验：从个人 Agent 产品推进到“算力换智力”
- 第二个实验和第一个实验有点不一样。
- 第一个实验：有点像产品，做个人 agent。做个人 agent 的过程中，会发现一些产品发布，例如 **Grok bot**（原识别：Grog bot / grb board / grp boss，疑似同一产品）；它开课前已发布，最近才火。
- 讲者把日常 job 迁移到自己的 Grok bot：
  - 每天给小朋友生成 **podcast**，开车时听；背后调用 **Claude Code** 的 **Opus 4.5** 模型（原识别：cloud code 的 opus s5.5）。
  - 每天收到 **morning paper** 推送，例如 **CVPR** 论文；这个 **prompt**（原识别：PROMPTY）是讲者调过的，所以直接让 AI 总结论文会得到不太一样的结果。
  - 还有 **GitHub trending**（原识别：github training）等。
- 第二个实验会取第一个实验里的一小部分：第一个实验中的 agent 可以帮你 **digest 邮件**，或根据你的数据库回答问题。
- 实验2要把 **“算力换智力”** 稍微向前推进一点。
- 讲者理由：Agent 虽然具备 **长程任务** 完成能力，但解决问题的 **直觉** 稍差一点。
- （整理者串联）所以实验2不是单纯重复个人 agent 产品，而是用更多算力/搜索去补这种直觉短板。

### 类比 PhD 学生：能 DFS 往下做，但要在 design space 里找解
- 讲者认为 Agent 有时很像 **PhD 学生**（原识别：pg student / p h d student）。
- 场景：有一个有趣问题，可能是研究问题；学生想到一个方法，这个方法肯定有合理性。
- 有了 problem 和 idea，就可以不停往下做：用 **DFS（深度优先搜索）**（原识别：DEFAST）的方法，先把 idea 实现成原型，再优化，再改进实验结果，继续。
- 但讲者强调这里有一个 **design space**。
- 他常对 PhD 学生说：通过做一个 **deep/narrow** 的具体研究——例如软件工程里 Python 代码某种类型补全问题，一个非常窄且很深的问题——你可以把它做好；但在过程中你会体会到，你其实是在一个很大的 design space 里找到这个问题的一个很好的解。
- 讲者结论：所以我们训练人类、训练模型，两者的东西是稍微有点不一样的。
- （整理者串联）链：Agent 会长程执行、沿一个合理 idea 做 DFS；但直觉弱，可能缺少在大 design space 中比较与选择的能力；PhD 训练则试图让人通过具体 narrow 问题体会 design space。

**小结：** Agent 能长程执行但直觉弱；“算力换智力”是第二个实验推进方向，博士生类比用来解释人类与模型训练的差异。

**人类训练与模型 RL 不同：模型像巴甫洛夫的狗，完成任务才给奖励**
- 讲者从“能不能找到这个问题的好解”切入，指出：人类训练出来的东西和模型训练出来的东西稍有不同。
- 模型强化学习的典型说法是：最后完成任务 → 就给奖励。讲者打比方：像巴甫洛夫的狗一样。
- **（整理者串联）** 这一对比为后文铺垫：模型 RL 很依赖最终任务奖励，而 design space 里的早期分叉会显著影响最终结果，所以不能只靠最后奖励来指导搜索。

**Design space 浅层分叉很多，搜索要综合宽度与深度**
- design space 里有很多分叉，而且它们都在搜索空间的浅层。
- 不同方案会对最终结果产生很大影响。
- 讲者称这是一个“分叉/分支（转写为 breakfast，疑为 branching）的过程，宽度有限”。
- 搜索必须综合宽度和深度，因为算力有限。
- 逻辑链：
  1. 浅层有多个分叉。
  2. 不同浅层选择会放大到最终结果。
  3. 只走窄或只铺宽都不够。
  4. 算力有限 → 必须做宽度与深度的折中。

**Agent loop 的参考：多模型互评比单模型一条路走到底更有效**
- 你们会自己做一个 **agent loop**，这个 loop 里也有参考做法。
- 例子：**Humanize**（原转写 HUMHUMANIZE/Humanize，疑似团队/项目名）。讲者说他“一直潜伏在他们的群里”，他们烧了很多 token，研究如何让 **multi-agent 协同**完成更困难的事情。
- 他们最后发现最有效的方式：让 **GPT 和 Claude 互相 review、互相挑刺**。
- 类比人的多样性：要找两个人，而且互补。讲者提到“很容易达成共识”的问题：如果我说这个方案这样会更好，另一个人可能很容易就同意。
- 在**宽度优先搜索**过程中，用两个不同模型：两个不同模型带有不同偏见；讲者说每个人也都是带偏见的。一个模型说往这走，另一个就可能岔开。
- 讲者提到“几轮以后可能找到一个更好的 **solution**”。**（整理者串联）** 这应指两个不同模型互相 review、在宽度上岔开后的搜索过程；若只让一个模型“一路走到黑”，就可能沿单一偏见走，效果不同。
- 技术要点：还要构建**知识库**。

**Deeper research 需要更多知识来源，不只是实验 database**
- 第一个实验里，你们已经构建了自己的 **database**。
- 如果想做 **deeper research**，需要更多 **knowledge**：实验作业、奖学金申请、个人简历、研究论文、博客、GitHub 项目、从书里摘选的片段等，并放进 **report**。
- 因此这个实验会稍微开放，但基本上仍有框架。
- 讲者说，实验可以选择“摆烂”——直接不做，可能也能 OK，课也可能就这么过去。
- 但如果做过，有 first time 经验，真正观察过 **agent trajectory**，会发现一些有趣的、只有自己才有的体会。

**软件工程也解决同一空间问题：intent → spec → implementation 是一对多**
- 讲者特意画了图。软件工程解决的问题也是这个空间里的问题：从 **intent → spec（原转写 spark）→ implementation**。
- 他举例：我可以画圈，也可以画三角——说明选择不是唯一的。
- 人的脑容量有限。组一个小团队做一件事，或自己做一个大作业，在 **intent space** 里都只是采样一个点。
- 但实际上 intent space 里有很多点。
- **intent → spec 是一对多**；**spec → implementation 又是一对多**。

## intent→spec、spec→implementation 都是一对多：每个箭头靠 review/讨论/迭代收敛

讲者先给出结构：

- **intent → spec** 是一对多。
- **spec → implementation** 也是一对多。
- 由此，一个 **review** 可以和参与者来回讨论；经过几轮迭代达成共识后，落到一个点；再到下一个点，又经过几轮迭代，再达成共识。
- **（整理者串联）** 这套结构的关键不是一次确定，而是在每个一对多分叉处局部收敛；收敛结果再进入下一步。

## 需求阶段：访谈和 checklist 对齐甲方；甲方越说得清，intent 越清楚

- 讲者举例：需求与架构。
- 在需求阶段，可能做 **访谈**、**checklist**，与甲方对齐。
- 如果甲方是说得清楚、对自己想做的事非常清楚的人，就可以走向一个更清楚的 **intent**：到底要做什么。

## specification 阶段：与有经验架构师讨论技术选择，多想法可能收敛出很不一样的实现

- 在 **specification** 阶段，可以和**有经验的架构师**讨论：用什么数据库；用不用 **event sourcing**。
- 讲者提到最近某 “pad”（原文，术语不确定）开发者站出来说，他们不要用 event sourcing，而用了另一种 **functional design**，也是类似的，需要 **persist everything**。
- 讲者认为，这个过程会产生很多不同想法，最终收敛到一些很不一样的实现上；“一条线走到黑”的实现，在**可维护性、可观测性**上会差**十万八千里**。

## 软件工程解决的就是一种智慧：用 UML 等约束设计空间，让早期达成一致；工具链支撑日常实践

- 讲者说，软件工程解决的就是一种智慧。比如用 **UML** 建模；当你用 UML 建模时，就是在约束这个空间的行为，让你在项目早期就可以和别人达成一致。
- 也有很多工具：从 **IDE / VS Code IDE**，到管理版本状态的 **git worktree**，还有更先进的工具和无数工具，讲者说举不过来。
- 如果你或 agent 每天在 **GitHub** 上给你推一个 **GitHub trending project**，进去看，会发现每个项目用了不同**技术栈**，里面有很多好东西；每天花几分钟，比如追问一下，就能提升自己的技术积累和品味。讲者说这是前一半讲过的内容。

## AI 的最大能力：从任意阶段随时开始，让 AI 向下推进并生成版本比较趋势

- 讲者认为 AI 给我们的最大能力，还是**随时随地都可以开始**。
- 你可以想着可以学、可以想，但不需要想太多；在任何一个阶段，哪怕最开始只有一个想法，就可以直接让 AI 向下做。
- AI 可能到不了那么深：做到最后可能 stop、维护不下去，或者你觉得看不下去了。
- 在讨论过程中，也可以随时让 AI 生成一个版本；这个版本可以比较：是变好了还是变坏了，趋势上是变好还是变坏。若变坏了，就再讨论，再让它做一个版本。

## AI 可承担员工甚至团队职责；需求分解好时可启动并行 agent

- 讲者说，AI 实际上承担了一个员工，甚至不只是一个员工，甚至一个团队的职责。
- 如果需求可以分解成两个 **subsystem**、需求模块分得比较好，就完全可以启动两个**并行 agent**。
- 讲者说，像他现在实际开发一个项目的时候……

### 需求能拆成两个 subsystem，就可启动并行 agent

讲者的推理链：

1. 需求可以分解为两个 **subsystem**；
2. 需求模块分得比较好；
3. → 完全可以启动两个并行 **agent**。

讲者自己的做法：

- 实际开发一个项目时，他有一个 **tmux 窗口**（原转写“TMARS 窗口”），分四份，就有四个 agent。
- 他最多只开四个并行：不是技术上限，而是个人上限——不然大脑跟不上 AI 输出速度。
- 他负责**监工**，因此可以很快在**搜索树**（原转写“搜索书”）上探索，也可以推进并行的需求想法。

### AI 成本足够低时，先让它搓原型，再用典型 use case 评审

- 当前阶段可能只有一个 **intent** 或 **spec**；如果 AI 成本足够低，就可以先让它承担，帮助预测。
- 他举的预测问题：这个架构如果“这个人来了”会怎样？用户多了以后会怎样？两个模块之间有没有之前没想到的交互？
- 讲者的判断：很多问题只有真正实现出来以后，才意识到“这个地方设计出了一个小问题”。
- 因此他的做法是 **let it fail**（原转写“let it feel”）：我现在没想清楚不要紧，你给我搓一个；搓完以后，把 **use case** 构建出来，再评审一下。
- 讲者认为：它可以替代人类的智力；有些事情他做的就可以让 AI 做了。
- 所以 AI 给了**构建原型**的非常好的能力；而要用 AI 构建非常好的原型，就需要 **agent loop**。

### 早期模型有幻觉，所以 Devin 式自主 agent 当时被观望

- ChatGPT 大家当然有印象。
- 讲者提到：2023 年时你们大概在上初中或高中，可能在社交媒体上看到新闻；有人提醒“模型有幻觉”，模型很强但不能完全相信。
- 他举了一个 milestone 叫 **Devin**（原转写“Dave in / DEI”）：最早一批 coding agent，号称能解决数学问题等。
- 那时大家观望，因为 GPT-4 幻觉非常严重，说着说着就不知道在说什么；也没有像 **o1**（原转写“欧冠”）那样的思维链模型。
- 所以当时的疑问是：这到底行不行？它好像确实能够自主产生。
- 讲者的理论推演：如果模型学会了这个过程，又是不知疲倦的永动机，那么 assign 一个任务后，理论上就可以无穷无尽尝试下去，直到得到相对最好的解。

### 模型没有学会无穷试错：RL 奖励“完成任务”

- 讲者认为，模型没有学会的原因之一是：强化学习时有一个很重要的奖励——**你要完成任务**。
- 如果你花了很多时间都没有完成任务，就会停留在这个上面。
- 他觉得这跟训练博士生其实有点像。

## 设计/调研阶段：调研清楚不是目的，快速推进才是；要平衡广度优先与深度优先

- 讲者先描述一个现象：花了很多时间仍未完成任务，一直停留在某个点上。讲者认为，这跟训练博士生有点像。
- 很多同学喜欢在**设计阶段**读大量文献，把问题调研清楚；这时导师会说：你的时间有限，可能需要进入“看到什么、需要什么就学什么”的阶段，然后快速把问题推进下去。
- 讲者由此提出：关键是 **breadth-first search（广度优先搜索）** 与 **depth-first search（深度优先搜索）** 的平衡。
- 逻辑链：
  1. 设计阶段追求完备调研 → 2. 时间有限、任务卡住 → 3. 改为按需学习、快速推进 → 4. 本质是广度搜索与深度搜索的取舍。

## ReAct 型自主 Agent：任务压力与奖励让它偏向较短的广度搜索

- 讲者指出，今天的模型，尤其是 **ReAct 型 agent**、自主调用工具的 agent，仍有完成任务的压力；而且完成得更快会获得奖励。
- 因此，讲者认为它会倾向于一个比较短的 **breadth-first** 搜索。
- 它也会在思维链里想：“如果我要做这件事怎么办？”但会有“but wait”式的停顿。
- 讲者提到看 **DeepSeek** 的思维链时，它经常说“等一等，也许可能不一样”，会做一些思考；一旦找到一个它认为合适的路线，就会继续往下。
- DeepSeek 的例子：它会想一段时间；如果讲者给它太难的任务，它会摆烂，说“这个任务我解决不了”就停下。讲者认为，这是它受到**强化学习**影响的表现。

## 理论上：足够好的模型 + 一个工具 → 可以做任何人类可做之事

- 讲者设想：如果给一个足够好的模型一个工具，比如 **Bash** 或 **Python**，理论上就可以让它去造芯片、证明**黎曼猜想**。
- 他的类比是：想象模型把讲者本人蒸馏了，把他知道的东西都蒸馏进去；那只要给“我”一个 **Bash**，讲者好像就可以干自己能干的所有事情：用 Bash 编辑文档、用 Bash 看文档。
- 历史类比：早期 **UNIX** 时代还没有今天的图形用户界面；那些大师，例如 **Knuth（克努特）** 还在写 *The Art of Computer Programming* 的时候，就真的是在一个 **shell** 里和其他工具交互。
- 讲者说，在那个 shell 里，你可以造芯片、证明黎曼猜想、做任何事情。
- 逻辑链：足够强的模型 + 通用工具接口（Bash/Python/shell） → 工具可交互、可组合 → 任务范围扩展到极广。

- 讲者同时承认：现在模型还没有到万能、和最好的人一样好。
- 因此，你需要一个 **agent loop**。

## 自己做一个 ReAct Agent：先简单核心，再与成熟系统比增量

- 讲者说给大家准备了一个 **Agent** 例子，并问大家有没有实现过一个 ReAct 类型的 Agent。
- 讲者认为：在 AI 时代最重要的是，你有任何想法，都可以自己做一个；做完之后，再和成熟的东西比一比，看那个**增量**。
- 方法上：先了解一个简单的核心，再去知道自己的东西和复杂东西之间多做了什么；然后很快把增量“加进来、加进来、加进来”。

- 安全提醒：讲者说这里应该没有他的 **API 泄漏**；大家要小心保护 **API key**，尤其在不锁屏的时候。

小结：讲者用博士生设计阶段的调研困境类比 agent 的搜索策略，提出“足够模型 + 工具”的理论上限，但现实仍需 agent loop，并鼓励自己实现简单 agent 再对比成熟系统。

## API key 要保护好：bash tool 能读到本地终端里的东西

## bash tool 不是黑盒：它就是可序列化的 Python object
- 讲者展示：bash tool 是一个合法的 **Python object**，可以 **serialize 成 JSON**。
- 它的结构：
  - `type`: function
  - `name`: bash
  - `description`: ...
  - parameter：`command`
- 含义：你可以用 bash 执行一个 command。讲者这里有一个对应的 `run_bash` 来执行。

## hardcode timeout 暴露 toy project 与真实 project 的差距
- 讲者在 toy project 里 **HARDCODE** 了一个 **timeout**。
- 讲者提醒：真实软件工程中，coding agent 会为某个任务设 timeout；但 timeout 可能因为**对环境感知不够好**而不合适。
- 例子：在“墙内”访问 GitHub，教育网可能确实能访问，但**速度与 agent 认为的 GitHub 速度不一样**。
- 讲者亲历：第一次“肉身到墙外”，看到 `git clone` 能跑满网卡带宽时非常震惊。他反思：自己的世界观一直在这个地方，所以**overfit 了这个环境**；到了另一个环境，git clone 可以跑满带宽，虽然知道可能是预期，但还是震撼。
- 逻辑链：
  1. 固定/不合适的 timeout
  2. 环境速度与 agent 假设不一致
  3. shell 被杀掉
  4. agent 需要换一个 timeout
  5. 讲者的这个软件不支持这个 feature
  6. 由此显出**最小原型和产品之间的 gap**，可能需要**架构**来补。
- 讲者结论：如果你不实现它，不让 AI 做一个最小实现，你就不可能被启发去思考这个方向的问题。

## Agent 主循环就是一个 while 循环
- 请求：直接调用 `api.deepseek.com/chat/completions`，然后 `read reply`。
- 循环步骤（讲者版）：
  1. 从终端读取用户输入
  2. 构建 message
  3. `read reply`
  4. 如果 reply 里没有 **tool call**，直接把 reply 输出
  5. 如果有 tool call，reply 里会带一个 tool call；也可以理解为大模型以文本方式输出，只是 API 帮你做了一层 parse
  6. 如果 tool call 是 **bash**，取出参数，跑 bash
  7. 把 run 的结果放回去：结果对应 tool call 的 **tool_call_id**，把 output 结果放进回复中
- 讲者结论：就这么简单，这个 agent 真的能用，约 **150 行**，“挺好”。

## 让 agent 生成 HTML 卡片：任务可能耗时
- 讲者给 agent 的指令：生成一个**生成式软件工程的简介 HTML 卡片**。
- 因为 agent 有 bash tool，理论上可以用字符串，直接在 **bash** 里写字符串（或写文件）。
- 讲者预计：输出 token 可能会有点长；他好像给了它一个**需要花一点时间**的任务。

- 讲者称今天 harness 的核心、或“今天的版本答案”，是一个叫 **Ralph loop** 的东西（ASR: RPFLOOP / rough loop / rap hop）。

- **（整理者串联）** 它把“同一 prompt + 反复检查修改”当作最小循环，停止条件是“无法改进”。

**同一 prompt 反复跑：prompt 不变，但世界/上下文在变**

- 讲者说，他们不断尝试把同一个 prompt 丢给 **Claude 的 API**，让同一个任务检查、修改，直到无法改进。
- GPT 给了一个总结，讲者觉得还挺 surprising：**“The prompt is the same, but the world changes.”**
- （整理者串联）这意味着：prompt 固定，不等于交互对象、任务状态、上下文固定；世界一变，模型面对的局面就变了。

**理想假设：足够好的模型 + bash 工具，就能自己探索搜索空间**

- 讲者提出一个基本假设：理论上，足够好的模型，给它一个 **bash 工具** 就够了。
- 极端说法：神仙模型拿到 bash 后，自己知道要探索这个搜索空间，自己探索，然后自己把 **黎曼猜想** 证明出来。
- 讲者认为，这种东西人类确实很难理解。

理想链：足够好的模型 + bash 工具 → 自己探索搜索空间 → 自己解决问题，甚至证明黎曼猜想。

**现实假设：模型容易漂移，还会被已有代码和指令遵循拖住**

- 但讲者假设，现在的模型还是很容易漂移，像 PhD student：
  - 脑子一热，哗哗哗全给你做完；
  - 已有的部分、已有的代码污染它的上下文；
  - 又有一种强烈的 **“舔狗”式倾向（sycophancy）**：它会遵循指令，不能去动用户的东西。
- 类比：讲者作为博士生导师，可以对刚开了一个 repo 的学生说：“你这个代码是零分的代码，再拿这种代码来，你就不要来见我了。”
- 学生虽然会感到痛苦，但能理解导师可能是为他好，这个项目确实不应该这样实现；所以下一个版本，他会把架构全部推掉。
- 模型不一样：如果上下文里加载了用户的 **slop 代码**，模型会有强烈倾向：“我的任务是把这个 slop 代码扶起来。”

现实链：模型易漂移 + 已有代码污染上下文 + 指令遵循/舔狗倾向 → 倾向于扶起 slop，而不是重构架构。

**为什么模型会陷入“扶 slop”而不是重构：重构破坏行为一致性，线上服务又只想先别崩**

- 当模型说架构要重构时，重构很可能不能保持代码行为 100% 一致。
- 这个变化可能把项目往好的方向推，但对用户来说，可能是一种比较粗鲁的行为。
- 因为代码可能就在线上跑着，用户真的只想让它花一分钟，把当前项目赶快扶起来，让在线服务不要崩掉。
- 所以讲者认为：**它遵循指令也是有道理的，不遵循指令也是有道理的。**
- 结果：如果它选择遵循用户的 slop 代码，就会继续把项目往泥潭里面拖。

**出路：让模型停留在 design space，用 BFS/DFS 管理搜索空间**

- 讲者问：如果是真实模型，那我们怎么办呢？有没有可能稍微往前进一步？
- 方法：让模型停留在 **design space** 里，做 **BFS**（breadth-first search；原文 ASR 为 “breakfast search”），再适当做 **DFS**（原文 ASR 为 “defer”）管理这个搜索空间。
- 管理方式不限：用 **prompt** 也好，用 **loop** 也好，用任何方式去管理这个搜索空间。
- 讲者指出，**ReAct loop**（原文 ASR 为 “rap loop”）是一种 **线性的管理方法**。
- （整理者串联）这样做的目的，是别让模型过早钻进 slop 实现里，而是在设计空间里先搜索、再收敛。

**长程任务与 compact：上下文装不下，compact 后用量剧增且常降智**

- 对非常长程的任务，模型上下文装不下。
- 讲者点名 **Codex**：今天哗哗哗跑得很好，突然 **compact** 开始了，然后等在那里，用量也急剧增加。
- 而且一般来说，**compact 以后都会经历一段时间的“降智”**。

小结：理想模型给 bash 就能自探索；现实模型会被 slop 上下文和指令遵循拖住，所以要用 BFS/DFS 管理 design space，而 ReAct loop 只是线性管理，长任务还要面对 compact 后的降智。

## 第 9 部分

![截图](images/08-Agent-native%E5%BC%80%E5%8F%91/chunk_09_26m45s-30m58s_frame_main_000_002645.jpg)

**compact 后先降智、再恢复、再 compact：长任务会反复遇到 context 不足**
- **compact** 会突然开始，然后等在那里；接下来用量急剧增加。
- 讲者描述一般规律：**compact 以后会经历一段时间的降智**，开始各种做不对；突然有一天加载了足够多上下文后，又能做对了；做了一会以后，又要 compact。
- 因此一般设置一个 **goal** 后，很可能会遇到 **context 不够**的情况。
- 最近有一个“史诗级”更新：把上下文更新到 **500K**。讲者认同这确实是史诗级更新。

**500K 的好处是分解大任务，讲者的解释框架是 Everything is a state machine**
- 讲者说，这个好处是可以把大的任务分解。
- 他的理解仍是：**Everything is a state machine**。
- 物理世界也是一个 **state transition system**。
- 所以可以把 **workspace 的状态**理解成整个系统、或者说软件开发的状态。

**状态迁移流程：spec.md/prompt → 做一轮 → git commit → 下一状态**
- 初始 state：workspace 中可能有一个 **spec.md**，或者任何东西，几乎没有实现。
- 如果有一个 **Ralph loop（原转录作 “rough loop”）**，就是同一个任务，例如 spec.md 或 prompt，甚至 **prompt.md** 写在里面。
- 流程是：做一轮 → 从当前状态进入下一个状态 → 可以做一个 **git commit** → 进入下一轮 → loop 不断向前。
- 可以在 loop 里面给 prompt，例如：每次不要做太多；做完以后要检查；要确保；在做的时候还可以 review，找另外一个 agent review。
- 讲者认为这就是 Ralph loop 的好处：把原来模型“一把头向下做、把任务做完”这件事，分成了很多小步。

**非确定性状态机：同一状态可换 agent/操作，于是回到 search procedure**
- 分成很多小步以后，这其实是一个 **non-deterministic 的状态机**。
- 讲者把它简化成“做一轮”的写法，但实际可以选择：
  - 用 **GPT** 做一轮；
  - 换一种方式，比如让 **Claude** review；
  - 也可以让 **DeepSeek** 来干活。
- 在同一个状态下，其实可以执行不同的操作；这又回到了上面说的 **search procedure**。
- 当视角是“当前 workspace 是一个状态”时，可以选择在这个 workspace 上做一件事，或者每隔一段时间做一件事。

**周期 review 与重构示例：发现 AI slop → 删掉重做 → 得到搜索树**
- 比如每个星期做一次 code / 架构的 code review，看现在这个项目有没有变成 **AI slop**。
- 如果有 AI slop，就要进入一个重构；就要有一个**重构 agent**。
- 讲者建议这个重构 agent 可以设计得“狠”一点：
  - 把所有属于 AI slop 的东西和相关的东西直接删掉；
  - 做一个 commit；
  - 再让一个 agent 重新应用更好的架构来实现。
- 这样就得到一个**搜索树**。

**实际执行仍是一条线性路径：一状态到下一状态，直到任务完成**
- 当然，实际运行、实际走的时候，最终还是要做一个选择。
- 线性地从一个状态再到下一个状态，直到任务完成。
- 讲者认为这个想法非常简单，但会非常有效。
- 核心命题是：**每一次开发都是状态的迁移**。
- 在这个基础上，就能推演出现在今天各种各样的 coding agent。

小结：讲者把 coding agent 工作流统一为 workspace 状态迁移；Ralph loop 做小步迁移，非确定性选择生成搜索树，执行时再落成一条线性路径。

## 关键 loop prompt：每轮小步推进，然后停下验证

Loop 过程中有一个非常重要的 prompt：

1. 每轮先检查当前状态；
2. 只推进一个明确的步骤；
3. 然后验证并评估结果。

为什么要这样？讲者给出的推理链是：

- 基本假设：agent 训练得不够好，或者在当前上下文下可能发生 **漂移**；
- agent 自己的思路、想法可能会漂移，去做不应该做的事；
- 所以先让它往前做一小步，做一个相对较小的 **状态迁移**；
- 在这个状态迁移时，要让它停下来 **wait**；
- 然后做检查：可以用另一个 agent 或模型去 **review** 本次提交，也可以跑一些测试、检查脚本等；
- 这样就能在一定程度上阻止状态漂移，同时对整个项目的推进也会有进展。

讲者认为，这个想法并不新；在软件工程里，这是一个非常常见的 practice：**开发者是不可信的**。

## “开发者不可信”来自软件工程的旧原则

- 讲者回顾“计算机系统基础”里的两条公理：
  1. **机器永远是对的**，不要怀疑机器；
  2. **被测代码永远是错的**（原音近“位测代码”）；错误其实就在你自己，所有东西出问题都不要埋怨别人。
- 这是做码农的 **first principle**：所有错都是你自己的错，没有别人可以埋怨。
- 但人的本性还是会相信自己；人不可能绝对不自信；而人的自信就带来开发者的某种 **不可信**。
- 具体表现是：开发者会想——
  - “我今天就改这一句话，文档里改一句话，应该没事的吧”；
  - “我就把这个循环变量从 1 开始改成从 0 开始，应该没事的吧”；
  - “啊，我单元测试通过了，应该没问题吧”；
  - 学生版：“样例过了，我是不是可以交 OJ 了？应该程序是对的吧。”
- 讲者说，正是因为这种不可信，才经常出现“实习生推了一个 PR……”这类情况。

小结：讲者的核心链是：设计空间未知 → 旧 prompt/skill 未必迁移到新模型 → 用背靠背对比验证 → 用“小步推进 + 每步检查”的 loop 抑制 agent 漂移，而这条原则又来自软件工程对开发者不可信的假设。

**不可信 PR 的现实，逼出“每个状态都要是好的”**
- 讲者先调侃常见心态：“应该程序是对的吧”，“你们脑子里面每天都是这样的事情”。
- 但现实中，这种不可信会导致：实习生推上去一个 **PR**，整个生产系统就挂掉；讲者说这种事经常发生。
- 于是自然会想：在状态推进过程中，希望每一个状态都是好的。
- 做法类比刚才的 **REPL loop**（[ASR 作 RFLOOP/rap loop]）：每个状态后面都做一次检查；检查不通过，就直接拒绝这一次 loop 的结束，回到上面，把所有问题都修好。

**这等于发明 CI/CD：把开发过程当成 state transition system**
1. 不可信的 PR → 可能挂掉生产系统。
2. 所以每个状态推进后都要检查。
3. 检查不通过 → 拒绝推进/发布。
4. 所有检查都通过，且找不到任何问题 → 可以发布。
5. 检查过程应自动化，发布过程也可以自动化。
- 讲者说，这就是软件工程大约 20 年前开始热门的东西：**CI/CD**（CICD）。听起来很高大上，老师会说“你们要 CI/CD”，其实想法就是上述。
- 具体说，就是把软件开发过程也想象成 **state transition system**：每个开发步骤之后都停下来，做足够多的检查；检查多到一定程度、全部通过，才发布。

**First principle：不要相信任何开发者**
- 讲者说，这是 **first principle**：不要相信任何开发者。
- 实习生例子：你进公司第一天就跟实习生说“做好测试”，他不会去测试。
- 算法题类比：老师不断说做算法题要写测试、写断言，你们不会；你们一定是过了用例就提交。
- 原因：你们是 **speculative** 的，大脑很聪明，先算一个期望；交题（ASR 作“交互”）又不花钱，也许十秒钟就能得到正确反馈，**fast path**（[ASR 作 fast pass]）就过了；如果不对，还可以再回到 **slow path**（[ASR 作斯洛帕斯]）。
- 讲者结论：人总有投机的倾向；因为人是社会中生存的，一旦有这种投机倾向，你就变得有点不可信。

**工程化不信任：门控写进脚本，且不让实习生运行**
- 如果不相信实习生，就把所有门控全部写在脚本上。
- 不仅要把东西写在脚本里，还不能让实习生去运行——不要相信实习生会运行它。
- 所以你发明了一个东西叫 **.github**：repo 里都有 .github，里面有一大堆运行配置和脚本，你看都看不懂。
- **（整理者串联）** 这一步把“不可信”落成自动门控：检查不由人手动做，而由系统脚本执行。

**CI/CD 为什么学生不熟：它通常嵌在生产流程里**
- 尤其学生不理解 CI/CD，因为它通常集成到一个生产流程里。
- 这会涉及：容器的创建；需要一个独立于你本机的环境（讲者说本机实际上不可信）；跑完所有流程；把流程结果同步到整个企业流程里；你可能要在一个页面上看到。
- 这些复杂性都需要学，需要了解软件系统的设计，才能去做。
- 所以同学之间用得相对比较少，但讲者强调：它的想法真的就是这样。

**小结**：讲者把 CI/CD 还原为“不信任人，所以自动门控”的状态推进问题。

### **在适当状态做适当检查，就能自动推进后续步骤**

讲者承认，这种做法在同学之间可能相对少用；但他认为核心想法就是：**在适当的时候做适当的检查**，然后就能自动推下面的步骤。

**讲者给出的逻辑链**：

1. 做 **integration**，集成到主干；
2. 每次集成可自动 **build**，甚至编译；
3. 推完以后，整个项目可以 build、可以编译；不仅可编译，还可检查、验证、发布；
4. 上线可由人决定；通过检查的变更也可自动上线；
5. 只要看到 **release tag**，就可自动把所有 release build 全部推上去，全自动。

（整理者串联）这里的重点不是某一步本身，而是把“检查”接到“后续动作”上，形成自动流水线。

### **开发流程中的事件与 hook：状态迁移前后都可插入动作**

- 开发流程中有各种事件：**commit**、**push**、发起 **pull request**、merge 到某个分支、merge 到 **protected branch**。
- 讲者说，理论上可以在任何事件上放一个 **hook**。
- Hook 可加在某个状态/事件之前，相当于 **transition** 之前；也可加在 transition 之后。
- 只要把 hook 配置好，就能指定“要干什么、干什么、干什么”。
- 讲者举自己环境中的例子：之前播放声音失败，现在声音好了；每次需要他输入时都会“叮”一下提醒，代表输出结束。比如让 **Codex** 总结这里的 **CI** 流程，总结完应该会“叮”一声提醒。这个例子说明事件/hook 可用来触发通知或其他动作。

## 写成 `doc.md` 后，它与 `implementation.py` 形成关联，但 repo 维护方式看不见

一旦写进文档，就会出现一个问题：你有一个 `doc.md`，还有一个 `implementation.py`，两者之间是有关联的，代码和文档关联。但今天基于 **repo**（原音 rapport）的软件维护方式，这个关联你是看不见的。它只是说，你在写的那一刻、实现文档的那一刻，知道这两个东西是关联的。

下一次如果你换了一个 agent，比如上下文经过压缩，那个 agent 不记得这两个文档要保持一致，那就完蛋了。

**讲者给出的逻辑链：**

1. agent 把思考流程、agent loop 中遇到的问题写进 `doc.md` → `doc.md` 与 `implementation.py` 有关联。
2. 当前基于 repo 的维护方式看不见这个关联，只有写的那一刻知道。
3. 换 agent 或上下文压缩 → 新 agent 不记得两个文档要保持一致。
4. agent 改改改，把 Python 改改改 → 文档和代码不一致。
5. 文档代码不一致，到底听谁的？不知道 → 项目滑向 **slop** 的崩溃边缘。

## 文档与代码不一致时，“听谁的”无法决定

讲者说，agent 会改 Python，改了以后就会出现文档和代码不一致。文档代码不一致，到底听谁的？不知道。整个项目就开始走向、滑向 **slop** 的崩溃边缘。讲者认为，AI 非常容易产生这种代码。

## AI 偏爱过细文档，细节随版本调整，维护成本越来越高

原因之一是：如果你让 AI 写文档，它太喜欢写非常细节、非常细节的文档。而这些细节会随着版本不断调整，也导致项目维护成本越来越高。

讲者说，AI 会过度反应，会在不重要的细枝末节上面疯狂出力，而对这个 **design space** 里面最重要的那些视而不见。

（整理者串联）这条链可以写成：过度行动 → 截图和工具输出填满上下文 → 真正重要的 design 判断被淹没。

- 看 docs 里随便一个 **Architecture.md**（原声“Architecture 点 markdown1”），是非常有人感的文档，看起来很干净舒适。

- 这引出追问：项目里有中文和英文文档，它们如何保持一致，又如何保持人感？

## 解决方案：三套件 + 一个门禁，把每篇文档变成“同目录三兄弟”的配对契约

逻辑链：中英双文档 → 同目录三兄弟配对契约 → 双侧 hash + git 历史判断新旧 → 不匹配触发 AI patch 翻译 → 程序校验 hash → 一致性。

1. 每篇文档在范围内都是同目录的 **三个兄弟文件**，定义配对的契约。
2. 这三个文件包括：中文 markdown、英文 markdown；讲者说中文 markdown 现在还是 **开发者预览阶段**。
3. 还有一个现在不太常见的 practice：**i18n.yaml**（原声“I18N点 yao”，internationalization 的 yaml）。
4. 讲者说“两侧是权威”：谁先写谁就是源，另一侧由 **co-agent** 翻译过来。
5. 绑定它们的要求是：必须做同一件事。
6. 一致性由 **`pnpm run verify-translation-pair`**（原声近“p m p m run verify translation Parry”）检查。
7. 办法：在另外的文件里放一个 **hash**，两边各放一个 hash。所有过往都留在 **git 版本管理历史**里，所以知道谁变了、谁先变、谁没变、谁更新谁更旧。
8. 类似 `git reflog`（原声“get it ripple”）的新旧判断：旧的 hash 是见过的，新的 hash 是没见过的；在工作区或更新侧，能判断谁新谁旧。
9. 一旦发现新旧版本不匹配，就用 **AI 翻译**。
10. 翻译也是 **patch-based**：看这个文档改了什么，把另一份文档对应位置也改掉，其他地方保持一致。
11. 有些东西由程序保证，比如 hash。例如 English/中文两侧对应的 hash 会放在文档中（原声“DEEPC和list ENGLISH的这个中文的hash在这里”）。这段很短的文本就能保证一致性。

**（整理者串联）** 以上机制形成一条链：配对契约 → hash/git 新旧判断 → AI patch 翻译 → 程序校验，用来保证中英文文档一致性。

小结：讲者用三套件加一个门禁，把中英文文档一致性交给配对契约、hash/git 判断和 AI patch 翻译来保证。

## 文档没有 document 或接口设计变了，代码必须同步

- 讲者先立了一条硬规则：如果**文档没有 document**，或者**文档改了接口设计**，而**代码没有跟上**，就“绝对杜绝这种情况”。
- **（整理者串联）** 这实际上是在防止 **文档—代码漂移**：接口设计一变，代码必须同步，不能文档说一套、代码做一套。
- **（整理者串联）** 这也解释了后文为什么要用大量 CI/检查把一致性机械化：靠人记不可靠，必须让漂移被门禁拦住。

## code block 带执行语义：把 spec 和轻量检查写进 Markdown

- 讲者说，他们把这个想法在 **agent native 项目**里稍微扩展了一点：**code block 是带执行语义的**。
- code block 里可以 **specify 一个非常小的说明**，表明“我这段东西是干嘛用的”。例如：
  - 我需要它出现在某一个位置；
  - 我希望它以某一种形式和另外一个东西关联起来。
- 里面还有一些**轻量级 check**，扩展了 **Markdown fenced code block / code block** 的语法（原音频近似 “markdown 的 fans code block / gold block”）。
- **Code review** 也是一个环节；之后继续用 **skills** 分离出各种机械门禁：**Doc sync CI、static CI、coverage CI、snapshot** 等。

## 机械门禁的代价与收益：提交前多跑检查，换来项目被维护住

讲者给出的逻辑链可以整理为：

1. code block 带执行语义，可写小 spec 和轻量 check。
2. 这些 check 进一步被拆成机械门禁，如 **Doc sync CI、static CI、coverage CI、snapshot** 等。
3. 代价是：每一次提交之前，可能都要运行大量门禁。
4. 但在 agent native 工作方式下，“你又不写代码，大部分时候你都是监工”；你写 **plan**，和 AI 一起写 plan。
5. 具体做法：在 **log book** 里写 plan；在 **plan mode** 先搞清楚要做什么、做到什么程度；剩下的事情不是人做的，是 AI 做的。
6. 所以改 log book 时不需要运行那些 CI：**所有代码都没有动过**，因此不需要运行任何 CR/检查。
7. 单个门禁看起来都非常小，但把它们全部加起来时，就会发现：**项目被维护起来了**。

需要运行的验证包括：

- **verify client、UI、WiFi translation、pairing application entry points**；
- 一些 **TypeScript script** 相关检查；
- 其中一个关键是 **verify type equivalence**（原词近似 “verify type equivalent”）：**文档里粘贴的类型必须与源码一致，且不允许漂移**。

讲者还提到还有很多类似机制，比如**文档分层**、**从任务到机制的路由**（原音频近似 “税任务到机制的路由”）等。讲者把这一整套称为 **agent native**。

## 这些 agent native 经验来自真实实践，不是教室里推演出来的

- 讲者从 agent 时代的时间线说起：从去年到今年，尤其到今年年初，大家发现 agent；短短半年。
- 这个项目从 **6 月份**开始，就已经在规划这些事了。
- 讲者认为他们看到了一个非常好、非常有启发性的东西，并且它是**开源**的。
- 这些做法来自**真正的经验**：你一看就知道“确实应该是这样”，但很难完全凭空想出。
- 如果只是在教室里做**语言律师**，思维会被当前上下文禁锢，只能不停往下走；你不会发现 **design space / 搜索空间**里还有巨大空间，可以朝另一个方向探索。
- 讲者认为这些人肯定失败过、写过代码；他们的年龄可能和讲者差不多，是同龄人。因此他们有这些经验。

## 架构烂掉后的重构策略：新开空白项目，逐步迁移旧功能

- 讲者说，即便如此，大家做项目时可能都逃不过重构：最终有一天你会发现项目烂掉了。
- 他讲了自己对学生说的话：因为那个项目的 **architecture** 烂掉了，所以：
  1. 先开一份新的、白的[项目]；
  2. 然后一点一点把旧的功能迁进来；
  3. 保持一个好的架构。

小结：讲者主张用带执行语义的 code block 和拆碎的机械门禁，把 agent native 项目的维护变成可自动检查的约束；经验来自实践，架构烂掉时宁开新白项目逐步迁移。

## 方向不对时，重构比垃圾回收更根本：开新空白项目，逐步迁移旧功能

- 讲者的建议：先开一份新的空白（项目），然后把旧功能一点一点迁进来，保持一个好的架构；他用 “be like 好” 表示认可这种说法。
- 在 **DAFIRST（原词，疑似 design first）** 阶段，如果发现矛头不对，**garbage collection（垃圾回收）** 可能无法解决所有问题。
- 所以必要时要做**重构**：可以**模块级重构**，也可以**整个项目级重构**。讲者认为这能让项目走上更正确的方向。
- （整理者串联）这里的关键不只是清理垃圾代码，而是纠正项目的架构与方向。

## 历史失败（Friendster）被讲者当作 agent-native 开发经验的来源

- 讲者举社交网络先驱 **FRANSTER（Friendster）**：它迅速吸引大量用户，然后价格崩溃。
- 讲者说这是 **PREMM（原词）时代** 的事；在今天 **AI agent（原词 A 证）** 时代，可能 AI agent 能把它富起来。
- 讲者认为，这些经验最终促成了一个 **agent-native 开发** 的好范例。

## 威胁一：不反复试错、失败、建东西，好 intent 也会变成 AI slop

- 讲者判断：你不做很多次、不失败很多次、不建很多东西，就不太可能把一个东西真正做好。
- 你可能确实有一个好想法，在 **intent** 方面是世界级的。
- 但如果组一个**草台班子**去做，讲者说可能进入“一个直线”，海量产生 **AI slop**，最后好想法被别人抄走。
- 反之，如果有**有经验的团队**，更可能**收敛到一个更好的方向**。
- 讲者的链：好 intent + 草台班子/缺少试错 → AI slop → 被抄走；好 intent + 有经验团队 → 收敛到更好方向。

## 威胁二（社会性）：没有 token 就没有足够试错机会

- 讲者提到开学时随口说“没有 token 的学生应该立即退学”，并说明这是**玩笑**。
- 但真实发生的事是：**没有 token，尝试的机会就不如别人多**。
- 不去经历试错过程，就只能看别人；最后看你的**悟性**，能否通过看别人 **open source（原词 open 手）** 的东西学会。现在 open source 还有好的东西。
- 讲者认为，即便如此，你还是需要做很多尝试、失败。
- （整理者串联）token 在这里不只是工具成本，而是试错机会的分配条件；token 不平等会转化为能力积累的不平等。

## 斩杀线：读完博士不如 AI agent 好用，用人单位会选 senior + 无限 token

- 讲者问：如果读完博士时依然不如 **AI agent** 好用，用人单位会做什么？
- 讲者判断：他们会选一个 **senior**，给他**无穷的 token**，而不是培养一个 **PhD 学生**。
- 理由：如果是资本家，要最大化社会/企业的运行效率。
- 以前可以“师傅带徒弟”，招新兵蛋子，看潜力。
- 但如果你的**上升/回报点太长**，比如需要 **4–5 年**，公司早就黄了，你才达到 agent 的水平。
- 同时 agent 现在就在这里，而且 AI agent 实际上也在上涨；所有人都在被不断“斩杀”。
- 讲者的链：培养 PhD 需 4–5 年 → 回报周期长 → 公司/资本等不起 → 直接选 senior + 无限 token。

## 斩杀线继续下移：本科生毕业还有没有 $20 Claude Pro 的价值？

- 讲者说这条**斩杀线**现在越过，比如**本科生毕业**的时候：你还有没有一个 **$20 的 Claude Pro** 的价值？
- （整理者串联）这等于把同一套性价比逻辑下移到本科毕业：若你的作用不如每月 $20 的 Claude Pro，雇佣/培养你的经济理由就更弱。

### 20 美元 Claude Pro 订阅：Opus 4.5 的额度够用且能力很强
- 讲者说自己现在有一个 **20 美元 Claude Pro 订阅**，在 Anthropic 账号和某个工具（原文“ground bot”）里养自己的 **Claude Code**。
- 他发现 **Opus 4.5**（原文“OPPOS5.5”）的额度其实还挺够用，而且 Opus 4.5 真的很强。
- 他由此发问：本科生毕业的时候，是否还值一个 **20 美元 Claude Pro** 的钱？他的判断是：本科生要达到 Opus 4.5 的水平，“很困难，非常困难”。

### 有 big picture 的 senior + 好的 agent harness，是另一条优势条件
- 讲者设想：如果自己是 **senior**，有比较大的 **big picture**，又有一个好的自己的 **agent harness**，情况就不同。
- （整理者串联）这里与上一条形成对照：单纯“本科生水平”容易被模型追上，而全局判断加工具编排可能仍是讲者眼中的优势。

### 闭源大厂把能力锁在内部，会造成“越来越多人被斩杀”
- 讲者指出：像 **OpenAI、Anthropic** 这种东西从来没有开源出来。
- 还要靠“国产之光” **DeepSeek**（原文“d pk”）来开源。
- 他的推理链：
  1. 如果这些能力都留在公司内部；
  2. 并且永远不让别人知道；
  3. 那就会**越来越多的人被斩杀**。
- 讲者把这称为一个**社会性问题**。

### 理想解法可能在大学，但现实大学也是资本化、KPI 化、学阀化
- 讲者认为，这个问题的解决**可能只有在大学里能解决**，因为大学是**非盈利**的，不是以盈利性质或 KPI 为导向的地方。
- 但他马上转折：“话是这么说”，现实里大家都清楚：**学阀一手遮天**，网上能刷到这类故事。
- 他用自己的处境说明：考核指标不是上课，而是所谓的**科研经费**。
- 所以高校某种程度上也是**资本家和公司化运营**，越来越**资本化**。
- 区别在于：这是另一套资本体系，不是外面的资本体系，而是由 **基金委、科技部、优青、杰青、院士** 等构成的**金字塔**。
- 当这个金字塔下面每一个 **杰青**（原文“结晶”）的产出都类似公司产品时，体系就按公司逻辑运转。

### 学生追不上 agent → 老师学生被斩 → 旧体系失效 → 大学崩溃
- 讲者给出的链条：
  1. 当**学生永远赶不上 agent**；
  2. 老师和学生都被“斩”；
  3. 这个体系就完全失效。
- 因此他的结论是：**大学肯定要崩溃**。他自称这又是在“发表暴论”。

### 学而思被讲者看成“新形态大学”：样板课 + 资本化运营 + AI 执行
- 讲者反而觉得，像**学而思**这样的东西可能是一种**新形态的大学**。
- 理由是它从上到下都是**资本化运营**。
- 它靠的是**样板课**，而且样板课很牛逼。
- 具体做法：
  - 花 **100 万**雇一个清北天才来设计样板课；
  - 上样板课、试；
  - 试完以后，**每一个老师都是执行的机器**。
- 讲者进一步说：现在把老师的执行机器换成**老师 + AI**。
- 它还花 **1000 万**去“技摩场”（原文如此）抢最好的天才，然后设计样板课。
- 结果是：它把**教学、教育体系完全颠覆**。
- 对比传统大学：我们没办法，因为**惯性很大**，还得这样上课，还得用这个方式上课；而学而思因为是资本化运营，所以能这样做。
- 对“未来会发生什么”，讲者说：**我不知道**。

### 开源社区给了讲者今天的理解；建议去互联网找真正优秀的项目
- 讲者非常感谢**开源社区**。
- 他说：尤其是我自己，我自己的这一切都是开源社区给的。
- 如果不在开源社区里看到那些好的东西，他就不会有今天的理解，也不会来上这个课。
- 因此他的建议是：大家现在可以回去，在互联网上找一找那些**真正优秀的项目**。

## 今天的 demo：小到不能算标准 RL loop，重点在“一切皆插件”

- 讲者对自己今天演示的定位：它是一个“特别特别小”的 **RL loop**。
- 但严格说，它不能算 RL loop，更像一个 **A正点P**（原文如此；术语不确定，保留原词）。
- 他又说，可以把它理解成 **DPC Harness**。
- 它的关键特征是：**一切皆插件**，所有东西都插件化了。
- 讲者认为这里面有“一些有趣的东西”。

## 逻辑链

1. 真正优秀的项目值得去互联网上找。
2. 找的时候可以从 **DPC Harness** 开始看。
3. 因为 DPC Harness 与今天那个极小 demo 本质同类：都是 RL loop / 插件化结构。
4. 今天 demo 太小，甚至不能算标准 RL loop，只能算 **A正点P**；但可以把它当作 DPC Harness 的简化理解。
5. **（整理者串联）** 先看成熟项目，再回看今天的小 demo，更容易看清“一切皆插件”的设计如何支撑 RL 循环。

小结：讲者最后把 **DPC Harness** 作为成熟参照，并强调今天的小 RL 循环核心是插件化。
