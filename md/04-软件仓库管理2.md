## 1. 让 AI 一口气做完个人助手，会掉进焦油坑

<small>▶ [00:00](https://www.bilibili.com/video/BV1Q6en6NEUo?t=0)–05:17　·　开场　·　话题：个人助手实验与焦油坑</small>

- **Lab1 是做会成长的个人助手，做法不限** 作业选做自愿，最后由讲者的机器人验收评分。
    - 讲者建议用 vibe coding（字幕原文：web code，待确认），今天课上现场做一个。
    - 周日调休上课，会讲软件架构，并连起这个例子。
    - 学生做完后要交一些链接，由机器人评分。
    - 讲者说这个需求算比较时髦。
    - 讲者会告诉大家，直接让 AI 做会遇到什么小坑。
- **需求取自每个学生都用得上的场景** 需求只供参考，讲者自己也需要。
    - 讲者说实现这个助手会有一点成就感。
    - 讲者说这个项目对每个同学都有用，这是设计实验的初衷。
    - 资料库：存专业课资料，如计算机网络、概率，或研究组的论文和教科书。
    - 自动填表：把姓名、学号、身份证号、个人简历这些个人信息交给 agent 填 DOC 表格，讲者已全交给 agent。
        - 表格要填姓名、学号、身份证号，有时还要填个人简历。
        - 讲者说今年的填表效率比以往有非常大的进步。
        - **吐槽** 「我不知道大家是不是已经填表填得很烦了」
    - **玩笑** 讲者疫情时招的研究生做了 3 年自动填表系统，毕业时 ChatGPT 出现，他很慌，讲者说：「不要紧，你赶快答辩，然后就可以毕业了，这世界就是发展得这么快。」
    - 邮箱联动：agent 可能读邮件并回信，如讲者两周后半夜发的邮件。
    - always on：一两百元的嵌入式小设备可在宿舍持续跑 agent loop。
    - 手机端联动：网页、苹果 app 或 Android app 均可。
        - 只要让 agent 去做，它会自己下载所需的东西并实现。
- **直接让 AI 做完，会陷入焦油坑** 任务都在 AI 能力内，但它的决定看似合理，却难维护。
    - 讲者没试过直接丢需求，今天现场试。
    - AI 不断消耗 token，学生终会决定删除项目重做，或回退到早期版本。
    - 讲者认为每个同学都有必要体验软件工程里的焦油坑。
    - **吐槽** 「当你的 AI slop 开始不断地消耗你的 token 的时候」
- **后续 lab 会加冲突需求，让学生改到崩溃** 下个 lab 与此关联，学生暂时猜不到。
    - 新需求与 Lab1 全部功能关联且冲突，越改越崩溃。
    - **玩笑** 「然后越改越崩溃，就有一个这样的体验」
    - 躺倒让 AI 做完再删，就没有这次体验。

> 原话：「你终于会有一天会下定决心，好，我要把这个项目删掉从头重做。」

## 2. 文件系统表达不了制品间的关联，未来项目可能是带视图的图

<small>▶ [05:17](https://www.bilibili.com/video/BV1Q6en6NEUo?t=317)–19:20　·　转向　·　话题：文件系统装不下项目的关联</small>

- **项目的关联装不进文件系统，这是历史遗留。** 项目是 intent、spec、code 的集合，但 1950、60 年代操作系统只提供文件存储，程序员别无选择。
    - **README 只该写 intent，不该写成长文。** 讲者不喜欢 AI 写的超长 README。
        - README 写最初的初衷：想做什么产品，能达到什么效果。可附两张截图（字幕原文：两个spring shots，待确认）。再写最重要的设计。
        - 比方说有人想用好点子挣一亿，要说服懂 computer science 的人出来干。他只需要一份短 README，也就是 intent。
        - 对方补出 spec 和 code。内容有数据库选型、编程语言、项目结构、每个模块的接口。还有用户数从 1 涨到 1 亿怎么撑住。创业者不需要懂这些。
        - **玩笑** 讲者举创业的例子：「有一天你突然想了一个非常好的点子，然后你真的想用它去挣一个亿」
    - 那时关系型数据库还没发明，操作系统只给文件，所以项目只能存成文件。这个做法一直沿用到今天。
    - 讲者说大家用文件系统管理项目，真的只是图方便。他自己认为文件系统可能不是组织项目的正确方式。
    - 文件系统丢掉了不适合表达的信息。intent、spec、测试用例的输入输出和 assert 容易写成文档，文件之间的隐藏关联却没有地方记。

- **文档和代码的关联没人维护，会变成技术债。** 文档先于代码写成，代码一改关联就断，不一致只增不减。
    - **改了数据结构，文档仍写旧结构。**
        - 开发者让 AI 把 link list 换成更高效的 tree 来优化性能，AI 很快改完代码。
        - 某个 markdown 里仍写着「数据用 link list 管理」。文档、代码、测试之间有关联，但没有被强制联系。
        - 现在的 agent 好一点，有时仍会漏。
        - **玩笑** 讲者描述 AI 改代码的速度：「AI 就啪啪啪给你代码给改了」
    - 不一致只会越来越多，软件陷入维护泥潭。后来的人和 AI 分不清文档对还是代码对：聊天记录已消失，换了电脑，git 仓库里至多有一些 change 日志。
    - 这是 traceability 问题，软件工程研究了很长时间。幻灯片展示一篇 2014 年的综述。问题是测试用例、文档、文档里的一行与代码的关联，能否在演进中持续维护。
    - **吐槽** 讲者评价文件系统沿用至今：「文件系统将错就错了」。
    - 打压缩包发给合作者，终于维护不下去，于是有了 SVN 和 git。下一个工具是 Jujutsu，讲者稍后介绍（见第 4 节）。
    - **玩笑** 讲者说总有一天大家会撑不住：「你用文件系统来管理代码，你受不了了对吧」

- **未来项目可能是带视图的图，存在 repo.db** 讲者设想把文档切成对象，用有环的图记录关系，由 AI 维护。
    - 讲者说如果以后人不再写代码，软件就不该像现在这样管理。现在的仓库里有 README.md、hello.c 和各种文档。
    - **图能表达树装不下的关系。**
        - 文档切成多个切片，变成 object 或 entity。
        - 代码实现文档，测试用例对应文档，测试用例关联代码，文档关联文档。
        - 这是带环的图，树状文件系统表达不了。可以放进数据库，叫 repo.db。
    - 人用现有 UNIX 工具维护不了 repo.db，讲者的办法是训练 AI：只要有强化学习的反馈信号就能训练。这适用于 Linux 内核、数据库、价值一亿的产品。
    - **玩笑** 说到人类维护不了 repo.db：「用魔法打败魔法。人类理解不了的东西，我们只要训练 AI。」
    - AI 自动维护制品之间的一致性。文档说 link list，实现必须是 link list。文档说测试有 A、B、C 三方面，test case 必须有 A、B、C。
    - **视图让人只看和这一小步相关的部分。**
        - 例：讲者对幻灯片样式不满意，这是一小步。他的仓库顶层有 assets、.cache、P1 到 P5 和脚本，大部分与这一步无关。
        - AI 根据 chat 摘出相关的文件、测试用例和文档。AI 能动态生成任何内容（讲者说 everything is code），所以能生成视图。
        - 视图借用数据库的 view：数据不动，用另一种查询以另一种形式展示。人看到的可能是可视化看板，列出相关项并问要改什么。
        - 改完从 V0 到 V1，仍是 repo.db。AI 在相关处增删改测试用例，让系统从一个一致状态进入下一个一致状态。
    - 讲者认为这可能发生：AI 内部这样生产软件，人以后不再看代码。

- **AI 初期仍应小步修改，沿用 git 的经验** git 管理快照和快照之间的关系，鼓励小步前进。
    - 每修一个 bug、改一个文档就产生一个 commit。多人各自产生 commit，再用 rebase、merge、fast forward 合成可追踪的历史。
    - 软件已在工作时，开发者一般是增加或修改一个功能，不会把产品变成另一个产品。
    - 模型若强到让大型项目一步变成下一个，讲者说现在还不知道怎么做。初期仍沿用已有的软件工程经验，小步走向他所说的「极乐世界」。
    - 讲者仍然相信，这个极乐世界确实有可能到达。

- **讲者顺带讲了 2 件事：对 Cursor 的不满和学生的焦虑** 两件事都与小步修改的主线无关。
    - Cursor 打开就默认 agent mode，原来熟悉的 IDE 模式没有了，强迫用类似 chat 的方式沟通。讲者不喜欢。
        - **吐槽** 讲者说现代 IDE 如 Cursor：「我其实还蛮讨厌的」，还说它「强迫你用一个类似于 chat 的方式去跟他沟通」。
        - **自嘲** 讲者承认自己有掌控欲：「因为我还是相对来说比较精通古法编程，有时候我还是对代码有一些掌控欲，可能是不好的，这个可能是不对的」
    - 学生会焦虑：一两年后真有公司做了这东西，学的东西怎么办。讲者指出，上面的设想用的都是经典课程：数据库的 view、实体和关系，以及 git 的小步模型（见第 3 节）。

> 原话：「如果在这个模型底下我们是大步向前呢，那就惨了」

## 3. 经典课程的知识不会过时，要主动去看外面的世界

<small>▶ [19:20](https://www.bilibili.com/video/BV1Q6en6NEUo?t=1160)–22:56　·　转向　·　话题：经典课程不会被 AI 淘汰</small>

- **学生不熟悉 rebase，是因为作业不需要协作。** 学生时代多是独自做作业，几乎用不到 rebase 和 merge。讲者认为这个观点成立。
    - 上节课讲者问 git rebase，同学都答不上来。
    - 一位应该已毕业的同学评论说，学生时代大多数人不会和他人合作，只做作业。
    - 讲者的回应是：这个观点对，但走进外面的世界就不同了。
- **走进开源社区，迟早会在 contributing.md 里遇到 rebase。** 互联网开发者社区的文档铺天盖地，总有一天会看到别人的项目。
    - contributing.md 是仓库根目录下的贡献者指南，回答「怎么参与这个项目」。
    - 内容包括项目总体结构，以及分支、提交信息、PR 的规范和流程。
    - 讲者建议随手打开几个项目的 contributing.md 看一眼。
    - 如果文档里的内容都已知道，就不用管它。
    - **项目可能强制要求 rebase。** 讲者设想的情形：
        - 文档要求在自己的分支上 rebase，保持线性历史。
        - 文档禁止直接创建分叉的 merge。
        - 读到这里，就会知道 rebase 是做什么的。
- **高中「不考就不学」的思维，带到大学会形成落差** 这种思维在高中是升学利益最大化的正确做法，不是错误。
    - 讲者说现在社会变得太快，接着谈到学生的思维。
    - 高中老师不教的内容不用会，考试不考的内容不用学。
    - 到大学仍带着这个思维，就会出现「新人类」和「旧人类」之间的 gap。
    - 讲者说这不是批评，每位同学都能成为新人类，只需多留意更多东西。
- **斩杀线以下的低端智力劳动会被 agent 替代，要靠经典课程形成自己的理解。** 讲者有危机感，认为 AI 时代斩杀线以下的价值全部归零。
    - 讲者认为斩杀线可能还斩不到 985 计算机专业的同学。
    - **玩笑** 「当然我觉得现在斩杀线可能还斩不到各位985大学computer science专业的同学」
    - 例子是会计从业者：讲者看过报道，中国可能有 1000 万人（数字不确定）。
    - 这个行业的顶端暂时没有威胁，底层大量的人面临被 agent 替代的危险。
    - **吐槽** 「底下大量的人都面临被agent替代、斩杀的危险」
    - 建议学经典课程，包括操作系统、编译器、软件工程。学其中的智慧，再形成自己的理解。

> 原话：「AI时代的斩杀线以下的价值就全部归零」

## 4. 把修改本身当一等对象，版本管理才顺手

<small>▶ [22:56](https://www.bilibili.com/video/BV1Q6en6NEUo?t=1376)–36:02　·　进一步　·　话题：把修改变成一等对象</small>

- **merge 会混淆作者，rebase 则反复生成新 commit** merge 把 B 的修改记到 A 名下，rebase 避开了这点，但冲突时风险高。
    - git 管理的是快照，即整个目录在某一时刻的样子。开发者在快照上小步开发，每一步是一个 commit。
    - 在 git 的原始模型里，rebase 相对不被提倡使用。
    - **merge 会留下隐藏的作者修改。** 原始模型用有 2 个 parent 的两路 merge 合并两条线。
        - merge 由 A 完成时，B 写的内容作者变成 A。
        - 冲突由 A 在 resolve 时完成，B 改的代码 ownership 也归到 A。
        - 讲者称这是小小的麻烦。
    - **rebase 解决了作者问题，但搬运可能失败。** 讲者在白板上画了 A、B 两条线的例子。
        - A 先改文档再加测试，B 先加 feature 再加测试。
        - rebase 先试着把 B 的 feature 接到 A 的提交后面，成功后再接 B 的测试。
        - 全程无冲突，就一路合并成线性历史。
        - 失败的情形有 2 种：A 的测试用例与 feature 不兼容，或双方改了同一处。
        - 失败时要 resolve，开发者进入 rebase 模式。feature 搬成功后，搬测试还可能再失败。
        - **吐槽** 讲者说进入 rebase 模式后的窘境：「你会发现瞬间自己就不知道应该怎么办了，然后这时候你就打开你的 agent：我现在发生了什么？然后 agent 会细心地解释给你。」
    - **每次 rebase 都生成新 commit，历史随之改变。** merge 保留所有 id 并新建一个，rebase 要把 commit 的 base 改到新位置，每次都生成新 id。讲者说这让人感到轻微的不一致。
- **commit 代表不了 change。Jujutsu 把 change 做成一等对象。** 讲者关心的是把修改搬过来，而 git 只用 commit 与 parent 的差来代替修改。
    - git 没有专门的 change 对象。多数情况下用 commit 代替修改够用。
    - **Jujutsu（jj）在兼容 git 的基础上新增 change 概念。**
        - 底层与 git 完全兼容，可以直接当 git 用。
        - rebase 时，jj 直接把 change 搬过来。
        - 冲突仍然无法自动解决，但 jj 把冲突随 change 一路带下来。
        - jj 沿用 git 的冲突记录，另有一套自己的记录方式，之后可以在新位置再 resolve。
        - 底层模型没变，用起来舒服很多。
    - 从「change 是一等对象」往后推，可以发明新的版本管理系统。讲者说这不是 jj 的全部，还有别的路线能推导出来。
- **有了 change，就不需要 staging area 和 stash** jj 在每次改动后自动更新当前提交，开发者随时都在编辑一个 change。
    - **git 里最讨厌的场景：改到一半被打断。** 讲者说上操作系统课时也会讲这个例子（字幕原文：操讯课，待确认）。
        - 开发者把 hello.c 改到一半，项目不能编译，测试也不过。
        - 导师来电，要求 1 分钟内修一个高优先级 bug，此时不该 commit。
        - 导师说客户的项目立刻要交不了差，所以要赶快修好。
        - **玩笑** 讲者模仿导师来电：「哎呀，我现在有一个很高优先级的项目，你这个有个 bug，马上客户这个项目就要交不了差了，赶快把这个 bug 给我一分钟修了」
        - 开发者要先加进 index，再 git stash，然后去修 bug。
        - 修到一半，导师又来电说有优先级更高的 bug，开发者要再 stash 一次。
        - **玩笑** 讲者模仿导师再次来电：「哎呀，你这个 bug 别修了，我还有一个更高优先级的 bug，你去把它修了」
        - stash 是一个栈，里面会堆很多提交，开发者要自己管理这个栈。
        - **吐槽** 讲者评价 stash：「这其实是一个比较讨厌的操作」
    - **jj 的做法：每改一个字节就立即做一次 git commit。** 讲者用「好像」描述这个机制。
        - 新提交会抹掉上一次的提交，用当前修改替代它。
        - 当前快照永远处于一个 change 的提交状态。
        - 所以 staging area 和 stash 都不再需要。
- **趁还没有肌肉记忆，直接学更对的设计** 讲者已有 git 肌肉记忆，没时间再练一套，学生正好相反。
    - 讲者这代人有 git 的肌肉记忆，更老一代有 SVN 的。肌肉记忆形成后，很难掰过来。
    - 讲者说，AI native 的学生能淘汰他们这一代人，原因就在肌肉记忆。
        - **自嘲** 「为什么你们作为 AI native 的人类能够淘汰掉我们这一代人，就是因为我已经形成了 git 的肌肉记忆了」
    - 讲者能从第一性原理理解 jj，可能比初学者理解得更好，相当于自己 virtually reimplement 这个系统。但讲者没有时间再训练另一套肌肉记忆。
    - **工具在不断迭代，先学最正确的设计再回头看旧工具。**
        - SVN 用不下去后才有 git，git 的缺点暴露后才有 jj。
        - git 出现时，大家觉得它是 persistent data structure，很先进。SVN 从纯 diff 那条线就走错了（字幕原文：纯纯DF，待确认）。
        - git 最早没想到 rebase 的影响这么大，有 merge 就能解决手上的问题，概念模型没有想得更清楚。
        - **吐槽** 讲者说，先学对的设计，再回头看 git：「哦，原来 git 这么蠢，对吧。」
    - **学习建议：质疑 git，让 agent 带着学 jj。**
        - 学生可以问 git 哪里做得不够好，更好的设计会是什么样。
        - 学生可以把「我要学 jj，想从 change 开始理解」这个 prompt 交给 agent。
        - jj 的 tutorial 一上来就说没有 staging area。
        - jj 对人更友好，对 agent 可能也稍微更友好。
        - 讲者说，借助 AI 可以不断往前学。

## 5. git 为单线程的人设计，agent 提速后跟不上

<small>▶ [36:02](https://www.bilibili.com/video/BV1Q6en6NEUo?t=2162)–51:13　·　转向　·　话题：agent 的速度超出 git 的设计</small>

- **git 为单线程的人设计，人的提交以分钟到小时计。** 人像一个线程，读到的值在动手时可能已经过期，所以人不会快速并行提交。
    - **人是 single-threaded 的，读和写不能同时做。** 讲者用操作系统课的线程比喻：线程访问共享内存只有 load 和 store 两种操作。
        - 人观察世界时只能看，要动手 write 就得闭上眼。
        - 闭眼期间，读到的值已经是旧值。
        - 例子：想用粉笔导弹射击一位同学，扔出去时依据的是上一刻的信息，结果可能是错的。
        - 线程被换下 CPU 一秒后恢复，寄存器里还是上次读到的 X=1，之后的写入就可能出错。
        - 同时读一个值又写一个值，需要原子指令才能做到。
        - 多线程共享内存会带来无穷的问题，人类协作也一样。
        - **玩笑** 讲者模仿人观察世界的样子：「我如果想要观察这个世界，那我对不起，我手要背在后面，我只能看。」
        - **玩笑** 讲者举例时拿同学开涮：「我想用这个粉笔导弹射击他」。
    - 人和人之间有无法逾越的物理屏障。人只有一双手、一张嘴、一对眼睛，不能理解彼此的思想。
        - **玩笑** 讲者形容人是孤立的个体：「我就是一个独立的个体，由分子把我很强地连在一起」。
    - 人写代码以小时计，约 10 分钟产生一个提交。十几个人负责一个模块，已经是不小的团队。
    - 提交比沟通慢。动手前先和师兄说一声，只要 10 到 30 秒。工厂里 leader 早会上半小时内划好 scope，各人领一块走。
    - 在这种古法编程的节奏下，stash 是合理设计。修到一半被导师打电话打断的概率低，stash 里绝大多数时候只有一层。多层 stash 麻烦，还要 rebase stash。人还可以拒绝工作，或者排队。
    - **玩笑** 讲者给没有 agent 的写法起了个名字：「这是古法编程」。
- **agent 以秒计提交，git 和 Jujutsu 都跟不上。** 现有版本管理系统都假设使用者是人，agent 提速 10 到 100 倍后这个假设失效。
    - Jujutsu 对人是大进步，对 agent 可能进步较小。agent 似乎已经擅长 rebase。
    - SVN 有局限，git 也有局限。它们共同的假设是使用者是人类。
    - agent 生成 slop 以分钟计，甚至更快。上下文还热时，让它 fix 一个问题只要几十秒。DeepSeek V4 Flash 干活只要几秒。
    - agent 能以秒产生一个原子提交，团队规模可以轻易到 10 倍、100 倍。
    - Jujutsu 兼容 git，同样是为人设计的模型，跟不上这个速度。
    - 大型项目有测试流水线作门控，一次要跑几分钟，可以放缓 agent 的提交。但 agent 加速了软件开发这一点不变。
- **最直接的做法是每个 agent 一台独立机器，当单人开发者。它用 tmux 收命令。** 讲者现场开两个 tmux 会话演示，这件事容易实现。
    - 做法：每个 agent 配一台独立电脑，可能是容器。
        - 把远端仓库放在 git 上（字幕原文：git点NHU点E点点CN，待确认）。
        - 告诉 agent「你是单人开发者」，然后它从 tmux 里收命令开干。
    - **演示：两个 tmux 会话分别跑一个 agent，讲者当领导发命令。** 实际开发时，两个会话应在两台机器或两个容器里，物理隔离，互相看不到。
        - 讲者说，agent 时代每个人都是领导。
        - 命令发出后，两个 agent 各自开始写代码。
    - **玩笑** 讲者说 agent 时代的好处：「agent 时代有点什么好呢，每个人都是领导」。
    - **玩笑** 讲者给两个 agent 分了主从角色，自己当 master：「还故意用一个这个可能在中国现在还能用的词，对吧，Master。」
    - 流行的监工 agent 范式：两个强模型互相打架，直到达成一致。
        - 例如让 Codex 设计，让 Claude review，目的是最大化模型的智力，防止生成不想要的东西。
        - 开两个 tmux 即可。主 agent 负责协调、看输出和总结报告，并往里 inject prompt。
    - **玩笑** 讲者形容两个模型互相制衡：「然后让他们互相打架，然后达成一致」。
    - 结果：同在一个 git 仓库上工作会有麻烦。各自在不同的仓库上工作则完全可行。
        - agent 去远端拉取别人的提交，冲突时自己修复。
        - 必要时它还能给主 agent 发消息，由此可以搭出多 agent 系统。
- **git worktree 是 git 现成的并行方式，更轻量，但冲突仍要 merge 和 rebase** 提交在本地互相可见，不用 pull 和 push。
    - 讲者的学习做法：看到微信公众号提到 git worktree 或 sandbox container，立即让 agent 试一试。讲者认为提问是关键。
    - 讲者让 agent 把两个 tmux 会话都放进 worktree，agent 写了脚本完成。
    - **吐槽** 讲者看着屏幕上 agent 的动作，现场点评：「诶，这不是一个相对来说比较容易的任务吗」。
    - git worktree 创建一个工作树，连接到同一个仓库，可在隔离环境里独立提交。
    - **worktree 里的 .git 是一个文本文件，不是目录。** 讲者也是追问 agent 才知道。
        - 主仓库的 .git 是目录，里面有 3 类对象，包括 logs 和 objects。
        - worktree 里的 .git 文件只有一行 gitdir，指向一个小型 git 目录（字幕原文：VTREE，待确认）。
        - 小目录里仍有 HEAD、index、locks，依附原 git 目录而生。讲者据此认为 git 最大程度复用了操作系统机制。
    - 这个特性在 AI 时代突然有用：提交在本地互相可见，不用互相 pull 和 push。
    - 多台虚拟机各放一个 agent 并往 tmux 注入命令，也能完成，但 worktree 更轻量，性能更高。
    - 局限：有冲突的修改仍然需要 merge 和 rebase 才能合并。

> 原话：「git 是给人用的，但是在 agent 的时代这件事情变了。」

## 6. agent 团队不需要追责，该用悲观锁防冲突

<small>▶ [51:13](https://www.bilibili.com/video/BV1Q6en6NEUo?t=3073)–63:44　·　进一步　·　话题：agent 团队用悲观锁</small>

- **人的沟通成本高，这塑造了 git 的各种最佳实践**。团队沟通效率低，规模变不大，只能靠快照和小步提交留下可追溯的记录。
    - 人靠每天早上开会来同步进展、分配任务。一个小团队约 10 分钟产生一个 commit。
    - **吐槽** 讲者举沟通难的例子，「你的室友向你请教一个数学问题，明明你会做，你就怎么都没办法给他讲明白」。
    - 讲者说除非是能共情、站在对方角度的好老师，否则很难讲明白。所以沟通成本很高。
    - 人多了以后沟通效率降低，产出也跟着降低。100 人团队达不到 10 人团队的 10 倍，有 2 到 3 倍就不错了。这也是初创团队效率更高的原因。
    - 团队变不大，所以需要快照和小步前进：改一个 title 也提交一次 commit。出问题时，团队回溯到当时的 commit。
    - 人有记忆，能想起当天早上开过会、接到需求、沟通出了问题，再去翻沟通记录来修正。git blame 就是为人设计的特性。
- **agent 团队不需要追责，项目只管向前修复**。agent 没有被开除的能力。它们还是同一个模型的克隆体，所以不再需要 git blame。
    - **玩笑** 讲者说人才能被追责，「你这个事情我 blame 你多了，你就该被开掉了，是吧，实习生你就背锅了」。
    - agent 没有坐牢、被开除的能力，追责这个模型就失效了。项目只要前进。
    - 开发者不必知道是哪个提交引入了错误，只要知道哪里错了并修好，不再追究历史上怎么造成的。
    - 各个 agent 是相同模型的克隆体。同样的 prompt 做同一件事，细节可能有细微差别，方向大概率收敛到相同结果。
    - 快照仍然需要。方向走错时，如果没有历史上的 snapshot，走远后再回去的代价可能比一点点修更大。
    - 讲者认为项目可以不断大步向前，几乎永远不要回头看过去。
    - commit 里只需留下 lessons，以及项目经历了怎样的演化。历史的价值从「谁写错了」变成「怎么修好」。
- **git 像乐观并发控制，agent 快 1000 倍时应改用悲观锁**。git 假设不冲突。agent 提速后冲突变多，先上锁可以几乎避免冲突。
    - **git 的模型像数据库的乐观并发控制。** 讲者用 SQL transaction 做比方。
        - transaction 中间可以混任意代码，例如 Python 或 JavaScript。代码图灵完备，先 select 读数据，算完再 update。
        - 代码甚至能根据当前时间算东西。你永远不知道它会算出什么，再去 update。
        - update 可能产生循环依赖或死锁。数据库检测到后，让该 transaction abort 并 roll back。
        - 乐观是指先假设两个 transaction 不冲突。教务系统里每个同学读写自己的选课数据，全局冲突概率低，这个假设大概率成立。
        - git 同理：早上开过会，各人顺着自己的路做，merge 或 rebase 大概率顺利。讲者说这是「古法编程时代」的做法。
    - agent 快 1000 倍，主 agent 分出很多任务，会更频繁触发 abort。讲者认为这在 AI 时代不是大问题，agent 出了 conflict 能修好。但可以换一种并发控制。
    - 悲观并发控制就是操作系统里的锁：使用资源前先 declare，先 lock 后访问，别人想 lock 必须等 release。
    - **玩笑** 讲者讲到锁，说起自己在操作系统课上的口头语，「一把大锁保平安」。
    - **做法是让 git 仓库或快照支持锁操作。**
        - 主 agent 规划完，立刻锁住项目的某一部分，并说明 scope。
        - agent 上锁、做完、commit 后释放。别的 agent 想锁已被锁的部分，必须等待。
        - 可以按文件级上锁，避免两个 agent 同时往同一个测试或配置里写。
    - 互斥锁的本质是不要并行，把并发程序退回串行。但系统里有许多独立、不冲突的线程时，即使每个线程都持锁，仍然高效。agent 数量足够多、速度足够快，整体进度仍能推进，因为其他 agent 可以继续运行。
- **操作系统和数据库的知识在 agent 时代会回用**。讲者认为可以从 first principle 重新设计版本控制系统，所以这些课仍值得学。
    - 要管理的对象是快照、版本、change，还有飞快的 change。git 是一条线，用锁管理软件可能是另一条线。
    - 只有真正学会操作系统和数据库，回头看软件工程才会发现这些概念又出现了一次。
    - 有人怀疑 AI 都会写，还学这些做什么。讲者答案是有用，要好好学。
    - 讲者承认学这些东西很痛苦。
    - **吐槽** 讲者模仿学生的怀疑，「虽然痛苦对吧，你怀疑在 AI 时代我学这种东西，AI 都会写了」。
    - **自嘲** 讲者说自己也不再手写数据库查询，「我早就不写任何 SQL 查询了」。
    - 数据库里也有类似悲观锁的机制（字幕原文：adversary lock，待确认）。
    - 讲者喜欢上课，因为备课要把话讲给听众。他必须共情听众，把最顶层的 idea 提炼出来。他自称做得还不够好。
    - 备课时讲者把这些事在脑子里再过一遍。不来上课，他可能不会去想。
    - **玩笑** 讲者备课时自问，「是不是地球上所有人都错了」。
    - 讲者说听众只能接受平实朴实的逻辑。不能直接讲事务系统怎么设计。

> 原话：「历史的价值可以从谁写错了变成我怎么把它修好。」

## 8. 早期用 git 存用户数据，需求收敛后再迁数据库

<small>▶ [68:25](https://www.bilibili.com/video/BV1Q6en6NEUo?t=4105)–77:50　·　举例　·　话题：汉诺塔产品：先用 git 存数据</small>

- **汉诺塔题可以做成小学生的代码游乐场，再卖 AI 助教服务**。讲者用这个假想产品，说明早期产品的数据该怎么存。
    - **题目是单向移动的汉诺塔，常规解法在限制下失效。**
        - 所有盘子只能朝同一个方向移。讲者在网上刷到，说可能是小学生考级题，也被当作面试题。
        - 2 个盘子能移。3 个盘子时，先把两个盘子移到中间、再移最大盘的常规做法做不到。
        - 最优解里，最大的盘子总是向右移一格，再向右移一格。这是不可避免的最少移动，其余盘子靠归纳法也最优。
        - 讲者现场运行自己写的程序，演示这个解。
        - **吐槽** 讲者说小学生很难做这道题，随后调侃机试：「想想如果现在是你们，保研机试（字幕原文：保研机制，待确认）就是小学生难度嘛，你就碰到这个题了。」
    - 游乐场里，学生写代码，可视化随代码运动。代码执行非法移动时，学生能据此找到出错的语句。
        - 学生的代码可以随时编辑，可视化会实时跟着变。
        - 举例：写错一句，试图把小盘移到大盘上，学生就能找到这条语句。
        - 产品现在只是纯粹的 playground，学生可以写代码并运行。
    - **增值服务是 AI 助教，按 token 加价收费。**
        - 学生做不下去时点「我要助教」，DeepSeek 的 token 开始消耗。收费高于 DeepSeek 原价，记在学生账户上。
        - 讲者把自己这个有经验的老教师蒸馏成独门 prompt，用它判断学生的问题并个性化指导。
        - **玩笑** 讲者刚设想完加价收费，立即改口：「当然这个是不是不太好啊，这个开玩笑的。我们还是尽可能以一个便宜的成本提供给小朋友们。」
        - **玩笑** 讲者说点助教后：「这个时候 DeepSeek 的 token 就开始燃烧。」
        - **玩笑** 讲者给自己的 prompt 抬价：「我作为一个有经验的老教师，我可以把我自己蒸馏成 prompt。」
- **GPT 给出标准的数据库方案，讲者不选它**。理由：需求本质是版本管理，不是数据库的压缩和性能。
    - 信息系统由学生设计，讲者没有时间做。他让 GPT 梳理学生和 AI 聊出的设计的需求。
    - **自嘲** 讲者说自己有时间也不想做：「我竟然有这么大的市场的钱，我竟然都不想挣。」
    - GPT 的方案包括 3 部分：1 个 API 应用，1 个关系数据库，1 个对象存储。点评异步时再加后台任务进程。
        - 数据库存关系和记录，课程包与完整轨迹放对象存储，任务量小时用数据库任务表。
        - 讲者说上软件工程课会觉得太正常，但他不喜欢。
        - **吐槽** 讲者评价这个方案：「这是一个非常正常的，如果你们上软件工程课，那太正常了。你看 GPT 嘛，它是一个语言模型，但我不喜欢这个设计。」
    - 数据库的好处是压缩更小、性能更高，但这不是他要的。
- **早期把用户数据存进 git，需求收敛后再迁数据库**。每次改动自动提交，AI 点评挂在分叉上，存储成本可以忽略。
    - **Overleaf 的 git 导出让讲者改论文时直接用 agent。**
        - Overleaf 可以把项目导出成 git 仓库。讲者给学生改论文时，克隆到本地，不用忍受网页界面。
        - **吐槽** 讲者说克隆到本地的好处：「我就不需要忍受那个网页界面了。」
        - 他打开 Codex，用一段很长的 prompt，让它修复每个 .tex 文件里的语法错误。论文随即改好。
    - 游乐场里，学生每次 idle、点运行或切换，系统自动做一次 git 提交。学生申请 AI 助教时，系统在该提交上产生分叉，点评是一条 comment。
    - 讲者说 GPT 没有算成本：生成一次点评的成本，远大于持久化其余数据的成本，后者可以忽略。
    - 最早期，学生代码直接存在代码库里，在上面探索性地创建 git 历史。
        - 文件目录格式、commit message 格式和文件使用方式都收敛后，再迁移到数据库。
    - 讲者最后说，学任何东西都有用，学 git 有用，学 agent 管理（字幕原文：mod agent的管理，待确认）也有用。

## 9. 直接把需求丢给 agent 只会得到没人要的成品

<small>▶ [77:50](https://www.bilibili.com/video/BV1Q6en6NEUo?t=4670)–98:29　·　回到　·　话题：直接丢需求只得到没人要的东西</small>

- **早期项目只用一个最强 agent 多轮对话**。开发者像包工头，不开 multi agent，现在动手比任何准备都好。
    - 早期阶段不能用 multi agent。开发者找手头能力最强的 agent，和它多轮对话。
    - 讲者劝同学现在就开始做，认为动手比什么都好。
    - **讲者没有事先准备，现场打开课程作业，让 agent 做 Lab1。**
        - **自嘲** 讲者对现场演示毫无把握：「我不知道会发生什么，完全没有事先准备过」
        - 第一种办法是把作业直接丢给 agent，然后回车。讲者认为每个同学都该体验一次，今天由他代劳。
        - 一线模型会先进入 plan mode，再确认一些事实，然后生成 workflow。
        - Claude Code 遇到复杂任务，会生成一段 TypeScript。代码里有函数 agent，参数是自然语言。
        - workflow 里甚至有循环：任务多时，agent 在循环里逐个处理。
        - 讲者说 AI 的直觉和人的直觉不太一样。看到 agent 直接开干，他决定让它先跑一会。
        - **吐槽** 讲者看着 agent 开始输出，感叹：「只能用魔法打败魔法」，又说输出速度「实在是太恐怖了」。
- **直接丢开放需求，agent 会过度遵循提示词，生成没人要的成品**。它满足了每条指令，却不是讲者想要的。
    - **agent 过度遵循提示词，因为模型被训练成服从指令。**
        - 提示词里每个词，self attention 都会看到。讲者说这是上下文工程和提示词工程里最危险的一点。
        - 开放的讨论稿需求丢给它，它会过度遵循，生成满足指令却不是想要的东西。
        - **吐槽** 讲者解释 agent 为什么不会替人纠偏：「因为 AI 现在已经被训练成了 prompt 的舔狗，所以它有一种没有办法往外拉的倾向，需要遵循你的指令」
    - **agent 的产出和讲者的 intent 有巨大 gap。**
        - 作业的言外之意是「实现一个持续为你工作的个人助手」，这句话最重要，其余只是解读。
        - 讲者问学生，一个月内最大的痛点是什么。学生答学习，也就是高效学习和复习。
        - **玩笑** 讲者解释学习为何排第一：「因为你们要卷成绩，所以这毫无疑问是最重要的一个」
        - 讲者想要的是：agent 自动从外网收集数据，层次化归档，再给一个好界面。他估计 agent 十有八九做不到。
        - 讲者把想要的学习助手告诉 agent，agent 却在做 database。
        - 没有精心设想和讨论时，AI 基本只会生成 slop。
        - 讲者真正需要的是 browser use agent，能帮他在各种网页上办事。Lab1（字幕原文：L1号，待确认）只是测试出口。
        - 第一步不用在教务系统上多做设计，过渡设计反而不好。
        - 从 README.md 看，agent 做的每件事都对，没有错误，最终却得到不想要的东西。
    - **agent 连 git repository 都没创建。**
        - 讲者猜 codex 可能会初始化目录，或先问项目怎么管。
        - 成熟的产品经理接到任务，会先和团队沟通项目怎么管。写第一行代码前，要定好协作方式、项目管理和每天何时开会。
        - **吐槽** 讲者对比 agent 的做法：「agent 很好玩，他就直接上手就做，他觉得 OK，这就是一个用一次就丢掉的东西」
        - 这次烧了不少 token，讲者说无所谓。他参与 DeepSeek 内测，对方送了 1000 块额度，到现在没用完。
- **起步先建空仓库再小步前进，架构要抵抗需求变化**。从零做东西比维护成熟项目更容易出 slop。
    - 不能把任务直接丢给 agent。第一件事是创建一个空的 git 仓库，然后想下一步往哪走。
    - 下一步只能往前迈一小步。AI 从零做东西出 slop 的风险，比到成熟项目里做维护任务大很多。
    - **软件工程要问的是：架构能否抵抗需求的根本变化。**
        - 讲者向团队或学生提的问题是：现在的架构或流程，能否抵抗未来需求发生根本变化。
        - 第 8 节的数据库方案是为赚钱设计的，讲者真正需要的是能扩展的架构。
        - AI 助教可能是文字的，也可能是图像的，可能有交互，也可能没有。AI 模型也会变。
        - 讲者希望架构以最少的改动应对这些变化。
        - 软件工程课不讲这件事，操作系统课和数据库课也不教。这两门课讲系统为什么长成现在这样，比如并发控制，每个设计都有原因。软件工程最不一样的地方，是面对未来需求的变化。
    - **版本管理做三件事：记住现在、记住历史、记住教训。** 在 agent 时代和古法编程时代都成立。
        - 记住现在：不管是 C、C++、Python 还是 JavaScript 项目，都要有 repository 把文件管起来。
        - 记住历史：删除的东西以后发现有用，可以捞回来。提交历史也能看出项目怎么演进到某一点。
        - 记住教训：路线失败后，失败留在历史里，回到另一个点重新走正确的路线。
        - 这些教训提醒开发者从第一步起就小步前进。讲者说不该是看一眼 agent 已经实现完了，就提交。
- **MVP 阶段先用文件系统，不要一开始就上数据库**。数据库每次重构都要 agent 迁移，文件系统自己就能调。
    - **agent 把项目做成了业务逻辑系统，风险大。**
        - agent 这时才做了一次提交。架构有入口层、编排层、能力层、数据层，是很典型的分层架构。
        - **吐槽** 讲者翻到 agent 的提交记录，说：「哎，他倒是做了一个提交」
        - 讲者翻看实现，看到它做了提交人民奖学金申请、准备退课这些功能。
        - agent 的汇报说，引擎全是真代码，手机端是真 HTTP 服务。
        - 汇报还说，模拟的部分里没有邮箱。
        - 讲者不逐条 review。他说它看起来已经像一个教务系统，有很大风险。
        - **玩笑** 讲者看着分层架构笑说：「哈哈，这个软件已经看起来像一个教务系统，我下节课就会讲教务系统」
    - **从零构建，主流 best practice 是先做 MVP。**
        - MVP 是最小可行产品，也就是一个最小的验证版本。
        - 产品开发里有一句话：「The biggest risk in product development is building something nobody wants」。讲者说 agent 做的就是他不要的东西。
        - 做最小版本，逼人想清楚绝对要的需求。讲者的个人助手只要两条：提升学习效率，提升工作效率。
        - 有了这两条，第一个 MVP 可能没有任何数据库。
    - **文件系统能自己调，数据库要 agent 迁移，还要做概念翻译。**
        - 文件系统膨胀后，可以让 agent 按现有数据组织提炼出数据库，问题就解决了。
        - 一开始就带数据库，每次数据库重构都要让 agent 做迁移。
        - 文件系统可以在文件管理器里自己调，逐步梳理到舒服的结构。
        - 调文件和调 schema 的心智负担不同。人从小学上电脑课起就操作文件目录，很习惯。
        - 很多同学没学过数据库，要把脑中的概念翻译成数据库结构。不如用已经熟悉的系统。
    - **讲者自己回邮件的 agent 没有用任何数据库。**
        - agent 收邮箱，把 email id 放到同步的共享云盘上。
        - email id 下是 agent 解析的结果，包括回复草稿和邮件分类，例如是不是垃圾邮件。下一级流水线再处理。
        - 讲者先想清楚系统有几级流水线、怎么协作、哪些东西走云盘。
        - 讲者希望邮件和资料都与云盘同步，这就是需求更改。
        - 他让 agent 评估现有架构。好架构的标准是需求变更时，改动不是摧毁性的，也不背技术债。
        - agent 的设计有 assistant.db：个人资料、邮件归档、索引放在里面，草稿仍在 db。讲者说现在看不会出大问题，多数项目都这样。
    - **讲者归纳了两种开发方式，并强调早期 prompt 影响最大。**
        - 一种是几个大步把需求实现完，再拖着技术债不断加功能。
        - 另一种是从最小版本出发，得到精巧的架构。
        - 讲者用 git 管学生提交，事情变得容易，控制也轻松（见第 8 节）。遇到性能瓶颈之前，他不迁移到数据库。
        - 最早的 prompt 对项目走向影响最大，例如直接把 README 给 agent，说要做 MVP。
        - 下一节课（周日）进入软件架构和构造。
