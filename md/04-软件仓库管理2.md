# 软件仓库管理 (2) [04-Raw⧸26生成式软件工程⧸NJU]

> 原视频：<https://www.bilibili.com/video/BV1Q6en6NEUo>　·　课程合集：<https://space.bilibili.com/202224425/lists/8942017>　·　讲者：蒋炎岩（NJU《生成式软件工程》2026）

## 全课主线

讲者想让听众相信：agent 时代不能把任务直接丢给 AI，也不能继续照搬只为人类设计的 Git/版本管理；要回到 intent、spec、架构、MVP 和团队管理，并用经典 CS 概念重新设计面向 agent 的版本管理系统。学生现在就该边用 agent 边建立项目管理和版本控制直觉，先小步、保留快照、管理 agent team，而不是无脑 vibe coding。

1. 讲者先以本周继续版本管理、作业验收和 Lab1“会成长的个人助手”切入，鼓励 vibe coding，并构想 always on 的个人助手。（第 1 部分）

2. 但是，如果直接把实验要求交给 AI，它会一开始做很多看似合理的决定，项目越来越难维护直到焦油坑；因此实验要让大家经历这个坑，下一 Lab 还会加冲突需求让你越改越崩溃。（第 2 部分）

3. 于是重点回到项目本身：项目是 intent、设计文档、README 等文件的集合，README 应短到能表达原始 intent、说服合作者，内容链条是 intent→spec→code implementation。（第 2、3 部分）

4. 然而文件系统只是历史遗留的方便存储，会丢失 intent/spec、测试、代码之间的隐藏关联；文档与代码各自演进、不一致累积会形成 technical debt，进入维护泥潭，这就是 traceability 问题。（第 3、4 部分）

5. 因此讲者设想未来软件是对象/实体之间有明确关系、甚至有环的图，放进数据库而不再是文件树；但人类用现有 UNIX 工具维护不了含 cycle 的 repo，所以要用 AI（有强化学习反馈）理解 repo、自动维护 artifacts 一致性，仍按 Git 式小步 commit，并由 AI 从 chat 抽取相关部分动态生成 view。讲者强调这靠数据库 view、实体关系、Git 小步等经典 CS 概念，所以学生不应因新范式放弃经典课程。（第 4、5、6、7 部分）

6. 回到 Git 本身：Git 管快照并要求小步 commit，但两路 merge 会把 B 的改动/冲突解决记到 A 头上；rebase 逐个搬 feature/test 追求线性历史，代价是冲突和 commit ID 重写。于是讲者指出 Git 没有专门 change 对象，只用 commit+parent 表示修改；若把 change 做成一等公民，就能得到下一代 VCS：rebase 可搬运 change，冲突可随 change 带下去、稍后 resolve，并且没有 staging area。（第 7-11 部分）

7. 但旧 VCS 都默认使用者是人类：人类单线程、读写不能同时、沟通慢，commit 以小时/十分钟计，所以 stash、merge/rebase 等为人设计是合理的；agent 可以秒级产生原子提交、轻易形成 10 倍/100 倍 team，因此必须重新设计面向 agent 的版本管理。（第 12、13 部分）

8. 在初期，讲者主张让 agent 沿用人的模型：一 agent 一开发机/容器/远程仓库，从 tmux 接命令，监工 agent+子 agent；同仓库有冲突，git worktree 是轻量隔离 workaround，但冲突仍需 merge/rebase。（第 14、15 部分）

9. 进一步，人的沟通成本随人数平方上升，团队不能线性放大；Git blame/bisect 服务于人类追责，agent team 更关注修错和前进，但快照仍必须保留。讲者又把 Git 类比乐观并发控制：agent 变快后会频繁冲突/abort，于是可能转向按 scope 上锁的悲观并发控制，代价是互斥锁排斥并行。（第 16-19 部分）

10. 所以讲者判断版本控制只是工具，真正难的是进度和团队管理；只要 AI 还不能一句话做出微信级产品、也还不会团队管理，软件工程就仍需要，最稀缺的是能分解任务的 team leader。（第 19、20 部分）

11. （整理者串联）随后讲者转到产品与信息系统：AI 助教/playground 等例子显示 AI 会过度遵循 prompt，完成字面指令却偏离真实 intent；自动 git commit 被他认为比过早 persist 到数据库更贴近版本管理的本质。（第 21-24 部分）

12. 因此他主张项目早期不要 multi-agent，先当包工头用最强 agent 多轮对话；第一件事是建空仓库，再小步走，并做 MVP，聚焦绝对要的学习/工作效率需求，可用熟悉的文件系统和云盘，数据库等性能瓶颈再迁移。最后落回架构：架构要以最小变化应对需求变化，版本管理要记住现在、历史和教训，早期 prompt 影响最大。（第 23、25、26、27、28 部分）

讲者的结论/号召是：现在就开始用 agent 做项目，但要像管理团队一样管理它，先小步、MVP、保留快照、练 team leader 能力，并继续学经典 CS 以重新设计 agent 时代的版本管理与软件工程。

- 讲者回忆：大概在疫情时招过一个学生，研究生在他这里做了 3 年，做的就是**自动填表系统**。
- 学生毕业时突然有了 **ChatGPT**，他很慌，觉得自己做的事情马上要被替代。

- 讲者借此表达：世界发展就是这么快。

## 从个人数据库到 always on：关联邮箱，在宿舍跑 agent loop

- 在个人数据库的基础上，可以把数据库和你的 **SMail 邮箱**关联起来。
- 讲者举例：他可能两周后会在半夜给大家发邮件，你的 **agent** 可能会把邮件回给他，实现一个 **always on**、在后台工作的助手。
- 设备方案：也许买一个很小的**嵌入式小设备**，一两百块钱，就可以在宿舍里持续跑你的 **agent loop**。
- 最后一步构想：用你的信息可以办理**一般的事务**；讲者说，就像他上课时说的，这就是一句话，直接一个像 agent 的**指令调用**就可以。
- 逻辑链：个人数据库 → 关联邮箱 → agent 在后台处理邮件 → always on → 小设备持续跑 agent loop → 用信息办理一般事务。

## 让 Agent 自己完成任务：一句话调用，甚至可做手机端联动

- 讲者说，让 Agent 用你的信息去办理某些事务，可能就像上课讲过的那样，只是一句话；直接让 Agent 调用/执行就可以。
- 如果你们有兴趣，还可以把 Lab 做成**手机端联动**：网页、iOS app、Android app 都行。
- 讲者认为，只要让 Agent 去做，它会自己帮你下好所有需要的东西，然后把你要的东西做出来。

## 任务都在 AI 能力范围内，但直接让 AI 做会让项目难维护

- 表面上看，所有任务都在 AI 的能力范围之内。
- 但讲者提出：如果直接把实验要求交给 AI 去做（他说自己没试过直接这样做），AI 在一开始就会做出很多它认为“看起来合理”的决定。
- 这些决定会让项目维护变得越来越困难，最后直到陷入软件工程里的**焦油坑**。
- 讲者认为每个同学都有必要体验一下这个焦油坑。逻辑链是：
  1. AI 一开始自主做很多看似合理的决定。
  2. 这些决定持续积累，项目越来越难维护。
  3. 当你的 AI agent 开始不断消耗你的 token 时，你总有一天会下决心：把项目删掉、从头重做，或者回退到某个很早期的版本再重做。
  4. 这就是这个实验想让大家经历的事情。
- 讲者相信这个项目对每个同学都是有用的，这也是他设计实验的初衷。

## 下一个 Lab 会故意制造“越改越崩溃”

- 讲者预告：下一个 lab 会和这个 lab 有非常大的关联，而且你们暂时猜不到。
- 情景是：lab1 的实验要求都做好后，它会成为一个非常舒适的个人助手；然后加一个需求，这个需求与前面所有内容都关联，并且有一定冲突。
- 你只能去改，然后越改越崩溃。讲者希望大家期待后面的 lab。
- 反过来，如果 lab1 选择躺平、不管它，直接让 AI 做，下一次可能就把做的直接删掉；讲者认为这样可能就没有软件工程的体验了。

## 回顾项目管理：项目是 intent、设计文档、README 等文件的集合

- 上节课讲的是软件项目管理。项目是各种文件的集合：你的 **intent**、一些设计文档、你的 **README** 都在项目里。
- 讲者不喜欢 AI 写出来的非常非常长的 README。
- 讲者喜欢的 README 是：写你在设计这个项目时最初的初衷——你想做一个什么样的产品，这个产品能达到什么样的效果；可能放两个 **screenshots**；以及你最重要的那些设计。

## README 的用途：短到能说服别人加入你的“挣一个亿”计划

- 讲者的类比：有一天你突然想到一个非常好的点子，真的想用它去挣一个亿。
- 想挣一个亿时，你要组建一个创业团队，要说服 computer science 里的人，比如说服讲者出来干。
- 这时你其实只需要一个比较短的 README。
- 讲者认为，这就是你的 **intent**：你想做这个东西。

## 说服 CS 合作者：只需最短 README 表达原始 intent

- 讲者设想：你要说服一个 **computer science** 背景的人出来一起干。
- 对方其实只需要给一个较短的 **README**，写清 **intent**：你到底想做什么。
- 剩下的比如“我有架构能力，我有写代码能力，我可以把剩下的东西给你补出来”。
- 因此，提出 intent 的人不需要先知道完整软件系统：**specification** 是什么、用什么数据库、怎么支持用户从 1 到 10、100、100 万、1 亿。
- 讲者强调：这个阶段你可能没有 **computer science** 的知识，但你不需要有；你只需要有最原始的设计，也就是 **intent**。

## 项目内容链条：intent → spec → code implementation

- 讲者给出的层级是：
  1. **intent**：最原始的设计，想做的东西。
  2. **spec**：比如选什么数据库、选什么编程语言、项目结构是什么；小到每个模块的接口都属于 spec。
  3. **code implementation**：代码实现。
- 这些内容现在都放在项目里。
- 有这样一个项目以后，很自然就需要一个 **容器**，把这些各种各样的文件管理起来。

## 文件系统管理项目：图方便 + 历史遗留

- 大家用 **文件系统** 来管理项目，讲者认为其实真的就是图方便。
- 历史原因：
  - 回到 1950、1960 年代，操作系统给你的存储功能就只有文件，没有别的。
  - 那时关系型数据库还没有发明出来。
  - 所以所有程序员别无他法，只能把项目以文件形式存进来。
- 因此这更多是历史原因，历史不停往后涨、往后涨导致的。
- 讲者认为：**文件系统可能不是组织项目的正确方式**。

## 文件系统丢失了“不适合由文件表达”的信息

- 文件系统丢失了很多“不适合由文件表达”的信息。
- 有些信息本来比较容易表达：
  - **intent/spec**：一条文档，写“这个地方我是怎么想的”。
  - **测试用例**：输入是什么、输出是什么，以及在程序运行过程中 **assert** 什么东西不能被违反。
- 但很快会发现：项目里有很多 **隐藏关联** 没有表达出来。

## 例子：linked list 文档与 tree 代码之间的隐藏关联

- 讲者举了 AI 写代码的例子：
  - 现在 **agent** 会稍微好一点，有时也不会。
  - 你让 AI 把某个实现方法从 **linked list** 换成更高效的 **tree** 结构来优化性能。这很常见：突然发现性能不够，就让 AI 去做。
  - AI 会啪啪啪把代码改掉。
- 但你可能没想到：某个文件里的 **markdown 文档** 写着：“我这个项目的数据是用 **linked list** 管理的。”
- 于是文档、代码、测试之间形成了一个关联。
- 问题在于：写文档时可能还没有代码，所以先随手写了“这是个 linked list”。等代码实现以后，这个关联又没有强行联系上。
- 这就成为 **technical debt（技术债）**。

## 结果：不一致只会越来越多，软件陷入维护泥潭

- 讲者给出的因果链：
  `文档随手写 linked list → 代码改成 tree → 文档/代码/测试的隐藏关联未被强制联系 → technical debt → 文档与代码不一致增多 → 维护泥潭`
- 因为以后随着文档和代码不断向前推演，它们的不一致只会越来越多，不会越来越少。
- 最终这个软件就陷入 **维护的泥潭**。

小结：讲者主张文件系统是历史惯性而非组织项目的正确方式；隐藏关联不被强制表达，会积累成 technical debt。

### 文档与代码各自演进 → 不一致累积成 **technical debt** → 维护泥潭
- 讲者核心判断：随着文档和代码不断向前推演，二者的不一致只会越来越多，不会越来越少。
- 结果：软件陷入维护泥潭。
- 具体困境：后面你拿出一份代码，甚至 AI 看到一份代码，到底是文档说得对，还是代码说得对？
- 判定依据会丢：聊天历史没了，chat 消失；换了一台电脑；Git repo 里可能还有一些 change 日志，但到最后真的不知道到底是代码对还是文档对。
- 讲者的推理链：
  1. 文档与代码继续演进；
  2. 二者不一致累积；
  3. 形成 **technical debt**；
  4. 软件进入维护泥潭；
  5. 代码/文档谁为权威变得不可判定。
  - （整理者串联：第 5 步是第 4 步的具体表现；讲者用 AI 看代码、chat 历史消失、换电脑、只剩 Git change 日志来说明判定依据的丢失。）

### 这个问题在软件工程里叫 **traceability（可追踪性）**
- 讲者说，这是软件工程里研究了非常非常长时间的问题，叫 **traceability**。
- 他提到 2014 年已经有 review 在总结更老的文章，题域可写作 **software traceability**。

### 若未来人不再直接写代码，软件应变成对象/实体的关联图
- 讲者设想的未来：如果以后我们都不再写代码，人几乎不管这些东西，软件就不应该像现在这样在 Git repo 里以一堆文件来管理。

- 讲者指出：不可能一下子把产品直接变成另一个产品；当软件系统已经在工作，一般就是给它**增加功能、修改功能**。

## Git 管理快照，开发要小步 commit
讲者从软件工程模型/未来畅想回到 Git 本身。  
- **Git 管理的是快照**：一个目录、整个项目的快照。  
- 可以在快照上开发；开发要求**小步**。  
- 有 A、B 两个开发者，可以独立在这些快照上开发。  
- 这个产物是 **commit**。

## 两路 merge 的问题：B 写的内容最后 ownership 可能归到 A
如果要把 A、B 的开发合起来：  
- 讲者说，在 Git 的原始模型里，**rebase** 相对不那么提倡；Git 会让你创建一个**两路 merge**。  
- 这个 merge 有 **2 个 parent**，继承两条线上的修改。  
- 问题在于：如果 merge 由 A 来做，merge 里由 B 写的内容，作者会变成 A；讲者称这是一种**隐藏的作者修改**。  
- 如果发生冲突，**resolve** 后提交也是由 A 完成；B 改的代码最后 **ownership** 又归到 A。  
- 讲者认为这会带来一点小麻烦。

**逻辑链**：A、B 各自 commit → 用两路 merge 合并 → merge 由 A 执行 → B 的内容/冲突解决被算到 A 头上 → ownership 转移。

## rebase 解决归属问题：不直接并线，而是把 B 的 feature 接到 A 后面
讲者画了两个历史：  
- A 做了两次提交，得到两个快照，记作 \(\Delta_1,\Delta_2\)。  
- 然后 B 开始改。  
- 具体例子：A 先改文档，再加测试；B 加一个 **feature**，再加测试。  
- **rebase** 不是直接创建一个把两条线路并起来的 merge commit，而是先试：B 的这个 feature 能不能在 A 的后面加上去。  
- 讲者说，rebase 正是这样解决前面提到的 ownership/作者归属问题。

**逻辑链**：两条历史 → 不用 merge commit 直接并线 → 把 B 的 feature 试着接到 A 之后 → 避免 B 的改动在 merge 中被归到 A。

## 用“逐个搬 feature/test”替代 merge：目标是线性历史

讲者接着设想：**不**创建一个把两条线路并起来的合并提交，而是先试在 **A** 后面加上 **feature**。如果加上了，就算成功；成功后再把 **test** 搬过来。如果再一次成功，说明两条线路上的修改完全没有冲突，就可以一路合并过去，得到一个**线性历史**。

逻辑链：
1. 在 A 后搬入 feature。
2. 再把 test 搬到 feature 之后。
3. 若两步都无冲突 → 两条线变成一条线性历史。

## 风险在“不兼容”：一步冲突就进入 rebase 模式

讲者认为这个做法有很大风险：
- 搬过来的 **test** 可能与 **feature** 不兼容；
- 或者两者改了同一个地方；
- 甚至可能做了两个完全不兼容的东西。

一旦失败/冲突：
- 你需要 **resolve**；
- 会进入 **rebase 模式**；
- 讲者描述：如果进入过这个模式，会发现“瞬间自己就不知道应该怎么办”，然后打开 **agent** 问“我现在发生了什么”，agent 会细心解释。
- 更麻烦的是：feature 搬过来了，搬 test 时可能又失败，还得再把 test 搬过来；而且每一次都会创建一个新的提交。

## merge 保留旧 commit ID；rebase 每次生成新 commit ID

每个 commit 都有 **ID**。
- 如果是两路 **merge**：所有原来的 commit ID 都保留，另外创建一个新的 merge commit ID。
- 如果是 **rebase**：每次 rebase 都会创建一个新的 commit，因为快照原本的 base 在这里，rebase 就是要把 base 改到新位置；base 一改，commit ID 就变。于是历史也变了，讲者说会感觉到“有一点点轻微的不一致”，好像不是完全想要这样去管理软件。

## Git 的“修改”由 commit + parent 表示，没有专门的 change 对象

讲者强调：软件管理真正关心的是**修改**，希望把修改搬过来。Git 里面修改是用 **commit** 来替代的：
- 一个 commit 和它的 parent 之间的关系，就称为一个**修改**；
- Git 没有专门的 **change** 对象；
- 讲者认为，绝大部分情况都还能满足，只是“用 commit 代替 change”。

## 把 change 做成一等公民：下一代 VCS 的切入点

讲者接着问：如果把 **change** 也变成 **first-class citizen**，会发生什么？  
他的回答：那就发明了下一代更好用的**版本控制系统**。

他提到一个系统（转录作“机器组”，疑为 **Jujutsu/jj**；整理者推测）：
- 与 Git 底层完全兼容；
- 可以直接当 Git 用；
- 但增加了一个 **change** 的概念；
- 每个 change 都可以 assign 一个 change（转录作“sin 一个 change”，疑为 change ID）；
- 例如 rebase 时，它会把很多 **change** 直接搬过来，而不是搬 commit。

最后他指出局限：即使把 change 做成一等公民，**change 还是可能冲突**；冲突不是靠这个模型就自动消失的（转录作“冲突是解决不了的”，此处中断）。

小结：讲者的链条是：用 rebase 逐个搬 feature/test 可换来线性历史，但代价是 commit ID 重写与冲突解决；若把 change 做成一等对象，就是下一代 VCS 的切入点，但冲突本身不会因此自动消失。

## change 是对象：rebase 可搬运 change，冲突可随 change 一起带下去

- 讲者说，这种系统可以把很多 **change** 在 **rebase** 时直接搬过来。
- 但 change 仍可能冲突；如果在 rebase 时就要解决冲突，会很麻烦/难以继续。
- 关键原因是它有 **change object** / **change 这个概念**：可以把这些 change 一路带下来，生成一个已经 rebase 到目标位置的结果，即使里面引入了很多冲突。
- 它仍然沿用 Git 的冲突记录，但内部有一套自己的记录方式，把所有 change 的冲突也塞进去。于是你可以先把它们搬过来，之后再 resolve。
- 讲者结论：底层模型没有变，但用起来舒服很多。
- **整理者串联**：change 成为一等对象 → rebase 不必被冲突阻塞，而是把“带冲突的 change”先搬过去 → 冲突处理从“当场解决”变成“稍后 resolve”。

## Git 最讨厌的场景：改到一半要切任务，只能 index + stash，stash 还会堆栈

讲者用上课会讲的例子说明 **staging area** 的痛点：

1. 工作区有一个 repo，你在改 **hello.c**，改到一半。
2. 此时项目还不能编译、不能运行，测试也通不过。
3. 导师突然打电话：有一个很高优先级的项目 bug，客户马上要交差，要求一分钟修好。
4. 讲者说，这时你不应该 commit。
5. 于是需要把当前改动加到 **index**，然后 **git stash**，把状态压栈。
6. 你去修原来的 bug，刚修一半，导师又来电话：这个别修了，还有优先级更高的 bug，去修那个。
7. 你又要再 **git stash**；而 **git stash 是一个栈**，里面会积很多提交，你需要管理这个 stack。

- 讲者认为这是一个比较讨厌的操作。
- **整理者串联**：痛点是频繁任务切换时，临时工作状态被 staging area 和 stash 栈管理复杂化。

## 把工作区编辑本身看成 change：自动提交，但用当前修改替换上一次提交

- 讲者反问：如果你想象在任何时候、随时随地都在编辑这个 repo，这不就是一个 **change** 吗？
- 你现在把 **hello.c** 改一改，加一行、减一行，都是 change。
- 所以 **Jujutsu（原转写为“JJS/jj”）** 看起来在做的是一件这样的事：
  - 你但凡改了一个字节，它就立即做一个 **git commit**；
  - 但这个 commit 不会产生很多线性的历史；
  - 它先把上一次的 commit 抹掉；
  - 然后用当前修改去替代那个提交；
  - 也就是说，你永远处于一个 **change 提交的状态**，当前 snapshot 永远是一个提交状态。
- 因此，你连 **staging area** 也不需要了。讲者认为这非常舒服。

## 从“change 作为 first-class citizen”出发，可以往后推出自己的 VCS

- 讲者说：从“我要把 **change 作为 first-class citizen**”开始往后推，你就可以发明自己的版本管理系统。
- 但这不是它的全部；讲者提到它还有一些别的特性，此处未展开。
- **整理者串联**：先确立 change 是一等对象，再推出 rebase 搬运与冲突延后、无 staging area 的工作流。

**旧 VCS 的隐含前提：使用者是人类**
- 讲者指出：此前所有 **version control system（VCS）** 都有一个假设——使用者是**人类**。
- 人类的关键特点：人类是**单线程（single-threaded）**的生物。
- 因此，若要为 agent 重新设计 VCS，就必须检查这个“用户=人类”的前提。

**操作系统并发类比：read 与 write 不能同时发生**
- 讲者用并发程序打比方：把线程想象成一个人，线程可以访问共享内存。
- 共享内存的基本操作是 **load/store**，也即 **read/write**。
- 读一个变量，是把 X 读到临时变量；写一个变量，是写 X 等于某个值。
- 这两个操作不能同时进行；若要求同时，就需要**原子指令**。
- 讲者把人的行为类比成共享内存访问：
  - 人观察世界像 **read**：手要抱在后面，只能看。
  - 等看完后，比如看到某位同学在这里，想对他施加效果，比如用粉笔导弹射击他。
  - 但真正要 **write**、要动手时，必须“把眼睛闭起来”。
  - 闭眼扔的时候，之前读到的值已经失效了，是上一个时刻读到的旧值。
  - 中间可能发生 CPU 切换、中断、另一个线程上来执行；恢复后寄存器里还是上次读到的 X。
  - 于是粉笔扔出去很可能就是错的。
- 讲者用这个例子说明：人和线程一样，受“读—写不能同时、读到的值会过期”的限制。

**单线程人类导致代码变更以小时计**
- 讲者进一步说：人和人之间有无可逾越的**物理屏障**。
- 你不能直接理解我的思想，我也不能直接理解你的思想；每个人是独立个体，由分子连在一起。
- 人只有一套 I/O 设备：一双手、一张嘴、一对眼睛。
- 所以以这种方式编辑代码库、产生 change，粒度是**以小时为单位**。
- 一个软件公司负责一个模块的开发，可能也就十几个人；十几个人已经是一个不小的团队。
- 这十几个人每个人仍然以小时为单位开发。

**逻辑链**
1. 旧 VCS 默认用户是人类。
2. 人类是单线程的：read 与 write 不能同时完成，观察和行动之间状态会过期。
3. 因此人类产生代码 change 的速度和并发度受生理、物理限制，粒度以小时计，团队协作也限于十几人级别。
4. （整理者串联）若 agent 不是这种单线程人类，继续沿用旧 VCS 就会保留“人类用户”假设带来的局限；这正是讲者要在 agent 时代重新设计版本管理系统的理由。

# 人类提交速度受沟通速度限制，所以 Git/stash 为人设计是合理的

**讲者的链条**：十几人团队、小时级开发 → 最快约 10 分钟一次提交 → 这比人与人沟通慢很多 → 因此 stash 不必太深，Git 为人设计是合理的。

- 一个软件公司负责一个模块开发，可能也就十几个人，已经是一个不小的团队。
- 这十几个人每个人以小时为单位开发；最多也就是以 10 分钟为单位产生一个提交。
- 讲者认为：以 10 分钟为单位产生提交，意味着这个速度比人与人之间沟通的速度要慢很多。
- 例子：
  - 尤其一个 team，工位都在一起；研究生的工位也都在一起。
  - 你要写一个东西要一两个小时，写之前肯定会先跟师兄说一声：“师兄，我要干这个行不行？”
  - 十几秒、二十秒、30 秒，师兄说行，“你去改吧，我们现在不改”。
  - 如果去厂里打工，厂里可能每天早上开会，leader 把任务分出来：今天要干什么，你做什么。
  - 你在半小时里划分一个 **scope**，把项目切开，领走其中一部分，然后去产生提交。
- 讲者称这是“**古法编程**”。

## 古法编程下，stash 是合理设计

- 在古法编程时代，**stash** 是一个合理设计。
- 因为导师给你打电话这件事可能发生；但你在修到一半的时候，导师再给你打电话，这件事不太可能发生，概率很低。
- 绝大部分时候，你的 stash，也就是 **stash stack**，里面只有一层。
- 如果你有好多层，收起来其实挺麻烦。
- 还有一点麻烦：你还需要去 **rebase stash**。
- 所以你会尽可能保证 stash 不要太深。
- 因为你可以拒绝一个工作，或者你说：“我手上有一个更高优先级的工作，现在对不起，我不能干这个事。”
- 等你干完了以后，你自己可以排一个队列。
- 讲者结论：**Git 是给人用的**。

# Agent 时代：单个 agent 以秒级产生原子提交，人设计的 Git/[GG] 跟不上

**讲者的链条**：单个 agent 生成速度快于人 → 以分钟级甚至秒级工作 → 可以产生原子提交 → 可以轻易得到 10 倍、100 倍 agent team → Git/[GG] 这种为人设计的模型跟不上。

- 但是在 agent 的时代，这件事变了。
- 如果是一个 **agent team**，单个 agent 首先生产 **AI slop**（原音近似 AISLOFT）的速度就远远快于人。
- 它生成 AI slop 以分钟级为单位，甚至更快。
- 有时候你让它 fix 一个东西，在上下文热的时候可能就只要几十秒；像 [DPCV4flash] 这样的模型，干活时几秒钟就做了。
- 当 agent 以秒级工作时，它可以产生一个**原子提交**。
- 并且你可以轻易得到一个 10 倍、100 倍的 agent team。
- 因此，Git 或 [GG] 这样与 Git 兼容、为人设计的模型，就有点跟不上这个速度。

## 测试门控只能放缓，不能逆转 agent 加速开发的事实

- 就算是大型项目，它也有一些**门控**：当你写完、改完这个部分以后，必须要经历一个测试流水线。
- 测试本身可能就要运行几分钟，这可以放缓 agent 提交的速度。
- 但讲者认为毫无疑问：**agent 加速了软件开发的过程**。

## 新问题：如何为 agent 设计版本管理系统？

- 如果 agent 加速了软件开发的过程，我们应该怎样为 agent 设计版本管理系统？
- 讲者提出，首先可以让 agent 沿用人的模型。
- 具体想象：每个 agent 都有一个自己的开发计算机。

**逻辑链（讲者的推进）**
1. agent 先沿用人的模型：把人类 **single developer（单人开发者）** 和 agent 做严格一一对应。
2. 每个 agent 有自己的开发计算机/容器 → 放到远程 Git 仓库 → 从 **tmux** 接收命令 → 收到就开干。

4. 讲者提出：AI agent 变快时，要想如果指挥发生一点点差错会怎样；随后转到流行的 **监工 agent + 多个子 agent** 范式。

6. 同一 Git 仓库会有麻烦；不同 **repo** 则可合并、拉取、修冲突、通知 master → 可立即构建多 agent 系统。

### 单人开发者类比：一 agent、一台开发机、一个远程仓库
- 讲者主张：让 agent 沿用人的模型，把 **single developer 的人类** 和 agent 做严格一一对应的类比。
- 每个 agent 都要有一台自己的**开发计算机**，可以是一个**容器**。
- 把它放到一个远程 Git 仓库上（转录：git 点 NHU 点 E 点 CN；具体域名不确定）。
- 直接 instruct agent：我的 remote 仓库是在 Git 的；你现在就是一个单人开发者；你从 **tmux** 里接收命令；收到命令就可以开干。
- 讲者结论：这件事非常容易实现。

### 演示：两个隔离 tmux session 各自开干
- 讲者用类似 **fancy project** 的演示，直接让 agent 开始工作。
- 两个 **tmux session** 可以位于两台不同机器或不同容器，**物理隔离**；它们看不到彼此，也看不到“世界上其他的人”。
- 演示中故意用 **Master / Slave** 命名（Slave 转录作 Slav）：讲者当 **master**，给每个 agent 起 coding agent 名，然后让它们工作。
- （整理者串联）这种物理隔离让多个“单人开发者”可以并行而不互相干扰。

### 多 agent 范式：监工 agent + 多个子 agent
- 讲者提醒：当 AI agent 变快时，如果指挥发生一点点差错，甚至只是指挥本身，就会引出问题。
- 现在流行一个 **paradigm**：一个**监工/supervisor agent** + 多个**子 agent**。
- 为了最大化模型智力、防止 AI 生成你不想要的东西，可以放两个较强模型：
  - **Codex** 来设计；
  - **Claude** 来 review；
  - 让它们互相打架，然后达成一致。
- 实现上只要开两个 **tmux session** 即可。
- 主 agent 负责协调：观看它们的输出或总结报告，然后往里 **inject prompt**。这样多 agent 就转起来了。
- 讲者查看 **report status**。

### 并行冲突：同一 Git 仓库麻烦，不同 repo 可行
- 观察：如果大家工作在同一个 Git 仓库上，就会有一些麻烦。
- 如果工作在不同的 **repo** 上，就完全可以：
  - 可以合并；
  - 可以去远端拉取别人的提交；
  - 冲突了就自己修复；
  - 必要时甚至可以给 **master agent** 发消息。
- 因此可以立即构建出一个多 agent 系统。

- 讲者提到今天也有一些 **workaround**，例如 Git 的 **worktree** 功能。
- 他给出提问示例：我的老师说 **git worktree** 可以改进这种并行工作方式，那么能不能让这两个 tmux session 都工作在 worktree 里？
- 讲者强调：**提问是关键**。你们可以在各种信息/场合提问，甚至比如今天早上走到教室的时候（转录后半不完整）。

## 能让多个 **tmux sessions** 都工作在 **worktree** 吗：讲者把“提问”当作关键

- 讲者开场问：能不能让两个 **tmux sessions**（转写里作 Mark sessions）都工作在 **worktree**？他认为“提问”本身是关键。
- 现实入口：比如早上走到教室时看微信公众号，看到有人提到 **git worktree** 或某种 **sandbox container**，就可以立刻让 **agent** 帮你试，自己观察它在做什么。
- Demo：agent 确实在写脚本，并产出了 **patch**（转写作 pad）；讲者认为这不是一个相对困难的任务，最后 worktree 应该是可用的。
- （整理者串联）多个 agent/tmux session 要并行提交，就需要隔离工作区；worktree 正好用共享仓库提供隔离工作树。

## worktree 的机制：`.git` 可以是目录，也可以只是文本文件

- `git worktree` 允许创建一个 **工作树**；讲者说可想象成连接到同一个 **Git 仓库**，在里面能做独立提交，而且是在隔离环境里提交。
- 普通仓库里，比如“我的 JS1”，`.git` 是目录，里面有 **logs、objects** 等；讲者提到有三种类型的对象。
- worktree 里的 `.git` 点开是普通文本文件；文件内容类似 **`gitdir:`**（转写作 GDIR），指向一个 **worktree 元数据目录**（转写里作 **VTREE**）。这个位置仍在文件系统里。
- 这个目录是一个小型 `.git`，或者说微型 Git 目录，依然有 **HEAD、index、locks** 等；但它依附于原有的 `.git` 目录而生。
- 讲者强调：Git 最大程度复用了操作系统里的机制。

## worktree 在 AI 时代有用：本地提交互相可见，不必互相 pull/push

- 讲者指出，worktree 这个“依附原 Git 目录衍生出的特性”，在 AI 时代突然显得有用。
- 因为多个 worktree/agent 的提交可以在本地互相可见，不需要互相 **pull** 和 **push**。
- 替代方案：开好几台虚拟机，每台虚拟机里放一个 agent，再直接往 **tmux** 里注入；讲者说这完全可行。
- 但 **worktree** 提供了更轻量的合作方式。

## worktree 的边界：冲突仍要 merge/rebase

- 如果有冲突的修改，仍然需要 **merge** 和 **rebase** 才能合并。
- 讲者说“这样性能会更高一点”（转写如此；可能指并行/性能）。

## 回到 agent team / agent swarm：为什么需要版本控制

- 讲者把话题拉回：如果我们有 **agent team** 或 **agent swarm**，除了 worktree 这样的机制，还要回头想：为什么需要 **版本控制 / 版本管理**？
- 他的解释是：因为**人的限制**。人的 commit 速度很慢——一个小的团队，哪怕是一个团队，也要约 **10 分钟**才产生一个 commit。
- 逻辑链：人的 commit 速度慢（约 10 分钟/commit）→ 人之间需要同步 → 每天早上要开一次会议，同步各人的进展，再把任务分下去 → 这些人类协作限制塑造了版本控制/版本管理工具。
- 讲者明确把“为什么需要版本控制”归因到人的限制与 **communication**。
- 他进一步说：“而且就算是人做了这样的沟通……”（此处结束）。

## 沟通成本随人数上升，团队不能按人数线性放大
- 人与人之间的 **communication** 会变成日常会议：每天早上开一次会，同步各人进展，再把任务分下去。
- 讲者强调，即使人做了沟通，也不保证讲得明白：室友来请教数学题，你明明会做，却可能怎么都没法给他讲明白；除非你是很好的老师，能**共情**、站在别人的角度思考。所以**沟通成本很高**。
- 由此解释大厂/小厂、尤其初创公司或初创团队为何效率更高：软件系统变大、人变多后，沟通效率下降，产出速度也下降。
- 讲者给出数量级判断：100 人团队不可能达到 10 人团队效率的 10 倍；有 2–3 倍就已经很不错。
- 所以团队没有办法无限变大。**（整理者串联）** 这正是要引入 Git 各种 best practice 的背景。

## Git 最佳实践：快照 + 小步 commit，让问题可追溯
- 使用 **快照（snapshot）**，**小步前进**。
- 小到改一个 title 也要做一次 **commit**；做任何事都做一个 commit，这些小的 commit 每个都可以追溯。
- 一旦出问题，需要回溯到某个人做那次 commit 的时间；那个人还有记忆。开发者会回想：当天早上开了会，收到这个需求；做需求时沟通出了问题；大家找到当时的沟通记录文档，再判断这个地方应该怎么修正。
- 所以有 **git bisect**（原音近似 “get it by sec”）、**git blame** 这类专门为人设计的特性。

## Agent 团队里 blame 失去意义：不再追责，只需修错和前进
- 讲者反问：如果由 **agent team** 或 **agent swarm** 来实现项目，还需要 **git blame** 吗？
- 因为人可以 blame：你被 blame 多了，就可能被开掉；实习生就会背锅。
- 但如果 agent 没有“坐牢/被开除”这种承担后果的能力，模型就变了：讲者认为，**再也不需要 blame**，项目只要前进就可以。
- 前进时有时也不需要知道到底是哪一个提交引入错误；只要知道这个地方错了，不必再管历史上怎么造成，直接把错误修了就行。
- 讲者提到 **agent 之间的 communication**，并强调更好玩的点：每个 **agent** 都是相同模型，是完全相同的克隆体。同一件事让它们做，大概率会收敛到相同结果；虽然模型仍有不确定性，同样 prompt 做同一件事会有细微差别，但最终方向性的东西可能收敛到相同结果。
- 因此项目被讲者描述为一个**永远向前进**的过程。**（整理者串联）** 这等于把 Git 的角色从人类追责部分转向状态保存与前进。

## 不需要 blame ≠ 不需要快照：方向错了仍要能回退
- 讲者明确说，**快照肯定还是需要的**。
- 例如方向走错时：如果没有保留历史上的某个 **snapshot**，已经往前走了很多之后再回去，代价与“一点一点往前修”相比会成为问题；所以保留快照仍然必要。
- **（整理者串联）** 这里的关键不是回溯责任，而是保留可回退的历史状态。

## 第 17 部分

![截图](images/04-%E8%BD%AF%E4%BB%B6%E4%BB%93%E5%BA%93%E7%AE%A1%E7%90%862/chunk_17_54m49s-58m19s_frame_main_000_005449.jpg)

**快照要留，但历史的价值从“追责”变成“继续前进”**
- 讲者认为：一下子往前走了很多再回去，代价可能比一点一点往前修更大；所以**保留快照**仍然需要。
- 但主线策略是：不断**大步向前**，几乎永远不要看过去；Git 的 commit 历史只留下一些 **lessons**，或记录项目经历过怎样的演化。
- 因此动作是“往前走、合并、合并、合并”。
- 逻辑链：大步前进 → 回退/修复代价高 → 仍要保留快照 → 但 commit 历史主要不是用来回头追责 → 历史价值从“谁写错了”变成“我怎么把它修好”。
- 只要保存了快照，能知道“从现在开始怎样往前进”就够了。

**Git 模型像数据库并发控制：事务里可以混任意代码**
- 讲者说，这里又回到计算机科学知识：操作系统里的**并发**、数据库里的**并发控制**。
- 现在的 Git 模型更像数据库中的并发控制。
- 例子：两个 SQL 都可以是一个 **transaction**，而且可以是很大的 transaction，中间可以混任何代码。
- 一个事务先 `SELECT` 读一下；另一个事务也可以 `SELECT`；读完后可以做代码计算，例如 Python 或 JavaScript 代码。
- 这些代码是**图灵完备**的：你永远不知道它会根据看到的结果算出什么；甚至可以根据当前时间等外部信息再计算。
- 算完以后再 `UPDATE`。
- 更新时可能冲突，可能死锁；可能是数据依赖，也可能是“我要锁你的对象、你要锁我的对象”的互相锁定。
- 若形成循环依赖，数据库检测到后会说这个事务不能继续，要中止（abort，原声近似 BT）并**回滚（rollback）**。
- 并发冲突链（整理者串联：用 A/B 指代两个事务）：A `SELECT` → 计算 → `UPDATE`；B `SELECT` → 计算 → `UPDATE`；若 update 彼此读取/锁定对方对象 → 循环依赖/死锁 → DB 检测 → abort → rollback。

**Git 像乐观并发控制：先假设两个 transaction 不会冲突**
- 讲者认为 Git 模型有点像**乐观并发控制**（optimistic concurrency control；原声近似 mist optimistic）。
- 为什么乐观：执行时假设两个 transaction 不会冲突。
- 这个假设在数据库系统中大概率成立。
- 例子：教务系统。每个同学读的是自己的数据、写的是自己的数据；选课选的是我的课，查看课表查看的是我的课表。两个同学哪怕同时开始选课，也是读我的、写我的，所以全局冲突不太可能发生。
- Git 开发同理：假设我们已经事先开过会（今天早上开过会），我可以顺着这条路先做这个，另一个人做那个；合并时大概率不会产生冲突。
- 因此不管是 **merge** 还是 **rebase**，都能顺利完成。
- 转折：讲者最后说，但是这就是“古法编程时代”的……

**小结：** 讲者把 Git 视为乐观并发控制：快照要留，但历史主要服务于继续前进；冲突用数据库式事务检测与回滚处理，而乐观假设只在冲突大概率不发生时成立。

## 第 18 部分

![截图](images/04-%E8%BD%AF%E4%BB%B6%E4%BB%93%E5%BA%93%E7%AE%A1%E7%90%862/chunk_18_58m06s-61m49s_frame_main_000_005806.jpg)

**核心链条：Agent 提速 → 频繁 abort/冲突 → 从乐观修冲突转向悲观上锁**
1. 如果 **agent 快 1000 倍**，而主进程/主协调者（转录作“主威镇”，按上下文理解为协调者）一下子分出很多任务，就更可能频繁触发 **transaction abort**（转录作“transaction 的 bot”）、类似 abort（转录作“OLBOT”）。
2. 在 AI 时代，这种 abort 不是大问题：agent 出错了、出了 **conflict**，就修，而且能修好。
3. 但讲者追问：是不是在 agent 时代，可以换一种 **并发控制** 方式？
4. 他给出的方向是：从 **optimistic** 的“大家先往前跑，跑了再说”，转向更偏 **悲观并发控制** 的“先 declare、先上锁、再执行”。
5. 具体做法是在 **git repo** 或快照上按 **scope** 上锁；冲突者等前一个 release，几乎避免所有冲突。
6. 代价是：**互斥锁** 的本质是不并行、不并发，与多处理器并行根本矛盾。

**Merge/rebase 本身能完成，问题是“古法编程时代”的冲突处理节奏**
- 讲者先承认：不管是 **merge** 还是 **rebase**，都能顺利完成。
- 但他把这种模式称作 **“古法编程时代”** 的做法；这里他提到可用 **SQL** 作比方（未展开）。
- 讲者认为，旧流程默认冲突不会以极高频率发生，或者发生后可以慢慢修。

**操作系统/数据库的锁语义：先声明、先上锁、后到者等待**
- 讲者提醒：并发控制不只在数据库里，操作系统课也学；操作系统里做并发控制靠 **上锁**。
- 锁和数据库里的 **transaction** 有点不一样：锁是对资源 **lock**。
- 讲者上课常说：**“一把大锁保平安”**。
- 做实验时，要访问可能冲突的资源，就先把它锁住；一旦锁住，别人再想 lock，就必须等前一个 **release**。
- 因此建立的是“先 lock、后 lock”的先后关系：必须等前面 release，后来者才能 lock。
- 这不是 **optimistic** 的“大家先往前跑，跑了再说”。
- 悲观锁要求在 **使用资源之前 declare** 对该资源的使用，用上锁的方式。
- 讲者感慨：只有在操作系统课、数据库课真学会这些东西，回到软件工程里想，会发现这些概念又再做一次。

**讲者的具体方案：主 agent 规划后，在 git repo/快照上按 scope 上锁**
- 因为 agent 动作非常快，讲者认为应该用更偏向 **悲观并发控制** 的方式。
- 具体设想：
  1. 今天要做什么，或有一个 **主 agent** 先规划。
  2. 规划完后，立刻把项目的某一个部分锁上。
  3. 在 **git repo**（转录作“git ripple”）或一个 **快照** 上支持锁操作。
  4. 把 **scope** 说好：现在锁住这些范围。
  5. 要做一件事，需要这些范围，就先上锁；上锁后做事，做完 **commit**。
  6. 另一边也可以上锁；但如果他想干的事情被另一个人锁上了，就必须等前面的人释放，才能再上锁。
- 讲者判断：这样几乎可以避免所有冲突。

**文件级锁例子：避免同写测试/配置，同时其他 agent 继续推进**
- 例如在 **文件级** 上锁，就能避免两个 agent 同时写同一个测试，或往同一个配置里做更改。
- 又因为 agent 数量足够多、速度足够快，即使有 agent 等待锁，整体项目进度仍可以往前推：也许还有别的 agent 可以继续运行。
- 这类似操作系统里实现并发程序。

**锁的代价：互斥锁排斥并行，与多处理器并行根本矛盾**
- 讲者提醒：哪怕做到“一把大锁保平安”，或把锁拆细（转录作“锁拆拆桥”），**互斥锁** 的本质仍是 **不要并行、不要并发**。
- 它和多处理器并行有根本矛盾。
- 按讲者说法，这会把一个本来能并行/并发的程序“退回”（整理者串联：即退回串行化/失去并行）。

## 互斥锁把冲突处退回串行，但不冲突时仍可高效

讲者认为，**互斥锁**的本质是“不要并行、不要并发”（原文“并罚”应作“并发”）。它和**多处理器并行**有根本矛盾：它要把本可并行/并发的程序退回成串行程序。

- 但讲者马上限定：当系统里有很多**独立、不冲突的线程**时，即便每个线程都持有一把锁，仍然可以继续高效运行；即便是**悲观锁**，也依然可以高效。
- 逻辑链：
  1. 互斥锁要求互斥/串行化；
  2. 这与多处理器并行的目标冲突；
  3. **（整理者串联）** 真正被串行化的是需要互斥的临界区，不是整个程序；
  4. 所以不冲突的线程仍可并行，整体不必低效。

## AI 时代可从 first principles 重做版本控制，OS/数据库仍值得学

讲者把这些知识关联起来看：在 **AI 时代**，可以重新设计一个**版本控制系统**，因此软件工程肯定要发生很大变化。

- 从 **first principles** 出发，要管理的是：**快照**、**版本**、**change**，还要管理**飞快的 change**。
- 讲者问“答案是什么”：**Git**（原文识别为“get it”）可能是一条线；如果“用一种像这样的方式来管理软件”，可能又是另外一条线。
- 因此，学**操作系统**、学**数据库**仍然有用。虽然会痛苦、会怀疑：AI 都会写数据库了，SQL 查询（原文先识别为“C口查询”）早就不自己写了；但讲者明确说：答案是有用的，还是要好好学习。
- 他举数据库里的 **advisory lock**（原文识别为“adversary lock”）机制为例。这也是他喜欢上课的原因之一：如果不来上操作系统课、不上生成式软件工程课，可能就不会让自己在备课中把这些事在脑子里再过一遍，去问“是不是地球上所有人都错了”。
- 讲者解释，自己讲给你们时必须**共情**听众：听众只能接受比较平实、朴实的逻辑，不能直接说“操作系统是怎么设计的”；所以必须把最顶层的 idea 提炼出来，再试图让大家共情。他自评可能做得不够好，学生可以在 AI 帮助下重新理解。

## 版本控制只是工具，真正难的是进度和团队管理

- 讲者对**版本管理**的讲述基本收束：从历史动机，到过去 **Git**，讲到现在，再讲到未来可能发生的事。
- 但他强调：版本控制本质上还是一个**工具**；哪怕是他刚才说的、基于**乐观锁或悲观锁**的版本控制，也一样。
- 真正困难的是**进度**，也就是**团队的管理**。
- 为什么现在还需要**软件工程**？因为现在还没有办法做到“一句话就直出一个高质量的产品”。

## 如果 AI 一句话做出微信级产品，软件工程就死了

- 讲者举例：如果“斩杀线”到了，老板有一个想法，比如“我要做一个 agent 用的微信”/“AI 时代的微信”，随口一说要做成社交爆款，以后大家社交不再用微信、而用“我”的；你可能还有更具体的思考。
- 此时如果 AI 直接就能做出**微信级的产品**，那么**软件工程就已经死了**。
- 讲者的判断链很直接：软件工程存在的理由是当前还不能一句话产出高质量产品 → 一旦 AI 能一句话产出微信级产品 → 软件工程的必要性就被打掉。

## 单向限制让汉诺塔的常规递归方案失效
讲者最近看到一道题：在**汉诺塔**上增加额外要求——所有盘子的移动只能沿同一个方向，不能折返。讲者说它常被当作面试题，也像小学生考级题；常规汉诺塔大家会递归，但这道题不行。讲者还带了一个模型/道具，并准备了一个小程序演示。

- 两个盘子时还不明显。
- 三个盘子时问题暴露：常规汉诺塔会先把上面两个盘子移到中间，再把最大盘从当前位置移到目标；但在单向限制下，最大盘不能这样直接移过去，只能沿规定方向走。

## 最优解的关键：最大盘被单向约束逼成“向右两次”，小盘递归让路
讲者把问题拆开看最大盘：

1. 在受限规则下，最优解里最大盘不能一次到位，而总是先向右移一个，再向右移一个。
2. 为了让最大盘完成这两步，它上面的那一摞盘子必须先被移开、让路；最大盘右移一次后，小盘还要再调整，之后最大盘再右移一次，最后小盘再归位到目标。
3. 因此处理小盘的部分仍是递归/归纳：先移开、再移回、再移开，围绕最大盘的两步移动展开。
4. 讲者称，这样最大盘的移动次数最少，是不可避免的；剩下的部分基于 **induction/归纳法**，也同样是最优。

逻辑链：  
常规汉诺塔：小盘让路 → 最大盘一次到目标  
加单向限制 → 最大盘不能一次到目标  
→ 最大盘必须沿规定方向分两次移动  
→ 小盘必须分三段递归让路/归位  
→ 最大盘移动次数不可再省，剩余由归纳法保证最优。

## 程序演示证明的是“最优”，不是“能解”
- 讲者写了一个程序，按上述思路处理：如果最大盘还没到目标位置，它总是向右移一个、再向右移一个。
- 讲者认为，这使最大盘移动最少，无法再优化；剩余部分由归纳法也是最优。
- 讲者感叹这题有点难，很难想象小学生能做。
- 他调侃如果放在**保研机试**里，要求输出方案或输出数字，n 也不大，但确实需要先理解问题。

## 汉诺塔不是重点：重点是把产品卖给小学生，靠付费增值服务
讲者明确说，他不是在讲汉诺塔的故事。重点是“现在要推出这个产品”：例如把这个东西卖给小学生。问题不是算法怎么最优，而是怎么最好地卖给小学生。讲者给出的直接答案是：**提供付费的增值服务**。

- 这和前面展示的例子非常相关：从 **README.md** 来看，它做的所有事情都是对的，没有一个错误；但最终得到的是你不想要的东西。

- 讲者对比成熟产品经理的做法：如果一个成熟产品经理接到老板交代的项目，他肯定会先和团队沟通项目怎么管、协作怎么做、每天什么时候开会——甚至发生在写下第一行代码之前。

### 不能把任务直接丢给 Agent：先建空仓库，再小步走

- 讲者结论：刚开始时，脑子里还是要回到项目、回到管理。不能直接把任务丢给 Agent。
- 他给出的顺序是：
  1. 第一件事一定是先创建一个空的仓库/项目。
  2. 创建完之后，再想下一步要迈向哪里。
  3. 下一步不能大跨步，要往前迈一小步，再往前迈一小步。
- 讲者判断：现在 AI 从零开始做一个东西、做出 **slop**，比它到一个成熟项目里做维护性任务要难很多。

### 软件工程的真正考验：能否“以不变应万变”

- 讲者说，如果他要和一个 team 或一个学生谈论“要设计一个什么软件”，他的问题是：**你能不能以不变应万变？**
- 也就是说：现在设计的软件架构，或者流程方法，能不能抵抗未来需求发生根本性的变化？
- 例子：需求表面上可能是“生成一个挣钱的产品，去挣宝妈们的钱”；但讲者真正需要的是一个**能扩展的架构**。
- 未来会变化的东西包括：别的需求来了、AI 模型发生变化、软件工程/合作模式发生变化。
- **AI 助教**的例子：它可能是文字助教，也可能是图像助教；可能有交互，也可能没有交互；各种需求在不断变化。
- **（整理者串联）** 因此关键不只是让 Agent 完成眼前一步，而是让架构和流程在需求根本变化时仍然承受得住。

## 需求会变，架构要用最小变化应对变化

- 讲者从 **AI 助教** 展开：AI 助教可能是**文字助教**，也可能是**图像助教**；可能有交互，也可能没有交互。
- 当这些需求不断变化时，他提出的核心问题是：**我的架构还有没有可能以最少的变化去应对需求的变化**。
- 讲者认为，这正是软件工程最不一样的地方：数据库、操作系统往往会解释“为什么今天的数据库是这样、为什么要并发控制”等原因；而软件工程要面对的是**未来需求的变化**。
- 逻辑链：
  1. AI 助教的需求形态多样且会变。
  2. 如果每次变化都大改架构，代价高。
  3. 所以架构应尽量用最小变化吸收需求变化。
  4. 讲者把“应对未来需求变化”放在软件工程的核心位置。

## 版本管理三件事：记住现在、记住历史、记住教训

- 讲者在讲版本管理时说，版本管理做三件事：
  1. **记住现在**：必须有一个 **repository**。不管是某种形式，还是 C/C++、Python、JavaScript 项目，都要把文件管起来。
  2. **记住历史**：某天某个东西不要了，或删掉后才发现有用，还可以把它捞回来；从提交历史中能看到自己如何演进到某一点，发现某件事失败，可能停在那里，再回到另一个点，开始另一条正确的路线。
  3. **记住教训**：版本控制里的 lessons 不停警示你该怎么做，怎么从第一步开始迈出向后的一小步。
- 讲者强调：这三件事在 **agent 时代** 和软件工程的“古法编程”时代都成立。
- 逻辑链：repository 管住现在 → 历史可恢复、可回溯 → 从历史中吸取教训 → 指导下一步演进。

## 学生项目：真代码、真 HTTP 服务，但被做成业务逻辑系统有风险

- 讲者看一个提交/项目时提到：已经做了“提交人民奖学金申请、准备退课、看有没有 get”等事（功能名按转写保留）。
- 他的评价是：**引擎全部是真代码**，**手机端是真 HTTP 服务**，模拟部分/邮箱没有（此处 ASR 不清，保留原词，不展开）。
- 架构上有 **入口层**、**编排层**、**能力层**，讲者称其“非常非常典型”；**数据层**他说不想再 re-review。
- 但讲者指出风险：学生显然把它当成一个**业务逻辑系统**来做，这个软件已经看起来像一个**教务系统**/教育系统；他还说下节课会讲教务系统。
- 讲者认为这有很大风险：它容易把大量并非真正需要的东西先实现出来。

## 从零构建更符合 best practice 的做法：先做 MVP，逼清楚绝对要的需求

- 讲者提出，如果真要从零开始构建，现在更符合主流 best practice 的是用 **MVP**：**minimum viable product / minimal viable product**，也就是一个**最小验证版本**。
- 他引用：**The biggest risk in product development is building something nobody wants.**
- 讲者用学生项目说明：他做的东西就是“我不要的”；绝大部分东西其实不是我要的。讲者说自己在看他代码时已经解释过自己真正想要的是什么。
- 因此，MVP 在讲者这里的意义是：**逼迫你想清楚，什么样的需求才是你绝对要的**。

## 绝对要的需求：个人助手先要提升学习效率和工作效率

讲者先问：什么样的需求才是你绝对要的？以个人助手为例，讲者最想要的是两点：**提升学习效率**、**提升工作效率**。讲者认为，总结出这两条后，第一个 **MVP** 里可以没有任何数据库。

**逻辑链：**
1. 个人助手的核心需求是提升学习/工作效率。
2. 做 MVP 时，不必先上数据库。
3. 因为文件系统膨胀时，可以直接跟 Agent 说：按这个数据组织帮我提炼出一个数据库，问题就结束了。
4. 一旦一开始带上数据库，每次数据库重构都需要让 Agent 做 **database 迁移**。
5. 文件系统不同：你可以自己在文件管理器里调整目录结构，逐渐梳理到舒服的结构。
6. 调文件与调 **database schema** 的**心智负担**不一样。
7. 人类从小（小学电脑课）就操作文件目录，对直观模式非常习惯；很多同学还没学过数据库课，面对 database schema 是未知物，需要强行做一次概念翻译：“我脑子里是这种概念，要翻译到数据库里是那样。”
8. 所以讲者主张：不如用一个已经适应、熟悉的 system，用最简单的方式帮你管理学习资料、录入学习资料和通知消息等。

## 回邮件 Agent 实例：云盘 + 多级流水线，没有数据库

讲者说自己回邮件的 Agent 都没有用任何数据库。流程大致是：
- 我的 Agent 会收我的邮箱；
- 然后把 **email id** 放到一个共享云盘同步上；
- 这个 email id 里有 Agent 解析出来的内容，比如：我回复的草稿、邮件分类、是不是垃圾邮件；
- 再由下一级流水线去处理。

讲者强调，先要明白：
- 系统里有哪几级流水线；
- 这些流水线之间应该怎么协作；
- 哪些东西通过云盘。

## 需求变更：喜欢云盘会牵动架构

讲者说因为自己很喜欢云盘，就会问：是不是引入云盘要做一些**架构修改**？他希望**邮件和资料等都和云盘保持同步**。讲者把这件事称为**需求的更改**。他现在不知道它的架构做得好不好，于是让 Agent 帮自己看一看。

## 好架构的判断：需求变更时改动是否摧毁性、是否背技术债

讲者的推理是：
- 当前当然有一个需求；
- 现在的实现可能满足这个需求；
- 但当需求发生变更时，相应做出的变化可能是**摧毁性的**，或者背上**技术债**，还是别的，那就不知道了。

## 两种开发方式：先做大拖技术债，或先做最小精巧架构

- 方式 A：一上来就做一个大的，几大步把需求都实现完，然后拖着**技术债**不断往后迭代，继续加功能。
- 方式 B：从最小开始，得到一个特别精巧的**架构**。
- 讲者举前面的例子：当你用 **git** 管理学生的提交以后，很多事情变得非常容易，自己控制起来也轻松很多。
- 由此讲者说：直到遇到**性能瓶颈**之前，他都不想去把它迁移到任何一种数据库。
- **逻辑链**：
  1. system.db 把个人资料、邮件归档、索引、草稿放在一起，短期看问题不大。
  2. 项目继续走，常见一种做法是先做大、拖技术债、再加功能。
  3. 另一种做法是从最小精巧架构起步，像 git 管学生提交一样，很多事更容易控制。
  4. 因此不必过早迁移数据库；把迁移推迟到性能瓶颈出现。
  5. （整理者串联）这里的隐含取舍是：越早采用最小可用架构，越能把“何时迁移/重构”推到真正有性能压力时，而不是被早期大设计拖住。

## 早期 prompt 对项目走向影响最大

- 讲者结论：**早期的 prompt 对整个项目的走向影响最大**。
- 例子：最早直接把 **README** 给 AI，并说“我要做一个 **MVP**”，都会对项目造成很大的影响。
- 讲者强调，最早的这些输入会持续塑造后续方向。
