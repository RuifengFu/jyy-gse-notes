## 1. 软件架构决定测试怎么写，好的系统设计仍靠人的智慧

<small>▶ [00:00](https://www.bilibili.com/video/BV1LaW36WErp?t=0)–05:47　·　开场　·　话题：架构决定怎么测试</small>

- **bug 变成故障要走三步，每步都可能断** 链条是 fault → error → failure，靠测试、规约和断言守住。
    - 本节接着上节的调试理论，继续讲软件的质量保障。
    - **玩笑** 讲者以前在计算机系统基础课讲怎么调 QEMU，就先替程序员叫屈：「我们要心疼程序员」，因为程序员写的是 bug。
    - fault 是程序里的 bug，例如手滑写错、算法设计错。
    - 有 fault 不一定触发 error，要有合适的测试用例把程序运行起来。
    - silent error 观测不到，例如数字算错，或内存地址被覆盖但没影响后续计算。
        - 状态已违反 spec，开发者却可能产生程序是对的幻觉。
    - **玩笑** 讲者模仿开发者没观测到错误时的内心独白：「诶看起来挺对的嘛」
    - error 最终表现为 failure，包括 3 种：卡住、crash、输出错误。
        - 卡住的例子：应在 0.01 秒跑完的程序，跑了一分钟。
    - 触发 error 也不一定看到 failure。
- **架构决定系统怎么测试，好设计仍靠人的才智** 架构好不好测，由架构决定。
    - 真实软件系统里，最合适的测试用例要靠开发者的才智写出。
    - **玩笑** 讲到好的 system design 时，讲者顺口解释了为什么还要开这门课：「好像现在真正好的 system design 还是一种 AI 模型没有完全掌握的东西，对，可能这也是我们现在还要上这门课的主要原因」
- **引擎与渲染分离，引擎才好测** 以上节课许愿做的 CSGO 为例，引擎没有图像，不需要截图。
    - 讲者问学生如何给这个 CSGO 做测试。前提是架构已经做得好。
    - **玩笑** 讲者说这个 CSGO 做好后，能在教室里开枪：「我可以在这个教室里面突突突突突」
    - 引擎包括碰撞判定、射击和角色，与游戏界面分开。
    - 状态由数据构成，例如子弹有 XY 坐标、速度和 type（AK 子弹或 AWM 子弹）。
        - 在玩家眼里，状态是 dust two 地图上有人拿着枪。
        - 状态里绝大部分元素都是这类数据。
    - 状态按 frame 或 tick 更新。渲染跟不上时，更新仍要跟上实时玩家和网络另一端玩家的节奏。
    - 更新可能完全确定：同一状态走一步，必得同一个下一状态。
        - 输入包括子弹自行前进，也包括玩家指令，例如 player1 按 left key。
    - 引擎的测试包括 2 类：每个函数的单元测试，和 replay 测试。
- **同一状态投射成不同视角，replay 与 OB 都靠它** 一个函数投射无图形的状态。结果是显示状态，再渲染成画面。
    - 无图形的状态里，可能有人手臂的状态。
    - 投射出的显示状态，再渲染成沙盘上的模型。
    - 所有人在时间轴上看到的游戏状态绝对一致。玩家看第一人称，OB 看全局的上帝视角。
    - 讲者问了 GPT 如何测这样的系统，说这也是学生的练习（见第 2 节）。
- **顺带：讲课现场的小插曲**
    - **吐槽** 讲者发现话筒有爆音，担心：「诶有爆音啊这个我很担心」

## 2. 项目变大后，用一张文档表格统一定义并驱动所有测试

<small>▶ [05:47](https://www.bilibili.com/video/BV1LaW36WErp?t=347)–12:28　·　进一步　·　话题：测试清单只留一份来源</small>

- **小项目让 GPT 分三层目录加 justfile 就够用** 讲者让 GPT 把 unit、module、system 三层测试分开，答案在工程上合理。
    - 上一次做的过程中，agent 到某个时间点后反复截图、小修，白花 token 和钱。讲者因此想先建测试框架。
    - **吐槽** 描述 agent 卡住后的行为：「到某一个时间点以后他就开始疯狂的截图小修截图小修截图小修截图小修」
    - **吐槽** agent 反复截图小修的代价：「你就开始浪费你的token你的钱就浪费掉了」
    - GPT 的答案：源码一个目录，测试分 unit、module、system 三层，外面放一个 justfile。
    - justfile 是退化版 Makefile，是执行命令的入口，例如 just test system、just test unit（字幕待确认）。
    - **玩笑** 讲者对 justfile 的定位：「你可以理解成这是一个退化版的Makefile」
    - 讲者认为测试和软件设计需要聪明才智。原因是每个项目的规模都不一样。
    - 项目规模决定组织方式。让 DeepSeek 做个网页版 CSGO 发到 B 站，这样做已经够好。要维护 10 万行、将来可能 100 万行的项目，这样组织测试不够。
    - **吐槽** 设想把 DeepSeek 做 CSGO 的成果发到 B 站：「你想起一个什么震惊瘫坐的标题，说哎呀 CSGO 现在这个 DeepSeek 模型也能做到多好啊」
- **测试清单只写在一张 Markdown 表格里** 表格是单一事实来源，开发者读文档就知道要跑哪些测试。
    - 表格放在 docs/testing.md（字幕原文：DOS testing 点 MV，待确认）。每个 Rust crate 下的测试各占一行。
    - 每行写命令、参数和 tag，例如 cargo test（讲者说只是打个比方，实际不这样写）。
    - 加测试只需往表里添一行。DSL 不够用时可以扩展。
    - 表格与 justfile 原理没有本质区别，但不用双向同步，也不用额外维护配置。
    - 架构膨胀后必须写文档，文档与 justfile 就形成交叉依赖。模型不听指令时，一边改了另一边没改。
    - **吐槽** 讲者说维护两份配置时模型会漏改：「维护着维护着，比如说模型不听指令了，他这边改了那边就没改」
- **后台编译器把表格编译成 pre-commit、CI 和 Bazel 规则** 所有规则写在同一份文档，不散落各处。
    - 编译器是统一框架，可以编译多种产物。
    - pre-commit：声明某个 tag 的测试每次提交前都要运行，例如 unit test 全过才能 commit。
    - CI：声明完整 system test 通过，merge request 才能 merge。
    - 不用表格时，commit hook 要多一个文件，CI 要多一个 .github 目录。
    - **吐槽** 讲者不喜欢 CI 配置目录：「我非常讨厌那个点点 GitHub，因为它和 GitHub 绑定在一起」
    - tag 用项目自己定义的术语，项目保持干净。
    - Bazel 是工业界里比较成功的构建系统。
    - 思路与 Bazel 的底层想法相似。表格也可以编译成 Bazel 的各种 rules。
- **测试架构靠工程经验，且与强化学习求快冲突** 概念人人都懂，怎么做要靠多看系统积累。
    - 要做 unit、module、system test，这在概念上没有争议。难处是具体怎么做。
    - 工程智慧靠实践积累：看更多系统，看别人怎么做，慢慢形成自己的感觉。
    - 这类事的反馈信号弱，或者说特别长。
    - 强化学习要求模型尽可能快地完成任务。先建基础设施、可能复用别人的，完成得慢，还多花 token。讲者以「最终我们可能觉得对人来说……」收尾，字幕在此中断。

> 原话：「我们有一个 single source of truth，然后我们时刻都可以看到到底我们要做哪些测试」

## 3. 与其反复调试，不如证明程序满足规约，Hoare 逻辑是早期答案

<small>▶ [12:28](https://www.bilibili.com/video/BV1LaW36WErp?t=748)–28:45　·　但是　·　话题：证明程序比调试更根本</small>

- **证明程序满足规约，比反复测试调试更根本。** McCarthy 1962 年主张证明程序，并由计算机检查证明。
    - 测试能找出很多 bug，修复后质量更好。上节课引用的 Dijkstra 名言说，测试只能显示 bug 存在，不能显示 bug 不存在。
    - 学生默认写不出绝对正确的系统。做 NEMU 实验、操作系统内核、数据库时，大家都默认一定有 bug。
    - **吐槽** 讲者替学生说出默认的想法：「你们已经默认了我不可能写一个绝对正确的东西，它一定会有 bug 的」
    - **吐槽** 讲者形容人和 agent 现在的写法：「都是写出一段代码，堆一个 10 万行的屎山，然后堆出来以后我可以运行它，它大概是对的，然后不停的测试让它更对」
    - McCarthy 的主张是「Instead of debugging a program, one should prove that it meets its specifications. And this proof should be checked by a computer program.」讲者先说这个想法可追溯到 Turing 时代（字幕如此，待确认）。
    - McCarthy 说要做到这一点，需要形式化系统（formal system），也需要能写证明。
- **程序可以像自然数一样，写成严格的数学对象。** 皮亚诺公理用零和加一定义自然数，运算和程序可以建在其上。
    - 从 McCarthy 到冯诺依曼，都在问能不能用严格的数学对象描述计算。
    - **学生学过的证明课是离散数学。** 课上先学逻辑，再学各种证明，学完大家想回到写程序的世界。
        - **吐槽** 讲者说离散数学：「你被思维体操折磨得死去活来。每当想到那个五个学分的离散数学的时候，每个字都听懂了，然后面对一个看起来非常简单的题目的时候，无从下手」
        - **玩笑** 讲者模仿学生考完离散数学的心情：「我终于再也不用去处理这个非常复杂的数学系统，而是我可以直接 rush 一个 CSGO 出来，然后这个 CSGO 就可以运行，又回到计算机的世界了」
    - **自然数由两条规则定义，名字只是标签。**
        - 零是自然数。
        - 任何自然数加一也是自然数。0+1 叫一，再加一叫二。二进制里可以叫 0、1、10。
        - 在自然数上能定义加减乘除。在皮亚诺算术上也能定义程序、递归、函数。
        - 这些对象和 x²+2x+1=(x+1)² 一样严格，初中就会证。
    - 讲者提出，程序也可以写得同样严格，这就是形式化方法。数学家出身的人走了很长这条路，1960 到 1970 年代已有卓越成果。
- **Hoare 逻辑把程序看成状态转移，再用前后条件证明。** 最难的是循环，要找到每次循环都不变的性质（循环不变式）。
    - Hoare 论文题为 An Axiomatic Basis for Computer Programming（计算机程序的公理基础）。摘要说，它用几何学里的技术探索程序的逻辑基础，并展示一个简单定理的形式化证明。
    - **玩笑** 讲者点评屏幕上的论文标题：「你看这个标题就写的很厉害」
    - 论文像初中的平面几何，有公理和规则。讲者说论文表格里是学生熟悉的数学。
    - 这篇论文篇幅很短，却开创了一整条路。讲者认为它让形式化方法走上了对程序员发展更快的另一条路。
    - 讲者提到霍尔三元组，说学生可能听过。
    - **程序被看成状态机，证明靠前置条件和后置条件。**
        - 程序是状态转移（state transition），Everything is a state machine。每个输入把状态转到下一个状态。
        - 目标是覆盖程序所有可能的行为。
        - 在公理推理系统里，假设程序运行前满足前置条件，就能推出执行后的后置条件。
        - 如果程序能终止，就能把执行一步步串起来，包括循环。
        - 顺序程序简单，讲者称这一步是「废话」。
    - **循环的证明靠不变量。** while P 结束后，一定可以断言 not P。
        - 开发者要找一条不管循环多少次都不变的数学性质。
        - 把这条性质和退出条件合起来，就能证明循环后的性质。
        - 讲者不展开，因为这是数学，只要有个感觉。
        - **玩笑** 讲者自称一讲就会讲很久：「我讲一讲讲半天，因为它是数学」
    - 两段顺序执行可以串联。例如已知 x 大于 0，执行 x 加一后，x 仍大于 0。
    - 程序的数学性质可以变成证明目标，包括数组不越界、指针不乱指、数据结构不损坏。
- **断言写下想证明的性质，形式化方法要求证明它为真。** 带 parent 指针的平衡树旋转时容易写错，断言能逮到。
    - 讲者让有经验的同学回想自己写错的过程，并说做质量保障一定会写很多 assert。
    - **带 parent 指针的平衡二叉搜索树是典型例子。**
        - 根的值要大于左边、小于右边。例如九、七、十是合法的树（整理者补充：9 为根，7 在左，10 在右）。
        - 每个节点有 parent 指针，旋转时要同时维护，写着写着就丢了。
        - 节点不空时，断言 p 的 parent 的 left 等于 p，或 p 的 parent 的 right 等于 p。
        - 还可以断言 p 的值大于 p 的 left 的值。
        - 旋转把指针扯坏时，例如 parent 指向了下面的节点，断言会逮到。
    - **玩笑** 讲者问听众第一次写树旋转有没有写对：「如果你们不抄书的话，谁写谁知道，非常非常容易写错，你写着写着就丢了」
    - 每条语句自带断言。程序永不 crash，要求指针访问永远合法。写 p 除以 Q，就隐含 Q 不等于 0。
    - 程序里的 assert 只检查当前状态。也可以证明从开始执行到现在的性质。理论上可以用列表收集执行过的语句，再证明当前状态的性质。
    - 形式化方法要求所有写出的性质最终被证明为真，无可辩驳。程序带着这样的证明，就是对的。
- **当年证明靠人脑，无法扩展，AI 让这一点改变。** 今天复制一份模型权重，就多一份博士水平的智力。
    - 讲者认为这个愿景美好，但生不逢时。原因之一是编程语言的发展速度。
    - **玩笑** 讲者评价这个愿景的时机：「有点生不逢时」
    - **多数投票算法的循环不变式很难构造。**
        - 算法：手上有一个名字和票数。新选票与手上名字相同就加一，不同就减一。减到零后，下一张选票换人。
        - 如果有人票数严格过半，最后手上的人就是他。
        - 循环里只有 candidate 和 vote 两个变量，历史被丢掉，算法是有损压缩。
        - 开发者要构造一个巧妙的不变式，覆盖所有历史，以及这些历史得到的当前状态。
        - 数据结构、指针和更复杂的算法，更难证明。
        - **吐槽** 讲者先反话夸这个算法：「哎，这个程序很好啊」
        - **吐槽** 讲者说这个算法：「他把这个算法正确性留给了后人的智慧」
    - **当年的形式化方法把大家带歪了。** 人用大量智力证明平衡树正确，到 1990 年左右仍是困难的研究问题。
        - **吐槽** 讲者直言：「他把大家带歪了」
        - 研究者可以提出一种新逻辑，声称它证明二叉搜索树更好。
        - 声称的收益，只是证明红黑树比另一种证明系统稍微简单一点点。
        - **吐槽** 讲者说程序员不会用这些逻辑：「没有任何程序员会干这件事」「他学完离散课他就不想再学逻辑了」
        - 没有程序员懂数理逻辑，还要被迫学一种新逻辑。
    - 当时人类的智力不可扩展（not scale）。今天 AI 的博士水平智力可以扩展。
    - 先驱做得太早。理论做得很漂亮。另一条路意外地在程序员群体里变得更流行。

> 原话：「你只要把模型的权重复制一份，你就多了一个 PhD level 的 intelligence」

## 4. 枚举状态空间同样能证明正确，精化映射把模型连到代码

<small>▶ [28:45](https://www.bilibili.com/video/BV1LaW36WErp?t=1725)–47:44　·　转向　·　话题：暴力穷举与模型检验</small>

- **暴力穷举状态空间，同样能证明程序正确**　程序有初始状态，每步确定。枚举全部状态并检查 assert，就不必学 Hoare 三元组（见第 3 节）。
    - 程序执行一步，就得到确定的下一个状态。初始 x 等于 1，解释执行后仍是 x 等于 1。
    - **外部输入会让下一状态变多，但过程仍是确定的。**
        - 例子：`y = int(input())`。
        - 即使把 y 限定在 -10 到 10 之间，也立刻生成一批可能的下一状态。
        - **吐槽** 讲者说有外界输入就麻烦了：「如果我有个外界输入就惨了」。
    - 先不计代价构建状态转换图，再在每个状态上用 assert 判断合法性，例如 assert y 大于 0。找到一个不合法状态，就找到一个错误。
    - 穷举让程序员的心智负担小得多。他不用学 Hoare 三元组，也不用重走公理系统。
        - **吐槽** 背景：对比 Hoare 论文里的公理系统。讲者说穷举不会「再把这个平面几何的噩梦再重现一下」。
    - 讲者在课上用 proof by brute force 讲线程。
        - **线程例子说明：穷举能证明并发程序的怪结果，代价是状态爆炸。**
            - 多个线程各自执行 sum++。
            - 可以证明：不管多少个线程、每个线程循环多少次，最终都可能得到 sum 等于 2。
            - 顺序执行完后有若干状态，每个状态都可以选 T1 或 T2 执行一步，之后每步再分叉。
            - 状态空间很快爆炸。但从理论上说，枚举可行，概念也更容易。
    - 只要写出程序的解释器，就能用暴力方式证明程序正确。此后几十年，研究者一直沿这条路改进。
    - 讲者说这批方法只有做软件工程的人才知道，所以他要科普。这条路线的研究者同样拿了图灵奖（讲者未点名），走的是数理逻辑形式化与完全暴力之间的平衡。口号是 everything is a state machine。
        - **自嘲** 讲者说这些方法外人不熟：「你们可能不知道的，就只有我这种做软件工程的人才知道的解法」。
- **程序太大时，先抽象成几十个状态的模型再穷举**　讲者以自动售货机为例。几千上万行代码无法直接证明。抽成状态图后，可以搜索坏状态。
    - 讲者说，自动售货机是 model checking 领域很爱用的例子（字幕写作 MOCHIN，待确认）。
    - 现在的售货机有二维码，甚至扫脸。
        - **玩笑** 背景：讲 1980、1990 年代的售货机有纸币入口。讲者问听众：「你们有多久没有用过纸币了」。
    - 当年的售货机有纸币入口、硬币入口和退币口。控制程序要识别纸币和硬币，硬币要称重，重量不对就走另一套逻辑。这样的代码有几千上万行，当年计算机又慢。
        - **吐槽** 几千上万行代码想直接证明或做质量保障，讲者说：「那对不起，这个方法还不行」。
    - **建模方式：把钱数当状态，只保留核心逻辑。**
        - 初始状态是 0。收到 1 元硬币变成 1，收到 5 元硬币变成 5。
        - 状态 5 再收到 1 元硬币，变成 6。
        - 饮料只有几种，状态图就不大。
        - 退币有专门状态，再按一次选择键才回到 0。
        - 讲者说这是个不太好的建模方法，学界提出过各种状态机。
    - 状态图缩到几十或几百个状态，就能暴力证明。卡住的状态是坏状态。只要证明不存在从初始状态到坏状态的路径。
    - 用 BFS 或 DFS 就能找到这样的路径。讲者说实际情况更复杂，这里只是概念上的理解。
- **精化映射把已验证的模型逐层连到代码**　模型对不等于代码对。Lamport 证明精化映射总存在，代码状态可投射回模型状态。
    - **取舍：这条路线只证明模型正确，没有证明代码正确。**
        - **吐槽** 讲者先学开发者得到正确模型的口气：「很好，你很开心，你先得到了一个正确的模型」。
        - 讲者说：「如果你的代码第一行就写了一个 return，它就不是这个模型了」。
        - 所以正确性分两步。第一步证明模型正确，由机器保证。第二步保证代码确实实现了这个模型。
        - 两步都做完，模型的正确性才能在一定程度上体现为代码的正确性。
    - 模型正确，系统仍可能出错。例子：算重量时有一个除以 y，售货机 crash。
    - 代码会处理模型没建模的现实事件。例如检测物体有没有掉下来。
        - **玩笑** 背景：讲者在售货机买东西，东西没掉下来，自动退款，他又买了一次，结果掉下来两个。讲者说：「然后我就赚了」。
    - Lamport 的论文是 The Existence of Refinement Mappings（字幕原文：existence suering fmmapping，待确认）。它在数学意义上证明：总能把模型一层层变复杂，最终连到代码。
    - 即使没有资源证明代码，也可以用测试建立信心。
        - **做法：让模型和代码执行同一个测试用例，对比状态迁移日志。**
            - 代码在每次状态迁移时用 print 打日志。
            - 模型执行同一个测试用例，记录状态迁移。
            - 日志从哪个状态到哪个状态完全一致，就说明代码大概实现了模型。
            - 这不能百分之百保证，但说明代码不是完全错，例如没有第一行就 return。
    - 信心来自两部分：模型枚举了所有路径，代码在一定程度上实现了模型。除零用别的方式查。memory corruption 可以选一门不会出现它的编程语言。
    - TLA+ 是 Lamport 的代表性工作，已证明分布式共识协议等的正确性。
    - **TLA+ 的模型还能生成测试用例。**
        - 协议被证明正确，不代表实现正确。
        - 开发者从形式化模型采样各种奇怪的测试用例，送进代码运行。
        - 模型知道每个用例最终会停在哪个状态。开发者检查代码是否落到同一状态。
        - 这就是 refinement mapping：把代码状态投射回模型状态。
    - 前人几十年里研究的是几十个状态的小系统。讲者说这些想法最终可以用到真实的大型软件系统。
- **用方程表示路径，可以推迟展开搜索树并生成测试用例**　每条语句列一条方程。分支加一个条件。问方程有没有解。有解就得到一条路径。
    - 人类从未放弃暴力证明。遇到 y 等于 input，开发者可以不立刻展开搜索树，改用数学公式表示当前搜索状态。
    - **例子：方程表示变量。**
        - 初始：x 等于 1，y 是任意整数。
        - 下一条语句是 z 等于 x 加 y，就多列一条方程 z 等于 x 加 y。
        - 每个状态是一组方程。程序每步确定，所以每执行一条语句就加一条方程，搜索树不再展开。
    - **分支只多一个条件。**
        - 遇到 if z 大于 5，有两种情况。两种情况的 x、y、z 方程相同。
        - 一种是 if 被取到，进入 z 大于 5 的分支，PC 指向分支入口（字幕：第八行、else 第十二行，待确认）。
        - 另一种是 if 没被取到，条件是 z 不大于 5。
        - 不断加方程，就能建模大量路径，搜索被推迟。
    - 问题变成：这组方程有没有解。有解就解出一条从头到尾的路径，也就是一个测试用例。
    - **同一思路可以找 assert 的反例。**
        - 程序里写 assert y 不等于 0，改写成 if y 等于 0 则 abort。
        - 问题变成：程序开头到 abort 之间是否存在一条路径。
        - 找到这条路径，就得到一个反例测试用例。
    - 对模型来说，这是很早以前就有的技术。对真实程序，工程实现很重。
        - **吐槽** 讲者说要证明真实程序就麻烦了：「如果你想要证明一个真实的程序，那就惨了」。
        - 需要代码的中间表示，如 LLVM IR 或 WASM（字幕原文：WM，待确认），相当于一套指令集。
        - 需要模拟执行指令集里的所有指令，并为每条指令列方程，包括跳转指令。
        - 好处是可以在真正的程序上跑路径。
- **讲者顺带讲了 2 件和主线无关的事**　讲课中途遇到录音问题，结尾预告了后面的内容。
    - 38:46 讲者发现麦克风出问题，确认自己应该内录了，最终会用音频里的版本。
        - **吐槽** 讲者说：「他们说麦炸了」。
    - 本节结尾，讲者预告「一会我要真正说的」内容，说它可能是人类在软件可靠性上的一项成果，字幕在此中断。

> 原话：「如果你的代码第一行就写了一个 return，它就不是这个模型了」

## 5. 前人已证明整个编译器和操作系统内核，靠的是证明助手

<small>▶ [47:44](https://www.bilibili.com/video/BV1LaW36WErp?t=2864)–53:30　·　进一步　·　话题：证明编译器与内核</small>

- **前人已证明整个编译器和内核** 做法是对所有输入给出逻辑意义上的正确证明。
    - model checking、refinement mapping 和方程求解也在证明程序正确（见第 4 节）。
    - 方程求解法依赖好用的求解器。这类工作能成功，是因为求解器到某个时刻变得可用。
    - 讲者认为更疯狂的事，是从公理意义上证明真正的程序是对的，而且有人做成了。
    - 这些人都被历史记住了。技术细节也许不那么重要，但这两项工作值得了解。
    - **CompCert 证明编译器对任意合法 C 程序输出等价代码**
        - 编译器可以有 bug：合法程序让它 crash，或被翻译成错误指令。
        - 例如 int f() 返回 1，无法确认它不会把 2 放进返回寄存器，只能 blind trust。
        - **吐槽** 讲到无法确认编译器的翻译：「他万一把二放到那个返回寄存器里，你能控制吗？你不知道。你能相信吗？」
        - 证明把编译器看作字符串到字符串的函数，对任意合法 C 程序成立。
        - **吐槽** 讲到对任意输入证明编译器正确：「这是一件多么疯狂的事情」
        - 2009 年完成初步版本，机器语义部分未证明。成本 3 人年、4.2 万行证明代码。
    - seL4 证明内核永远不会 crash，成本 25 人年、20 万行证明脚本。
    - 动机：编译器编出错误代码，月球车运行到那段代码就挂了。他们不想靠测试。
- **证明助手是铁面无私的反馈机制** 上述工作背后都是它。OpenAI 因此能用强化学习训练大模型解数学题。
    - OpenAI 的 722 篇数学证明出现在这些先驱工作之后。黎曼猜想的 111 部分（字幕原文，待确认）也靠同一机制。
    - **玩笑** 讲到 OpenAI 发布 722 篇数学证明：「OpenAI就丢下了那个722篇的数学核弹，一举杀死了数学工作者」
- **证明助手让草稿纸的每一步都可检验** 中学数学不够严格，靠猜和蒙混也能过关。
    - 选择题可以猜，用来培养直觉。要真做对不能靠猜。人常用奇怪方法猜出结果，写点演示让改卷人批过。
    - **自嘲** 讲到靠演示蒙混过关：「让这个改卷人改得快的时候，可能就给我批过去了」
    - **吐槽** 讲到草稿纸上的计算过程可能是错的：「你的草稿纸也可能是骗人的，你的计算过程可能是错的，但最后负负得正，诶，你那个结果最后又算对了」
    - 类比平面几何：与其靠几条公理来回推，不如把每一小步推导都严格写出来。
    - 做法：每一小步只写所用规则，由证明助手检验并完成内部推导。
    - 例：用乘法分配律而表达式没有乘法，计算机直接拒绝。没说清对哪个乘号做分配，下一步推不下去。

> 原话：「他是一个铁面无私的反馈机制」

## 6. 证明助手把证明变成改写目标，命题就是类型、证明就是程序

<small>▶ [53:30](https://www.bilibili.com/video/BV1LaW36WErp?t=3210)–72:50　·　进一步　·　话题：证明助手如何工作</small>

- **证明助手把证明变成改写目标，直到已知与待证逐字符相同**。人写证明，证明助手检查每一步改写是否合法，所以叫 assistant。
    - 证明助手是让人手写证明、再检查证明对不对的软件，能省掉很多事。
    - 证明从「已知」和「待证」出发，要证的是由已知推出待证。
    - 已知可以是各人的成绩，也可以从别处搬来定理或公理。
    - 已知和待证逐字符相同时，证明成立。逻辑、程序、数学的性质，最终都归到「严格逐字符相等」。
    - 可以通过改写目标让证明更容易。但改写后不代表一定能证过去。
    - **存在命题的例子：选对见证才能对上已知。**
        - 目标是「班上至少有一个同学得了满分」，已知是各人成绩：A 90 分、B 100 分、C 另有成绩。
        - 开发者可以选 A，用一条规则（字幕原文：truth，待确认）把「存在 x，x 考 100」改写成「A 考 100」。这步改写合法，不改变证明的正确性。
        - 改写后卡住：已知是 A 考 90，和「A 考 100」不逐字符相等，说明选错了。
        - 改选 B，目标变成「B 考 100」，与已知对上，证明完成。
- **任意命题引入自由变量，归纳命题拆成两个目标，目标压成栈**。每步都是不改变正确性的改写。
    - 证明就是不停改写：一开始只有一个定理，用合法改写把所有目标证完。
    - 证明「所有同学都及格」，用 intro x 去掉「任取」，x 变成自由变量。这步不改变正确性，但还需要领域定理才能继续。
    - 证明「对任意自然数 n，P(n) 成立」，改写成两个待证：P(0) 成立，对任意 n，P(n) 推出 P(n+1)。这就是 base case 和 inductive step。
    - 证明「所有保研同学都及格」，把 P(x) 移到已知，待证改成 Q(x)。
    - 证明状态本质上是一个状态，但现有证明助手设成 proof stack。执行归纳指令，栈顶目标变成两个。
    - 某个目标和已知直接对上，就从栈里清掉，继续证栈顶的下一个。
    - 皮亚诺公理用零和加一递归定义自然数，计算机科学里几乎一切东西都能由它构建。证明系统的能力因此很强。
    - 证明助手还能叠语法糖。它可以放进 Hoare 逻辑的公理，在同一套逻辑里推导（见第 3 节）。
- **命题就是类型，证明就是程序，归纳就是递归**。这是 Curry-Howard 对应，证明变成写一个类型正确的函数。
    - 讲者认为 Curry-Howard 对应是「人类文明真正的高光时刻」，是他最喜欢的计算机科学内容之一。
    - **玩笑** 讲者先说这个概念有点绕，又说自己第一次讲，接着提到南大那门专讲它的课：「虽然你们上到最后应该是比较痛苦和折磨的……因为你每天就是处理这种非常奇怪的函数」
    - **自嘲** 讲者说自己第一次讲 Curry-Howard：「我不确定我能不能讲好，我第一次讲这个 Curry-Howard correspondence」
    - **任何要证的性质都能写成逻辑公式。**
        - 例子包括：「所有保研学生的所有课程都及格」；哥德巴赫猜想；程序在所有 step 上都不会到达 crash 状态；编译器对任意程序都正确。
        - 无限状态图也能写：用一个不断加一的计数器记录第 x 步运行到哪里。
        - 程序是字符串，字符串能和自然数一一对应，所以能写「对任意程序」。讲者回扣离散数学里的基数和笛卡尔积。
        - 公式再复杂，构成它的基本元素都是 P、Q、R 这类命题，最终归到皮亚诺算术。其中最关键的是蕴含。
    - **证明 P 推出 Q，就是写一个从 P 的类型到 Q 的类型的函数。**
        - 每个命题对应一个类型，P 对应 type of P，Q 对应 type of Q。
        - 函数不用真的运行。它拿到一个 P 类型的对象，只能用公理系统和定理允许的操作变换，不能强制类型转换。
        - 例如从整数构建整数二元组，用「或」「且」得到别的类型。这些操作讲者称为「类型体操」，对应证明栈里的各种改写。
        - 在类型安全的系统里，只要给出能把 P 对象变成 Q 对象的程序，就证明了 P 推出 Q。
        - 最简单的例子是 P 推出 P，函数直接返回输入：lambda x: x。
    - **归纳写成递归程序。**
        - 以 A+B=B+A 为例，对 A 做归纳。base case 是对任意 B，0+B=B+0。step 是 P(A) 推出 P(A+1)。
        - 构造的函数输入任意 N。N 为 0 时调用 base case，否则调用 step。返回的函数类型和归纳公理合上。
        - 这给出一个递归计算过程，所以递归和归纳等价。讲者称之为「非常非常美妙」。
    - 初学会觉得难：A+B=B+A 看起来很简单，却得用归纳法拆开。
- **Lean 既能写证明又能当普通函数式语言，可以更早教给学生**。讲者认为离散数学课应教一点证明助手。
    - 讲者学证明助手已是多年前的事，设计课程时就有这个考虑。南大学生既然能学编程语言的形式语义，为什么不能更早学。
    - **自嘲** 讲者说自己学证明助手是很久以前的事：「一晃已经好多年过去了」
    - **玩笑** 讲者说小学生不会数学，可以在高年级「洗脑」：「因为小学反正大家小学生也不会数学嘛，那你也许可以在他高年级的时候就给他洗脑成，来，这个就叫数学」
    - 讲者把课上讲过的 Python playground（移汉诺塔碟子）改成 Lean playground，网页版，即证明助手的 playground。
    - **自嘲** 在 tactic mode 下写证明会出现 simplify only 这类写法：「你也不知道他是怎么证的 anyway」
    - Lean 能定义函数，如返回布尔的 f x y。C 里能写的计算函数，Lean 里都能写。
    - 学生可能先学 Scratch、Python、C++，也可以学 Lean 这种函数式语言。
    - **演示：用 Lean 定义函数画图，并证明图的性质。**
        - 讲者让 Lean 生成可执行代码，链接到 JavaScript 里，画出 100×100 的谢尔宾斯基三角形。
        - 学生会发现自己只是定义了一个函数，它还能证明自身正确。
        - 证明对所有整数成立，不只是检查 1 万个点。例如证明画布外面全是白色。

> 原话：「命题及类型，证明及程序。」

## 7. AI 使证明不再昂贵，难处移到规约与意图的对齐

<small>▶ [72:50](https://www.bilibili.com/video/BV1LaW36WErp?t=4370)–83:18　·　因此　·　话题：AI 让证明变便宜</small>

- **讲者的博士论文烂尾，靠 GPT 和 Lean 补上了证明** 讲者只证了受限情况，GPT 给出完整证明，Lean 写了 2 万行。
    - **玩笑** 讲者开讲前先预告：「我来给大家讲一个跟 proof assistant 相关的鬼故事」。

    - **玩笑** 讲者说这个猜想没人做成过，自己只是：「盲猜一个没有」。

    - **自嘲** 讲者担心证明有错，说「我每天都在想万一我这个错了，我就彻底晚节不保了」。
    - 讲者还担心这个猜想有一天被推翻，那样同样晚节不保。
    - **玩笑** 讲者把这个担心比作立 flag：「这个相当于我立了个 flag，然后这个 flag 倒了」。

## 8. 断言将来要能编译成证明，软件可靠性教科书都得重写

<small>▶ [83:18](https://www.bilibili.com/video/BV1LaW36WErp?t=4998)–89:07　·　进一步　·　话题：证明随代码一起交付</small>

- **代码可以带着证明交付。检查器验证后才放行。** Proof-carrying code 的愿景：拿到源代码的人可以不信它，改由检查器验证随附证明。
    - 现在所有人都盲信编译器。编译器有 bug，只是常见代码的 bug 已被触发并修掉，另有海量 regression test。
    - 证明的目标不必高：只证明不会 memory crash、不会 crash。
    - eBPF 与它相像但不同：程序绝对安全，才能插进操作系统内核，且不破坏内核里的其他部分。
    - 论文 1996 年发表于 OSDI，1997 年又在 POPL（字幕原文：POPO，待确认）重写一篇。
    - 这个名字 proof carrying code 被大家记住，广为流传。
    - 讲者是在证明突然变得可行之后，才翻出这篇老论文。
- **断言就是规约，将来要能编译成证明** 现在 assert 只在运行时校验。LLM 若不能把它译成证明助手代码，代码就过不了编译。
    - 代码里有很多规约，都可以直接写成 assert。例：平衡树节点的 parent 的 left 或 right 必须是自己（见第 3 节）。
    - 运行时可以收集 trace，一边收集一边断言，从程序开始执行到现在，哪些状态成立。
    - 目标是代码自带规约和 assertion，编译器自带校验。
- **软件可靠性教科书都得重写** 证明过去需要极高的数学智力，AI 让它不再难。
    - 过去证明链表是链表、树是树太难。
    - LLM 之前，讲者估计要 30 年。现在他认为很快实现。
    - 所有 search 都能证明时，故事完全变了。
- **老想法值得重读，SOTA 应站在前人肩膀上** 这篇论文没有新东西，却拿了 OSDI 96 best paper。原因是 PL 与 OS 之间有鄙视链。
    - Curry-Howard 对应等优雅的东西早就有（见第 6 节）。
    - PL 人只管做，不管有没有用。OS 人只管用，不管它怎么来。
        - **吐槽** 讲者模仿 PL 人的心态：「我只管做我不管用」；模仿 OS 人的心态：「我只管用我不管它是怎么来的」
    - PL 人看不起 OS 人重复做过的事。OS 人看不起 PL 人做的没用。
        - **吐槽** PL 人看 OS 人：「你们这帮做操作系统的人就一天到晚就做这个我们已经做过的东西」
        - **吐槽** OS 人看 PL 人：「你们一天到晚就做这个没有用」
        - **玩笑** 讲完两边互相鄙视后补了一句：「软工人在后面瑟瑟发抖是吧」
    - 讲者昨天重读老文章，发了小红书。他建议毕业要发 SOTA paper 的学生回看历史，在前人肩膀上多走一点。
        - **玩笑** 讲者给 SOTA 起了三个展开：「state of trial arrogance」「slap optimito essence」「science of tribute advances」（后两个字幕原文，待确认）
- **顺带：讲者今天想谈软件质量的未来，开场先给了一条建议**
    - 讲者前面讲了形式化方法。他说人类的终极目标还是证明。
    - 开场建议：要去掌握自己掌控不了的力量，体验超出能力边界的事，再一点点收进自己的能力边界。

> 原话：「整个软件可靠性的所有的教科书，上课讲的所有东西，都要重写」

## 9. 只有能独立于实现简洁表达的正确性，才适合形式化

<small>▶ [89:07](https://www.bilibili.com/video/BV1LaW36WErp?t=5347)–95:12　·　但是　·　话题：形式化止于人类意图</small>

- **形式化只适合能独立于实现简洁表达的正确性**。价值取决于能否用比实现更简单的方式表达正确。
    - 形式化会蓬勃发展，但仍没有银弹。意图与实现的缺口仍在（见第 7 节）。
    - 算力足够时，不 crash、数据结构正确、performance 和 cache miss rate 达标，都能证明。
    - 「任意 memory access 都不越界」简洁且独立于实现。
    - 不 crash、不越界、数学定理，都是容易形式化的例子。
- **软件最难的是决定造什么，这步难以形式化** 把非形式需求译成形式规约叫 auto formalization，数学里已出问题。
    - OpenAI 的一个证明图文不符。原因可能是模型翻译幻觉，讲者不确定。若公理系统没问题，证明应仍成立。
    - 领导满意的教务系统：领导可能只关心向上汇报的界面和 dashboard，不关心性能与 crash。这动摇了从 Hoare 逻辑到 Curry-Howard 对应的地基。
        - 讲者说「领导满意」是一种艺术，要去猜领导到底想要什么。
    - **吐槽** 讲者调侃揣摩领导心思和地基动摇：「那到底什么是领导满意呢？所以这是一种艺术，对吧？你要猜领导到底想要什么」「整个大厦的这个地基就动摇」
    - 折叠屏关闭特效：某款 iPhone（字幕原文：IPHONE65，待确认）合上时有毛玻璃效果。这只是众多合理特效之一，用户要的是自然舒适、符合预期。
        - 合上时窗口像纸一样缓缓折上。
        - 正面屏上还有一个等价的效果。
        - **玩笑** 讲者学用户的现场反应：「诶，合上，啪，合上，你觉得很好」
    - 模型在数学强化学习里强，但不是人，无法完全共情人。规约能写但很长时，人也难检查。
        - 讲者说人有细小的、受 chemical driven 驱动的思想，模型学不到。
        - **吐槽** 「我们人类那个细小的有这个 chemical driven 的这种思想」
- **人的创新可能来自随机性，AI 对齐意图后 AGI 就来了** 这是讲者自称的暴论。
    - **玩笑** 讲者先打预防针：「我有一个暴论，就是人类，尤其是我们人类的推理系统，就 system two，是完全理性的」
    - 人的 system two 完全理性，所有行为可解释。输出由接近 deterministic 的形式推理系统产生，grounding 部分可能是神经网络或打分网络。
    - 很多人认为创造力是上天赋予的，讲者不这么认为。
    - **自嘲** 讲者拿自己的创新性举例：「我可能能够写出有一定创新性的论文，能够上出有一定创新性的课，以及在小红书上发抽象的发帖」
    - 随机来自两处：auto formalization 今天觉得好、明天觉得不好；推理出错把系统引向新方向，看起来像创新。
        - **玩笑** 讲者模仿人反复无常的判断：「我今天觉得他好，我明天就觉得它不好」
    - AI 在形式世界已解决问题，一定程度也能 auto formalize。讲者相信 OpenAI 和 Anthropic 的下一步是对齐人类意图。

> 原话：「我觉得那天AGI就来了」
